17. 플랫폼 노트

Android나 iOS 앱이 설정해야 할 것, 라이브러리가 키와 세션을 보관하는 위치, 알아 두면 좋은 플랫폼 동작을 정리합니다. 실기기에서 아직 확인되지 않은 항목은 그렇다고 표시합니다.

지원 범위

  • Android 12(API 31) 이상, iOS 16 이상이며, 앱이 포그라운드에 있어야 합니다. 백그라운드 블루투스는 범위 밖입니다.
  • JVM 타깃은 테스트와 실험용입니다. 키는 메모리에만 있고 프로세스가 끝나면 사라집니다.

Android

두 가지 블루투스 권한을 선언하고 런타임에 요청하세요. 권한이 없으면 스캔과 연결이 PermissionDenied를 반환합니다. 라이브러리는 서버를 호출하지 않으므로 인터넷 권한은 필요 없습니다.

<uses-permission android:name="android.permission.BLUETOOTH_SCAN" android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<uses-feature android:name="android.hardware.bluetooth_le" android:required="true" />
  • 라이브러리는 PlatformContext(context)로 만듭니다. 애플리케이션 컨텍스트를 보관합니다.
  • 연결할 때 라이브러리는 MTU 517을 요청하고, 실패하면 20바이트 블록으로 대체합니다.
  • Keystore 항목 이름은 teslable.key:<alias>와 teslable.wrap:<alias>이므로 앱 자체의 항목과 겹치지 않습니다.
키 파일을 자동 백업에서 제외하세요

소프트웨어 키는 files/teslable/keys/<alias>.enc로 저장되며, 백업되지 않는 Keystore 키로 래핑됩니다. 자동 백업이 래핑 키 없이 파일만 복원하면 키가 손상된 것으로 읽힙니다. dataExtractionRules나 fullBackupContent에서 files/teslable/keys/를 제외하세요. 샘플 앱은 간단히 android:allowBackup="false"를 설정합니다. files/teslable/sessions의 저장된 세션은 잃어도 문제없지만, 제외하는 편이 깔끔합니다.

샘플 앱의 Android 백그라운드 사용

라이브러리는 포그라운드 사용을 지원합니다(지원 범위 참고). Android 샘플의 모니터 앱은 포그라운드 서비스로 백그라운드에서도 연결을 유지하며 아직 실기기에서 확인하지 않았으므로, 백그라운드에서의 라이브러리 동작은 확인되지 않은 것으로 보세요.

  • 매니페스트: FOREGROUND_SERVICE, FOREGROUND_SERVICE_CONNECTED_DEVICE, POST_NOTIFICATIONS(런타임에 요청), <service android:foregroundServiceType="connectedDevice" />. INTERNET은 여전히 없습니다.
  • Android 14 이상: connectedDevice 포그라운드 서비스는 BLUETOOTH_CONNECT가 허용된 뒤에, 그리고 앱이 보이는 동안에만(또는 다른 시작 예외가 적용될 때) 시작할 수 있습니다. 시스템이 서비스를 다시 시작해 주리라고 기대하지 마세요.
  • 서비스가 라이브러리 인스턴스 하나를 소유하고, 링크가 끊길 때마다 vehicle.disconnect()를 부른 뒤 새 Vehicle로 다시 연결합니다(2초 대기, 최대 30초까지 두 배씩). 재시도는 라이브러리가 아니라 앱이 할 일입니다.
  • 키 저장소: 샘플은 KeyAccessibility.AFTER_FIRST_UNLOCK으로 키를 만듭니다. Android는 이 인자를 무시하고 AFTER_FIRST_UNLOCK을 돌려줍니다(API 문서 기준이며 아직 기기에서 확인하지 않았습니다. 키 저장 참고).

iOS

  • Info.plist에 NSBluetoothAlwaysUsageDescription을 추가하세요. 첫 스캔에서 권한 요청 창이 표시됩니다. 사용자가 거부하면 호출이 PermissionDenied를 반환합니다.
  • 라이브러리는 PlatformContext()로 만듭니다.
  • 시뮬레이터에는 블루투스가 없습니다. 스캔과 연결은 실제 iPhone에서만 시험할 수 있습니다.
  • iOS에는 MTU 협상 API가 없으므로 라이브러리는 시스템이 정한 쓰기 길이를 사용합니다. 실제 iPhone에서 관찰한 블록 길이는 512입니다. 응답 특성은 notification과 indication을 모두 지원하며, Kable 기본 구독(notify)이 실차에서 동작함을 확인했습니다(ADR-0003).
  • Swift는 SKIE를 통해 Kotlin을 호출합니다. suspend 함수는 async throws가 되고, Flow는 AsyncSequence가 되며, sealed 타입은 switch onEnum(of:)로 다루고, companion 멤버는 .companion으로 접근합니다.
  • Swift에서 공개 VehicleStatus는 VehicleStatus_라는 이름이 됩니다. 생성된 VCSEC 메시지 타입이 원래 이름을 이미 쓰기 때문입니다. vehicleStatus()의 결과와 VehicleEvent.Status.status가 이 타입입니다.

샘플 앱의 iOS 백그라운드 사용

라이브러리는 포그라운드 사용을 지원합니다(지원 범위 참고). iOS 샘플의 모니터 앱은 UIBackgroundModes: [bluetooth-central]를 선언하고 Android 샘플과 같은 재연결 루프를 실행합니다. 아직 실제 iPhone에서 확인하지 않았으므로, 백그라운드에서의 라이브러리 동작은 확인되지 않은 것으로 보세요.

  • Info.plist(project.yml을 통해): UIBackgroundModes: [bluetooth-central]. UIFileSharingEnabled와 LSSupportsOpeningDocumentsInPlace는 샘플의 로그 폴더를 위해서만 둡니다.
  • 앱이 라이브러리 인스턴스 하나를 앱 수명 동안 소유하고, 링크가 끊길 때마다 vehicle.disconnect()를 부른 뒤 새 Vehicle로 다시 연결합니다(2초 대기, 최대 30초까지 두 배씩). 재시도는 라이브러리가 아니라 앱이 할 일입니다.
  • 확인되지 않음: 앱이 백그라운드에 있거나 휴대폰이 잠겨 있을 때 iOS가 앱의 스캔과 재연결을 허용하는지 여부(라이브러리는 현재 기기 이름으로 스캔하며, iOS의 백그라운드 스캔에는 보통 서비스 UUID 필터가 필요합니다. 계획 Task 2와 8). 실차 스파이크를 실행하기 전까지 지원하는 백그라운드 경우는 링크가 유지되는 경우뿐입니다. iOS가 앱을 계속 실행해 주는 동안에는 이벤트가 계속 도착합니다.
  • 키 저장소: 샘플은 KeyAccessibility.AFTER_FIRST_UNLOCK으로 키를 만듭니다. 휴대폰이 잠겨 있어 키 저장소가 KeyStoreError.Locked를 돌려주는 동안 샘플은 기다렸다가 다시 시도하며, 키를 지우지 않습니다.

휴대폰이 잠겨 있을 때 키 쓰기

키마다 접근성 설정 VehicleKey.accessibility가 있습니다. 고르는 방법과 키를 바꾸는 절차는 13. 키와 페어링에 있습니다.

플랫폼키를 만들 때이미 있는 키가 보고하는 값
iOSWHEN_UNLOCKED(기본값)는 kSecAttrAccessibleWhenUnlockedThisDeviceOnly, AFTER_FIRST_UNLOCK은 kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly를 씀. Secure Enclave 키와 소프트웨어 키 모두 같음저장된 키에서 다시 읽은 설정. 나중에 바뀌지 않음
Android설정을 무시함항상 AFTER_FIRST_UNLOCK. Keystore 키에는 잠금 해제나 사용자 인증 요구가 없고, 키 파일은 첫 잠금 해제 뒤 읽을 수 있음. API 기준이며 실기기에서는 아직 확인하지 않음
JVM설정을 무시함항상 AFTER_FIRST_UNLOCK. 메모리의 키에는 잠금이 없음
  • 잠긴 iPhone에서 키체인 오류 errSecInteractionNotAllowed(-25308)는 KeyStoreError.Locked가 됩니다. WHEN_UNLOCKED 키는 휴대폰이 잠긴 동안 읽거나 핸드셰이크에 쓸 수 없고, AFTER_FIRST_UNLOCK 키는 마지막 재시동 뒤 한 번 잠금을 푼 다음부터 쓸 수 있습니다. 첫 잠금 해제 전에는 모든 키가 잠겨 있습니다. 휴대폰이 잠겨 만들지 못한 키를 소프트웨어 키로 대신하지 않습니다.
  • 휴대폰이 잠기기 전에 읽어 둔 키 객체: Secure Enclave가 같은 오류(-25308)로 키 합의를 거부하면 핸드셰이크는 차량이 답하자마자 KeyStoreError.Locked로 끝나고 다시 시도하지 않으며, 그 키가 필요한 저장된 세션은 복원하지 않지만 그대로 남깁니다(13). 다른 키 합의 오류는 이전과 같습니다(핸드셰이크가 시간 제한까지 계속 시도). 소프트웨어 키 객체는 개인키를 메모리에 두므로 잠긴 뒤에도 계속 동작합니다(API 기준).
  • 실기기에서 아직 확인하지 않은 것: 두 설정의 키체인 왕복, 설정 다시 읽기, 잠긴 iPhone에서 AFTER_FIRST_UNLOCK Secure Enclave 키로 하는 핸드셰이크, 그리고 잠긴 iPhone이 WHEN_UNLOCKED Secure Enclave 키의 키 합의에 어떤 오류를 내는지(라이브러리는 -25308을 기대합니다. 다른 오류면 startSession()은 여전히 시간 초과로 끝납니다). 샘플 앱으로 확인합니다(빌드 10이 준비되었고, 확인은 계획 Task 11입니다). 휴대폰이 잠긴 동안 키를 쓰려면 앱이 백그라운드에서 계속 실행되어야 하며, 이 내용은 아직 이 문서에서 다루지 않습니다.
손상된 키는 자동으로 교체되지 않습니다

getOrCreate나 get이 stored key is corrupted와 함께 PlatformFailure를 반환하면, 사용자에게 알린 뒤 delete와 getOrCreate를 호출하세요. 새 키는 공개키가 다르므로 차량에 다시 등록해야 합니다. 조용히 교체하면 사용자는 이유도 모른 채 차량을 제어할 수 없게 됩니다.

세션 캐시

  • 저장된 세션이 있으면 다음 연결에서 핸드셰이크를 건너뜁니다. Android에서는 files/teslable/sessions/에, iOS에서는 키체인에, JVM에서는 메모리에 저장됩니다. TeslaBleConfig.sessionCache로 직접 구현을 제공할 수도 있습니다.
  • 이름은 VIN의 해시이므로 VIN 자체는 저장되지 않습니다.
  • 세션은 키 하나에 속합니다. 키가 바뀌거나 차량 쪽 상태가 앞서 나가면, 다음 연결에서 이전 세션을 버립니다.
  • 캐시가 없거나 오래된 것은 오류가 아닙니다. 라이브러리는 그냥 새 세션을 시작합니다.
  • 폰 잠금이 키를 막아 복원하지 못한 저장된 세션(iOS)은 오래된 것이 아닙니다. 차량의 그 부분에 다시 세션이 생길 때까지 라이브러리는 캐시에 아무것도 쓰지 않으므로, 휴대폰이 잠긴 동안 연결을 끊어도 저장된 세션은 남습니다. 예외: 같은 연결에서 복원한 다른 세션이 오래된 것으로 판명되면 라이브러리는 그 세션을 빼고 캐시를 다시 쓰며, 막혔던 세션도 함께 빠집니다(차량의 그 부분은 다음에 새로 핸드셰이크합니다).

시계

세션 시간 계산에는 단조 시계를 사용하는데, 일부 플랫폼에서는 휴대폰이 잠자는 동안 이 시계가 멈춥니다. 오래 잠든 뒤에는 저장된 세션으로 보낸 첫 명령이 만료 fault로 실패할 수 있습니다. 이때 라이브러리는 차량이 돌려준 새 세션 정보를 받아 재시도하므로 앱에는 아무것도 보이지 않습니다.

연결 슬롯과 끊긴 링크

  • 차량은 블루투스 연결을 최대 세 개까지 받습니다. 다 쓰면 disconnect()를 호출해 슬롯을 비우세요. 세 개가 모두 차 있으면 연결이 MaxConnectionsExceeded를 반환합니다.
  • 링크가 끊겨 connection이 Disconnected로 바뀌어도, 세션 키가 지워지도록 disconnect()를 호출하세요. 다시 호출해도 문제없습니다.
  • 연결이 끊긴 Vehicle은 다시 쓸 수 없습니다. TeslaBle.connect로 다시 연결하세요.

Swift: 시간 제한

Kotlin의 Duration은 인라인 값 클래스입니다. Swift에서는 박싱된 Any?로만 보여서 Swift 코드가 직접 만들 수 없습니다. 도우미 두 개로 해결합니다.

  • Timeouts.shared.seconds(seconds:)는 모든 timeout: 인자에 넘길 박싱된 값을 돌려줍니다. 0, 음수, NaN, 무한대를 넣으면 IllegalArgumentException이 발생합니다. Timeouts.shared.millisecondsOf(timeout:)는 박싱된 값의 밀리초를 돌려주며(nil이면 -1) 왕복 확인용입니다. iOS 샘플의 XCTest 타깃은 tools/ci/verify.sh (d) 단계에서 실행됩니다.
  • TeslaBleConfig.companion.withSeconds(logger:commandTimeoutSeconds:handshakeTimeoutSeconds:connectTimeoutSeconds:pairingTimeoutSeconds:)는 초 단위로 설정을 만듭니다. 모든 인자가 필수이고 commandLifetime은 기본값을 씁니다. TeslaBleConfig.companion.default(logger:)는 그대로입니다.
  • timeout: nil은 여전히 "설정 기본값 사용"입니다.
