18. Troubleshooting

Common problems with scanning, connecting and keys, what usually causes them, and what to do. Problems specific to pairing and commands are added with M4 and M5.

On this page
  1. Scanning and connecting
  2. Keys and sessions
  3. Other messages
  4. Debug logging

Scanning and connecting

SymptomLikely causeWhat to do
PermissionDeniedBluetooth permission missing or declinedAndroid: request BLUETOOTH_SCAN and BLUETOOTH_CONNECT at runtime. iOS: add NSBluetoothAlwaysUsageDescription; if declined, send the user to Settings
BluetoothOffBluetooth is offAsk the user to turn it on
The scan finds nothing, connecting ends with ScanTimeoutOut of range, wrong VIN, or the iOS simulatorMove closer, check the VIN (the car is matched by a name derived from it), use a real device
MaxConnectionsExceededThe car already has three Bluetooth connectionsDisconnect another phone or app, and always call disconnect() in yours
ConnectFailed keeps coming backWeak signal or a busy carThe library already retries for 30 seconds; try again later
connection turns DisconnectedThe link was lostCall disconnect(), then connect again

Keys and sessions

SymptomLikely causeWhat to do
startSession() returns RequiresKeyConnected without a keyConnect with a VehicleKey
startSession() returns KeyNotPairedThe car does not know this keyEnroll it (M4). Check with listKeys(); see 13. Keys and Pairing
stored key is corruptedAndroid backup restored the key file without its wrapping key, or storage damageDelete, create and enroll a new key; exclude the key files from backup (Platform Notes)
HardwareUnavailableHardware required on a device without StrongBox, TEE or Secure EnclaveUse PREFER_HARDWARE
First command after a long sleep fails, the retry succeedsThe phone's clock paused while it sleptNothing; the library resynchronizes on its own

Other messages

SymptomLikely causeWhat to do
Uncertain with a timeoutThe answer was lost after sendingRead the state again; do not resend
UnknownFault, UnknownKeychainCode, values read as UNKNOWNNewer car firmwareCheck for a library update
A Keychain test fails with -25291 on the simulatorPlain Kotlin/Native test binaries cannot use the KeychainCheck Keychain behaviour in the sample app instead

Debug logging

  • Pass a logger in TeslaBleConfig. The default logs nothing.
  • DebugLogger() writes to Logcat on Android, the unified log on iOS and java.util.logging on the JVM. Use it in development builds only.
  • To send logs elsewhere, implement TeslaLogger: one function receiving a level, a tag and a lazily built message. A logger that throws does not stop the library.
  • Levels: DEBUG (raw bytes sent and received), INFO (connections and sessions), WARN (dropped or discarded messages), ERROR (situations the library cannot recover from).
What never appears in logs

The library masks VINs and never logs private keys, session keys, nonces or decrypted content. Keep it that way in your own logs: do not print vin.value, and mask VINs before sharing logs.

To report a problem, use the iOS sample's "copy whole result" button log together with DebugLogger. There is no probe or diagnostics entry point.
