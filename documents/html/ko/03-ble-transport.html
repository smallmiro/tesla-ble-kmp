3. BLE 전송 계층

pkg/connector/ble가 차량과 GATT로 바이트를 주고받는 방법: 광고 이름, 서비스/특성 UUID, 길이 프레이밍, MTU 분할, 스캔과 연결 재시도, 플랫폼별 차이.

전송 계층은 암호를 모른다

ble.Connection은 connector.Connector 인터페이스만 구현합니다. 즉 []byte를 보내고 받을 뿐, protobuf나 세션, 서명은 모두 상위 계층(internal/dispatcher, internal/authentication)의 일입니다. 이 페이지는 그 바이트가 무선으로 어떻게 실려 가는지만 다룹니다.

광고 이름 계산

차량은 VIN을 직접 광고하지 않습니다. VIN의 SHA-1 다이제스트 앞 8바이트를 소문자 hex로 인코딩하고 앞뒤에 S, C를 붙인 이름을 Local Name으로 광고합니다.

// pkg/connector/ble/ble.go
func VehicleLocalName(vin string) string {
	vinBytes := []byte(vin)
	digest := sha1.Sum(vinBytes)
	return fmt.Sprintf("S%02xC", digest[:8])
}
# 셸에서 확인: VIN 5YJS0000000000000 → S1a87a5a75f3df858C
printf '5YJS0000000000000' | shasum | cut -c1-16 | sed 's/^/S/; s/$/C/'
# S1a87a5a75f3df858C

스캔 콜백은 a.LocalName() != localName이면 무시합니다. 호출자가 넘긴 ScanResult의 이름이 VIN으로 계산한 이름과 다르면 tryToConnect가 ble: beacon with unexpected local name 오류를 내고 재시도하지 않습니다.

GATT 연결 절차

tryToConnect가 수행하는 순서입니다. 각 단계의 실패는 retry=true(재시도 가능)로 분류됩니다(어댑터 오류와 이름 불일치, 연결 불가 광고 제외).

  1. 어댑터 초기화 initAdapter(nil). 전역 device가 이미 있으면 재사용.
  2. 스캔 (target이 nil일 때) scanVehicleBeacon(ctx, localName)으로 광고 주소를 얻는다.
  3. 연결 가능 확인 target.Connectable == false면 ErrMaxConnectionsExceeded 반환, 재시도 없음.
  4. Dial device.Dial(ctx, ble.NewAddr(target.Address)).
  5. 서비스 탐색 client.DiscoverServices([]ble.UUID{vehicleServiceUUID}). 결과가 비어 있으면 failed to discover service.
  6. 특성 탐색 client.DiscoverCharacteristics([]ble.UUID{toVehicleUUID, fromVehicleUUID}, services[0]). 두 특성이 모두 없으면 failed to find required characteristics.
  7. 디스크립터 탐색 각 특성마다 client.DiscoverDescriptors(nil, characteristic). go-ble가 CCCD(0x2902)를 찾아야 구독이 가능하다.
  8. 구독 client.Subscribe(conn.rxChar, true, conn.rx): 0213 특성의 indication을 켜고 수신 콜백 rx를 등록.
  9. MTU 교환 client.ExchangeMTU(ble.MaxMTU). 성공하면 blockLength = min(txMtu, 1024) - 3, 실패하면 경고 로그 후 ble.DefaultMTU - 3(= 20바이트)로 폴백. 3바이트는 ATT Write Request 헤더(opcode 1 + handle 2).

성공 시 [info ] Connected to vehicle BLE가 기록되고 *Connection이 반환됩니다. Close()는 ClearSubscriptions()와 CancelConnection()을 호출하며 여러 번 호출해도 안전합니다.

메시지 프레이밍과 MTU

BLE 특성 쓰기 한 번은 MTU에 묶여 있지만 RoutableMessage는 수백 바이트가 될 수 있으므로 SDK는 길이 프리픽스 스트림으로 취급합니다.

상수/필드값의미
maxBLEMessageSize1024길이 프리픽스가 이 값을 넘는 수신 메시지는 버퍼를 비우고 폐기. 송신 블록 길이 상한에도 사용
maxBLEMTUSizeble.MaxMTU (go-ble 정의, ATT 최대 517)ExchangeMTU에 요청하는 클라이언트 측 최대 MTU

inboxchan []byte, 버퍼 5완성된 메시지 큐. 가득 차면 flush가 메시지를 버리고 false 반환

송신 코드

func (c *Connection) Send(_ context.Context, buffer []byte) error {
	c.lock.Lock()
	defer c.lock.Unlock()
	var out []byte
	out = append(out, uint8(len(buffer)>>8), uint8(len(buffer)))  // 2바이트 big-endian 길이
	out = append(out, buffer...)
	blockLength := c.blockLength
	for len(out) > 0 {
		if blockLength > len(out) { blockLength = len(out) }
		if err := c.client.WriteCharacteristic(c.txChar, out[:blockLength], false); err != nil {
			return err
		}
		out = out[blockLength:]
	}
	return nil
}

Send는 ctx를 무시합니다(go-ble의 write API에 컨텍스트가 없음). 뮤텍스로 한 번에 한 메시지만 쓰므로 청크가 섞이지 않습니다.

수신 코드

func (c *Connection) rx(p []byte) {
	if time.Since(c.lastRx) > rxTimeout {
		c.inputBuffer = []byte{}          // 오래된 부분 메시지 폐기
	}
	c.lastRx = time.Now()
	c.inputBuffer = append(c.inputBuffer, p...)
	for c.flush() {}                       // 버퍼에 완성 메시지가 여러 개면 모두 배달
}

func (c *Connection) flush() bool {
	if len(c.inputBuffer) >= 2 {
		msgLength := 256*int(c.inputBuffer[0]) + int(c.inputBuffer[1])
		if msgLength > maxBLEMessageSize { c.inputBuffer = []byte{}; return false }
		if len(c.inputBuffer) >= 2+msgLength {
			buffer := c.inputBuffer[2 : 2+msgLength]
			c.inputBuffer = c.inputBuffer[2+msgLength:]
			select {
			case c.inbox <- buffer:
			default:
				return false                 // inbox 가득 참: 메시지 드롭
			}
			return true
		}
	}
	return false
}
수신 경로에 잠금이 없다

rx와 flush는 go-ble의 알림 고루틴에서 순차 호출되는 것을 전제로 하며 별도 잠금이 없습니다. 다른 BLE 스택으로 포팅할 때 콜백이 병렬로 올 수 있다면 직렬화가 필요합니다.

스캔

type ScanResult struct {
	Address     string  // 광고 주소 (macOS는 CoreBluetooth 식별자, Linux는 MAC)
	LocalName   string  // "S…C"
	RSSI        int16   // dBm
	Connectable bool    // false면 차량이 이미 최대 연결 수에 도달
}

func ScanVehicleBeacon(ctx context.Context, vin string) (*ScanResult, error)
  • ScanVehicleBeacon은 어댑터를 초기화하고 VehicleLocalName(vin)과 일치하는 첫 광고를 반환합니다. ctx가 만료될 때까지 계속 스캔합니다.
  • 내부 scanVehicleBeacon은 일치하는 광고를 찾으면 파생 컨텍스트를 취소해 device.Scan을 멈춥니다. macOS의 device.Scan은 컨텍스트가 취소될 때까지 반환하지 않고 항상 context.Canceled를 돌려주므로, 코드는 errors.Is(err, context.Canceled)가 아닌 오류만 실패로 취급합니다.
  • Connectable == false: 차량(VCSEC)은 하드웨어 제약으로 동시에 최대 3개의 BLE 연결만 유지하며 키포브와 폰 키가 이를 공유합니다. 이때 연결을 시도하면 ErrMaxConnectionsExceeded("the vehicle is already connected to the maximum number of BLE devices")를 즉시 반환합니다. 근처의 폰 키를 끄거나 차에서 멀어지게 하세요.
  • RSSI로 여러 차량 중 가까운 차를 고르는 로직은 없습니다. 같은 VIN은 하나뿐이므로 필요 없습니다.
  • 스캔만 하려면 examples/ble의 -scan-only 플래그를 참고하세요. ScanVehicleBeacon은 NewConnectionFromScanResult에 결과를 넘겨 재스캔을 생략할 수 있습니다.

연결 재시도 루프

func NewConnection(ctx context.Context, vin string) (*Connection, error) {
	return NewConnectionFromScanResult(ctx, vin, nil)
}

func NewConnectionFromScanResult(ctx context.Context, vin string, target *ScanResult) (*Connection, error) {
	var lastError error
	for {
		conn, retry, err := tryToConnect(ctx, vin, target)
		if err == nil { return conn, nil }
		if !retry || IsAdapterError(err) { return nil, err }   // 치명적: 즉시 포기
		log.Warning("BLE connection attempt failed: %s", err)
		if err := ctx.Err(); err != nil {                        // ctx 만료: 마지막 실제 오류를 반환
			if lastError != nil { return nil, lastError }
			return nil, err
		}
		lastError = err
	}
}

재시도 사이에 대기가 없으므로 실질적인 상한은 ctx의 데드라인입니다. tesla-control은 -connect-timeout(기본 20초)으로 이 ctx를 만듭니다. 연결 후 Vehicle.Connect와 StartSession도 같은 ctx를 공유하므로 스캔이 오래 걸리는 환경에서는 넉넉히 잡아야 합니다.

어댑터 관리

패키지는 전역 device ble.Device 하나와 뮤텍스 mu를 가집니다. Linux에서 newDevice()를 여러 번 호출하면 실패하므로 한 번 만든 어댑터를 재사용합니다.

함수설명
InitAdapterWithID(id string) error지정한 어댑터로 전역 device를 만든다. 기본 어댑터를 쓸 때는 호출하지 않아도 되며, ScanVehicleBeacon/NewConnection이 initAdapter(nil)로 자동 초기화한다. 비기본 어댑터를 쓰려면 다른 BLE 호출 전에 반드시 호출. Linux는 "hci0"~"hci15", 그 외 형식은 ErrAdapterInvalidID. macOS에서 빈 문자열이 아닌 ID를 주면 경고 후 ErrAdapterInvalidID.
CloseAdapter() errordevice.Stop() 후 전역 변수를 nil로. 기존 연결을 끊거나 스캔을 멈추지는 않으므로 먼저 Connection.Close()와 스캔 ctx 취소를 해야 한다. 이후 다음 호출에서 새 어댑터가 만들어진다.

VCSEC 응답 특성과 동시성

BLE로 직접 연결하면 Fleet API가 숨겨 주던 VCSEC의 특성이 그대로 드러납니다. dispatcher가 처리하지만 동작을 이해해 두어야 합니다.

  • request_uuid가 없다. VCSEC는 메모리 제약으로 응답에 요청 UUID를 채우지 않습니다. 그래서 dispatcher는 VCSEC로 보내는 요청마다 랜덤 16바이트 routing_address를 새로 만들고, 응답의 to_destination.routing_address로 대기 중인 receiver를 찾습니다(Infotainment는 연결 단위 고정 주소 + request_uuid).
  • 동시 요청 금지. VCSEC는 카운터가 순서대로 도착해야 하고 동시 요청을 구분하기 어려우므로 한 번에 하나씩 보냅니다. tesla-control과 프록시(lockVIN)는 명령을 직렬화합니다.
  • 한 요청에 최대 3개 응답. OPERATIONSTATUS_WAIT(NFC 탭 대기 또는 바쁨), 중간 상태, 최종 결과가 따로 올 수 있습니다. pkg/vehicle/vcsec.go의 readUntil이 종료 조건(isTerminalTest)이 참이 될 때까지 receiver 채널을 계속 읽습니다. 예를 들어 Lock은 commandStatus가 없는 빈 메시지를 성공으로, whitelist 작업은 whitelistOperationStatus가 채워진 메시지를 종료로 봅니다.
  • OPERATIONSTATUS_ERROR는 무시. 레거시 클라이언트용이며 새 클라이언트는 다음 메시지의 구체적 오류 코드를 기다립니다. dispatcher는 이 경우 whitelistOperationInformation이 NONE이 아니면 KeychainError, signedMessageStatus가 없으면 ErrUnknown으로 변환합니다.
  • Infotainment 수면. VCSEC 세션만 맺으려면 StartSession(ctx, []Domain{DomainVCSEC}). 두 도메인에 모두 핸드셰이크하면 잠든 Infotainment 때문에 실패하거나 차량이 깨어날 때까지 지연됩니다.

시퀀스 다이어그램
