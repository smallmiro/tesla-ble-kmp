14. 車両状態の取得

ライブラリが BLE で車両から読み取れるすべての情報を 2 部構成でまとめます。A 部は要求して受け取るデータ（セキュリティコントローラーへの 4 つのクエリ）、B 部は車両が自分から送ってくるデータ（ブロードキャスト）です。クエリは、インフォテインメントコンピューターがスリープしていても VCSEC が応答するため、キー、セッション、ウェイクアップのいずれも不要です。

現在の実装範囲

A 部の 4 つのクエリは実装済みです。車両のブロードキャスト（B 部）は vehicle.events でアプリに届き（B2）、観察ログでも引き続き見られます。getState()（インフォテインメント）は M5 の予定で、まだ存在しません。

VCSEC 要求のルーティング規則:

  • to_destination.domain は DOMAIN_VEHICLE_SECURITY、from_destination.routing_address は要求ごとに新しく作るランダムな 16 バイトのアドレスです。応答はそのアドレス宛てに戻り、ライブラリはアドレス（と車両のドメイン）で対応付けます。VCSEC の応答の対応付けに request_uuid は使いません。uuid（51）にはランダムな 16 バイトを引き続き入れます。
  • 別のルーティングアドレス宛ての応答は自分のものではなく、no-handler として破棄されます（B3 参照）。
  • クエリは認証しません。signature_data はなく、protobuf_message_as_bytes は平文の UnsignedMessage です。コマンドは同じ封筒に signature_data と AES-GCM で保護したペイロードを入れます。
  • sessionInfo のペイロードは session_info_request（14）で、to_destination.domain は問い合わせるドメインです。応答は session_info（15）に入って戻ります。

ClosureStatuses には 1〜8 番の ClosureState_E フィールドが 8 つあります: frontDriverDoor、frontPassengerDoor、rearDriverDoor、rearPassengerDoor、rearTrunk、frontTrunk、chargePort、tonneau。

変換規則

スキーマ外の値は 0 番の値ではなく UNKNOWN に変換します。proto3 では欠けた enum と 0 番の値を区別できないため、ロック状態が欠けると UNLOCKED と読まれ、クエリでは Go の動作をそのまま踏襲しています。gear には Go 側の対応がありません（公式 Go のスキーマはフィールド 5 まで）。0 番の値が GEAR_UNKNOWN なので、ギアが欠けると UNKNOWN と読まれます。ギアはブロードキャストで確認しましたが、車両がクエリの応答にギアを入れるかは実車で確認していません。実車の結果では、車両はすべてのフィールドが CLOSED（0 番の値）のとき closureStatuses を省き、1 つでもそうでなければ送ってくるため（運転席と運転席側の後席ドア、リアトランク、充電ポートで確認）、「なければすべて閉」は観測と合っています。唯一の例外は室内ボタンで操作したトランクで、ブロードキャストがまったくありませんでしたが、このクエリでは報告されるはずです（実車ではまだ確認していません）。

スリープとウェイクアップ

  • どのクエリも車両を起こしません。スリープ中かどうかを表示するには sleepStatus を使います。
  • M5 で追加予定: getState(category) は、インフォテインメントの 12 カテゴリ（充電、空調、走行、位置、開口部、充電スケジュール、プレコンディショニングスケジュール、タイヤ空気圧、メディア、メディア詳細、ソフトウェア更新、ペアレンタルコントロール）を読みます。登録済みのキーと起きている車両が必要です。
  • wakeUp()（M4）は VCSEC セッションだけで動きます。
  • ロックやトランクのコマンド（M4）が Uncertain で返ったら、コマンドを再送せず vehicleStatus() を読み直してください。

B2. ブロードキャストイベント: vehicle.events

応答の対応付けはこれまでどおりで、Go 原本とも同じです。ブロードキャストにはルーティングアドレスがないため、ディスパッチャーはルーティングから破棄します (破棄理由 TO_DOMAIN)。ブロードキャストは待機中の要求に届かず、応答と取り違えられることもありません。観察ログも引き続き [drop:to-domain] の行を書きます (18. トラブルシューティング)。

それに加えて、ライブラリは平文のブロードキャストをすべて vehicle.events でアプリに渡します (FR-035)。Go 原本にはこのような機能はなく、フレームを破棄するだけです。Kotlin と Swift の例は 12. ライブラリ入門 に、各メッセージの意味は B3 にあります。

val events: Flow<VehicleEvent>                    // Vehicle のメンバー

sealed interface VehicleEvent {                   // dev.mirolab.teslable.model
    val raw: ByteArray                            // 受信したフレーム全体。アクセスのたびに新しいコピー。VIN はマスクしない
    val unknownFields: List<String>               // スキーマが知らないフィールドのパス。例: "53"、"1.8"
    class Status(val status: VehicleStatus, …) : VehicleEvent
    class AuthenticationRequest(val requestedLevel: AuthenticationLevel, val reasons: List<AuthenticationReason>, …) : VehicleEvent
    class Unrecognized(…) : VehicleEvent
}

イベントになるフレーム

次のすべてを満たす必要があります。観察ログの詳細デコードの条件と同じですが、ペイロードがデコードできなくてもかまいません (デコードできないペイロードは Unrecognized になります)。

フィールド必要な値
from_destinationdomain = DOMAIN_VEHICLE_SECURITY
to_destinationdomain = DOMAIN_BROADCAST (ルーティングアドレスなし)
request_uuid空
signature_dataなし
session_infoなし

それ以外のフレームは観察ログの 1 行として残るだけです。他のスマートフォン宛ての応答、署名または暗号化されたフレーム、解析できないフレーム、送信元のないフレームがこれに当たります。ライブラリはブロードキャストを復号せず、復号したデータがイベントに入ることもありません (FR-112)。

イベントの種類

イベントいつ持つ内容

VehicleEvent.AuthenticationRequestフレームに authenticationRequest (フィールド 3) があるrequestedLevel と reasons (B3.2)。20 バイトのトークンはフィールドにせず、raw にある
VehicleEvent.Unrecognizedどちらもない: 未知のフィールドだけ (実車では 48 と 53)、他のフィールド、ペイロードなし、デコードできないペイロード (このとき unknownFields は空)raw と unknownFields のみ
  • 1 つのフレームが 2 つのイベントになることがあります。両方のフィールドがあると Status が先、AuthenticationRequest が後に来て、どちらも同じ raw と unknownFields を持ちます。スキーマが 2 つのフィールドを 1 つの oneof に入れているため通常のデコードでは片方しか残りませんが、ライブラリは両方を読みます。
  • raw は受信したフレーム全体 (BLE の長さプレフィックス 2 バイトを除く) で、車両が平文で送ったそのままです。アクセスのたびに新しいコピーを作るので、一度だけ読んでください。VIN はマスクされていないので、保存や共有の前に VIN をマスクしてください。観察ログの詳細デコードと同じく「平文ペイロード禁止」の狭い例外で、FR-112 には抵触しません。車両が平文で送ったフレームだけが対象で、ライブラリが復号したものは決して入りません。
  • 2 つのイベントは、フィールドと raw のバイトが同じなら等しくなります。イベントを出力すると raw は長さだけが表示されます。

スキーマ外の enum の値もそのフィールド番号で載ります (モデルでは UNKNOWN)。新しいギアの値なら "1.7" です。サブメッセージ内では、そのメッセージ自身のフィールドが、その中のメッセージのフィールドより先に来ます。2 回出た番号は 2 回載ります。リストが空でなければフレームの一部を解釈できなかったという意味で、バイトは raw にあります。

アプリが守るルール

  • 繰り返しは変化ではありません。車両は何も変わらなくても 1〜25 秒ごとに、ときには 1 秒以内に何度も状態を送り直します。ライブラリは繰り返しを除かないので、前の値と自分で比べてください。
  • トランク: 外側から手でトランクを開け閉めしたときはブロードキャストが来ました (rearTrunk = OPEN、その後 closureStatuses なし)。室内ボタンでは来なかったため、events でトランクを追跡するアプリには CLOSED のまま見えます。トランクの状態が重要なときは vehicleStatus() で確認してください。
  • 起動中の車両: スリープ中の車両の最初のフレームでは、開閉状態が UNKNOWN、gear = UNKNOWN になることがあります。実際の値は約 0.5 秒以内に続きます (B3.1)。これらの UNKNOWN を変化として扱わないでください。これらのフレームではロック状態も UNLOCKED と読まれますが、UNLOCKED はエンコードされない値なので、車両がまだロックされていたかは分かりません。重要な場合は vehicleStatus() で確認してください。
  • 購読: 収集は始めた瞬間から受け取ります。それより前のブロードキャストは再送されません。複数の場所で収集すると、それぞれがすべてのイベントを受け取ります。
  • 終わり: connection が理由を問わず Disconnected になるか disconnect() を呼ぶと、先に起きたほうでフローは例外なく正常に終わります。その後に始めた収集はすぐに終わります。その瞬間に受け渡し中だったフレームは失われることがあります。再接続の判断は connection で行い、リンクが切れた後も disconnect() は呼んでください。新しい接続は、自分の events を持つ新しい Vehicle です。
  • 遅い収集側: ライブラリは遅れた収集側のためにフレームを 64 個まで保持します。それを超えると、その接続のすべての収集側から新しいフレームが抜け、破棄数を数え、最初と 100 回ごとに WARN の行を出します。エラーではありません (16. エラー処理)。収集処理は軽く保ってください。
  • キーもセッションも不要で、connect(vin, key = null) で十分です。実車での観察は登録していないキーで行いました。

頻度: 変化がなくても繰り返し届きます。1 回目は起きている間 1〜25 秒ごと（UNLOCKED は 26 バイト、それ以外は 28 バイト）、2 回目は 1 秒以内に複数届くこともありました。3 回目は起動中の 0.5 秒以内に 9 フレーム、その後は変化があるあいだ 0.1〜8 秒に 1 回でした。繰り返しを変化として扱わないでください。

ライブラリの規則: closureStatuses がなければすべて閉と見なします (A2)。両方の運転席側ドア、リアトランク、充電ポートで確認済みです。間違いになるのは、ブロードキャストを送らない室内ボタン操作のトランクだけです。UNLOCKED はロック状態の 0 番の値で、エンコードされないため、ブロードキャストではロック状態が欠けている場合と区別できません（車両がまだ ASLEEP の間に確認）。

B3.2 authenticationRequest（フィールド 3）

状態: 発生は 確認済み、下位フィールド名は未検証（Teslemetry スキーマ）。

#フィールド（AuthenticationRequest）型意味
2sessionInfo（名前は未検証）AuthenticationRequestToken{token = 1}token: 20 バイト
3requestedLevel（名前は未検証）AuthenticationLevel_E0 NONE、1 UNLOCK、2 DRIVE（接頭辞 AUTHENTICATION_LEVEL_）
4reasonsForAuth（名前は未検証）repeated AuthenticationReason_E車両が認証を求める理由

AuthenticationReason_E（接頭辞 AUTHENTICATIONREASON_）: 0 NOT_DOCUMENTED、1 IDENTIFICATION、2 POWER_ON_VEHICLE_REQUEST、3 GTW_REQUEST、4 UI_UNLOCK_PASSIVE_AUTH、5 PASSIVE_UNLOCK_EXTERIOR_HANDLE_PULL、6 PASSIVE_UNLOCK_INTERIOR_HANDLE_PULL、7 PASSIVE_UNLOCK_AUTOPRESENT_DOOR、8 ENTERED_HIGHER_AUTH_ZONE、9 WALK_UP_UNLOCK、10 IMMOBILIZER。関連する AuthenticationResponse（UnsignedMessage のフィールド 3、スマートフォンキーが送る）と AuthenticationRejection_E はスキーマにあり、ライブラリは送りません。

公開モデル (VehicleEvent.AuthenticationRequest、B2) では、requestedLevel は NONE、UNLOCK、DRIVE で、スキーマ外の値は UNKNOWN です。レベルがないことと NONE は区別できません。reasons は車両が送った値ごとに 1 つずつで、名前は上の接頭辞を除いたものです。スキーマ外の値は UNKNOWN になり、既知の値の後に並びます (正確な順序は raw にあります)。

観察: 室内ハンドルを引くと requestedLevel = DRIVE、reasons = [PASSIVE_UNLOCK_INTERIOR_HANDLE_PULL]。充電ポートを開けて充電が始まるときは ENTERED_HIGHER_AUTH_ZONE が加わりました。同じ瞬間に vehicleStatus（とフィールド 53）が一緒に届きました。他の理由は観察できていません。3 回目（スリープ中、続いて起きている車両の外側ハンドル、充電ポートのラッチ解除、手でのトランク操作）では authenticationRequest もフィールド 53 も届かず、PASSIVE_UNLOCK_EXTERIOR_HANDLE_PULL は一度も見られませんでした。

包まれており、裸ではない

この車両はこれを RoutableMessage に包んで（上記のブロードキャスト形式）送ってきました。約 1.1 秒ごとに包まれていない FromVCSECMessage{authenticationRequest} が届くという他の報告（Teslemetry PR #179）とは異なります。この車両では包まれていないフレームは見えませんでした（drop:missing-source、drop:unparseable: 0 行）。

B3.3 フィールド 53（不明）

B3.5 他のクライアント宛ての応答

ブロードキャストではありません。署名された 83 バイトの応答（to_destination.routing_address が別のクライアントの 16 バイトのアドレス、16 バイトの request_uuid、本文は空）は、別のスマートフォンの VCSEC 要求への応答です。こちらのリンクにも約 1〜2 分ごとに、またドアのイベント直後に届きます。ライブラリはこれを no-handler（持ち主 other）として破棄します。
