# M6 배포 1단계: iOS SPM 1.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** iOS 앱 개발자가 Xcode의 *Add Package*로 `https://github.com/smallmiro/tesla-ble-kmp` 버전 `1.0.0`을 받아 `import Teslable`로 쓸 수 있게 한다.

**Architecture:** `:sdk`가 SKIE 배포 설정으로 static `Teslable.xcframework`를 만든다. 저장소 루트의 `Package.swift`가 `binaryTarget`으로 GitHub Release의 zip을 가리킨다. 릴리스는 두 단계: **준비**(`prepare.sh`가 브랜치에 `Package.swift`를 커밋하고 zip을 보관 → PR) → **배포**(머지된 `main`에서 `publish.sh`가 태그와 GitHub Release를 만들고 원격 zip을 확인). GitHub Actions는 쓰지 않는다(ADR-0012). Android 배포(Maven Central)는 2단계로 미룬다.

**Tech Stack:** Kotlin XCFramework DSL, SKIE 0.10.15, Swift Package Manager `binaryTarget`, xcodegen, `gh`.

**Spec:** (ADR 번호: 0016은 세션 캐시 counter 예약이 이미 사용, 이 계획은 0017.) 사용자 결정(2026-11-14): "SPM으로", "1.0.0으로 시작", Android는 Maven Central(나중), CocoaPods 미지원. `{{PRD_FILE}}` D13(이 계획이 개정), 로드맵 M6(381행). `{{SDD_FILE}}` §8.5. ADR-0012. 라이브러리 문서 `{{LIB_DOCS_DIR}}11-lib-overview.md` §Installation, `12-lib-getting-started.md`, `17-lib-platform-notes.md`. Go 매뉴얼은 해당 없음(배포는 포팅 대상이 아님).

## Global Constraints

- 첫 버전 `1.0.0`(SemVer). 태그 `v1.0.0`. GitHub Release는 정식(prerelease 아님). 릴리스 노트와 문서에 "실차 확인 대기 항목(#118, Android 실기기)"을 그대로 적는다.
- XCFramework: 이름 `Teslable`, static, 슬라이스 정확히 `ios-arm64` + `ios-arm64-simulator`(시뮬레이터는 `arm64`만, Apple Silicon Mac 전용), 각 슬라이스 `MinimumOSVersion` 16.0, SKIE `skie { build { produceDistributableFramework() } }`.
- zip: `ditto -c -k --keepParent`로 압축 루트에 `Teslable.xcframework/`. 이름 `Teslable.xcframework.zip`. 체크섬은 `swift package compute-checksum`. **체크섬을 낸 zip을 그대로 올린다. 준비 뒤 다시 만들지 않는다.**
- `Package.swift`: 저장소 루트, `// swift-tools-version:5.9`, `name: "Teslable"`, `platforms: [.iOS(.v16)]`, product·target 이름 `Teslable`, `.binaryTarget(name: "Teslable", url: "https://github.com/smallmiro/tesla-ble-kmp/releases/download/v<VERSION>/Teslable.xcframework.zip", checksum: "<sha256>")`.
- `main`은 보호 브랜치: 스크립트는 `main`에 직접 푸시하지 않고 태그만 푸시한다. 브랜치 푸시와 PR 생성은 사람이 한다.
- CocoaPods는 지원하지 않는다(trunk가 2026-12-02 읽기 전용). 문서에 한 줄로 적는다.
- 샘플 앱은 계속 로컬 프레임워크 경로를 쓴다(SPM으로 바꾸지 않음).
- 비밀 없음: `gh` 인증만 쓴다. 로그에 토큰을 출력하지 않는다.
- TDD(빌드·스크립트는 검사 스크립트를 먼저 쓰고 실패 확인), Tidy First, `tools/ci/verify.sh`, 사용 문서 MD + HTML ko/en/ja(절대 규칙 13), Rebase merge.
- 역할: 빌드·스크립트·MD 문서 `library-developer`, HTML ko/ja `docs-translator`, iOS 소비자 앱 검토는 `ios-developer` 관점(문서의 Swift 규칙)으로 리뷰.

## Review Focus

1. **소비자 앱 링크에서 CryptoKit Swift 코드나 Swift 런타임 심볼 누락**: 프로듀서 빌드는 되지만 소비자 Xcode 앱이 링크에 실패할 수 있다 → Task 2가 키 생성 경로를 실제로 호출하고 기기용(`generic/platform=iOS`)으로도 빌드.
2. **체크섬 불일치**: 준비 뒤 zip을 다시 만들면 SPM이 설치를 거부한다 → Task 3 `publish.sh`가 올릴 zip의 체크섬을 `Package.swift`와 대조하고 다르면 중단.
3. **재시도 중 반쯤 만든 릴리스**: 태그만 있고 Release나 자산이 없는 상태 → Task 3 `publish.sh`가 단계마다 기존 태그·Release·자산을 확인하고 끝난 단계는 건너뜀.
4. **Intel Mac 시뮬레이터에서 빌드 실패**: x86_64 슬라이스가 없다 → 문서(`17`)에 명시. Task 1 검사가 슬라이스 구성을 고정해 의도치 않은 변경을 막음.
5. **디버그 프레임워크 경로 회귀**: 샘플 앱과 `verify.sh` (c) 단계는 `sdk/build/bin/.../debugFramework`를 쓴다 → Task 1 뒤 `verify.sh` 전체 통과로 확인.
