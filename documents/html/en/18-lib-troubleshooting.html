The connect time budget

connectTimeout (30 seconds by default) or ConnectOptions.timeout covers scanning, opening the link and the retries between attempts. When connect fails on it:

  • It returns at once, with the error of the last failed attempt, or ScanTimeout if no attempt failed. The Go original does the same.
  • It does not wait for an attempt still running. That attempt is cancelled and cleans up after connect has returned, waiting at most 5 seconds for the platform disconnect. If it still opens a link, the library disconnects that link.
  • The only wait past the budget: a connection created at the very moment the budget ran out is closed before connect returns, which also takes at most 5 seconds. So the library itself adds at most 5 seconds to a failed connect.
  • The budget is a timer, and a timer cannot fire while the app is not running, so a suspended app can overrun by any amount. On a real iPhone a 30-second budget ended 36 minutes late (docs/analysis/2026-11-01-build18-link-health.md F3, likely, not confirmed). No timeout can prevent this.

Seen once on a real iPhone: ConnectFailed after 32.63 seconds. The likely cause is a late timer, not confirmed because the log records no process state. ScanTimeout returns, where no attempt had failed, overran the same way (at 31.35, 32.40 and 33.19 seconds), and the app's next 4-second wait took 9.03 seconds. The log cannot exclude the one library wait above, which would need a link to open at the instant the budget ran out. No harm was seen (#130).

Frames without a source

Decision (#130): a frame without a source stays out of vehicle.events and remains a [drop:missing-source] line in the observation log.

  • It is not a plain broadcast (14, B2), and the Go original drops it too. Without a source nothing says the frame came from the security domain: reinterpreted=… only shows how the same bytes read as a FromVCSECMessage.
  • Delivering these frames would widen the public contract: raw is always a whole RoutableMessage frame, and any stray frame would become an event.
  • The gain is small. A real car sent 2 such frames in 12 connections. The authenticationRequest (DRIVE, IDENTIFICATION) arrived 1 ms before the app saw connected, so nothing was collecting yet and, with no replay, a wider rule would not have delivered it. The other was a bare commandStatus, which has no event type. An app also cannot act on an AuthenticationRequest: the library does not send AuthenticationResponse.

Reconsider this if a car sends such frames often: reports elsewhere describe one about every 1.1 seconds (14, B3.2).

Debug logging

  • Pass a logger in TeslaBleConfig. The default logs nothing.
  • DebugLogger() writes to Logcat on Android, the unified log on iOS and java.util.logging on the JVM. Use it in development builds only.
  • To send logs elsewhere, implement TeslaLogger: one function receiving a level, a tag and a lazily built message. A logger that throws does not stop the library.
  • Levels: DEBUG (raw bytes sent and received), INFO (connections and sessions), WARN (dropped or discarded messages), ERROR (situations the library cannot recover from).
What never appears in logs

The library masks VINs and never logs private keys, session keys, nonces or decrypted content. Keep it that way in your own logs: do not print vin.value, and mask VINs before sharing logs. Do not log getState results either, toString() included: a VehicleData can hold the location and the destination, and InfotainmentRejected.message carries the car's own text.

To report a problem, use the iOS sample's "copy whole result" button log together with DebugLogger. There is no probe or diagnostics entry point.

  • When one frame carries both vehicleStatus and authenticationRequest, the observe line shows only the one that comes last: the schema puts both in one oneof, and an ordinary decode keeps only the last one. vehicle.events reads both fields and delivers both events (Status, then AuthenticationRequest).

Observation log (development)

While you develop, the library can write one summary line for every message it drops and for every reply from the vehicle security domain. It shows what the car sends without being asked. It changes no behaviour: broadcasts are still kept out of reply matching, and the plain ones also reach apps through vehicle.events (previous section). What each pushed message means is in 14. Reading Vehicle State, Part B. The Bluetooth transport adds one line for every scan hit of connect.

  • Tag observe, level DEBUG. A logger that discards DEBUG never builds the line. Visible through DebugLogger() or your own TeslaLogger. The iOS sample's observation mode collects only these lines.
  • Shape: [point] NB from=… to=… request_uuid=… payload=…, where NB is the size of the received frame.
  • Scan hit line (FR-038): [connect:scan-hit] after=<ms>ms rssi=<dBm|unavailable> connectable=<true|false|unknown> attempt=<n>. One line for every advertisement found by a scan that connect runs itself, written before the connectable check and before opening, so it also appears for a connect that fails and for each retry. after is the time since connect started (the same measure as hitAfterMillis, 12. Getting Started), attempt is the open attempt the hit was found for. The time your logger receives the line is the wall-clock time of the hit. ble.scan(vin) and a target reused without a scan write no line. It has no advertised name and no device identifier.

Detail form (exploration only)

Example: unknownFields=[48:len(8){1:varint=3(0x3), 2:len(4)"ABCD"}, 9]. Entries keep their arrival order and repeated fields repeat. The field number and wire type are kept; no field name is invented.

VINs (17 characters) are masked in text and in raw bytes before any hex is produced; only the first 3 and last 4 characters stay. Masking runs on the raw bytes before they are parsed, so masked bytes can change the value or structure that is shown (nothing leaks). This output is for exploration only. It does not tell what a field means. On the real car a missing closureStatuses meant all closed for the driver doors, the rear trunk and the charge port, but a trunk operated by the interior button produced no broadcast at all, so a broadcast alone cannot prove the trunk is closed (see 14, Part B).

Limits and rules

  • Detailed decoding is a narrow exception, and only for frames the car originally sent as plaintext (never for anything the library decrypted, so FR-112 is unaffected); vehicle.events hands such frames to apps as raw, decodable or not. All of these must hold: from the security domain, to the broadcast domain, empty request UUID, no signature, no session info, and a payload that reads as FromVCSECMessage. Then only FromVCSECMessage unknown fields 48 and 53 and VehicleStatus unknown fields 7 and 8 are decoded (field 7 is now the named gear, so it is unknown only when its value is outside the definitions; that raw value is still shown, for example unknownFields=[7:varint=9(0x9)], because that value is outside the definitions). Every other field and frame keeps the number-only form.
  • A missing enum value cannot be told from its zero value: an absent lock state reads VEHICLELOCKSTATE_UNLOCKED (sleep and presence read UNKNOWN). Only message parts can be reported as absent.
  • Encrypted content and session info appear by length only, public keys by SHA-1 prefix only. The VIN and decrypted content never appear. Keep this rule when you add lines.
  • The BLE transport counts inbox overflows per connection. Each dropped message logs Dropping received message because inbox is full (dropped N since connect) at ERROR; when the link ends, one line BLE inbox overflowed N time(s) during this connection is logged at WARN (only if N is above 0).
  • DebugLogger also prints the raw BLE bytes (TX: and RX:) at DEBUG. Do not share such platform logs. Only what the car encrypted stays encrypted there. Everything else appears as the car sent it, including VCSEC query replies, broadcasts and a plaintext infotainment reply (firmware before 2024.38, see 16. Error Handling), which can hold the location.
