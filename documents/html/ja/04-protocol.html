メッセージのエンコード: RoutableMessage

すべてのメッセージは Protocol Buffers でエンコードされ、最上位の型は UniversalMessage.RoutableMessage(protobuf/universal_message.proto)です。典型的なリクエストは次のとおりです(バイナリフィールドは hex で表記)。

to_destination {
  domain: DOMAIN_VEHICLE_SECURITY
}
from_destination {
  routing_address: 0a7962c10d38b61dd2a7722780a4f096
}
protobuf_message_as_bytes: 0a020805
uuid: 05514f57616bcc81a8ce0f9d7b483229
フィールド (番号)型リクエストではレスポンスでは
to_destination (6)Destination oneof {domain, routing_address}コマンドを処理するドメインリクエストの from_destination(routing_address)がコピーされる
from_destination (7)Destination接続を識別するランダムな 16 バイトの routing_address。車両がレスポンスをトランスポート層のアドレスへ返すときに使用応答したドメイン
payload oneof: protobuf_message_as_bytes (10)bytesアプリケーションペイロード。VCSEC → VCSEC.UnsignedMessage、Infotainment → CarServer.Action。AES-GCM の場合は暗号文VCSEC → VCSEC.FromVCSECMessage、Infotainment → CarServer.Response。レスポンス暗号化時は暗号文
payload: session_info_request (14)SessionInfoRequest{public_key, challenge}ハンドシェイクリクエスト。クライアント公開鍵-
payload: session_info (15)bytes (エンコードされた Signatures.SessionInfo)-ハンドシェイクレスポンス、または同期エラー時にエラーとともに同梱
signature_data (13)Signatures.SignatureDatasigner_identity.public_key + HMAC_Personalized_data または AES_GCM_Personalized_datasession_info_tag(ハンドシェイク HMAC)または AES_GCM_Response_data(暗号化レスポンス)
signedMessageStatus (12)MessageStatus{operation_status, signed_message_fault}-プロトコル層のエラー。MessageFault_E の値は9 章
uuid (51)bytes ≤ 16コマンドを一意に識別する予測不可能な値。ハンドシェイクレスポンスのリプレイ防止に使われるため、ランダムでなければならない-
request_uuid (50)bytes-リクエストの uuid のコピー。VCSEC はメモリ制約のため通常は設定しない
flags (52)uint32 ビットマスクFlags enum のビット。常に 1 << FLAG_ENCRYPT_RESPONSE(= 2)を設定することを推奨。車両が認証し、未知のビットは無視するレスポンスの flags。レスポンスメタデータに含まれる

Flags enum: FLAG_USER_COMMAND = 0、FLAG_ENCRYPT_RESPONSE = 1。SDK の vehicle.DefaultFlags = 1 << FLAG_ENCRYPT_RESPONSE であり、Vehicle.Flags フィールドで変更できます。

protoc によるメッセージのデコード

tesla-control -ble -debug list-keys の TX: ログに出力された hex は、pkg/protocol ディレクトリで次のようにデコードできます。

echo 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805 \
    | xxd -r -p \
    | protoc --decode=UniversalMessage.RoutableMessage -I protobuf protobuf/*.proto
to_destination {
  domain: DOMAIN_VEHICLE_SECURITY
}
from_destination {
  routing_address: "\nyb\301\r8\266\035\322\247r\'\200\244\360\226"
}
protobuf_message_as_bytes: "\n\002\010\005"
uuid: "\005QOWak\314\201\250\316\017\235{H2)"

VCSEC 宛てのメッセージなので、protobuf_message_as_bytes は VCSEC.UnsignedMessage です。

printf "\n\002\010\005" | protoc --decode=VCSEC.UnsignedMessage -I protobuf protobuf/*.proto
# InformationRequest {
#   informationRequestType: INFORMATION_REQUEST_TYPE_GET_WHITELIST_INFO
# }

逆に protoc --encode でペイロードを作ることもできます(後述の AES-GCM の例)。*.proto から他言語のバインディングも生成できます。

プロトコルの概念: ドメイン、時刻、ロール

ドメイン

車両のサブシステムはそれぞれ異なる公開鍵を持つため、ドメインごとにハンドシェイクとセッション状態を個別に管理します。VCSEC(DOMAIN_VEHICLE_SECURITY = 2)はロック、リモートスタート、トランク、キーチェーンを担当し、Infotainment(DOMAIN_INFOTAINMENT = 3)が残りを処理します。VCSEC は Infotainment がスリープ中でも BLE でアクセスできます。

時刻

各ドメインは独自の時計を持ち、時刻を (epoch_id, timestamp) のペアで表します。epoch_id は起動時に生成されるランダムな 16 バイト、timestamp は epoch 開始からの秒単位の整数です。クライアントはドメインの時計とローカルの時計の差を追跡し、コマンドの有効期限(expires_at)を計算します。SDK は SessionInfo.clock_time と受信時刻から timeZero を決め、リクエスト後 AllowedLatency(BLE 4 秒、インターネット 10 秒)を超えて到着したセッション情報は時計の補正に使いません。

ロール

公開鍵ごとにロール(Owner、Driver、Fleet Manager、Vehicle Monitor、Charging Manager、Guest、Service)があります。1 章のロール表を参照してください。ロールごとの権限はファームウェアの更新によって変わる可能性があります。

メタデータのシリアライズ (TLV)

認証ではメッセージを VIN などのメタデータに結び付ける必要があるため、メタデータをハッシュ入力として使える正規のシリアライズが必要です。各項目は tag(1B) || length(1B) || value としてエンコードされ、tag の値は Signatures.Tag に定義されています。

Tag値内容
TAG_SIGNATURE_TYPE0SignatureType 1 バイト
TAG_DOMAIN1Domain 1 バイト
TAG_PERSONALIZATION2VIN (17 文字の ASCII)
TAG_EPOCH316 バイトの epoch_id
TAG_EXPIRES_AT4uint32 big-endian
TAG_COUNTER5uint32 big-endian
TAG_CHALLENGE616 バイト (ハンドシェイクリクエストの uuid)
TAG_FLAGS7uint32 big-endian
TAG_REQUEST_HASH8レスポンス復号用のリクエストハッシュ
TAG_FAULT9uint32 big-endian MessageFault_E
TAG_END255終端マーカー 0xFF
 
TLV(VIN: "abc")   = TAG_PERSONALIZATION || LEN("abc") || "abc"
                  = 0x02 || 0x03 || 0x61 0x62 0x63
                  = 0x0203616263

TLV(COUNTER: 100) = TAG_COUNTER || LEN(uint32) || 0x00000064    (整数は 4 バイト big-endian)
                  = 0x05 || 0x04 || 0x00000064
                  = 0x050400000064

SERIALIZE({COUNTER: 100, VIN: "abc"})
                  = TLV(VIN) || TLV(COUNTER) || 0xFF               (tag の昇順に並べて連結し、末尾に 0xFF)
                  = 0x0203616263050400000064FF

Go の実装(internal/authentication/metadata.go)では、項目を必ず tag の昇順で追加する必要があり(errOutOfOrderMetadata)、値の長さは 255 バイト以下でなければならず(ErrMetadataFieldTooLong)、nil の値はスキップされます。Checksum(message) が 0xFF を付けたあと、メッセージのバイト列を続けてハッシュします。

鍵合意 (ECDH)

S = (Sx, Sy) = ECDH(c, V) = ECDH(v, C)

# client.key と vehicle.pem から K を計算

    | openssl dgst -sha1 -binary | head -c 16 | xxd -p)
echo $K
# 1b2fce19967b79db696f909cff89ea9a
自前で実装しないこと

ECDH と AES-GCM には OpenSSL や Go の crypto のような検証済みライブラリを使ってください。プロトコルは常に K のバイナリ値を使用し、上記の hex は表示用です。

レスポンスの認証 (session_info_tag の検証)

MITM 攻撃者が有効期限のより長いコマンドを入手できないよう、クライアントはセッション情報レスポンスを認証しなければなりません。攻撃者が公開鍵を差し替えると車両がコマンドを拒否し、公開鍵をそのままにして残りを変更するとクライアントがタグ検証で拒否します。

  1. セッション情報認証鍵の導出。 SESSION_INFO_KEY = HMAC-SHA256(K, "session info")。文字列は ASCII リテラル。 
    export SESSION_INFO_KEY=$(echo -n "session info" | openssl dgst -sha256 -mac hmac -macopt hexkey:"$K")
# fceb679ee7bca756fcd441bf238bf2f338629b41d9eb9c67be1b32c9672ce300
  2. メタデータのシリアライズ。 TAG_SIGNATURE_TYPE = SIGNATURE_TYPE_HMAC(6)、TAG_PERSONALIZATION = VIN、TAG_CHALLENGE = リクエストの uuid。 
    VIN = 5YJ30123456789ABC
METADATA = 00 01 06
        || 02 11 35594a3330313233343536373839414243
        || 06 10 1588d5a30eabc6f8fc9a951b11f6fd11
        || ff
       = 000106021135594a333031323334353637383941424306101588d5a30eabc6f8fc9a951b11f6fd11ff
  3. タグの計算。 HMAC-SHA256(SESSION_INFO_KEY, METADATA || session_info) 
    echo "$METADATA$SESSION_INFO" | xxd -r -p | openssl dgst -sha256 -mac hmac -macopt hexkey:"$SESSION_INFO_KEY"
# 996c1fe38331be138f8039c194b14db2198846ed7d8251e6749284d7b32ea002
  4. 比較。 レスポンスの signature_data.session_info_tag.tag と定数時間で比較(Go: hmac.Equal)。一致しなければレスポンスを破棄。

Go では internal/authentication.NewAuthenticatedSigner がこの検証を行い、NativeSession.SessionInfoHMAC がタグを計算します。SDK は、uuid が最近のリクエストのものでない、または AllowedLatency を超えて到着したセッション情報を、タグ検証の前に破棄します。

コマンドの認可

ハンドシェイク後、クライアントはドメインの時計(epoch、timestamp)、アンチリプレイカウンター、共有鍵 K を持ちます。コマンドの protobuf P(VCSEC.UnsignedMessage または CarServer.Action)を作成したあと、以下のメタデータ M をシリアライズします。

値Tag説明
署名の種類TAG_SIGNATURE_TYPESIGNATURE_TYPE_HMAC_PERSONALIZED(8) または SIGNATURE_TYPE_AES_GCM_PERSONALIZED(5)
ドメインTAG_DOMAINDOMAIN_VEHICLE_SECURITY(2) または DOMAIN_INFOTAINMENT(3)
VINTAG_PERSONALIZATION17 文字の VIN
EpochTAG_EPOCHsession_info.epoch をコピー
有効期限TAG_EXPIRES_ATドメインの時計基準の秒。SDK は ctx のデッドラインまで(なければ 5 秒)に設定
カウンターTAG_COUNTER単調増加。初期値は session_info.counter、コマンドごとに +1
フラグTAG_FLAGSリクエストの flags。0 でない場合のみ含める
  • カウンターは同じ epoch 内でコマンドごとに増加しなければなりません。Infotainment は順序が入れ替わった到着を許容するスライディングウィンドウを維持しますが、VCSEC にはカウンター順に到着する必要があります。
  • 遠すぎる有効期限は MESSAGEFAULT_ERROR_TIME_TO_LIVE_TOO_LONG で拒否されます。

HMAC-SHA256 認証

  1. 鍵の導出: K' = HMAC-SHA256(K, "authenticated command")。
  2. RoutableMessage を作成し、payload.protobuf_message_as_bytes = P とする。
  3. signature_data.signer_identity.public_key = ENCODE_PUBLIC(C)。
  4. tag = HMAC-SHA256(K', M || P)。
  5. signature_data.HMAC_Personalized_data に epoch、counter、expires_at、tag を設定する。
message HMAC_Personalized_Signature_Data {
    bytes   epoch       = 1;
    uint32  counter     = 2;
    fixed32 expires_at  = 3;
    bytes   tag         = 4;
}

AES-GCM 暗号化

  1. 128 ビット鍵 K をそのまま AES-GCM の鍵として使用する。
  2. ランダムな 12 バイトの nonce(IV)。他の長さは MESSAGEFAULT_ERROR_IV_INCORRECT_LENGTH。
  3. AAD(Associated Authenticated Data) = SHA256(M)。
  4. P を暗号化し、暗号文 x と 16 バイトの tag を得る。
  5. payload.protobuf_message_as_bytes = x、signer_identity.public_key = ENCODE_PUBLIC(C)。
  6. signature_data.AES_GCM_Personalized_data に epoch、nonce、counter、expires_at、tag を設定する。epoch は省略できるが、含めると不一致時により具体的なエラーを受け取れる。

セッションキャッシュと同期エラーからの復旧

セッションキャッシュ

常時実行されないクライアントは、セッション状態とローカル/車両の時計の差をディスクに保存する必要があります。キャッシュを使うと最初のコマンドの遅延が減り、Fleet API の呼び出し回数も減ります。キャッシュが古くなっていても、後述の復旧手順はハンドシェイク 1 回と同じコストなので、楽観的にキャッシュを信頼しても損はありません。SDK: pkg/cache.SessionCache、Vehicle.UpdateCachedSessions/LoadCachedSessions、CLI の TESLA_CACHE_FILE。

同期エラーからの復旧

車両は、認証エラーが同期の問題(例: Infotainment の再起動による epoch の変更)である可能性がある場合、エラーメッセージに最新のセッション情報を同梱します。クライアントは、次のいずれかが真であればセッション情報を破棄しなければなりません(MUST)。

  • 直近数秒以内に、その request_uuid でリクエストを送っていない。
  • セッション情報の HMAC タグが正しくない。
  • 同じ epoch で以前に認証されたセッション情報よりも clock_time が早い。

すべて偽であればセッション状態を更新しなければなりません(MUST)。更新時には、epoch が変わらない限りアンチリプレイカウンターを巻き戻してはなりません(MUST NOT)。これはセキュリティ要件というより(リプレイの拒否は車両の責任)、不安定な接続や順序の入れ替わりに耐えるためのルールです。Go: Dispatcher.checkForSessionUpdate → session.processHello → Signer.UpdateSignedSessionInfo。dispatcher はセッションを更新したあと、エラーレスポンスもそのまま receiver に渡し、Vehicle.Send は ShouldRetry なエラー(INVALID_SIGNATURE、INVALID_TOKEN_OR_COUNTER、INCORRECT_EPOCH、TIME_EXPIRED など)であれば更新されたセッションで再送します。

レスポンスの処理

レスポンスがなくても実行されている可能性がある

コマンドを送ったのにレスポンスを受け取れなかった場合、車両はすでにコマンドを受信・実行している可能性があります。不安定なネットワークでは特によく起こります。SDK はこのような場合に protocol.MayHaveSucceeded(err) == true となるエラーを返し、自動ではリトライしません。

プロトコル層のエラー

レスポンスも RoutableMessage です。プロトコル層のエラーがあると signedMessageStatus.signed_message_fault が設定されます。コードと対処法は universal_message.proto の MessageFault_E のコメントと9 章にあります。Go の protocol.GetError がこれを *RoutableMessageError(UNKNOWN_KEY_ID の場合は ErrKeyNotPaired)に変換し、session_info.status == KEY_NOT_ON_WHITELIST も ErrKeyNotPaired に、operation_status == WAIT は ErrBusy にします。

レスポンスの復号

レスポンスに signature_data.AES_GCM_Response_data があれば protobuf_message_as_bytes は暗号文であり、なければ平文です。

message AES_GCM_Response_Signature_Data {
    bytes  nonce   = 1;
    uint32 counter = 2;
    bytes  tag     = 3;
}

リクエストハッシュ (request hash)

クライアントは送信したリクエストごとに「リクエストハッシュ」を計算しておく必要があります。認証方式 1 バイト || リクエストの認証タグです。

  • AES-GCM リクエスト: 0x05 || AES_GCM_Personalized_data.tag (16 バイトのタグ → 合計 17 バイト)
  • HMAC リクエスト: 0x08 || HMAC_Personalized_data.tag (32 バイトのタグ → 合計 33 バイト)
  • VCSEC に送ったリクエストは 17 バイトに切り詰める: 方式 1 バイト + MAC の先頭 16 バイト。AES-GCM のタグはもともと 16 バイトなので、影響するのは HMAC リクエストのみ

Go: internal/authentication.RequestID(message)。dispatcher が Send 時に receiver に requestID として保存します。

カウンターの検証

レスポンスの counter が、同じリクエストに対する以前のレスポンスですでに使われた値でないことを検証する必要があります。1 つのリクエストが複数のレスポンスを引き起こすことがあり、順序が入れ替わることもあります。この検査を省くとリプレイ攻撃に対して脆弱になります。Go: receiver ごとに authentication.SlidingWindow を置き、session.decrypt で antireplay.Update(counter) が false なら ErrReplayedResponse として破棄(internal/authentication/window.go)。

レスポンスメタデータ

AES-GCM で、鍵 K、レスポンスの nonce と tag、そして以下のメタデータをシリアライズした値の SHA-256 ダイジェスト SHA256(TLV || 0xFF) を AAD として使って復号します(リクエストと同じ方式です。Go の responseMetadata は Checksum(nil) を AAD として渡します)。リクエストと異なり、flags は 0 でも常に含め、fault は 32 ビット big-endian でエンコードします。

アプリケーション層のレスポンス

Infotainment

protobuf_message_as_bytes を CarServer.Response としてパースします。ステータスコードは Response.actionStatus.result で、OPERATIONSTATUS_ERROR の場合は result_reason.plain_text に理由が入っています。Go: Vehicle.getCarServerResponse が NominalError{"car could not execute command: <理由>"} に変換。状態照会の結果は Response.vehicleData。

VCSEC

VCSEC.FromVCSECMessage としてパースします。VCSEC は 1 つのリクエストに対して最大 3 つのレスポンスを送ります。Fleet API クライアントは最終レスポンスのみを受け取りますが、BLE クライアントはどのレスポンスが最終かを自分で判断する必要があります。
