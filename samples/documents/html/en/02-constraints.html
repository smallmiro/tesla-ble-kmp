2. Constraints

Every change to a sample follows these rules. They add to the repository rules in AGENTS.md and never relax them.

On this page

What the samples may call

  • Only the public API of :sdk that the library manual (chapters 11 to 19) lists as available. The "Which page to read" table in chapter 11 tells you which chapter to open.
  • Never: types from :application or :adapter-*, anything marked @InternalTeslableApi, an API the manual calls planned, or reading library log text as if it were data.
  • Call order, error handling (Success, Uncertain, Failure), timeouts and platform setup follow the manual. After an Uncertain VCSEC command, read the state again with vehicleStatus(). Never send the command again.
  • Swift: Kotlin default arguments do not turn into Swift overloads, so pass every argument.
  • The sample code and the code examples in the manual must match. If a manual example is wrong, fix it in the same pull request.
No workarounds in the samples

If a sample needs something the manual does not describe, or the library behaves differently from the manual, fix the manual first (Markdown and HTML in three languages), or write a library request with the library-api-request skill and add it to the plan. The sample requirement waits until then.

The library manual does not cover background use yet (chapter 17). A sample that needs it writes down the platform setup it uses on these pages and in chapter 17 in the same pull request.

Logs, secrets and vehicle data

  • Never log, put in a fixture or commit a private key, a session key or a real VIN. Mask the VIN (keep the first 3 and last 4 characters) before anything leaves the phone.
  • Logs shown on screen or copied contain only the library's observe lines and the sample's own result lines. The raw BLE TX:/RX: hex from DebugLogger stays in the system log and is never shared.
  • Logs pulled from a phone go to samples/logs/, which git ignores. Analysis reports go to docs/analysis/.
  • The app screens are in Korean for now. Library error messages are in English and are shown as they are.

  • Logic that can be tested without a car (parsing, masking, timers, state changes) gets a unit test first: Swift tests in samples/ios/Tests/, Kotlin tests in samples/android/src/test/ (that folder does not exist yet; create it with the first test).
  • Screens and real-car behaviour are checked on a real phone with a written checklist. The simulator has no Bluetooth.

Keeping the documents in step

  • When a sample's behaviour changes, update 1. Requirements, 3. Current Apps (or the app's own page) and their HTML versions in Korean, English and Japanese in the same pull request.
  • A sample pull request lists the library manual chapters and sections it relied on.
