4. モニターアプリ

車内または車の近くに置いたスマートフォンが自動で接続し、接続を保ち、車の状態をライブで表示し、ライブラリが読み取れるものをすべてポーリングし、すべてのブロードキャストを生のバイト列とともに記録します。これにより、未知のプロトコルフィールドを後から分析できます。

Android と iOS は実装済み、実機確認待ち

Android アプリ（ビルド 0.2.0 (2)）と iOS アプリ（ビルド 0.4.0 (10)）は実装済みで、単体テストは通過しています。どちらも実車での確認を待っています。iOS がバックグラウンドで再接続するかどうかは、計画の Task 2 のスパイクまで未確認です。必要なライブラリ API はすべて使えます: Vehicle.events（ライブラリマニュアル 12 章「ブロードキャストイベント」、14 章 B2）と iOS のキーアクセシビリティの選択（13 章「スマートフォンのロック中にキーを使う」、FR-037）。

ロック中のスマートフォンでのキー

モニターは専用のキー teslable-monitor を使います。このキーは、スマートフォンがロックされていても使えるように作られます（iOS では KeyAccessibility.AFTER_FIRST_UNLOCK、Android のキーはもともとロック中でも使えると報告します。実機ではまだ確認していません）。この設定はキーを作る時点で固定されます。スマートフォンにすでにそのキーが厳しい設定で存在する場合、アプリは、それを削除して新しく作り、車に登録し直すよう求めます。Control タブには、キーがどの設定になっているかが表示されます。アプリは起動時にキーを読み込み、そのハンドルを使い続けます。キーストアが KeyStoreError.Locked を返した場合（再起動後にまだロックを解除していない、またはロック解除中にだけ使えるキーの場合）、アプリは待ってからロック解除後にキーを読み直し、この理由でキーを削除することはありません。

ログファイル

1 行に 1 つの JSON オブジェクトです。すべての行に ts（オフセット付きの時刻）と kind があります。各ファイルは、スマートフォンとアプリのビルドを記した session 行から始まります。

{"ts":"2026-10-24T10:00:00.123+09:00","kind":"session","platform":"ios","app":"0.4.0(10)","os":"27.0.1","phone":"iPhone"}
{"ts":"…","kind":"event","type":"Status","summary":"lock=LOCKED gear=PARK presence=NOT_PRESENT","unknownFields":["1.8"],"unrecognized":true,"raw":"<hex>"}
{"ts":"…","kind":"observe","line":"[drop:no-handler] 83B from=domain(DOMAIN_VEHICLE_SECURITY) …"}
{"ts":"…","kind":"query","call":"vehicleStatus","result":"Success","summary":"…"}
{"ts":"…","kind":"link","state":"backoff","reason":"…","attempt":3,"delayMs":8000}
{"ts":"…","kind":"mark","memo":"before: open driver door"}
Kind内容
event車からのブロードキャスト：その種類（Status、AuthenticationRequest、Unrecognized）、要約、ライブラリが認識しなかったフィールド番号、未認識の内容を示すフラグ、16 進数の生のバイト列
observeライブラリの観察行（ライブラリがすでにマスク済み）。生の BLE の TX:/RX: 行は書き込まれません
queryQuery タブの結果
link接続中、接続済み、切断、再試行待ち、停止
markMark ボタンで残したメモ

フィールドの補足（両アプリは同じ名前と順序で書きます）:

  • event.summary は lock=… gear=… presence=… で始まり、Status ではその後に sleep=…、doors=FD/FP/RD/RP、frunk=…、trunk=…、chargePort=… が続きます。AuthenticationRequest は level=… reasons=[…]、Unrecognized は unknownFields=[…] です。
  • link: 該当しない reason、attempt、delayMs は書きません。connecting.attempt は開始、またはリンクが切れてからの試行回数です。backoff.attempt は連続失敗の回数（リンクが切れたこともその 1 回目として数えます）で、delayMs は次の試行までの待ち時間なので、待ち時間は 2000、4000、8000、16000、30000、30000 と並びます。リンクが切れると disconnected の行（ライブラリが理由を返したときはその理由つき）を書き、続けて backoff の行を書きます。10 秒以上続いた接続は、待ち時間を再び 2 秒から始めます。
  • vehicleStatus の query.summary は Status イベントの要約と同じ形式です。公開鍵も VIN も含みません。
  • VIN のマスク：書き込む前に、生のバイト列やテキストに含まれる VIN の文字が 17 文字以上続く部分は、その部分の先頭 3 文字と末尾 4 文字を残し、残りを * に置き換えます。そのため長さは変わりません。前後にそのような文字が付いている VIN は、より長い 1 つの連なりとしてマスクされます。
  • マークのメモは最大 80 文字です。空のメモは無視されます。
  • ファイル名は monitor-<yyyyMMdd-HHmmss>.jsonl です。20 MB で新しいファイルを開始し、フォルダーが 200 MB を超えると最も古いファイルから削除します。
  • 書き込みがイベントの収集を止めることはありません。ライターは小さなインターフェースの背後にあり、将来クラウドへの出力先を追加できます。
  • ファイルの場所：Android は Android/data/dev.mirolab.teslable.sample/files/logs/（adb pull で読み取れます）。iOS は Documents/logs/ で、Finder とファイルアプリからも見えます。

動作のしかたと、設計で余地を残した部分:

  • 接続は 1 つ。 Control タブはモニターの接続とキーを使います（車は BLE 接続を 3 つまで受け付けます）。Control タブの接続ボタンと切断ボタンは、モニターのループを開始・停止します。新しい接続は、前の車両の接続が切れてから始まります。
  • プロセスごとにエンジンは 1 つ。 最初に使うときに作られ、プロセスが続く間は保たれます（プロセスごとにライブラリのインスタンスは 1 つ、12 章）。サービスがプロセスをフォアグラウンドに保ちます。通知の停止は、接続を切り、自動再接続を止め、サービスを終了させます。同じプロセスでアプリを開き直しても自動では接続しません。接続ボタンを押してください。新しいプロセスは、VIN が保存されていれば自動で接続します。
  • キーのエラー。 KeyStoreError.Locked ならその試行は失敗となり、ループは待ってからキーを読み直します（キーは消しません）。それ以外のキーのエラーは、キーなしで接続します。ブロードキャストと 3 つの問い合わせにキーは要りません（14 章 B2.4）。Control タブはキーの protection と accessibility を表示し、キーが WHEN_UNLOCKED なら警告します。
  • Live タブ。 最近のイベントの一覧には、変化、認証要求、認識できないブロードキャストが入ります（最大 100 件）。同じ状態のブロードキャストが繰り返されても、動くのは「最後のブロードキャスト」だけです。繰り返しかどうかにかかわらず、すべてのイベントはログファイルに入ります。最初の状態はそれ以前を知りようがないので、「初めて観測」の時刻を表示します。保存した VIN はマスクして表示します。
  • Query タブ。 間隔を変えるとすぐに 1 回問い合わせ、そこから数え直します。問い合わせは車を起こしません。
  • ログファイル。 サイズは 10 進の MB です（20 000 000 バイトと 200 000 000 バイト）。削除はフォルダを上限以下に保ち、書き込み中のファイルは消しません。同じ秒に 2 つのファイルが始まるときは、2 つ目の名前を 1 秒後にします。行は書くたびにフラッシュします。書き込みのキューは 4096 行で、いっぱいになると、待たずに新しい行を捨てて数えます（Log タブ）。書き込みエラー（ディスクがいっぱい、フォルダがないなど）はその行を捨てたものとして数え、次の行でファイルを開き直します。アプリは落ちません。
  • 取り出し。 adb pull はファイルを samples/logs/android/<date>/logs/ に置きます。
  • ゲートの対象外。 lintKotlin と detekt はライブラリのモジュールにだけ動き、samples/ には動きません。

  • Android と同じ動作。 ログのスキーマ、上のフィールドの補足、バックオフの数値、10 秒の安定リセット、VIN の連なり、書き込みエラーの規則、「新しい接続は、前の車両が解放されるまで待つ」は、Swift でも同じロジックで、同じテスト名があります（VinMaskTests、LogWriterTests、ConnectionLoopTests、LiveStateTests）。

  • キーのエラー。 Locked ならその試行は失敗となり、ループは待ってからキーを読み直します。UIApplication.protectedDataDidBecomeAvailableNotification が届いたときも、アプリはすぐに再試行します。キーは消しません。それ以外のキーのエラーは、キーなしで接続します（ブロードキャストと 3 つの問い合わせにキーは要りません）。Control タブは protection と accessibility を表示し、WHEN_UNLOCKED のキーなら警告します（削除して、新しく作り、もう一度登録します）。
  • 見つかったライブラリの不足。 ありません。ライブラリへの要望は出していません。
  • Log タブ。 以前の観察モードはなくなりました。observe 行は常にログファイルに書かれ、メモと Mark ボタンは mark 行を書きます。以前のコピーボタンは、「最後の行をコピー」と、Control タブの「全結果をコピー」（最後のログ行で終わるようになりました）に置き換わりました。
  • ログファイル。 規則は Android と同じです（10 進の MB、削除は書き込み中のファイルを消さない、名前は 1 秒ずらす、4096 行のキュー、書き込みエラーはその行を捨てて数え、次の行でファイルを開き直す）。行は届くたびにファイルへ書きます（バッファリングなし）。ファイルは Documents/logs/ にあり、ファイル保護は既定のままです（最初のロック解除後に読み取れます）。
  • 画面の点灯。 isIdleTimerDisabled はシーンがアクティブな間だけ true で、バックグラウンドと非アクティブのときはシステムの既定に戻ります。
  • バックグラウンド。 iOS がアプリを動かし続けている間は、同じループがバックグラウンドでも動きます。リンクが切れた後に iOS がアプリを起こしてスキャンと再接続をさせるかどうかは未確認です（計画 Task 2 のスパイク）。iOS がアプリを一時停止している間はループは動かず、2 つの link 行の間隔でその長さが分かります。
  • 取り出し。 tools/samples/pull-monitor-logs.sh ios [--device <id>] は、実機ビルド（dev.mirolab.TeslableSampleDevice）の Documents/logs を xcrun devicectl device copy from で samples/logs/ios/<date>/ にコピーします。
  • バージョン。 project.yml には MARKETING_VERSION 0.4.0 と CURRENT_PROJECT_VERSION 10 があります。実機での確認ラウンドごとにビルド番号を上げてください。

実車チェックリスト

  1. 新規インストール：VIN を入力し、モニターキーを作成して登録します。アプリを再起動すると、自動で接続します。
  2. Live タブ：運転席ドアを開閉し、P、R、N、D とシフトし、外からロックします。それぞれの変化が時刻付きで表示されます。
  3. リンクが切れるまで離れてから戻ります。スマートフォンに触れなくても、画面を点灯したままの場合とロックした場合の両方で再接続します。
  4. ロックしたスマートフォンを車の近くに 30 分置きます。接続したまま、または再接続され、ログが増え続けます。
  5. Disconnect を押します。2 分間、再接続を試みません。
  6. Mac でスクリプトを使ってログを取り出します。最初の行は session 行で、17 文字の VIN を検索しても何も見つかりません。
