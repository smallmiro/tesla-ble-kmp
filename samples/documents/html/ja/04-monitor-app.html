4. モニターアプリ

車内または車の近くに置いたスマートフォンが自動で接続し、接続を保ち、車の状態をライブで表示し、ライブラリが読み取れるものをすべてポーリングし、すべてのブロードキャストを生のバイト列とともに記録します。これにより、未知のプロトコルフィールドを後から分析できます。

Android と iOS は実装済み、実機確認待ち

Android アプリ（ビルド 0.4.0 (4)）と iOS アプリ（ビルド 0.5.0 (26)）は実装済みで、単体テストは通過しています。どちらも実車での確認を待っています。iOS がバックグラウンドで再接続するかどうかは、計画の Task 2 のスパイクまで未確認です。必要なライブラリ API はすべて使えます: Vehicle.events（ライブラリマニュアル 12 章「ブロードキャストイベント」、14 章 B2）と iOS のキーアクセシビリティの選択（13 章「スマートフォンのロック中にキーを使う」、FR-037）。

ロック中のスマートフォンでのキー

モニターは専用のキー teslable-monitor を使います。このキーは、スマートフォンがロックされていても使えるように作られます（iOS では KeyAccessibility.AFTER_FIRST_UNLOCK、Android のキーはもともとロック中でも使えると報告します。実機ではまだ確認していません）。この設定はキーを作る時点で固定されます。スマートフォンにすでにそのキーが厳しい設定で存在する場合、アプリは、それを削除して新しく作り、車に登録し直すよう求めます。Control タブには、キーがどの設定になっているかが表示されます。アプリは起動時にキーを読み込み、そのハンドルを使い続けます。キーストアが KeyStoreError.Locked を返した場合（再起動後にまだロックを解除していない、またはロック解除中にだけ使えるキーの場合）、アプリは待ってからロック解除後にキーを読み直し、この理由でキーを削除することはありません。

キーのニックネーム（ローカル専用）

車両にはキー名の欄がありません。VCSEC の KeyMetadata メッセージは keyFormFactor だけを持つため、車は既定の名前を表示し、listKeys() も名前を返しません（ライブラリマニュアル 14 章 A4）。キーを見分けられるよう、コントロールタブでキーごとにこのスマートフォンだけにあるニックネームを付けられます。ニックネームは車両へ送らず、車の画面にも表示せず、ログファイルや結果リストにも書きません（結果リストにはスロットだけを書いた 1 行が残ります）。

ルール内容
場所コントロールタブのキー一覧（キー一覧ボタンの下）。各行は通常のラベル（スロット、フォームファクター、ロール、「この端末」）の上にニックネームを表示し、名前 / 名前を編集ボタンを置きます。ボタンを押すと、名前はスマートフォンにだけ保存される旨の案内とともに入力欄が開きます。
キーキー ID: WhitelistEntry.keyIdSha1Hex（公開鍵の SHA-1、16 進数）。スロットは変わり得るため、スロットでは保存しません。エントリにキー ID がない行（keyIdSha1Hex が null または空）にはニックネームを付けられず、ボタンは無効になります。
入力前後の空白と改行を削ります。最大 32 文字（文字数で数えるので絵文字 1 つが 1 文字）で、入力欄はそれより長い入力を切り詰めます（先頭の空白は数えません）。空または空白だけの入力はニックネームを削除します。
保存UserDefaults（iOS）または SharedPreferences（Android、予定）: キー ID（小文字）をニックネームに対応づけた 1 項目。通常のアプリ設定なので、アプリを削除すると一緒に消えます。後で車から削除したキーのニックネームは、上書きまたは削除するまで残り、同じキーを再登録すると以前の名前が戻ります。
表示しないもの公開鍵の全体と VIN。画面にはニックネームと通常の行ラベルだけが出て、削除の確認ダイアログにもニックネームが表示されます。

ルールは小さな純粋な型です（KeyNickname: 削る、長さの確認、切り詰め。KeyNicknameStore: 注入した UserDefaults への保存、取得、削除）。車両なしで単体テストします（Tests/KeyNicknameTests.swift）。画面は samples/ios/README.md の実機確認リストで確認します（SFR-019）。

状態: iOS ビルド済み（0.5.0 (26)）、単体テストは通過、実機確認待ち。Android: 予定、同じ仕様。

状態診断（SFR-023）

Query タブには、人が getState() を呼んで車両が返す値を読む手動の領域があります。ライブラリマニュアルが未確認として挙げている実車の事実（14 章 A8.5）を集めるためのものです: カテゴリごとにどのフィールドが来るか、speed の単位、応答が大きすぎないか、眠っている車がどう振る舞うか。製品機能ではありません。定期的な getState も、自動の再試行も、Location のボタンもありません。

ルール内容
場所Query タブの定期問い合わせの下: ボタン 3 つ Drive、Media、MediaDetail、直近の結果、そして別枠の眠っている車に送る（実験）。
オンになる条件キー付きで張った接続（Vehicle.hasKey）、キー・制御タブが登録済みと確認したキー、そして直近に成功した vehicleStatus() の sleepStatus == AWAKE（モニターのポーリング、または直前のタップの読み直し）。ASLEEP、UNKNOWN、「まだ読んでいない」ならボタンはオフで、理由がボタンの下に出ます。問い合わせが動いている間もオフです。
1 回のタップの順序(1) vehicleStatus(timeout: null): AWAKE 以外なら NotSent で終わります。(2) startSession(setOf(INFOTAINMENT), timeout: null): セッションがすでに Ready ならライブラリは何も送りません（14 章 A8.2: getState はセッションを開始しません）。(3) getState(category, timeout: null) を 1 回。既定のタイムアウトを使います（16 章「リトライとタイムアウト」）。
結果ライブラリが返す Success、Uncertain、Failure、そしてアプリが送る前に止まった場合（スリープ中、スリープ状態不明、vehicleStatus() 失敗、セッション失敗）の NotSent。それぞれ文が違います: サイズエラーは車が応答したと、タイムアウトは何も返らなかったと、NoSession は何も送っていないと伝えます。Timeout の文は 16-lib-errors.md（Timeout(afterSend) の行）に従います: afterSend = true は送った可能性がある（Uncertain、最初の BLE 書き込みが始まっていた）こと、値は確認できていないこと、問い合わせは車を変えないのでもう一度問い合わせてよいことを伝え、バックグラウンドでは BLE の書き込みが遅くなることがあると添えます。afterSend = false は実行されていない（書き込みを始める前、または車が再試行を求めた後の待機、またはハンドシェイクで時間切れ、Failure）ことを伝えます。自動の再試行はありません。Failure(NoSession)（車がもう受け付けないキャッシュ済みセッション、A8.2）の後は、次のタップが新しいセッションを開始します。サンプルが自分で行うことはありません。
起こすことこの画面は wakeUp() を決して呼ばず、「車を起こしません」ではなく「wakeUp() を呼びません」と書きます。Infotainment のハンドシェイクが眠っている車に何をするかは未確認だからです。
眠っている車の実験カテゴリを別に選べるボタンと、車が起きる可能性があると伝える確認ダイアログがあります。確認するとスリープ確認だけを省きます: 接続と登録済みのキーは引き続き必要で、同じセッション手順を踏んで getState を 1 回送ります。wakeUp() は決して呼びません。記録を取りながら 1 回試す用途です。
重なりキーの入れ替え中や、他のタブ（Control、キー・制御）が呼び出しを行っている間は開始せず、問い合わせが動いている間はキーを入れ替えられません（KeyOperationGate）。問い合わせ中の 2 回目のタップは何もしません。
接続の変更結果とスリープ状態は、それを読んだ接続のものです。接続が変わると結果は消え、スリープ状態は UNKNOWN に戻り、古い接続から遅れて届いた結果は捨てます（表示も記録もしません）。

表示するフィールド。次の名前を付けたフィールドだけを読みます。DriveState にはルートや目的地のフィールドもありますが、アプリは読まず、Location のボタンもありません。ない値は —、0 は 0 のままです（14 章 A8.3）。

ログ。終わったタップごとに query 行を 1 本だけ残し、ほかは残しません: call は getState(DRIVE)、getState(MEDIA)、getState(MEDIA_DETAIL)、result は Success、Uncertain、Failure、NotSent、summary は durationMs=<n> に error=<種類> または reason=<理由> を付けたもの、startedAt はそのタップの最初のライブラリ呼び出しを始めた時刻です。値も、曲名も、フィールド名もログには届きません（FR-112、14 章 A8.3「結果をログに残さない」）: ログ行はそれらを入れる場所のない小さな値（StateLogEntry）から作り、要約がログに行くサンプルの record ヘルパーは getState には使いません。エラーの種類はライブラリの型名（ResponseTooLarge、Timeout(afterSend=true)、NoSession、またはクラス名）で、message や車両が送った文は使いません。

VehicleData、KotlinInt? の数値、getEpochSecond()（14 章 A8.3、17 章「Swift: 生成された型」）、結果の扱いとサイズエラー（16 章「getState の結果」「getState の応答サイズ制限」）。純粋なルール（StateDiagnostics）と画面状態（偽のリンクを使う StateDiagnosticsModel）は車両なしで単体テストします（Tests/StateDiagnosticsTests.swift）。実機確認リストは samples/ios/README.md（SFR-023）にあります。

広い画面と折りたたみ画面 (SFR-024)

アプリは、折りたたみ式の iPhone Duo で公式 Tesla アプリ(4.62)が使う大画面レイアウトに合わせます。内側ディスプレイでは 2 つの領域を表示します。左はナビゲーションメニュー、右は常に見える大きな車両と、下に並ぶクイック操作です。外側ディスプレイは通常のフォンレイアウトのままです。サンプルも自分の画面で同じことをします。使うのはサイズクラスと使える幅だけなので、iPad や分割ウィンドウにも当てはまります。機種、UIScreen、向き、ヒンジの角度は見ず、iOS 27.1 の折りたたみ API も使いません。

ルール内容
判定DuoLayout.mode(isRegularWidth:width:)(純粋関数、Tests/DuoLayoutTests.swift): 水平サイズクラスが regular かつ使える幅(セーフエリアを除く)が 540pt 以上のときだけ2 領域、それ以外はフォンレイアウトです。ContentView が幅を測り、変わるたび(折りたたみ、展開、回転、分割ウィンドウ)に判定し直します。Xcode 27.2 の iPhone Duo シミュレータのプロファイルは、外側ディスプレイが 466 x 678pt、内側ディスプレイが 669 x 951pt(どちらも 3 倍)です。
フォンレイアウト変更なし: Live、Query、Log、Control、キー＆コントロール の 5 つのタブ(SFR-010、SFR-018)。外側ディスプレイと通常の iPhone で使います。
左の領域使える幅の 40%、260~520pt。公式 Tesla アプリの大画面の左の列に合わせますが、アプリが持つデータだけを使います。ヘッダー: 大きなタイトル(Control タブのキー一覧でこのスマホのキーにニックネームを付けていればそれ、なければ "Tesla"。VIN はマスクして小さく)と、ギア、ロック、スリープから作る状態 1 行(HomeHeader: P は「駐車中」、R、N、D は「走行中」、続けて分かる範囲でロックとスリープ)。塗りつぶしの角丸カード 2 枚(右向きの矢印): Live 詳細(最後のイベントの時刻)とキー＆コントロール(終わっていない最初のステップのヒント、すべて済んでいれば「登録済み」)。カードのない行: ロック、ドアとトランク、スリープ、在車、走行(ギアと最後の手動 Drive 取得の速度)。各行のグレーの副題はクラスターの状態から取り、なければ — です(HomeStatus)。タップすると Live 詳細が開きます。続けて、カードのない行 Query(最後の vehicleStatus() の結果と時刻)、Log(書いた行数)、Control(接続)がそれぞれのページを開きます。開いているページは矢印のない塗りつぶしカードになり、メニューの下にその場で開きます(メニュー領域は縮み、スクロールします)。ページはフォンのタブと同じビューで(コピーなし)、キー＆コントロールはコマンドの確認ダイアログを右の領域に任せます(ownsCommandDialog: false)。フッター: アプリのビルドと、最後の手動 Drive 取得が走行距離を返したときだけその値(生の値、1/100 マイル、取得からの経過)。作り出した値はありません。バッテリー、空調、位置、カメラ、モデル名はありません。
右の領域接続状態と設定ボタンのヘッダー(歯車は右のドックを避けます)、ギア行 P R N D、そして速度: この接続で最後に成功した手動 Drive 取得の生の数値と「単位未確認」と、「12 秒前」のような経過。取得がまだなければ — と Query タブを使うヒントを表示します。アプリは今も getState() を自分では呼ばず、そのために wakeUp() も呼びません(SFR-023)。その下に、吹き出し(ロック、フランク、トランク、充電口)付きの斜めの車の写真、ヒントと最新の結果行、操作行があります。車や開閉の行をタップすると詳細シートが、歯車ボタンで VIN と接続のシートが開きます。
吹き出しと操作吹き出し: 写真の上中央のロックアイコンと屋根まで下りる細い縦線(LockCallout: 施錠中は閉じた南京錠でタップすると解除、解錠中は開いた南京錠でタップするとロック、状態が不明なら無効)、左上の 2 行の文字(小さな灰色の「開く」の下に太字の「フロント」)とボンネットまで下りる縦線(フランクを開く、先に確認)、右上の「開閉」の下に太字の「トランク」(トランク開閉)と車の後ろへの線、車の後ろの横に短い横線の付いた充電口の稲妻(開いていれば赤、そうでなければ灰色、タップ不可)。開いているフランクとトランクは線が車に当たる所に赤いアイコンが付き、開いているドアごとにそのドアの位置の横に短い線の付いた小さな赤いドアアイコンが付きます。下の操作行(カードなしのアイコンと文字): スリープ解除、トランクを閉じる(QuickControls.actionRow。オートセキュアは Model X 専用で、キー＆コントロールも「他の車種」の下に置くためここにはなく、リモートドライブは 1 タップにしません)。すべてのボタンはキー＆コントロールタブにある既存のボタンで、同じ KeyControlModel.press で送ります。ステップ 4 が有効なときだけ有効(そうでなければ薄くし、同じオレンジのヒントを 1 回表示)、VCSEC セッションを確認し、コマンドは 1 回だけ送り、続けて vehicleStatus() を呼び、Uncertain は再送せず(5. キー＆コントロールタブ)、2 領域が始まるとき登録状態を再確認します。新しいコマンドはありません。クラクション、フラッシュ、空調はありません。

ログファイル

1 行に 1 つの JSON オブジェクトです。すべての行に ts（オフセット付きの時刻）と kind があります。各ファイルは、スマートフォンとアプリのビルドを記した session 行から始まります。

{"ts":"2026-10-24T10:00:00.123+09:00","kind":"session","platform":"ios","app":"0.4.0(11)","os":"27.0.1","phone":"iPhone"}
{"ts":"…","kind":"event","type":"Status","summary":"lock=LOCKED gear=PARK presence=NOT_PRESENT","unknownFields":["1.8"],"unrecognized":true,"raw":"<hex>"}
{"ts":"…","kind":"observe","line":"[drop:no-handler] 83B from=domain(DOMAIN_VEHICLE_SECURITY) …"}
{"ts":"…","kind":"query","call":"vehicleStatus","result":"Success","summary":"…","startedAt":"…"}
{"ts":"…","kind":"query","call":"getState(DRIVE)","result":"Uncertain","summary":"durationMs=5012 error=Timeout(afterSend=true)","startedAt":"…"}
{"ts":"…","kind":"link","state":"backoff","reason":"…","attempt":3,"delayMs":8000}
{"ts":"…","kind":"mark","memo":"before: open driver door"}
{"ts":"…","kind":"app","event":"scenePhase","phase":"background"}
{"ts":"…","kind":"app","event":"protectedData","state":"unavailable"}
{"ts":"…","kind":"app","event":"start","reason":"connect-button","effect":"woke"}
Kind内容
event車からのブロードキャスト：その種類（Status、AuthenticationRequest、Unrecognized）、要約、ライブラリが認識しなかったフィールド番号、未認識の内容を示すフラグ、16 進数の生のバイト列
observeライブラリの観察行（ライブラリがすでにマスク済み）。生の BLE の TX:/RX: 行は書き込まれません
queryQuery タブの結果（ポーリング、iOS は状態診断のタップも）
link接続中、接続済み、切断、再試行待ち、停止
markMark ボタンで残したメモ
app今のところ iOS のみ: リンク周りのアプリと端末の状態（画面の状態、端末のロック、接続の試行を始めた理由）

フィールドの補足（両アプリは同じ名前と順序で書きますが、下の iOS 限定の追加は例外です）:

  • event.summary は lock=… gear=… presence=… で始まり、Status ではその後に sleep=…、doors=FD/FP/RD/RP、frunk=…、trunk=…、chargePort=… が続きます。AuthenticationRequest は level=… reasons=[…]、Unrecognized は unknownFields=[…] です。
  • link: 該当しない reason、attempt、delayMs は書きません。connecting.attempt は開始、またはリンクが切れてからの試行回数です。backoff.attempt は連続失敗の回数（リンクが切れたこともその 1 回目として数えます）で、delayMs は次の試行までの待ち時間なので、待ち時間は 2000、4000、8000、16000、30000、30000 と並びます。リンクが切れると disconnected の行（ライブラリが理由を返したときはその理由つき）を書き、続けて backoff の行を書きます。10 秒以上続いた接続は、待ち時間を再び 2 秒から始めます。
  • vehicleStatus の query.summary は Status イベントの要約と同じ形式です。公開鍵も VIN も含みません。
  • call が getState(<CATEGORY>) の query 行（iOS のみ、SFR-023、状態診断）は、ポーリングではなく手動のタップから出ます。result は Success、Uncertain、Failure、NotSent で、summary は durationMs=<n>、Success 以外では error=<種類> または reason=<理由> です。値は決して載せません。

ビルド 18 以降の追加（iOS のみ）

issue #128 とビルド 18 のリンク状態分析からの変更です。新しいフィールドは行末に足し、新しい行は新しい kind を使うので、未知のキーと kind を無視するパーサーはそのまま動きます。Android はまだ書きません。Android アプリを揃えるまで、ここに差があります。

  • query.startedAt: リクエストを送った時刻（ts と同じ形式）。ts は結果が届いた時刻のままなので、ts - startedAt が呼び出しにかかった時間です。vehicleStatus、keySummary、listKeys に書きます。
  • app / event: "scenePhase": phase は active、inactive、background（SwiftUI の scene phase）です。実行の最初の scenePhase 行が開始時の状態です。その前に session 行と start 行（自動接続）が来ることがあります。
  • app / event: "protectedData": state は available（端末のロックが解除された）または unavailable（端末がまもなくロックされる）です。
  • app / event: "start": 接続ループの start() が呼ばれるたびに、それによって生じうる connecting 行の前に書きます。reason: launch（アプリ起動時の自動接続）、connect-button、protected-data（ロック解除が待機中の再試行を起こした）、key-replaced（「キーを削除して作り直す」後の再接続）。effect: started（新しいループを開始）、woke（backoff で待っていたのをすぐ試すようにした）、ignored（すでに接続中または接続済みで何も起きなかった）。直前に effect が started または woke の start 行がない connecting 行は、バックオフのタイマーによるものです（ignored の行は試行を生みません）。
  • link / state: "connected": scanHitMs、rssi、openAttempt（#134）。Vehicle.scanObservation（マニュアル 12 章、Connect scan observation）から取ります。scanHitMs は connect の開始から、ライブラリがリンクを開いたアドバタイズを受け取るまでの時間です（以前の試行とその間の待ちを含む）。rssi は dBm の信号強度で、プラットフォームが値を返さないときは省きます。openAttempt は何回目のオープン試行でリンクができたかです（1 より大きいのは以前のオープンが失敗したという意味で、車を再スキャンしたという意味ではありません）。記憶していた target で connect した場合（スキャンなし）は 3 つとも省きます。scanHitMs は単調時計の値なので、壁時計の時刻が必要なときは [connect:scan-hit] の observe 行の ts を使います。失敗した connect は Vehicle を返さないので、そのスキャン検出は observe 行にだけあります（マニュアル 18 章）。モニターは connect の前にスキャンしないため、測っている接続経路は変わりません。
  • VIN のマスク：書き込む前に、生のバイト列やテキストに含まれる VIN の文字が 17 文字以上続く部分は、その部分の先頭 3 文字と末尾 4 文字を残し、残りを * に置き換えます。そのため長さは変わりません。前後にそのような文字が付いている VIN は、より長い 1 つの連なりとしてマスクされます。
  • マークのメモは最大 80 文字です。空のメモは無視されます。
  • ファイル名は monitor-<yyyyMMdd-HHmmss>.jsonl です。20 MB で新しいファイルを開始し、フォルダーが 200 MB を超えると最も古いファイルから削除します。
  • 書き込みがイベントの収集を止めることはありません。ライターは小さなインターフェースの背後にあり、将来クラウドへの出力先を追加できます。
  • ファイルの場所：Android は Android/data/dev.mirolab.teslable.sample/files/logs/（adb pull で読み取れます）。iOS は Documents/logs/ で、Finder とファイルアプリからも見えます。

動作のしかたと、設計で余地を残した部分:

  • 接続は 1 つ。 Control タブはモニターの接続とキーを使います（車は BLE 接続を 3 つまで受け付けます）。Control タブの接続ボタンと切断ボタンは、モニターのループを開始・停止します。新しい接続は、前の車両の接続が切れてから始まります。
  • プロセスごとにエンジンは 1 つ。 最初に使うときに作られ、プロセスが続く間は保たれます（プロセスごとにライブラリのインスタンスは 1 つ、12 章）。サービスがプロセスをフォアグラウンドに保ちます。通知の停止は、接続を切り、自動再接続を止め、サービスを終了させます。同じプロセスでアプリを開き直しても自動では接続しません。接続ボタンを押してください。新しいプロセスは、VIN が保存されていれば自動で接続します。
  • キーのエラー。 KeyStoreError.Locked ならその試行は失敗となり、ループは待ってからキーを読み直します（キーは消しません）。それ以外のキーのエラーは、キーなしで接続します。ブロードキャストと 3 つの問い合わせにキーは要りません（14 章 B2.4）。Control タブはキーの protection と accessibility を表示し、キーが WHEN_UNLOCKED なら警告します。
  • Live タブ。 最近のイベントの一覧には、変化、認証要求、認識できないブロードキャストが入ります（最大 100 件）。同じ状態（ブロードキャストまたは問い合わせ）が繰り返されても、動くのは「最後の受信」だけです。繰り返しかどうかにかかわらず、すべてのイベントはログファイルに入ります。最初の状態はそれ以前を知りようがないので、「初めて観測」の時刻を表示します。保存した VIN はマスクして表示します。
  • Query タブ。 間隔を変えるとすぐに 1 回問い合わせ、そこから数え直します。問い合わせは車を起こしません。
  • ログファイル。 サイズは 10 進の MB です（20 000 000 バイトと 200 000 000 バイト）。削除はフォルダを上限以下に保ち、書き込み中のファイルは消しません。同じ秒に 2 つのファイルが始まるときは、2 つ目の名前を 1 秒後にします。行は書くたびにフラッシュします。書き込みのキューは 4096 行で、いっぱいになると、待たずに新しい行を捨てて数えます（Log タブ）。書き込みエラー（ディスクがいっぱい、フォルダがないなど）はその行を捨てたものとして数え、次の行でファイルを開き直します。アプリは落ちません。
  • 取り出し。 adb pull はファイルを samples/logs/android/<date>/logs/ に置きます。
  • スタイルゲート。 lintKotlin と detekt は :samples:android（main と test のソース）にも動くので、tools/ci/verify.sh のステップ (a) がこのモジュールを検査します。ライブラリ専用のルール（explicitApi、forbiddenTokens）はサンプルには適用しません。detekt は detekt.yml の上に config/detekt/detekt-samples.yml を重ねます（Compose の関数名と長さ、android.* の import、省略できる注入引数）。samples/ios/ の Swift ソースはこの Kotlin タスクの対象外です。

動作のしかたと、設計で余地を残した部分:

  • Android と同じ動作。 ログのスキーマ、上のフィールドの補足、バックオフの数値、10 秒の安定リセット、VIN の連なり、書き込みエラーの規則、「新しい接続は、前の車両が解放されるまで待つ」は、Swift でも同じロジックで、同じテスト名があります（VinMaskTests、LogWriterTests、ConnectionLoopTests、LiveStateTests）。
  • 接続は 1 つ。 Control タブはモニターの接続とキーを使います。Control タブの接続ボタンと切断ボタンは、モニターのループを開始・停止します。VIN は Live タブで入力・消去し、Control タブはマスクして表示します。
  • キーのエラー。 Locked ならその試行は失敗となり、ループは待ってからキーを読み直します。UIApplication.protectedDataDidBecomeAvailableNotification が届いたときも、アプリはすぐに再試行します。キーは消しません。それ以外のキーのエラーは、キーなしで接続します（ブロードキャストと 3 つの問い合わせにキーは要りません）。Control タブは protection と accessibility を表示し、WHEN_UNLOCKED のキーなら警告します（削除して、新しく作り、もう一度登録します）。
  • 見つかったライブラリの不足。 ありません。ライブラリへの要望は出していません。
  • Log タブ。 以前の観察モードはなくなりました。observe 行は常にログファイルに書かれ、メモと Mark ボタンは mark 行を書きます。以前のコピーボタンは、「最後の行をコピー」と、Control タブの「全結果をコピー」（最後のログ行で終わるようになりました）に置き換わりました。
  • ログファイル。 規則は Android と同じです（10 進の MB、削除は書き込み中のファイルを消さない、名前は 1 秒ずらす、4096 行のキュー、書き込みエラーはその行を捨てて数え、次の行でファイルを開き直す）。行は届くたびにファイルへ書きます（バッファリングなし）。ファイルは Documents/logs/ にあり、ファイル保護は既定のままです（最初のロック解除後に読み取れます）。
  • 画面の点灯。 isIdleTimerDisabled はシーンがアクティブな間だけ true で、バックグラウンドと非アクティブのときはシステムの既定に戻ります。
  • バックグラウンド。 iOS がアプリを動かし続けている間は、同じループがバックグラウンドでも動きます。リンクが切れた後に iOS がアプリを起こしてスキャンと再接続をさせるかどうかは未確認です（計画 Task 2 のスパイク）。iOS がアプリを一時停止している間はループは動かず、2 つの link 行の間隔でその長さが分かります。
  • 取り出し。 tools/samples/pull-monitor-logs.sh ios [--device <id>] は、実機ビルド（dev.mirolab.TeslableSampleDevice）の Documents/logs を xcrun devicectl device copy from で samples/logs/ios/<date>/ にコピーします。
  • バージョン。 project.yml には MARKETING_VERSION 0.5.0 と CURRENT_PROJECT_VERSION 12 があります。実機での確認ラウンドごとにビルド番号を上げてください。

実車チェックリスト

  1. 新規インストール：VIN を入力し、モニターキーを作成して登録します。アプリを再起動すると、自動で接続します。
  2. Live タブ：運転席ドアを開閉し、P、R、N、D とシフトし、外からロックします。それぞれの変化が時刻付きで表示されます。
  3. リンクが切れるまで離れてから戻ります。スマートフォンに触れなくても、画面を点灯したままの場合とロックした場合の両方で再接続します。
  4. ロックしたスマートフォンを車の近くに 30 分置きます。接続したまま、または再接続され、ログが増え続けます。
  5. Disconnect を押します。2 分間、再接続を試みません。
  6. Mac でスクリプトを使ってログを取り出します。最初の行は session 行で、17 文字の VIN を検索しても何も見つかりません。

iOS のみ（期待される結果つきの完全な手順は samples/ios/README.md の "Monitor app: real-device checklist" にあります）:

  1. アプリをもう一度起動した後、モニターのキーが afterFirstUnlock と報告されます（Secure Enclave のキー、計画 Task 11）。
  2. ロックされた iPhone で、モニターのキーを使ってハンドシェイクします（計画 Task 11）。スマートフォンがロックされている間に Secure Enclave のキーの作成が失敗した場合は、エラーの文面をそのままコピーしてください。
  3. バックグラウンド: スマートフォンをロックして離れ、戻ってから link 行を読み、iOS が自力で再接続したかどうかを確認します（計画 Task 2 のスパイクの結果）。
