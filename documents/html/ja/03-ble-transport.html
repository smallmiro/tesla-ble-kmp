トランスポート層は暗号を知らない

ble.Connection は connector.Connector インターフェースだけを実装します。つまり []byte を送受信するだけで、protobuf やセッション、署名はすべて上位レイヤー(internal/dispatcher、internal/authentication)の仕事です。このページでは、そのバイトが無線でどのように運ばれるかだけを扱います。

アドバタイズ名の計算

車両は VIN を直接アドバタイズしません。VIN の SHA-1 ダイジェストの先頭 8 バイトを小文字の hex でエンコードし、前後に S、C を付けた名前を Local Name としてアドバタイズします。

// pkg/connector/ble/ble.go
func VehicleLocalName(vin string) string {
	vinBytes := []byte(vin)
	digest := sha1.Sum(vinBytes)
	return fmt.Sprintf("S%02xC", digest[:8])
}
# シェルで確認: VIN 5YJS0000000000000 → S1a87a5a75f3df858C
printf '5YJS0000000000000' | shasum | cut -c1-16 | sed 's/^/S/; s/$/C/'
# S1a87a5a75f3df858C

スキャンコールバックは a.LocalName() != localName であれば無視します。呼び出し側が渡した ScanResult の名前が VIN から計算した名前と異なると、tryToConnect は ble: beacon with unexpected local name エラーを出し、リトライしません。

GATT 接続手順

tryToConnect が実行する順序です。各段階の失敗は retry=true(リトライ可能)に分類されます(アダプターエラー、名前の不一致、接続不可のアドバタイズを除く)。

  1. アダプターの初期化 initAdapter(nil)。グローバルな device がすでにあれば再利用。
  2. スキャン (target が nil のとき) scanVehicleBeacon(ctx, localName) でアドバタイズのアドレスを取得する。
  3. 接続可能かの確認 target.Connectable == false なら ErrMaxConnectionsExceeded を返し、リトライなし。
  4. Dial device.Dial(ctx, ble.NewAddr(target.Address))。
  5. サービスの探索 client.DiscoverServices([]ble.UUID{vehicleServiceUUID})。結果が空なら failed to discover service。
  6. キャラクタリスティックの探索 client.DiscoverCharacteristics([]ble.UUID{toVehicleUUID, fromVehicleUUID}, services[0])。両方のキャラクタリスティックが揃っていなければ failed to find required characteristics。
  7. ディスクリプターの探索 キャラクタリスティックごとに client.DiscoverDescriptors(nil, characteristic)。go-ble が CCCD(0x2902)を見つけないと購読できない。
  8. 購読 client.Subscribe(conn.rxChar, true, conn.rx): 0213 キャラクタリスティックの indication を有効にし、受信コールバック rx を登録。
  9. MTU 交換 client.ExchangeMTU(ble.MaxMTU)。成功すれば blockLength = min(txMtu, 1024) - 3、失敗すれば警告ログを出して ble.DefaultMTU - 3(= 20 バイト)にフォールバック。3 バイトは ATT Write Request ヘッダー(opcode 1 + handle 2)。

成功すると [info ] Connected to vehicle BLE が記録され、*Connection が返されます。Close() は ClearSubscriptions() と CancelConnection() を呼び出し、何度呼び出しても安全です。

メッセージフレーミングと MTU

BLE キャラクタリスティックへの 1 回の書き込みは MTU に縛られますが、RoutableMessage は数百バイトになることがあるため、SDK は長さプレフィックス付きストリームとして扱います。

定数/フィールド値意味
maxBLEMessageSize1024長さプレフィックスがこの値を超える受信メッセージはバッファを空にして破棄。送信ブロック長の上限にも使用
maxBLEMTUSizeble.MaxMTU (go-ble の定義、ATT 最大 517)ExchangeMTU に要求するクライアント側の最大 MTU
Connection.blockLengthmin(MTU, 1024) - 3、フォールバック ble.DefaultMTU - 3 (= 20)1 回のキャラクタリスティック書き込みに載せる最大バイト数
rxTimeout1 秒最後の受信チャンクからこの時間が経過すると inputBuffer を破棄し、新しいメッセージとみなす (部分受信からの復旧)
inboxchan []byte、バッファ 5完成したメッセージのキュー。満杯になると flush がメッセージを破棄して false を返す

送信コード

func (c *Connection) Send(_ context.Context, buffer []byte) error {
	c.lock.Lock()
	defer c.lock.Unlock()
	var out []byte
	out = append(out, uint8(len(buffer)>>8), uint8(len(buffer)))  // 2 バイト big-endian の長さ
	out = append(out, buffer...)
	blockLength := c.blockLength
	for len(out) > 0 {
		if blockLength > len(out) { blockLength = len(out) }
		if err := c.client.WriteCharacteristic(c.txChar, out[:blockLength], false); err != nil {
			return err
		}
		out = out[blockLength:]
	}
	return nil
}

Send は ctx を無視します(go-ble の write API にコンテキストがないため)。ミューテックスで一度に 1 メッセージだけを書き込むため、チャンクが混ざることはありません。

受信コード

func (c *Connection) rx(p []byte) {
	if time.Since(c.lastRx) > rxTimeout {
		c.inputBuffer = []byte{}          // 古い部分メッセージを破棄
	}
	c.lastRx = time.Now()
	c.inputBuffer = append(c.inputBuffer, p...)
	for c.flush() {}                       // バッファに完成メッセージが複数あればすべて配送
}

func (c *Connection) flush() bool {
	if len(c.inputBuffer) >= 2 {
		msgLength := 256*int(c.inputBuffer[0]) + int(c.inputBuffer[1])
		if msgLength > maxBLEMessageSize { c.inputBuffer = []byte{}; return false }
		if len(c.inputBuffer) >= 2+msgLength {
			buffer := c.inputBuffer[2 : 2+msgLength]
			c.inputBuffer = c.inputBuffer[2+msgLength:]
			select {
			case c.inbox <- buffer:
			default:
				return false                 // inbox が満杯: メッセージをドロップ
			}
			return true
		}
	}
	return false
}
受信経路にロックがない

rx と flush は go-ble の通知ゴルーチンから逐次呼び出されることを前提としており、別途ロックはありません。他の BLE スタックに移植する際、コールバックが並列に来る可能性がある場合は直列化が必要です。

スキャン

type ScanResult struct {
	Address     string  // アドバタイズのアドレス (macOS は CoreBluetooth の識別子、Linux は MAC)
	LocalName   string  // "S…C"
	RSSI        int16   // dBm
	Connectable bool    // false なら車両はすでに最大接続数に達している
}

func ScanVehicleBeacon(ctx context.Context, vin string) (*ScanResult, error)
  • ScanVehicleBeacon はアダプターを初期化し、VehicleLocalName(vin) と一致する最初のアドバタイズを返します。ctx が期限切れになるまでスキャンを続けます。
  • 内部の scanVehicleBeacon は一致するアドバタイズを見つけると派生コンテキストをキャンセルして device.Scan を止めます。macOS の device.Scan はコンテキストがキャンセルされるまで戻らず、常に context.Canceled を返すため、コードは errors.Is(err, context.Canceled) ではないエラーだけを失敗として扱います。
  • Connectable == false: 車両(VCSEC)はハードウェアの制約により同時に最大 3 つの BLE 接続しか維持せず、キーフォブとスマートフォンキーがこれを共有します。このとき接続を試みると、ErrMaxConnectionsExceeded("the vehicle is already connected to the maximum number of BLE devices")を即座に返します。近くのスマートフォンキーをオフにするか、車から離してください。
  • RSSI で複数の車両の中から近い車を選ぶロジックはありません。同じ VIN は 1 台しかないため不要です。
  • スキャンだけを行うには、examples/ble の -scan-only フラグを参考にしてください。ScanVehicleBeacon の結果を NewConnectionFromScanResult に渡せば再スキャンを省略できます。

接続リトライループ

func NewConnection(ctx context.Context, vin string) (*Connection, error) {
	return NewConnectionFromScanResult(ctx, vin, nil)
}

func NewConnectionFromScanResult(ctx context.Context, vin string, target *ScanResult) (*Connection, error) {
	var lastError error
	for {
		conn, retry, err := tryToConnect(ctx, vin, target)
		if err == nil { return conn, nil }
		if !retry || IsAdapterError(err) { return nil, err }   // 致命的: 即座に断念
		log.Warning("BLE connection attempt failed: %s", err)
		if err := ctx.Err(); err != nil {                        // ctx 期限切れ: 最後の実際のエラーを返す
			if lastError != nil { return nil, lastError }
			return nil, err
		}
		lastError = err
	}
}

リトライの間に待機がないため、実質的な上限は ctx のデッドラインです。tesla-control は -connect-timeout(デフォルト 20 秒)でこの ctx を作ります。接続後の Vehicle.Connect と StartSession も同じ ctx を共有するため、スキャンに時間がかかる環境では余裕を持って設定する必要があります。

アダプター管理

パッケージはグローバルな device ble.Device 1 つとミューテックス mu を持ちます。Linux では newDevice() を複数回呼び出すと失敗するため、一度作ったアダプターを再利用します。

関数説明
InitAdapterWithID(id string) error指定したアダプターでグローバルな device を作る。デフォルトのアダプターを使う場合は呼び出さなくてよく、ScanVehicleBeacon/NewConnection が initAdapter(nil) で自動的に初期化する。デフォルト以外のアダプターを使うには、他の BLE 呼び出しより前に必ず呼び出す。Linux では "hci0"〜"hci15"、それ以外の形式は ErrAdapterInvalidID。macOS で空文字列以外の ID を渡すと警告の後 ErrAdapterInvalidID。

pkg/cli.Config.ConnectLocal は ble.InitAdapterWithID(c.BtAdapterID) → ble.NewConnection(ctx, c.VIN) → vehicle.NewVehicle(conn, skey, c.sessions) の順に呼び出します。複数の車両に順次接続する長時間実行プロセスであれば、アダプターは一度だけ初期化し、Connection だけを開閉すれば済みます。

VCSEC のレスポンス特性と並行性

BLE で直接接続すると、Fleet API が隠していた VCSEC の特性がそのまま表に出ます。dispatcher が処理しますが、動作を理解しておく必要があります。

  • request_uuid がない。 VCSEC はメモリ制約のため、レスポンスにリクエスト UUID を入れません。そのため dispatcher は VCSEC に送るリクエストごとにランダムな 16 バイトの routing_address を新たに作り、レスポンスの to_destination.routing_address で待機中の receiver を探します(Infotainment は接続単位の固定アドレス + request_uuid)。
  • 同時リクエストの禁止。 VCSEC はカウンターが順番どおりに届く必要があり、同時リクエストを区別しにくいため、一度に 1 つずつ送ります。tesla-control とプロキシ(lockVIN)はコマンドを直列化します。
  • 1 リクエストに最大 3 つのレスポンス。 OPERATIONSTATUS_WAIT(NFC タップ待ちまたはビジー)、中間状態、最終結果が別々に届くことがあります。pkg/vehicle/vcsec.go の readUntil が、終了条件(isTerminalTest)が真になるまで receiver チャネルを読み続けます。たとえば Lock は commandStatus のない空メッセージを成功とみなし、whitelist 操作は whitelistOperationStatus が設定されたメッセージを終了とみなします。
  • OPERATIONSTATUS_ERROR は無視。 レガシークライアント向けのもので、新しいクライアントは次のメッセージの具体的なエラーコードを待ちます。dispatcher はこの場合、whitelistOperationInformation が NONE でなければ KeychainError、signedMessageStatus がなければ ErrUnknown に変換します。
  • Infotainment のスリープ。 VCSEC のセッションだけを確立するには StartSession(ctx, []Domain{DomainVCSEC})。両方のドメインとハンドシェイクすると、スリープ中の Infotainment のために失敗するか、車両が起きるまで遅延します。

シーケンス図

他の BLE スタックで実装する場合

Python(bleak)、Swift(CoreBluetooth)、Kotlin(Android BluetoothGatt)、Rust(btleplug)などでこのトランスポート層を再実装する際に守るべき条件です。詳しいチェックリストは ../md/10-porting-guide.md。

要件詳細
アドバタイズフィルターLocal Name が S+hex(SHA1(VIN)[:8])+C と完全に一致すること。サービス UUID がアドバタイズされるかどうかに依存しないこと
接続可能性アドバタイズの connectable フラグがオフなら、接続を試みる代わりにユーザーに「他の鍵の接続を解除」するよう案内
サービス/キャラクタリスティック0211 サービスで 0212(write)、0213(indicate)を探索。128 ビット UUID で比較
書き込みモードWrite With Response(ATT Write Request)。Write Without Response を使うと順序/フロー制御が崩れる可能性がある
通知モードIndication の購読(CCCD = 0x0002)。スタックが自動的に確認応答を送るかを確認
MTU可能な最大値(517)を要求し、ネゴシエーション値から 3 を引いたサイズでチャンク分割。ネゴシエーションできなければ 20 バイト
フレーミング2 バイト big-endian の長さプレフィックス。受信時はチャンクを蓄積し、長さが満たされるたびに 1 メッセージとして分離。1024 を超える長さは破棄。1 秒以上途切れたら部分バッファを破棄
レスポンスのマッチングVCSEC: to_destination.routing_address のみでマッチング。Infotainment: routing_address + request_uuid。1 リクエストに複数のレスポンスを許容
並行性車両ごとに一度に 1 つのリクエスト。書き込み呼び出しを直列化
認証方式BLE では AES-GCM で暗号化したコマンドを使用 (4. プロトコル仕様)。HMAC の平文も車両は受け付けるが、公式実装は GCM
再接続車両には 3 接続の制限があるため、使用後は必ず接続を解除。アプリがバックグラウンドに移ったら切断し、再度スキャン
