# ADR-0015: 명령 응답 인증 정책 (Go와 의도적으로 다름)

| 항목 | 내용 |
|---|---|
| 상태 | **채택** (2026-11-01, 사용자 승인). 구현은 #118 첫 실차 수집 뒤. 태그 없는 `WAIT` 처리만 수집 결과를 보고 확정한다 |
| 관련 | `{{PRD_FILE}}` FR-100, FR-101, FR-105, NFR-017, `{{SDD_FILE}}` 알려진 한계, #116, #118 |

## 맥락
- Go는 `FLAG_ENCRYPT_RESPONSE`를 기본으로 요청하지만 `AES_GCM_Response_data`가 없는 응답도 받아들인다(`internal/dispatcher/dispatcher.go:301`). 이 라이브러리도 같다(`Dispatcher.decryptIfNeeded`).
- 그래서 위조 평문 응답을 받으면 차량이 실행하지 않은 `lock()`도 `Success`가 된다(임시 시험으로 확인). `getState` 데이터도 마찬가지다.
- 위조 응답을 실제로 주입할 수 있는지는 확인하지 않았다. 연결 위장, 중계, 링크 주입 같은 수단이 필요하다.
- 위조 `WAIT`는 재인가 재전송을 일으켜 이미 승인된 명령을 한 번 더 실행하게 할 수 있다. `openTrunk()`는 토글이라 결과가 뒤집힐 수 있다.
- 실차 관찰 로그(2026-10-24~11-01, 차량 1대, 펌웨어 미기록): 인증 명령의 성공 35건은 모두 `encrypted(0B)`, `request_uuid`가 있는 평문 데이터는 0건, 평문 데이터는 인증 없는 조회뿐이었다. `WAIT` 6건은 47바이트로 태그가 들어갈 자리가 없다. `encrypted(...)`는 서명 필드가 있다는 뜻일 뿐 검증 성공을 뜻하지 않는다. 우리 요청의 Infotainment 응답은 아직 수집하지 못했다.

## 선택지
1. **Go와 같이 평문 수용**: 호환성은 가장 좋지만 위조 성공을 막지 못한다.
2. **페이로드가 있는 평문만 거부** (자동 보안 리뷰 제안): 페이로드 없는 응답도 성공으로 해석되므로(`VcsecResponses`, `InfotainmentResponses`) 위조 `lock()` 성공이 그대로 남는다.
3. **성공과 데이터에 검증된 응답을 요구 (채택)**: 양 도메인에 같은 규칙을 적용한다.

## 결정
| 응답 | 처리 |
|---|---|
| 암호화 명령의 성공·데이터 (양 도메인, 빈 성공 포함) | AES-GCM 검증과 재전송 검사를 통과해야만 인정한다 |
| 태그 없는 애플리케이션 응답, 페이로드 없는 성공 | 완료 근거로 쓰지 않고 원래 시간 제한까지 기다린다 |
| 태그 없는 fault | 검증되지 않은 진단 정보로 보존한다. 실행되지 않았다고 단정하지 않고 기본적으로 자동 재전송하지 않는다 |
| 세션 정보 | HMAC, challenge, 신선도를 검증해 따로 반영한다. 함께 온 fault를 인증하는 것은 아니다 |
| 인증 없는 VCSEC 조회, 브로드캐스트 | 지금처럼 허용하고 미인증임을 명시한다 |
| 2024.38 이전 펌웨어 | 지원하지 않는다. 옵트인과 평문 수신 시 자동 다운그레이드는 없다 |

- 시간 제한까지 인정할 응답이 없으면 `Uncertain`으로 끝낸다. 검증되지 않은 fault가 있으면 함께 전달한다(MTU fault를 `Timeout`과 구분하기 위해, #116).
- 요청별로 인증 방식과 기대하는 응답 정책을 기록하고, 검증 결과를 메시지와 함께 전달한다. `Signer`가 복호화 후 서명 데이터를 지우므로 뒤에서 확인할 수 없다. 응답 전체를 뭉뚱그린 인증 여부 하나로 표현하지 않는다: AES-GCM은 페이로드와 `signed_message_fault`만 덮고 바깥 `operation_status`는 덮지 않는다.

## 미결정: 태그 없는 `WAIT`
실차의 정상 `WAIT`에는 태그가 없다. 지금은 `WAIT`가 요청을 닫고 재전송한다.
- Codex 안: 재전송 없이 같은 요청을 계속 기다리고, 끝내 검증된 응답이 없으면 `Uncertain`. 감사를 거친 반복 안전 명령에만 제한된 재시도를 허용한다. FR-101이 바뀐다.
- 필요한 사실: `WAIT` 뒤에 같은 요청의 최종 응답이 오는가. 로그에는 일부 `WAIT` 직후 버려진 `[drop:no-handler] encrypted(0B)`가 있는데, 늦은 성공 응답인지 다른 기기의 응답인지 알 수 없다.

## 결과
- Go와 의도적으로 달라진다(절대 규칙 5, NFR-017). 구현 PR은 코드 주석과 원본 줄 인용 시험을 함께 넣는다.
- 2024.38 이전 펌웨어에서는 인증 명령이 `Uncertain`으로 끝난다.
- 위조 응답을 받아도 `Success`는 나오지 않지만, 공격자가 응답을 막아 `Uncertain`을 만드는 것은 막지 못한다.
- 구현 전 #118에서 우리 `getState` 응답과 `WAIT`·최종 응답의 대응을 수집한다. 그때까지 코드 동작은 Go와 같다.
