なぜ新しいプロトコルなのか

Tesla 車両はエンドツーエンドのコマンド認証(end-to-end command authentication)を提供するプロトコルをサポートしています。コマンドはクライアントの秘密鍵で認証(または暗号化)されて車両まで届けられ、車両は自身のキーチェーンに登録された公開鍵でのみコマンドを検証します。Tesla のサーバーでさえコマンドを偽造することはできません。

  • 従来の Owner API は、車両がエンドツーエンド認証を要求し始めたことで動作しなくなります。Owner API ベースのアプリケーションは、この SDK に直接移植するか、このリポジトリの HTTP プロキシを前段に置くことで REST 呼び出しをそのまま維持できます。
  • 2021 年より前の Model S/X はこのプロトコルをサポートしていません。これらの車両では Fleet API が引き続き動作し、プロキシは ErrProtocolNotSupported(HTTP 422)を受け取るとその VIN を記憶しておき、以降のリクエストを REST API にそのまま転送します。
  • この SDK は Go で書かれた公式実装です。プロトコル仕様(pkg/protocol/protocol.md)と protobuf 定義が公開されているため、他の言語で実装することもできます(../md/10-porting-guide.md を参照)。

2 段階の認証モデル

インターネット経路でコマンドを送るには、互いに独立した 2 つの認証を通過する必要があります。BLE 経路では 2 番目の段階だけが必要です。

  1. Tesla サーバー認証 (OAuth)。 Tesla のサーバーは、クライアントが有効な OAuth アクセストークンを提示した場合にのみメッセージを車両に転送します。トークンの aud/ou_code クレームから地域ごとの Fleet API ホストを決定します(pkg/account)。BLE ではこの段階はありません。
  2. 車両認証 (秘密鍵)。 車両は、コマンドがキーチェーンに登録された公開鍵で認証されている場合にのみ実行します。鍵は NIST P-256 ECDH 鍵で、ユーザーが NFC カードで承認するか(BLE)、Tesla アプリの https://tesla.com/_ak/<domain> リンクを通じて登録します。
BLE では OAuth は不要

BLE で直接接続すると Tesla のサーバーを経由しないため、OAuth トークンなしで VIN と秘密鍵だけでコマンドを送れます。ただし、車両は MESSAGEFAULT_ERROR_COMMAND_REQUIRES_ACCOUNT_CREDENTIALS で一部のコマンドを拒否することがあり、Fleet Manager ロールの鍵は 2023.38 以降 BLE でコマンドを送れません。

ドメイン: VCSEC と Infotainment

車両にはドメイン(domain)と呼ばれる独立したサブシステムがあります。各ドメインは独自の公開鍵、時計(epoch + timestamp)、アンチリプレイカウンターを持つため、ドメインごとに別々のハンドシェイクとセッションが必要です。

VCSEC はスリープしない

VCSEC は Infotainment が省電力状態でも BLE で応答します。したがって、body-controller-state、wake、lock のような VCSEC コマンドは車両を起こさずに実行できます。StartSession(ctx, []Domain{DomainVCSEC}) のようにドメインを限定すれば、不必要に Infotainment を起こしません。一方で VCSEC はメモリ制約のためレスポンスに request_uuid を含めず、カウンターは順番どおりに届く必要があり、同時リクエストは避けなければなりません。

鍵のロール(Role)

車両は登録された公開鍵ごとにロールを付与し、ロールによって認可できるコマンドが異なります。値は pkg/protocol/protobuf/keys.proto に定義されています。

ロールprotobufCLI 引数権限
OwnerROLE_OWNER = 2ownerすべてのコマンド。他の鍵の追加/削除を含む。
DriverROLE_DRIVER = 3driverほとんどのコマンド。鍵管理、PIN 変更などのアクセス制御設定は不可。
Fleet ManagerROLE_FM = 4fmクラウドベースの Owner 鍵。2023.38 以降、他の鍵の追加/削除は不可、BLE でのコマンドは不可。アカウントレベルの管理は Fleet API を使用。
Vehicle MonitorROLE_VEHICLE_MONITOR = 5vehicle_monitor位置などのデータ読み取りのみ可能。状態を変更するコマンドは不可。
Charging ManagerROLE_CHARGING_MANAGER = 6charging_managerデータ読み取り + 充電関連コマンド。
GuestROLE_GUEST = 8(CLI 非対応)一時的な Driver 鍵。レンタル用の自動ライフサイクル。Fleet API の Guest Mode を参照。
ServiceROLE_SERVICE = 1(追加不可)他の鍵のペアリングのブートストラップ、ロードサイド用のリモートロック/解除、Driver/Guest/FM 鍵のリモート削除。デフォルト状態ではインターネット経由で他のコマンドを認可できない。
NoneROLE_NONE = 0-ロールのない鍵を追加すると WHITELISTOPERATION_INFORMATION_ATTEMPTING_TO_ADD_KEY_WITHOUT_ROLE エラー。

鍵にはロールのほかにフォームファクター(form factor)メタデータも付きます(vcsec.proto): KEY_FORM_FACTOR_NFC_CARD = 1、IOS_DEVICE = 6、ANDROID_DEVICE = 7、CLOUD_KEY = 9、UNKNOWN = 0。車両画面の Locks 一覧でアイコンとして表示されます。

  • Connector はバイト配列だけをやり取りするデータグラム伝送です。認証や protobuf についてはまったく関知しません。自前で実装すれば、他の伝送(例: シリアル、テスト用のメモリパイプ)を接続できます。
  • Dispatcher は Connector をラップして RoutableMessage をエンコード/デコードし、ドメインごとのセッション(session)を維持し、受信メッセージを routing_address(+ Infotainment の場合は request_uuid)によって待機中の receiver に配送します。車両がエラーとともに新しい session_info を送ってきた場合は、自動的にセッションを更新します。
  • Vehicle はユーザーに見えるメソッドの集合です。各メソッドはドメインに合った protobuf を作成し、Send(リトライ込み)で送信したあと、レスポンスを protocol.Error に変換します。

1 つのコマンドのライフサイクル

tesla-control -ble lock が実行されたときに起こることです。インターネット経路では 1〜2 段階目が account.GetVehicle に置き換わります。

  1. スキャン: VIN の SHA1 の先頭 8 バイトからアドバタイズ名を計算し、一致するアドバタイズを探します。
  2. GATT 接続: サービス 00000211-… を見つけ、書き込みキャラクタリスティック(0212)と通知キャラクタリスティック(0213)を購読したあと、MTU をネゴシエーションします。
  3. Connect: Dispatcher.Start が受信ゴルーチンを起動します。セッションキャッシュがあれば、この時点でドメインごとのセッションを復元します。
  4. StartSession: キャッシュのないドメインごとに SessionInfoRequest を送り、レスポンスの HMAC タグを検証したあと、ECDH で共有鍵 K を作ります。キャッシュがあればこの往復は省略されます。
  5. Send: コマンドの protobuf をメタデータとともに AES-GCM(BLE)または HMAC(インターネット)で認可して送信します。protocol.ShouldRetry が真となるエラー(Busy、カウンター/epoch の不一致など)は RetryInterval 後に自動でリトライします。
  6. レスポンス: 車両がエラーとともに新しいセッション情報を送ってくると dispatcher がセッションを更新し、レスポンスが暗号化されていれば復号とカウンター検証を経て、Vehicle メソッドが最終結果をエラー型で返します。
