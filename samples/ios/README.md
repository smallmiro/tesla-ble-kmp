# iOS 샘플 (모니터 앱, 빌드 27)

> 샘플 스펙과 제약: `samples/documents/md/`(에이전트용) · `samples/documents/html/`(사람용). 에이전트 지침: `samples/ios/AGENTS.md`.
> 이 README는 빌드 절차와 실차 확인 절차(runbook)를 담습니다.

1. `./gradlew :sdk:linkDebugFrameworkIosSimulatorArm64`
2. `cd samples/ios && xcodegen generate`
3. `open TeslableSample.xcodeproj` 또는
   `xcodebuild -project TeslableSample.xcodeproj -scheme TeslableSample -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build`

`.xcodeproj`는 생성물이라 커밋하지 않는다(`.gitignore`).
`Sources/Info.plist`도 `xcodegen generate`가 `project.yml`로부터 매번 새로 생성하므로 커밋하지 않는다.

## 실기기 실행

1. `./gradlew :sdk:linkDebugFrameworkIosArm64`
2. `cp Local.xcconfig.example Local.xcconfig` 후 `DEVELOPMENT_TEAM`에 팀 ID 입력(커밋 금지)
3. `xcodegen generate`
4. Xcode에서 `TeslableSampleDevice` 스킴을 iPhone에 실행
5. 샘플 화면으로 확인(체크리스트, 결과에 VIN·공개키 전문은 적지 않는다). 이 폰의 키는 아직 차량에 등록되어 있지 않으므로 인증이 필요한 동작은 대상이 아니다.
   - 기록은 "결과" 칸의 **결과 전체 복사** 버튼으로 앱 정보·연결 상태·키·시각별 결과를 한 번에 클립보드로 복사해 전달한다(VIN은 포함되지 않는다). **결과 지우기**로 다음 확인을 새로 시작한다.
   1. 키 만들기: `secureEnclave` + 공개키 지문, 앱을 다시 실행해도 같은 지문
   2. 스캔(차량 근처): `S…C` 광고, rssi, connectable=true
   3. 연결: "연결됨" (실패하면 오류 문구)
   4. VehicleStatus: 잠금·문 상태가 실제와 같음(문 하나 열고 다시)
   5. 키 목록: 차량 화면(잠금 → 키)의 키 수와 같음, 역할·형태 표시
   6. 연결 끊기 후 다시 연결: 둘 다 성공
   7. 블루투스를 끄고 스캔: `bluetooth is powered off`
   8. 설정에서 블루투스 권한을 거부하고 스캔: `bluetooth permission not granted` (크래시 없음)
   9. (선택) 명령 중 차량에서 멀어짐: 불확실(시간 초과) 뒤 `vehicle not connected`

## 실차 푸시 관찰 (M4 Task 1, 빌드 6 / 관찰 로그 v2, 빌드 8)

차량이 요청 없이 먼저 보내는 메시지(푸시)가 어떤 모양으로, 얼마나 자주, 무슨 내용으로 오는지 기록한다. M5 `vehicle.events` 설계의 근거가 된다.
라이브러리는 이 메시지를 여전히 버린다. 샘플이 DEBUG 로그(태그 `observe`)의 요약 줄만 화면에 모아 준다.

사전 준비: 실기기 실행 절차(위)를 따라 빌드 6을 설치한다. 키 불러오기 → 연결 후 **관찰 모드** 스위치를 켠다.
관찰 중에는 VehicleStatus와 키 목록 버튼이 막힌다(차량을 깨우는 요청을 보내지 않기 위해). 샘플은 자동으로 조회하지 않는다.

| # | 시나리오 | 할 일 | 기다릴 시간 | 기록할 내용 |
|---|---|---|---|---|
| 1 | 새로 연결한 직후 | 키 불러오기 → 연결 → 바로 관찰 모드 켜기 | 30초 | 처음 30초의 줄 수, `reinterpreted=…unknownFields=[…]` 줄의 간격(약 1.1초인지)과 필드 번호 |
| 2 | 문·트렁크를 손으로 열고 닫기 | 운전석 문 열기 → 10초 → 닫기, 트렁크도 같게 | 동작마다 10초 | 동작 뒤 몇 초 안에 `vehicleStatus` 줄이 오는지, `to=`의 형태(none/domain/address+owner), `closures` 값 |
| 3 | 키카드나 공식 앱으로 잠금·해제 | 샘플은 그대로 두고 카드/앱으로 잠금 → 10초 → 해제 | 동작마다 10초 | `lock=` 변화가 오는지, 주소 형태 |
| 4 | 차에 타고 내리기 | 운전석에 앉기 → 20초 → 내려 문 닫기 | 20초씩 | `presence=` 변화 |
| 5 | 충전 케이블 꽂고 빼기 | 충전구 열기 → 케이블 꽂기 → 빼기 | 동작마다 10초 | `chargePort=` 변화, Infotainment 줄(`from=domain(DOMAIN_INFOTAINMENT)`)이 있는지 |
| 6 | 차량이 잠들거나 깨어날 때 | 문 닫고 잠근 뒤 휴대폰을 두고 관찰 유지 | **최소 15분** | `sleep=` 변화 시각, 잠든 뒤 줄 간격, `absent=` 목록, 연결이 끊기는지 |
| 7 | 다른 폰 키가 다가올 때 | 다른 폰(공식 앱 키) 들고 차에 다가가기 | 30초 | `drop:no-handler`의 `to=address(16B, other)` 줄, 빈도 |

각 시나리오가 끝나면 **결과 전체 복사**로 붙여 넣어 보낸다(VIN은 들어가지 않는다). 시나리오 사이에 **관찰 기록 지우기**로 비우면 구분하기 쉽다.

주의:
- 복사본에는 화면 결과와 `observe` 태그 줄만 들어간다. 암호문은 길이만, 공개키는 SHA-1 앞 4바이트(`key=sha1:xxxxxxxx`)만 적힌다.
- Console.app(통합 로그)은 공유하지 않는다. 거기에는 BLE 원문 헥사(`TX:`/`RX:`)가 들어 있다.
- 줄 형식은 `documents/md/18-lib-troubleshooting.md`의 "Observation log (development)" 절을 본다.

결과를 받은 컨트롤러는 `docs/handoff/<날짜>-m4-push-observation-results.md`에 다음 머리말로 정리한다: `## 관찰 환경`(iPhone/iOS, 차량/펌웨어, 빌드), `## 시나리오별 결과`(위 표 + "푸시 주소 형태 / 빈도 / 내용"), `## M5 판단에 쓸 사실`(인계 노트 "실차 로그로 확인할 것" 두 가지에 대한 답), `## 응답과 섞인 사례`(`[reply:vcsec]` 중 `vehicleStatus` 페이로드가 있었는지).

### 표시 버튼과 2차 시나리오 (관찰 로그 v2, 빌드 8)

빌드 8부터 평문 브로드캐스트의 미공개 필드(`FromVCSECMessage` 48·53, `VehicleStatus` 7·8)는 번호만이 아니라 값을 풀어서 적는다
(`unknownFields=[48:len(8){1:varint=3(0x3), …}]`). 탐색용이며 필드의 뜻을 알려 주지 않는다. `closureStatuses`가 없다고 "모두 닫힘"이 아니다.
VIN은 가려지고 키·서명처럼 보이는 값은 `redacted(NB)`로만 남는다.

**표시**: 관찰 모드에서 메모 칸에 한 줄을 적고 `표시`를 누르면 `[HH:mm:ss +12.3s] [mark] <메모>` 줄이 관찰 목록에 들어간다(결과 전체 복사에도 같은 순서로).
행동 **직전**에 누르는지 **직후**에 누르는지를 메모에 적는다(예: `직전: 운전석 문 열기`). 시각은 버튼을 누른 시각이다.
비밀(키, 비밀번호, VIN)은 적지 않는다. 빈 메모는 무시되고, 80자까지만 남으며, VIN 모양은 가려진다. 차량에는 아무 요청도 가지 않는다.

| # | 시나리오 | 할 일 | 기록할 내용 |
|---|---|---|---|
| A | 문을 손으로 열고 닫기 | 각 문마다 `표시`(직전) → 열기 → 10초 → `표시`(직후) → 닫기 → 10초 | 동작 뒤 48·53·7·8의 값 변화 |
| B | 트렁크·프렁크를 손으로 열고 닫기 | A와 같게 | 같음 |
| C | 충전 케이블 꽂고 빼기 | `표시`(직전) → 충전구 열고 꽂기 → 10초 → `표시`(직전) → 빼기 → 10초 | 값 변화, Infotainment 줄 여부 |
| D | 다른 폰 키가 다가오거나 차가 잠들 때 | 다른 폰으로 다가가기 `표시` → 30초. 또는 잠근 뒤 **15분 이상** 두고 `표시`로 시각 기록 | 주기(48이 약 5초인지), 값 변화, `sleep=` 변화 |

## M4 실차 확인 (페어링·키 삭제·VCSEC 제어, 빌드 7)

빌드 7(`TeslableSampleDevice`)을 설치한다. 키 만들기/불러오기 → 연결 후 아래 순서로 진행하고, 끝나면 **결과 전체 복사**로 붙여 넣어 보낸다(VIN은 들어가지 않는다).
관찰 모드가 켜져 있으면 제어·조회 버튼이 막힌다 — 확인 중에는 끈다(9번만 켠 채로 둔다).

## 키·제어 탭 실기기 확인 (SFR-018, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)를 설치한다. 새 탭 **키·제어**(다섯 번째): 키 → 연결 → 등록 → 제어 네 단계와 버튼 격자.
규칙과 버튼 표는 `samples/documents/md/05-key-control-tab.md`. 모든 명령은 먼저 VCSEC 세션을 보장하고(`startSession(setOf(VCSEC))`), 명령을 한 번만 보내고, 그 뒤에 `vehicleStatus()`로 재조회한다(`Uncertain`도 다시 보내지 않는다).
결과에는 VIN·공개키 전문을 적지 않는다. 시뮬레이터에는 블루투스가 없으므로 아래는 모두 실기기에서만 확인한다. 기록은 화면 "결과" 목록(최신이 위)과 Log 탭 `observe` 줄로 한다.

## 키 별명 실기기 확인 (SFR-019, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)를 설치한다. Control 탭의 키 목록 각 행에 **이 폰에만 저장되는** 별명을 붙인다.
차량에는 키 이름 칸이 없다(VCSEC `KeyMetadata`는 `keyFormFactor`뿐이다). 그래서 별명은 차 화면에 나타나지 않고 차량으로 가지도 않는다.
규칙은 `samples/documents/md/04-monitor-app.md` §Key nickname. 저장소 규칙(자르기, 32자, 빈 입력 삭제)은 `Tests/KeyNicknameTests.swift`가 시험한다.
결과·화면에 공개키 전문과 VIN을 적지 않는다. 키 목록을 읽으려면 차에 연결돼 있어야 하므로 아래는 실기기에서만 확인한다.

| # | 확인 | 할 일 | 기대 |
|---|---|---|---|
| N1 | 별명 붙이기 | Control 탭에서 연결 → **키 목록** → 행의 **이름** 누르기 → `아빠 폰` 입력 → 저장 | 입력창에 "이 폰에만 저장됩니다"(차량 이름은 안 바뀐다는) 안내가 보이고, 행 위에 굵은 `아빠 폰`, 아래에 평소 라벨(`슬롯 N …`)이 보인다. 버튼이 **이름 수정**으로 바뀐다. 결과에는 `키 이름 저장(슬롯 N)`만 있고 이름 자체는 없다 |
| N2 | 앱을 다시 켜도 유지 | 앱을 완전히 종료 후 다시 실행 → 연결 → **키 목록** | 같은 행에 같은 별명이 보인다 |
| N3 | 수정 | **이름 수정** → 입력창에 현재 별명이 채워져 있음 → `엄마 폰`으로 바꿔 저장 | 행의 별명이 바뀐다 |
| N4 | 앞뒤 공백 | 별명을 `   새 이름  `(앞뒤 공백)으로 저장 | 공백 없이 `새 이름`으로 보인다 |
| N5 | 32자 제한 | 입력창에 40자 이상 붙여 넣기 | 32자에서 잘린다. 32자는 저장된다. 앞 공백 3개 + 32자를 붙여 넣어도 32자가 모두 저장된다(앞 공백은 세지 않는다). 단어 사이에 공백을 입력할 수 있다 |
| N6 | 지우기 | **이름 수정** → 글을 모두 지우거나 공백만 남기고 저장 | 행에서 별명이 사라지고 버튼이 **이름**으로 돌아온다. 결과에 `키 이름 지움(슬롯 N)` |
| N7 | 취소 | 입력창에서 **취소** | 별명은 그대로 |
| N8 | 슬롯이 아니라 키 ID | (가능하면) 차에서 앞쪽 키를 지워 슬롯 번호가 바뀐 뒤 **키 목록** | 별명이 슬롯이 아니라 같은 키를 따라간다(남은 키의 행에 그대로 붙음) |
| N9 | 키 ID 없음 | (재현되면) 키 ID가 없는 항목 | 그 행의 **이름** 버튼이 꺼져 있다 |
| N10 | 삭제 확인 창 | 별명이 있는 행의 **삭제** | 확인 창에 별명과 라벨이 함께 보인다(공개키 전문은 없다) |
| N11 | 복사본 | **결과 전체 복사** 후 붙여 넣기 | 별명 글, 공개키 전문, VIN이 없다 |

## 키 삭제 후 다시 만들기 실기기 확인 (SFR-020, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)를 설치한다. **키·제어** 탭 1단계의 **키 삭제 후 다시 만들기** 버튼이 모니터 키 `teslable-monitor`를 지우고 새로 만든다(같은 Secure Enclave·`afterFirstUnlock` 설정).
규칙은 `samples/documents/md/05-key-control-tab.md` §Delete and recreate the key. 순서·실패 처리는 `Tests/KeyReplacementTests.swift`가 시험한다.
**되돌릴 수 없다.** 실제로 쓰는 차량이면 새 키를 키카드로 다시 등록할 수 있을 때만 확인한다. 차량의 옛 공개키는 차 화면에서 지울 때까지 남는다. 결과·화면에 공개키 전문과 VIN을 적지 않는다.

| # | 확인 | 할 일 | 기대 |
|---|---|---|---|
| R1 | 확인 창 | 버튼 누르기 | 창에 ① 이 폰에서 영구히 지워짐 ② 차량에는 옛 공개키가 남음 ③ 키카드로 다시 등록해야 함 ④ 연결을 끊고 다시 연결함, 이 네 가지가 있다. **취소**하면 아무것도 바뀌지 않는다(키·연결 그대로) |
| R2 | 연결·등록된 상태에서 교체 | 연결되고 등록된 상태에서 확인 | 연결이 잠깐 끊겼다가 새 키로 다시 연결된다. 결과 `새 키를 만들었습니다 …`. 1단계는 완료, 3단계는 등록 확인 뒤 `등록되어 있지 않습니다`, 4단계 버튼은 꺼진다. 상태 카드는 비고 "아직 읽지 않았습니다" |
| R3 | Control 탭 | Control 탭 → **키 목록** | 차량에 옛 공개키가 그대로 보이고 "(이 기기)" 표시 행이 없다. 교체 직후 Control 탭의 키 목록과 키 정보는 비어 있었다 |
| R4 | 새 키 등록 | 3단계로 새 키 등록 | 등록되고 4단계 버튼이 켜진다. 옛 키 ID에 붙였던 별명은 새 키 행에 나타나지 않는다(별명은 옮기지 않는다) |
| R5 | 접근성 유지 | 교체 뒤 Control 탭의 키 정보 | `secureEnclave`, `afterFirstUnlock`, `WHEN_UNLOCKED` 경고 없음 |
| R6 | 잠긴 키 저장소 | 재시동 뒤 잠금 해제 전 버튼 누르기(또는 버튼이 꺼져 있음) | 키를 지우지 않고 연결도 그대로. 결과 `키 저장소가 잠겨 있어 아무것도 바꾸지 않았습니다 …` |
| R7 | 연결 없이 | 연결 끊기를 누른 상태에서 교체 | 새 키만 만들어지고 연결은 시작되지 않는다 |
| R8 | 삭제 실패(가능하면) | 재현되면 | 새 키를 만들지 않고 결과에 `옛 키는 그대로`, 1단계의 키가 그대로 보인다 |
| R9 | 손상된 키(재현되면만) | 저장된 키가 `stored key is corrupted` 로 읽히는 상태(예: Android의 래핑 키 없는 백업 복원, iOS는 재현이 어렵다) | 1단계가 `저장된 키가 손상되었습니다 …`, 버튼이 켜진다. 확인 창에 `옛 키는 복구할 수 없습니다`가 더해진다. 확인하면 새 키가 생기고 R2~R5와 같게 진행. 다른 키 오류(잠금 제외)에서는 버튼이 꺼져 있다 |
| R10 | 다른 탭과 겹침 | Control 탭에서 **키 등록 요청**을 시작한 채 키·제어 탭에서 교체 누르기. 또 교체가 도는 동안 Live 탭 **연결** 누르기 | 앞은 결과에 `다른 호출이 진행 중이거나 키를 바꾸는 중이라 …`, 아무것도 바뀌지 않는다. 뒤는 교체가 끝날 때까지 연결이 시작되지 않고, 누른 연결을 기억했다가 끝나면 새 키로 연결한다(그 전에 연결이 없었어도). 교체 중에 Live 탭 **연결 끊기**(또는 VIN 지우기)를 누르면 끝난 뒤에도 연결하지 않는다. 마지막에 누른 것이 이긴다(SFR-012). Control 탭 버튼도 교체 중에는 `키를 바꾸는 중이라 지금은 할 수 없습니다` |
| R11 | 지우기가 실패한 뒤 | (재현되면) 지우기 실패 뒤 키 상태 | 키가 있으면 `옛 키는 그대로`, 키가 없으면 `키 저장소에 키가 없습니다 … 연결을 다시 만들지 않았습니다`, 읽지 못하면 `키 상태도 읽지 못했습니다 …`, 폰이 잠겨 읽지 못하면 `폰이 잠겨 있어 키가 지금 어떤 상태인지 알 수 없습니다 …`(연결도 다시 만들지 않는다). 어느 경우에도 새 키가 조용히 생기지 않는다 |

## 등록 진행 팝업 실기기 확인 (SFR-021, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)를 설치한다. **키·제어** 탭 3단계의 **키 등록 요청**을 누르면 화면을 막는 시트(팝업)가 열려 진행을 보여 준다.
규칙은 `samples/documents/md/05-key-control-tab.md` §Enrollment progress popup. 단계·문구·버튼 규칙은 `Tests/EnrollmentPopupTests.swift`가 시험한다.
**취소는 기다리기를 멈출 뿐, 이미 차량에 보낸 요청은 되돌리지 못한다**(차 화면의 승인 창이 남을 수 있고, 그 뒤에 카드를 대면 등록될 수 있다).
Control 탭의 **키 등록 요청**은 예전처럼 결과 줄만 남기고 팝업이 없다. 아직 등록하지 않은 키(예: 위 R-시나리오 뒤의 새 키)로 확인한다.

| # | 확인 | 할 일 | 기대 |
|---|---|---|---|
| P1 | 열림 | 차 근처에서 연결 뒤 3단계 **키 등록 요청** | 시트가 바로 열린다. "요청 보냄 …"에서 `요청을 보냈습니다. 차량 중앙 콘솔에 키카드를 대고, 차량 화면에서 승인하세요.` 로 바뀐다. 세 줄 표시(요청 → 카드·승인 → 확인)가 보이고 **취소**만 있다 |
| P2 | 성공 | 키카드를 센터 콘솔에 대고 차 화면에서 승인 | 세 번째 줄이 진행 중이 되고 `확인 N번째 · 경과 0:03 / 2:00 · 남은 시간 1:57` 같은 줄과 진행 막대가 3초마다 바뀐다. 이어서 `등록 완료`, **닫기**. 닫으면 3단계 완료, 4단계 버튼이 켜진다 |
| P3 | 확인 못 함 | 요청 뒤 승인하지 않고 2분 기다리기 | `2분 안에 확인되지 않았습니다 …` 와 **닫기**. 닫은 뒤 **등록 상태 확인**이 동작하고, 그 사이 승인했다면 `등록되어 있습니다` |
| P4 | 취소 | 대기 중 **취소** | 곧 `멈추는 중…` → `기다리기를 멈췄습니다 … 되돌릴 수 없어 …` 와 **닫기**. Log 탭에 그 뒤 `sessionInfo` 요청이 더 가지 않는다(Kotlin 흐름이 실제로 취소를 받아 끝나는지는 기기에서만 확인된다 — 단위 테스트는 가짜 흐름으로 시험한다). 결과에 `키 등록: 기다리기를 멈췄습니다 …`. 3단계 상태는 그대로 |
| P5 | 취소 뒤 카드 | P4 뒤 카드를 대고 승인 → **등록 상태 확인** | `등록되어 있습니다`가 나올 수 있다(취소는 요청을 되돌리지 않는다) |
| P6 | 연결 끊김 | 시트가 열려 있을 때 블루투스를 끄거나 차에서 멀어지기 | 시트가 바로 닫히고 결과에 `연결이 바뀌어 등록 기다리기를 중단했습니다 …`. 시트가 남지 않는다 |
| P7 | 막힘 | 진행 중 시트를 아래로 끌기 | 닫히지 않는다(취소 버튼으로만 멈춘다) |
| P8 | 거부·실패(가능하면) | 차 화면에서 거부하거나 요청 중 연결 끊기 | `등록 실패`와 메시지, **닫기** |

## Infotainment 공조·충전 실기기 확인 (SFR-025, 빌드 26)

빌드 26(`TeslableSampleDevice`, 버전 0.5.0)을 설치한다. **키·제어** 탭 4단계의 VCSEC 격자 아래 **Infotainment (공조·충전)** 구역: 범주 **공조**(공조 켜기, 공조 끄기, 공조 상태 읽기)와 **충전**(충전 시작, 충전 중지, 충전 상태 읽기).
규칙은 `samples/documents/md/05-key-control-tab.md` §Infotainment controls (SFR-025, 확인 항목 21~27). 한 번 누르면 `vehicleStatus()`(`AWAKE`일 때만 계속) → `startSession(setOf(INFOTAINMENT))` → 호출 **한 번**이고, `wakeUp()`을 부르지 않고 다시 보내지 않으며 끝난 뒤 `getState`를 따로 부르지 않는다. 확인 창은 없다.
순서·문구·미확인 표시·늦은 결과 버리기는 `Tests/InfotainmentControlTests.swift`와 `Tests/InfotainmentModelTests.swift`가 가짜로 시험한다. **공조·충전 명령과 `getState(CLIMATE)`/`getState(CHARGE)`는 실차에서 한 번도 확인되지 않았다**(#118): 아래는 모두 "차가 한 일"을 적는 확인이고, 기대는 문서 기준의 예상이다. 값(온도, 배터리 %, 전력)은 결과 줄과 로그에 가지 않고 이 구역의 화면에만 보인다. 차 화면과 비교해 적을 때만 값을 옮겨 적는다. VIN은 적지 않는다.

| # | 확인(스펙 항목) | 할 일 | 기대 |
|---|---|---|---|
| I1 | 켜짐과 꺼짐 (21) | 깨어 있는 차, 등록된 키로 연결. 이어서 블루투스를 끄거나 3단계 전 상태로 | 여섯 버튼이 4단계 버튼과 같은 때 켜진다(연결 + 키 + 등록됨 + 다른 호출 없음). 블루투스를 끄거나 등록 전에는 모두 꺼지고 4단계와 같은 주황 안내가 보인다. 세션을 먼저 시작하는 버튼은 없다 |
| I2 | 공조 (22) | **공조 켜기** → **공조 상태 읽기** → **공조 끄기** → 다시 읽기 | `공조 켜기: 성공 N ms`. 읽기 뒤 `is_climate_on: true`, `inside_temp_celsius`, `driver_temp_setting`, `timestamp`와 읽은 시각(초가 올라감). 차 화면과 같은지 적는다. 끄기 뒤 읽기에서 `false`. 켜기 직후 자동으로 읽지 않는다(읽기 줄이 없다) |
| I3 | 충전 (23) | 충전 케이블을 꽂은 채 **충전 시작** → **충전 상태 읽기**, **충전 중지** → 읽기. 케이블 없이도 한 번 | 결과 줄과 읽기 값(`charger_power`, `battery_level`, `charge_limit_soc`, `charge_port_door_open`)을 적고 차가 보여 준 것과 비교한다. `charging_state`는 읽지 않는다(알려진 문서 공백, 요청서 대기). 케이블이 없을 때 차가 돌려준 결과 종류(`InfotainmentRejected` 등)를 그대로 적는다 |
| I4 | 잠든 차 (24) | 차가 잠들 때까지 기다린 뒤 **공조 켜기** | `보내지 않음` + "차량이 자고 있습니다 … 자동으로 깨우지 않습니다". 차가 깨지 않는다. Log 탭에 Infotainment 트래픽이 없다(통합 로그에 `startSession`/`getState`/명령 TX 없음). 상태 카드가 `수면 중`으로 바뀐다. 문 그룹 **깨우기** → 상태 카드가 `깨어 있음`이 되면 다시 누른다 |
| I5 | 불확실 (25) | (가능하면) 명령 직후 통신 한계 가장자리로 이동하거나 Infotainment가 졸 때 보낸다 | `불확실 (Timeout(afterSend=true))` 같은 줄과 "차량이 실행했을 수 있습니다. 다시 보내지 않습니다 …", 구역에 `공조 결과 미확인`(또는 충전)이 빨간 글씨로 나온다. 두 번째 명령이 자동으로 가지 않는다(통합 로그 TX 한 번). 버튼은 켜져 있다. **공조 상태 읽기**가 성공하면 표시가 사라진다. 읽기도 불확실이면 표시와 마지막 값이 남고 `조회는 차량을 바꾸지 않으니 다시 읽어도 됩니다` |
| I6 | 연결 끊김 (26) | 명령이 도는 동안(느린 응답일 때) 블루투스를 끄거나 멀어져 링크를 끊는다 | 늦게 끝난 결과는 버려지고 줄 하나 `연결이 바뀌어 결과를 버렸습니다 …`만 남는다. 읽은 값과 미확인 표시가 모두 사라지고, 상태 카드도 옛 연결의 것이 남지 않는다 |
| I7 | 복사본 (27) | 결과 목록의 줄을 선택해 복사해 붙인다 | 줄에는 버튼 이름, 결과 단어, 오류 종류 이름, 소요 시간만 있다. 값, 필드 이름, 차량이 보낸 글, `message`가 없다 |

기록은 첫 줄에 **기기, iOS 버전, 앱 빌드(26), 차량 펌웨어**를 쓰고, 항목마다 누른 버튼, 결과 줄, 읽은 필드와 차 화면의 값(적을 때만), 이상한 점을 적는다. 같은 구간의 통합 로그는 `tools/samples/pull-monitor-logs.sh ios` 로 가져와 `samples/logs/`에 두고(커밋하지 않는다) `protocol-analyst`에게 넘긴다.

## 상태 진단 실기기 확인 (SFR-023, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)을 설치한다. **Query** 탭 아래쪽의 **상태 진단**에서 사람이 직접 `getState()` 를 부른다.
규칙은 `samples/documents/md/04-monitor-app.md` §State diagnostics. 사용 문서: `14-lib-reading-state.md` A8.1~A8.3, A8.5, `16-lib-errors.md` §`getState` results, §Response size limit on `getState`, `17-lib-platform-notes.md` §Swift: generated types.
눌렀을 때만 한 번 보낸다(순서: `vehicleStatus()` → `startSession(INFOTAINMENT)` → `getState`). 자동 재시도와 주기 조회는 없고 `wakeUp()` 을 호출하지 않는다.
**값은 화면에만 나오고 로그에는 범주·결과·소요 시간·오류 종류와, 성공이면 차가 보낸 필드의 이름(`present=[…]`)만 남는다**(Log 탭 `query` 줄 `getState(DRIVE)` 꼴). 그래서 값(속도, 기어, 곡 제목, 위치 좌표 등)은 사람이 화면에서 옮겨 적는다. `Drive` 의 위치와 경로 값은 앱이 읽지 않는다. 버튼은 12개(`StateCategory` 전부)이고, 기존 셋 말고 나머지 9개는 아래 "추가 카테고리 확인(빌드 27)"에서 확인한다.
시뮬레이터에는 블루투스가 없으므로 아래는 모두 실기기·실차에서만 확인한다. **주행 중 조작은 동승자가 한다.**

기록은 첫 줄에 차량 화면에서 옮겨 적은 **펌웨어, 모델, 앱 빌드(27)** 를 쓰고, 이어서 확인마다 화면의 결과 줄(결과 종류, 시각, 소요 시간, 값)을 적는다. VIN은 적지 않는다.

| # | 확인 | 할 일 | 기대 |
|---|---|---|---|
| S1 | 버튼이 꺼지는 조건 | 연결 전, 키를 등록하기 전, 차가 잠든 뒤(Live 탭 수면이 `ASLEEP`)에 Query 탭을 본다 | 12개 범주 버튼이 모두 꺼져 있고 그 아래에 이유가 있다(연결 안 됨 / 등록된 키 필요 / 수면 중 / 수면 상태 모름). `UNKNOWN` 일 때도 꺼진다. 연결·등록·`AWAKE` 가 모두 되면 켜진다 |
| S2 | Drive, 정차 | 차를 깨운 상태로 정차해 **Drive** | 결과가 한 줄로 나온다: `Success` 이면 `speed: 0 (단위 미확인)`, `shift_state: P` 등. 차량이 보내지 않은 필드는 `—`(0이 아니다). 소요 시간(ms)이 보인다. 위치·목적지 행은 없다 |
| S3 | Media | 곡을 재생한 채, 멈춘 채 각각 **Media** | `media_playback_status`, `audio_volume`, 곡 제목이 화면에 보인다. Log 탭의 `getState(MEDIA)` 줄에는 곡 제목도 값도 없다 |
| S4 | MediaDetail | 곡 재생 중 **MediaDetail** | `now_playing_duration`, `now_playing_elapsed` 와 `timestamp`. 제목 행은 없다(제목은 Media 쪽) |
| S5 | 불확실의 두 모습 | (가능하면) 긴 목적지를 넣고 **Drive**. 그리고 차가 응답하지 않을 때(예: 링크가 약할 때) | 응답이 너무 크면 `Uncertain` 과 "차량이 응답했지만 응답이 너무 커서…(RESPONSE_MTU_EXCEEDED)", 응답이 없으면 `Uncertain` 과 "시간 안에 응답이 없습니다…보냈을 수 있음 — 값은 확인되지 않았습니다. 조회는 차를 바꾸지 않으니 다시 조회하세요. 앱이 백그라운드에 있으면 BLE 쓰기가 느려져…"(로그의 `error=Timeout(afterSend=true)`). 쓰기를 시작하기 전에 시간이 다하면 `Failure` 와 "실행되지 않았습니다…"(`afterSend=false`). 문장이 서로 다르고, 자동으로 다시 보내지 않는다(Log 탭에 줄이 한 개). 결과를 적을 때 어느 쪽인지 쓴다 |
| S6 | 캐시된 세션 | 세션이 만들어진 뒤 앱을 완전히 종료 → 재실행 → 연결 → 같은 버튼 | `Success`. 차가 캐시된 세션을 받아들이지 않으면 `Failure` 와 "Infotainment 세션이 없어 보내지 않았습니다…"가 나오고 자동 재시도는 없다. **다음 누름**은 새 세션을 시작하고 결과를 낸다. 어느 쪽이 나왔는지 적는다 |
| S7 | 두 번 누름 | 한 버튼을 빠르게 두 번, 또는 조회 중에 다른 버튼 | 조회는 한 번만 간다(버튼이 조회 중에 꺼지고 Log 탭의 `getState` 줄이 하나) |
| S8 | 연결이 바뀜 | 조회를 누른 직후 차에서 멀어지거나 Control 탭에서 연결 끊기 | 결과 칸이 비고 Log 탭에 그 조회의 `getState` 줄이 없다. 다시 연결한 뒤에도 옛 결과가 나타나지 않고, 다음 주기 조회(`vehicleStatus`)가 끝난 뒤에 버튼이 켜진다 |
| S9 | 다른 탭과 겹침 | 키·제어 탭에서 "키 삭제 후 다시 만들기"의 확인 창을 연 채(또는 Control 탭 명령 진행 중) Query 탭에서 버튼 | 조회가 시작되지 않고 "다른 키 동작이 진행 중이라…" 문구가 나온다. 키는 바뀌지 않는다. 조회 중에 키 삭제 후 다시 만들기를 누르면 시작되지 않고, 조회가 끝난 뒤 다시 누르면 시작된다 |
| S10 | 잠든 차 실험(1회) | 차가 잠든 것(`ASLEEP`)을 Live 탭에서 확인 → 일반 버튼이 꺼져 있음 → 범주를 고르고 **잠든 차에 보내기(실험)** → 확인 창 | 창에 "이 요청 때문에 차가 깨어날 수 있습니다. wakeUp() 은 호출하지 않습니다"가 있다. **보내기** 뒤 결과(Uncertain/Failure/Success 중 무엇인지, 소요 시간)와, 그 뒤 Live 탭 수면 값이 바뀌었는지를 적는다. 깨우기 버튼은 누르지 않는다 |
| S11 | 로그에 값이 없음 | S2~S10 뒤 **Log 탭 마지막 줄 복사**(또는 로그 pull) | `getState(...)` 줄은 `call`, `result`, `summary`(`durationMs=…`, `error=…` 또는 `reason=…`, 성공이면 `present=[필드 이름…]`), `startedAt` 뿐이다. `present` 에는 필드 이름만 있고 값은 없다. `getState` 의 값(`speed`, `shift_state`, `now_playing…`, `audio_volume`, `odometer…`, 위치)은 어느 줄에도 없다(곡 제목으로 검색해도 0건). **`vehicleStatus()` 와 방송 줄의 VCSEC `gear=` 는 설계상 로그에 남는다**(`getState` 값이 아니다) |
| S12 | `timestamp` | 같은 상태에서 같은 버튼을 연속으로 두 번 | 두 `timestamp`(epoch 초)가 같은지 다른지 적는다(`Success` 가 새 측정이라는 증거가 아니다, A8.3) |

## iPhone Duo 확인 (SFR-024, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)를 접는 iPhone Duo에 설치한다. 규칙은 `samples/documents/md/04-monitor-app.md` §Wide and foldable screens.
**안쪽 화면**(가로 크기 클래스 regular, 쓸 수 있는 너비 540pt 이상)에서는 공식 Tesla 앱처럼 두 영역(왼쪽 메뉴, 오른쪽 Live 클러스터와 아래의 빠른 제어)이 나오고,
**바깥 화면**은 지금까지처럼 탭 다섯 개다. 시뮬레이터에서는 펼친 상태의 안쪽 화면(`simctl io <기기> screenshot --display=3`)과 iPad로 두 영역 배치를 확인했고, 접기·펼치기 전환 중 상태 유지는 실기기에서 확인한다.
Xcode 27.2 `iPhone Duo` 프로필 기준으로 **바깥 화면 466 x 678pt, 안쪽 화면 669 x 951pt**(둘 다 3배)이다. 안쪽 화면의 오른쪽 도크 안전 영역을 뺀 너비가 540pt 아래로 내려가면 안쪽 화면도 탭 배치가 된다. 그렇다면 어느 너비로 보였는지 적어 임계값(`DuoLayout.twoPaneMinWidth`)을 다시 정한다.
차량 연결 없이도 화면 배치는 확인할 수 있고, 빠른 제어가 켜지는 조건은 키·제어 탭 규칙과 같다(키가 등록된 차량에 연결해야 켜진다).

| # | 확인 | 할 일 | 기대 |
|---|---|---|---|
| D1 | 바깥 화면(접은 상태) | 접은 채 앱을 연다. 다섯 탭을 차례로 본다 | 이전 빌드와 같은 탭 다섯 개. Live, Query, Log, Control, 키·제어 모두 보인다. Live 탭의 차는 위에서 본 사진이고 열린 부위는 빨간 아이콘이다. 오른쪽 도크 아래에 컨트롤이 깔리지 않는다 |
| D2 | 안쪽 화면(편 상태) 첫 화면 | 펼친 채 앱을 연다. 폰을 라이트 모드로 둔 채로도 본다 | 두 영역. **왼쪽**: 큰 제목(키 별명이 있으면 별명, 없으면 Tesla), 그 아래 상태 한 줄(주차 중/주행 중 · 잠금 · 수면, 아는 것만), 채워진 카드 둘(Live 상세, 키·제어, 오른쪽 화살표), 카드 없는 줄(잠금, 문·트렁크, 수면, 재실, 주행. 값이 없으면 `—`), Query, Log, Control 줄, 맨 아래 앱 빌드. **오른쪽**: 연결 상태 줄과 톱니, 기어 P R N D, 속도, 비스듬히 본 차량 사진(앞이 왼쪽 아래) 위의 잠금 아이콘(가운데, 지붕까지 가는 세로선), 왼쪽 위 "열기/전면"과 오른쪽 위 "열기/닫기" 위 "트렁크" 글자(각각 가는 세로선으로 차 앞·뒤), 차 뒤 옆의 충전구 번개(회색, 열리면 빨강), 아래 동작 줄(깨우기, 트렁크 닫기). 배터리, 공조, 위치, 카메라, 모델명은 없다. 폰이 라이트 모드여도 항상 다크 모드라 검은 바탕이다. **오른쪽 도크가 가리는 글자나 버튼이 없다**(톱니, 말풍선, 동작 줄 맨 오른쪽을 눈으로 확인) |

| D11 | 오른쪽 탭 막대 | 안쪽 화면 오른쪽 가장자리를 본다. Query, Log, Control, 키·제어, Live 를 차례로 누른다 | 시스템 탭 막대가 오른쪽 가장자리의 상태·센서 도크 **아래** 세로로 있고 아무것도 가리지 않는다. 탭을 고르면 왼쪽 영역에 그 페이지가 열리고 차량은 그대로이며, 막대의 강조와 왼쪽 줄(열린 카드)이 같은 항목을 가리킨다. Live 를 고르면 첫 화면(메뉴)으로 돌아온다. 접으면 폰 탭에서 같은 탭이 선택되어 있다 |
| D12 | 속도(마지막 수동 Drive 조회) | 차를 깨워 연결한 뒤 Query 탭에서 **Drive** 를 한 번 누르고 Live 첫 화면을 본다. 연결을 끊었다 다시 맺은 뒤에도 본다 | 속도 칸에 원시 숫자, "단위 미확인", "n초 전 조회"가 나오고 왼쪽 "주행" 줄에 기어와 같은 속도가 나온다. 왼쪽 맨 아래에 주행거리(1/100마일 단위의 원시 값)가 같이 나올 수 있다. 앱이 스스로 `getState()` 를 부르지 않는다(Log 탭 `getState` 줄이 눌렀을 때만 생긴다). 연결이 바뀌면 속도는 다시 `—` 가 된다. 실패하거나 `Uncertain` 이면 이전 성공값이 남는다 |
| D13 | 차량 사진과 아이콘(안쪽 화면) | 안쪽 화면 오른쪽에서 사진을 본다. 문을 하나씩 열고(운전석 문과 뒤 운전석 문은 사진에서 보이는 쪽, 조수석 문과 뒤 조수석 문은 지붕 유리 먼 쪽 가장자리), 프렁크, 트렁크, 충전구도 하나씩 열고 닫는다. 폰을 라이트 모드로 둔 채 본다 | 앞이 왼쪽 아래인 비스듬한 차 사진. 열린 문마다 그 문 위치 옆에 짧은 선이 붙은 작은 **빨간 문 아이콘**이 뜨고 닫으면 사라진다(문이 돌아가지 않는다). 프렁크는 왼쪽 위 글자에서 내려온 선이 차 앞에, 트렁크는 오른쪽 위 글자의 선이 차 뒤에 닿는 곳에 빨간 아이콘이 더 뜬다. 충전구 번개는 닫혀 있으면 회색, 열리면 빨강이고 눌러도 아무것도 가지 않는다. 상태를 모르는 부위는 아이콘이 없다. 사진은 검은 화면과 이어지는 어두운 둥근 판 위에 놓인다(앱이 항상 다크 모드). 잠금 아이콘, 글자, 충전구 번개가 오른쪽 도크 안전 영역 안에 있다. **아이콘과 선 끝이 사진의 맞는 부위를 가리키는지** 눈으로 확인하고, 어긋나면 사진 이름과 부위를 적는다(좌표 표는 `ClusterPhoto.swift`) |

기록은 첫 줄에 **기기(iPhone Duo), iOS 버전, 앱 빌드(27)** 를 쓰고, 확인마다 보인 화면(두 영역/탭), 너비, 어긋난 점을 적는다. VIN은 적지 않는다.

**타임아웃 문구 확인 (빌드 27)**: 일부러 만들지 않는다. 시간이 다한 결과가 우연히 나오면 화면 문구를 그대로 옮겨 적는다.
- 명령 결과 줄(키·제어, Control)에서 `Timeout(afterSend=true)` 이면 "보냈을 수 있음 — 차가 실행했을 수 있으니 상태를 다시 조회하세요. 앱이 백그라운드에 있으면 BLE 쓰기가 느려져 시간이 다할 수 있습니다"가 보이고, 재조회 결과가 같은 줄 끝에 붙는다(다시 보내지 않았다).
- `afterSend=false` 이면 "실행되지 않았습니다: …"가 보인다(쓰기를 시작하기 전, 또는 차가 재시도를 요청한 뒤 기다리던 중).
- 앱을 백그라운드에 둔 채 폰을 잠갔다 풀기를 10분 반복해 두면(명령은 보내지 않는다) 주기 조회의 타임아웃이 자연스럽게 나올 수 있다(보고서 N4).

## 추가 카테고리 확인 (SFR-023, 빌드 27)

빌드 27(`TeslableSampleDevice`, 버전 0.5.0)을 설치한다. Query 탭 **상태 진단**에 `Drive`, `Media`, `MediaDetail` 말고 **9개 버튼**이 더 생겼다: `Charge`, `Climate`, `Location`, `Closures`, `TirePressure`, `SoftwareUpdate`, `ChargeSchedule`, `PreconditioningSchedule`, `ParentalControls`. 한 번 누를 때 범주 하나만 보내고(합친 요청 없음) 자동 조회는 없다. 규칙: `samples/documents/md/04-monitor-app.md` §State diagnostics. 사용 문서: `14-lib-reading-state.md` A8.1(범주 표), A8.3(없는 값은 0이 아니다, 결과를 로그에 남기지 않는다), A8.4(위치 좌표), `16-lib-errors.md` §`getState` results, §Response size limit on `getState`.

**위 "다음 수집 순서"(#118)의 N1 규칙을 그대로 지킨다**: 다른 BLE 앱과 Tesla 앱을 완전히 종료하고, 차는 직접 깨우고, 폰은 잠금을 푼 채 앱을 앞 화면에 두고, Live 탭 수면이 `AWAKE` 일 때만 누른다. `wakeUp()` 을 부르는 버튼은 없다. 차가 잠들면 버튼이 꺼진다.

**먼저 `Drive`, `Media`, `MediaDetail` 로 연결이 정상인지 한 번씩 본 뒤**(이미 #118 순서를 끝냈다면 생략), 아래 순서로 **각 범주를 한 번씩** 누른다. 누르기 전에 Log 탭에 Mark를 남긴다(예: `cat CHARGE`). 같은 범주를 되풀이하지 않는다(응답 크기와 `Uncertain` 비율을 보려면 별도 수집으로 한다).

| 순서 | Mark | 누를 버튼 | 화면 값을 차량 화면·타이어 표시와 맞춰 본다 |
|---|---|---|---|
| 1 | `cat CHARGE` | Charge | **배터리 잔량(%)** 이 차량 화면 배터리 %와 같은가. 충전 상태, 충전 한도(%), 충전 포트 문/걸쇠. 충전 중이면 충전 전력·전압·전류와 완충까지(분). **주행 가능 거리**는 단위가 확인되지 않았다(`단위 미확인`). 차량 화면의 거리 숫자와 같은 값인지, 마일인지 km인지 적는다 |
| 2 | `cat CLIMATE` | Climate | **실내·실외 온도(°C)** 가 차량 화면과 같은가. 설정 온도는 단위가 확인되지 않았다(`단위 미확인`): 차량 화면의 설정 온도와 같은 숫자인지 적는다. 공조 켜짐, 배터리 히터, 시트 히터 |
| 3 | `cat LOCATION` | Location | **위도·경도**가 지금 차 위치와 맞는가(지도 앱과 비교, 소수 6자리). 좌표 출처 줄에 `native_*` 인지 `latitude/longitude` 인지, 좌표계(WGS/GCJ)가 보인다. 방향, `gps_as_of`(단위 미확인: 시각과 같은 에폭 초인지), 위치 이름. **좌표와 위치 이름은 화면에만 있다**: Log 탭에는 `present=[…]` 필드 이름만 나와야 한다. 화면을 캡처하면 위치가 담기고 앱 전환 화면(앱 스위처)에도 마지막 화면이 보이니, 조회한 뒤에는 다른 화면(Live 탭 등)으로 옮기고 캡처는 공유하지 않는다 |
| 4 | `cat CLOSURES` | Closures | 문, 창문, 프렁크/트렁크의 열림·닫힘이 실제와 같은가(문 하나를 열어 두고 한 번 더 누르는 것은 선택). 잠금, 센트리 모드, 운전자 존재가 차량 화면과 같은가. 선루프가 없는 차는 선루프 줄이 `—` |
| 5 | `cat TIRE` | TirePressure | **네 바퀴 압력(bar)** 이 차량 화면의 타이어 압력(차량이 psi 로 보이면 환산해서)과 맞는가. 바퀴마다 마지막 수신 시각, 하드/소프트 경고, 권장 압력(앞/뒤). 경고 요약 줄이 실제 경고 표시와 같은가 |
| 6 | `cat SWUPDATE` | SoftwareUpdate | **업데이트 상태**와 **버전**이 차량 화면의 소프트웨어 항목과 같은가(업데이트가 없으면 상태나 버전이 `—` 일 수 있다). 다운로드·설치 % |
| 7 | `cat CHGSCHED` | ChargeSchedule | 일정 수, 활성 일정 수, 다음 일정 있음. 차량 화면의 충전 일정 개수와 같은가. 일정 이름과 위치는 앱이 읽지 않는다 |
| 8 | `cat PRECOND` | PreconditioningSchedule | 일정 수, 활성 일정 수, 다음 일정 있음. 차량 화면의 예약 공조와 같은가 |
| 9 | `cat PARENTAL` | ParentalControls | 자녀 보호 활성, PIN 설정됨, 속도 제한(mph). 기능을 쓰지 않는 차는 대부분 `—` 일 수 있다 |

각 버튼마다 적는다: **결과 종류**(`Success` / `Uncertain` / `Failure`), **소요 시간(ms)**, 화면의 **받은 필드** 줄, 값이 차량 화면과 **맞았는지**(맞음 / 다름 + 어떻게 다른지), `—` 로 남은 필드. 그리고:
- **응답 크기**: Log 탭 `observe` 줄(`[reply:infotainment] <N>B …`)의 크기를 적는다. `Uncertain` 과 "응답이 너무 커서…(RESPONSE_MTU_EXCEEDED)" 가 나온 범주는 **그 사실과 범주 이름**을 적는다(앱은 다시 보내지 않는다). 더 작은 요청은 없다(`16-lib-errors.md` §Response size limit).
- **시간 초과**(`Uncertain(Timeout)` 또는 `Failure(Timeout)`): 화면 문구 그대로 옮겨 적고, 다시 누른 결과를 적는다.
- **값이 없는 범주**(`Success` 인데 받은 필드가 `없음`): "빈 응답" 으로 적는다. 0이나 정상으로 읽지 않는다.
- **로그 확인**: 끝난 뒤 Log 탭 `query` 줄에 좌표, 위치 이름, 압력, 버전 같은 값이 **없는지**(`present=[…]` 의 필드 이름만 있는지) 본다. `grep '"kind":"query"' samples/logs/ios/<날짜>/logs/*.jsonl | grep -E '[0-9]+\.[0-9]{4,}'` 가 0건인지 확인한다(소수점 좌표 모양. 관찰 줄의 다른 숫자는 이 확인과 상관없다).
- 끝나면 `tools/samples/pull-monitor-logs.sh ios` 로 로그를 가져와 `samples/logs/` 에 두고(커밋 금지) `protocol-analyst` 에게 넘긴다. 범주별 `present=[…]` 로 어떤 필드를 차가 실제로 보내는지 볼 수 있다.

## 링크 안정화 시나리오 (#124 N1~N6, 빌드 27)

빌드 18 분석의 유력 가설을 확인하는 기록이다. 근거: `docs/analysis/2026-11-01-build18-link-health.md` §Next scenarios, 이슈 #124. 결과는 #125(읽기 조회 재전송), #126(백그라운드 재연결), #129(문서 나머지)의 입력이 된다. 위 "응답 인증 수집"의 N1·N2와 이름이 겹치지 않게 여기서는 **L1~L6** 으로 부른다(괄호 안이 #124 번호).
