Message encoding: RoutableMessage

All messages are encoded with Protocol Buffers, and the top-level type is UniversalMessage.RoutableMessage (protobuf/universal_message.proto). A typical request looks like this (binary fields shown in hex).

}
from_destination {

Decoding messages with protoc

You can decode the hex printed in the TX: log of tesla-control -ble -debug list-keys from the pkg/protocol directory as follows.

echo 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805 \
    | xxd -r -p \
    | protoc --decode=UniversalMessage.RoutableMessage -I protobuf protobuf/*.proto
to_destination {
  domain: DOMAIN_VEHICLE_SECURITY
}
from_destination {
  routing_address: "\nyb\301\r8\266\035\322\247r\'\200\244\360\226"
}
protobuf_message_as_bytes: "\n\002\010\005"
uuid: "\005QOWak\314\201\250\316\017\235{H2)"

Because the message is addressed to VCSEC, protobuf_message_as_bytes is a VCSEC.UnsignedMessage.

printf "\n\002\010\005" | protoc --decode=VCSEC.UnsignedMessage -I protobuf protobuf/*.proto
# InformationRequest {
#   informationRequestType: INFORMATION_REQUEST_TYPE_GET_WHITELIST_INFO
# }

Conversely, you can build payloads with protoc --encode (see the AES-GCM example below). You can also generate bindings for other languages from the *.proto files.

Protocol concepts: domains, time, roles

Domains

Vehicle subsystems have different public keys, so handshakes and session state are managed separately per domain. VCSEC (DOMAIN_VEHICLE_SECURITY = 2) handles locking, remote start, the trunk and the keychain, while Infotainment (DOMAIN_INFOTAINMENT = 3) handles everything else. VCSEC is reachable over BLE even while Infotainment is asleep.

Time

Each domain has its own clock and represents time as an (epoch_id, timestamp) pair. epoch_id is a random 16-byte value generated at boot, and timestamp is an integer number of seconds since the epoch began. The client tracks the difference between the domain clock and its local clock to compute command expiration times (expires_at). The SDK sets timeZero from SessionInfo.clock_time and the time of receipt, and does not use session info for clock correction if it arrives more than AllowedLatency (4 seconds for BLE, 10 seconds for the internet) after the request.

Roles

Each public key has a role (Owner, Driver, Fleet Manager, Vehicle Monitor, Charging Manager, Guest, Service); see the role table in Chapter 1. Per-role permissions can change with firmware updates.

Metadata serialization (TLV)

Authentication must bind a message to metadata such as the VIN, so a canonical serialization of the metadata that can be used as hash input is required. Each item is encoded as tag(1B) || length(1B) || value, and tag values are defined in Signatures.Tag.

                  = 0x02 || 0x03 || 0x61 0x62 0x63
                  = 0x0203616263

TLV(COUNTER: 100) = TAG_COUNTER || LEN(uint32) || 0x00000064    (integers are 4-byte big-endian)
                  = 0x05 || 0x04 || 0x00000064
                  = 0x050400000064

SERIALIZE({COUNTER: 100, VIN: "abc"})
                  = TLV(VIN) || TLV(COUNTER) || 0xFF               (sorted by tag ascending, concatenated, 0xFF appended)

In the Go implementation (internal/authentication/metadata.go), items must be added in ascending tag order (errOutOfOrderMetadata), value length must be 255 bytes or less (ErrMetadataFieldTooLong), and nil values are skipped. Checksum(message) appends 0xFF and then hashes the message bytes after it.

Handshake

This assumes the client public key C is already enrolled on the vehicle. Key enrollment (bootstrapping) is done with an existing key or an NFC card, and the Tesla Service key is the root of trust (Chapter 2, pairing).

Request

Send a RoutableMessage with session_info_request.public_key = ENCODE_PUBLIC(C) to the domain you will send commands to.

Key agreement (ECDH)

S = (Sx, Sy) = ECDH(c, V) = ECDH(v, C)

Do not implement it yourself

Use vetted libraries such as OpenSSL or Go crypto for ECDH and AES-GCM. The protocol always uses the binary value of K; the hex above is for display only.

Response authentication (verifying session_info_tag)

The client must authenticate the session info response so that a MITM attacker cannot obtain commands with a longer expiration time. If the attacker changes the public key, the vehicle rejects the commands; if the attacker keeps the public key and changes anything else, the client rejects the response during tag verification.

  1. Derive the session info authentication key. SESSION_INFO_KEY = HMAC-SHA256(K, "session info"). The string is an ASCII literal. 
    export SESSION_INFO_KEY=$(echo -n "session info" | openssl dgst -sha256 -mac hmac -macopt hexkey:"$K")
# fceb679ee7bca756fcd441bf238bf2f338629b41d9eb9c67be1b32c9672ce300
  2. Serialize the metadata. TAG_SIGNATURE_TYPE = SIGNATURE_TYPE_HMAC(6), TAG_PERSONALIZATION = VIN, TAG_CHALLENGE = request uuid. 
    VIN = 5YJ30123456789ABC
METADATA = 00 01 06
        || 02 11 35594a3330313233343536373839414243
        || 06 10 1588d5a30eabc6f8fc9a951b11f6fd11
        || ff
       = 000106021135594a333031323334353637383941424306101588d5a30eabc6f8fc9a951b11f6fd11ff
  3. Compute the tag. HMAC-SHA256(SESSION_INFO_KEY, METADATA || session_info) 
    echo "$METADATA$SESSION_INFO" | xxd -r -p | openssl dgst -sha256 -mac hmac -macopt hexkey:"$SESSION_INFO_KEY"
# 996c1fe38331be138f8039c194b14db2198846ed7d8251e6749284d7b32ea002
  4. Compare. Compare it with the response's signature_data.session_info_tag.tag using a constant-time comparison (Go: hmac.Equal). Discard the response if they do not match.

In Go, internal/authentication.NewAuthenticatedSigner performs this verification and NativeSession.SessionInfoHMAC computes the tag. Before tag verification, the SDK discards session info whose uuid does not belong to a recent request or that arrived after AllowedLatency.

Command authorization

After the handshake, the client has the domain clock (epoch, timestamp), an anti-replay counter and the shared key K. It builds the command protobuf P (VCSEC.UnsignedMessage or CarServer.Action) and then serializes the metadata M below.

HMAC-SHA256 authentication

  1. Derive the key: K' = HMAC-SHA256(K, "authenticated command").
  2. Build a RoutableMessage with payload.protobuf_message_as_bytes = P.
  3. signature_data.signer_identity.public_key = ENCODE_PUBLIC(C).
  4. tag = HMAC-SHA256(K', M || P).
  5. Populate signature_data.HMAC_Personalized_data with epoch, counter, expires_at and tag.
message HMAC_Personalized_Signature_Data {
    bytes   epoch       = 1;
    uint32  counter     = 2;
    fixed32 expires_at  = 3;
    bytes   tag         = 4;
}

AES-GCM encryption

  1. Use the 128-bit key K directly as the AES-GCM key.
  2. A random 12-byte nonce (IV). Any other length yields MESSAGEFAULT_ERROR_IV_INCORRECT_LENGTH.
  3. AAD (Associated Authenticated Data) = SHA256(M).
  4. Encrypt P to obtain the ciphertext x and a 16-byte tag.
  5. payload.protobuf_message_as_bytes = x, signer_identity.public_key = ENCODE_PUBLIC(C).
  6. Populate signature_data.AES_GCM_Personalized_data with epoch, nonce, counter, expires_at and tag. The epoch may be omitted, but including it gets you a more specific error on a mismatch.

FLAG_ENCRYPT_RESPONSE

When this bit is set, firmware 2024.38 and later encrypts the response payload. Older firmware ignores the flag, so always set it without needing to check the firmware version. The flag is included in the metadata and authenticated, so an attacker cannot clear it.

Session cache and desync recovery

Session cache

Clients that do not run continuously should store session state and the local/vehicle clock offset on disk. A cache reduces the latency of the first command and also reduces the number of Fleet API calls. Even if the cache is stale, the recovery procedure below costs the same as a single handshake, so trusting the cache optimistically has no downside. SDK: pkg/cache.SessionCache, Vehicle.UpdateCachedSessions/LoadCachedSessions, and TESLA_CACHE_FILE in the CLI.

Desync recovery

When an authentication error may be caused by a synchronization problem (for example, the epoch changed because Infotainment rebooted), the vehicle attaches up-to-date session info to the error message. The client MUST discard the session info if any of the following is true.

  • It has not sent a request with that request_uuid in the last few seconds.
  • The session info HMAC tag is incorrect.
  • Its clock_time is earlier than that of previously authenticated session info in the same epoch.

If all of these are false, the client MUST update its session state. When updating, it MUST NOT roll back the anti-replay counter unless the epoch has changed. This rule exists less as a security requirement (rejecting replays is the vehicle's responsibility) than to tolerate unreliable connections and out-of-order delivery. Go: Dispatcher.checkForSessionUpdate → session.processHello → Signer.UpdateSignedSessionInfo. After updating the session, the dispatcher still forwards the error response to the receiver, and Vehicle.Send resends with the updated session if the error is one for which ShouldRetry holds (INVALID_SIGNATURE, INVALID_TOKEN_OR_COUNTER, INCORRECT_EPOCH, TIME_EXPIRED, etc.).

Response handling

No response does not mean it did not execute

If you sent a command but received no response, the vehicle may already have received and executed it. This is especially common on unreliable networks. In such cases the SDK returns an error for which protocol.MayHaveSucceeded(err) == true, and does not retry automatically.

Protocol-layer errors

Responses are also RoutableMessages. When there is a protocol-layer error, signedMessageStatus.signed_message_fault is set. The codes and how to handle them are in the MessageFault_E comments in universal_message.proto and in Chapter 9. Go's protocol.GetError converts this into a *RoutableMessageError (or ErrKeyNotPaired for UNKNOWN_KEY_ID), and also maps session_info.status == KEY_NOT_ON_WHITELIST to ErrKeyNotPaired and operation_status == WAIT to ErrBusy.

Response decryption

If the response contains signature_data.AES_GCM_Response_data, protobuf_message_as_bytes is ciphertext; otherwise it is plaintext.

message AES_GCM_Response_Signature_Data {
    bytes  nonce   = 1;
    uint32 counter = 2;
    bytes  tag     = 3;
}

Request hash

The client must compute and keep a "request hash" for each request it sends. It is 1 byte for the authentication method || the request's authentication tag.

  • AES-GCM requests: 0x05 || AES_GCM_Personalized_data.tag (16-byte tag → 17 bytes total)
  • HMAC requests: 0x08 || HMAC_Personalized_data.tag (32-byte tag → 33 bytes total)
  • Requests sent to VCSEC are truncated to 17 bytes: 1 method byte + the first 16 bytes of the MAC. AES-GCM tags are 16 bytes to begin with, so this affects only HMAC requests

Go: internal/authentication.RequestID(message). The dispatcher stores it on the receiver as requestID during Send.

Counter verification

The client must verify that the response's counter has not already been used by a previous response to the same request. A single request can trigger multiple responses, and they can arrive out of order. Omitting this check leaves the client vulnerable to replay attacks. Go: each receiver has an authentication.SlidingWindow, and in session.decrypt the response is discarded with ErrReplayedResponse if antireplay.Update(counter) returns false (internal/authentication/window.go).

Response metadata

Decrypt with AES-GCM using key K, the response's nonce and tag, and the serialization of the metadata below as AAD. Unlike requests, flags are always included, even when 0, and the fault is encoded as a 32-bit big-endian value.

Application-layer responses

Infotainment

Parse protobuf_message_as_bytes as CarServer.Response. The status code is Response.actionStatus.result; if it is OPERATIONSTATUS_ERROR, the reason is in result_reason.plain_text. Go: Vehicle.getCarServerResponse converts it to NominalError{"car could not execute command: <reason>"}. The result of a state query is Response.vehicleData.

Parse it as VCSEC.FromVCSECMessage. VCSEC sends up to three responses per request. Fleet API clients receive only the final response, but BLE clients must determine for themselves which response is final.
