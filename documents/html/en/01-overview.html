1. System Overview

Explains what problem the Tesla Vehicle Command SDK solves, which components it consists of, and how a single command travels to the vehicle.

Why a new protocol

Tesla vehicles support a protocol that provides end-to-end command authentication. Commands are authenticated (or encrypted) with the client's private key all the way to the vehicle, and the vehicle verifies commands only against public keys registered in its keychain. Not even Tesla's servers can forge a command.

  • The legacy Owner API stops working once vehicles start requiring end-to-end authentication. Applications built on the Owner API can be ported directly to this SDK, or can keep their REST calls unchanged by placing this repository's HTTP proxy in front.
  • Pre-2021 Model S/X vehicles do not support this protocol. The Fleet API continues to work for these vehicles; when the proxy receives ErrProtocolNotSupported (HTTP 422), it remembers that VIN and forwards subsequent requests to the REST API as-is.
  • This SDK is the official implementation, written in Go. Because the protocol specification (pkg/protocol/protocol.md) and protobuf definitions are public, it can also be implemented in other languages (see ../md/10-porting-guide.md).

Two-stage authentication model

To send a command over the internet path, you must pass two mutually independent authentications. The BLE path requires only the second stage.

  1. Tesla server authentication (OAuth). Tesla's servers forward messages to the vehicle only when the client presents a valid OAuth access token. The regional Fleet API host is determined from the token's aud/ou_code claims (pkg/account). This stage does not exist on BLE.
  2. Vehicle authentication (private key). The vehicle executes a command only when it is authenticated with a public key registered in its keychain. Keys are NIST P-256 ECDH keys, registered either by the user approving with an NFC card (BLE) or through a https://tesla.com/_ak/<domain> link in the Tesla app.
BLE does not require OAuth

A direct BLE connection does not go through Tesla's servers, so you can send commands with only the VIN and a private key, without an OAuth token. However, the vehicle may reject some commands with MESSAGEFAULT_ERROR_COMMAND_REQUIRES_ACCOUNT_CREDENTIALS, and keys with the Fleet Manager role cannot send commands over BLE as of 2023.38.

Domains: VCSEC and Infotainment

A vehicle contains independent subsystems called domains. Each domain has its own public key, clock (epoch + timestamp), and anti-replay counter, so every domain requires its own handshake and session.

VCSEC does not sleep

VCSEC responds over BLE even while Infotainment is in power-saving mode. VCSEC commands such as body-controller-state, wake, and lock can therefore run without waking the vehicle. Restricting the domains, as in StartSession(ctx, []Domain{DomainVCSEC}), avoids waking Infotainment unnecessarily. On the other hand, due to memory constraints VCSEC does not include request_uuid in responses, counters must arrive in order, and concurrent requests should be avoided.

The vehicle assigns a role to each registered public key, and the commands it can authorize depend on that role. The values are defined in pkg/protocol/protobuf/keys.proto.

Layered architecture

  • Connector is a datagram transport that only exchanges byte arrays. It knows nothing about authentication or protobuf. By implementing it yourself you can plug in other transports (for example, a serial link or an in-memory pipe for tests).
  • Dispatcher wraps the Connector, encodes/decodes RoutableMessage, maintains per-domain sessions (session), and delivers incoming messages to the waiting receiver by routing_address (plus request_uuid for Infotainment). When the vehicle sends a new session_info along with an error, it updates the session automatically.
  • Vehicle is the set of methods visible to the user. Each method builds the protobuf appropriate for its domain, sends it with Send (including retries), and converts the response into a protocol.Error.

Lifecycle of a single command

This is what happens when tesla-control -ble lock runs. On the internet path, steps 1–2 are replaced by account.GetVehicle.

  1. Scan: computes the advertised name from the first 8 bytes of the VIN's SHA1 and looks for a matching advertisement.
  2. GATT connection: finds service 00000211-…, subscribes to the write characteristic (0212) and the notification characteristic (0213), then negotiates the MTU.
  3. Connect: Dispatcher.Start launches the receive goroutine. If a session cache exists, per-domain sessions are restored at this point.
  4. StartSession: for each domain without a cache entry, sends a SessionInfoRequest, verifies the HMAC tag of the response, and derives the shared key K via ECDH. If a cache entry exists, this round trip is skipped.
  5. Send: authorizes the command protobuf together with metadata using AES-GCM (BLE) or HMAC (internet) and transmits it. Errors for which protocol.ShouldRetry is true (Busy, counter/epoch mismatch, etc.) are retried automatically after RetryInterval.
  6. Response: if the vehicle sends new session information along with an error, the dispatcher updates the session; if the response is encrypted, it goes through decryption and counter verification, and the Vehicle method returns the final result as an error type.
