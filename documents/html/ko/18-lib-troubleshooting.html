18. 문제 해결

스캔, 연결, 키에서 자주 생기는 문제와 흔한 원인, 대처법을 정리합니다. 페어링과 명령에 관한 문제는 M4와 M5에서 추가됩니다. 개발용 관찰 로그는 끝에서 설명합니다.

스캔과 연결

증상가능한 원인대처
PermissionDenied블루투스 권한이 없거나 거부됨Android: 런타임에 BLUETOOTH_SCAN과 BLUETOOTH_CONNECT를 요청. iOS: NSBluetoothAlwaysUsageDescription을 추가하고, 거부되었으면 사용자를 설정으로 안내
BluetoothOff블루투스가 꺼져 있음사용자에게 켜 달라고 요청
스캔에서 아무것도 찾지 못하고, 연결이 ScanTimeout으로 끝남범위 밖, 잘못된 VIN, 또는 iOS 시뮬레이터가까이 가고, VIN을 확인하고(차량은 VIN에서 만든 이름으로 찾음), 실기기를 사용
MaxConnectionsExceeded차량에 이미 블루투스 연결이 세 개 있음다른 휴대폰이나 앱의 연결을 끊고, 내 앱에서는 항상 disconnect()를 호출
ConnectFailed가 계속 발생약한 신호 또는 바쁜 차량라이브러리가 이미 30초 동안 재시도함. 나중에 다시 시도
connection이 Disconnected로 바뀜링크가 끊김disconnect()를 호출한 뒤 다시 연결

디버그 로깅

  • TeslaBleConfig에 로거를 전달하세요. 기본값은 아무것도 기록하지 않습니다.
  • DebugLogger()는 Android에서는 Logcat, iOS에서는 통합 로그, JVM에서는 java.util.logging에 기록합니다. 개발 빌드에서만 사용하세요.
  • 로그를 다른 곳으로 보내려면 TeslaLogger를 구현하세요. 레벨, 태그, 지연 생성되는 메시지를 받는 함수 하나입니다. 로거가 예외를 던져도 라이브러리는 멈추지 않습니다.
  • 레벨: DEBUG(송수신 원시 바이트), INFO(연결과 세션), WARN(누락되거나 버려진 메시지), ERROR(라이브러리가 복구할 수 없는 상황).
로그에 절대 나오지 않는 것

라이브러리는 VIN을 마스킹하며 개인키, 세션 키, nonce, 복호화된 내용을 기록하지 않습니다. 앱 자체의 로그도 그렇게 유지하세요. vin.value를 출력하지 말고, 로그를 공유하기 전에 VIN을 마스킹하세요.

문제를 보고할 때는 iOS 샘플의 "결과 전체 복사" 버튼으로 얻은 로그와 DebugLogger를 사용하세요. 프로브나 진단 진입점은 없습니다.

관찰 로그 (개발용)

개발하는 동안 라이브러리는 버리는 메시지마다, 그리고 차량 보안 도메인의 응답마다 요약 한 줄을 남길 수 있습니다. 차량이 요청 없이 보내는 것이 무엇인지 보여 줍니다. 동작은 바뀌지 않습니다. 라이브러리는 그 메시지를 여전히 버립니다(vehicle.events는 M5에서 계획).

  • 태그 observe, 레벨 DEBUG. DEBUG를 버리는 로거는 이 줄을 만들지도 않습니다. DebugLogger()나 직접 만든 TeslaLogger로 볼 수 있습니다. iOS 샘플의 관찰 모드는 이 줄만 모읍니다.
  • 형식: [지점] NB from=… to=… request_uuid=… payload=…. NB는 받은 프레임의 크기입니다.
항목값
[drop:unparseable]프레임이 라우팅 메시지로 해석되지 않았습니다. 줄 끝에 reinterpreted=…(또는 undecodable)이 붙습니다
[drop:missing-source]출발지가 없습니다. 줄 끝의 reinterpreted=…는 같은 바이트를 감싸지 않은 FromVCSECMessage로 읽은 결과입니다
[drop:missing-destination]목적지가 없습니다(차량이 먼저 보내는 푸시의 전형)
[drop:to-domain]클라이언트 주소가 아니라 도메인으로 보낸 메시지입니다
[drop:malformed]요청 UUID 길이 또는 주소 길이가 잘못되었습니다
[drop:no-handler]올바른 주소지만 그 주소의 열린 요청이 없습니다
[drop:handler-closed], [drop:queue-full]짝이 되는 요청이 그사이 닫혔거나 응답 큐가 가득 찼습니다
[reply:vcsec]열린 요청에 전달된 보안 도메인 응답입니다
from=, to=domain(DOMAIN_X), address(16B, self|open-request|other)(to=만), none, empty
payload=FromVCSECMessage{…}, Response{fields=[…]}, encrypted(NB), NB, none
unknownFields=[n]전송 중에는 있었지만 생성된 프로토콜이 모르는 필드 번호입니다
absent=[…]차량이 보내지 않은 차량 상태의 부분입니다(closureStatuses, detailedClosureStatus)
key=sha1:xxxxxxxx공개키: SHA-1의 앞 4바이트만 적습니다

한계와 규칙

  • enum 값이 빠진 것과 0번 값은 구분할 수 없습니다. 잠금 상태가 없으면 VEHICLELOCKSTATE_UNLOCKED로 읽힙니다(sleep, presence는 UNKNOWN). absent로 알 수 있는 것은 메시지 부분뿐입니다.
  • 암호화된 내용과 세션 정보는 길이만, 공개키는 SHA-1 앞부분만 적습니다. VIN과 복호화된 내용은 나오지 않습니다. 줄을 추가할 때도 이 규칙을 지키세요.
  • BLE 전송은 연결마다 수신 버퍼 넘침을 셉니다. 버려진 메시지마다 ERROR로 Dropping received message because inbox is full (dropped N since connect)를 남기고, 링크가 끝나면 WARN으로 BLE inbox overflowed N time(s) during this connection 한 줄을 남깁니다(N이 0보다 클 때만).
  • DebugLogger는 DEBUG에서 BLE 원문 바이트(TX:, RX:)도 출력합니다. 이런 플랫폼 로그는 공유하지 마세요.
