8. HTTP Proxy

tesla-http-proxy is an HTTPS server that accepts REST requests in Fleet API format, converts them into end-to-end authenticated commands signed with a private key, and delivers them to the vehicle via Tesla's servers. Use it to migrate existing Owner API clients with minimal changes.

How it works

The proxy handles two credentials: the OAuth token sent by the client (authenticates to Tesla's servers) and the private key the proxy loads at startup (authenticates to the vehicle). The public key of that private key must already be enrolled on the user's vehicle.

For the procedure to obtain an OAuth token (partner token → user authorization → code exchange), follow doc/authorization.puml and the Fleet API documentation. The proxy does not issue or refresh tokens.

TLS certificates

TLS cannot be disabled on the proxy. Create a self-signed certificate for development with OpenSSL.

mkdir config
openssl req -x509 -nodes -newkey ec \
    -pkeyopt ec_paramgen_curve:secp384r1 \
    -pkeyopt ec_param_enc:named_curve  \
    -subj '/CN=localhost' \
    -keyout config/tls-key.pem -out config/tls-cert.pem -sha256 -days 3650 \
    -addext "extendedKeyUsage = serverAuth" \
    -addext "keyUsage = digitalSignature, keyCertSign, keyAgreement"

Make clients trust this certificate with --cacert config/tls-cert.pem. In production, use a certificate from a public CA and put the full chain in -cert.

Startup is refused if the TLS key and the command authentication key are the same key

main.go reads the -tls-key file with protocol.LoadPublicKey and compares it with the command key's public key. If they match, it prints It is unsafe to use the same private key for TLS and command authentication. and exits. This is one reason the example above uses secp384r1 (P-384) (the command key is P-256).

Docker deployment

The image tesla/vehicle-command contains the five tools on a distroless runtime, and its default entrypoint is tesla-http-proxy. Mount the private key as a file (the container has no system keyring).

# docker run
docker pull tesla/vehicle-command:latest
docker run --security-opt=no-new-privileges:true -v ./config:/config -p 127.0.0.1:4443:4443 \
    tesla/vehicle-command:latest \
    -tls-key /config/tls-key.pem -cert /config/tls-cert.pem -key-file /config/fleet-key.pem -host 0.0.0.0 -port 4443

# docker compose (docker-compose.yml in the repository)
docker compose up

The repository's docker-compose.yml applies the same settings through environment variables.

services:
  tesla_http_proxy:
    image: tesla/vehicle-command:latest
    ports:
      - "4443:4443"
    environment:
      - TESLA_HTTP_PROXY_TLS_CERT=/config/tls-cert.pem
      - TESLA_HTTP_PROXY_TLS_KEY=/config/tls-key.pem
      - TESLA_HTTP_PROXY_HOST=0.0.0.0
      - TESLA_HTTP_PROXY_PORT=4443
      - TESLA_HTTP_PROXY_TIMEOUT=10s
      - TESLA_KEY_FILE=/config/fleet-key.pem
      - TESLA_VERBOSE=true
    security_opt:
      - no-new-privileges:true
    volumes:
      - ./config:/config

-host 0.0.0.0 is unavoidable inside a container, but prevent external exposure by binding the host port mapping to loopback, as in 127.0.0.1:4443:4443, or by placing an authenticating proxy in front.

Routing rules

(*proxy.Proxy).ServeHTTP handles requests in the following order, based on the request path.

OrderPathHandling
0All requestsLimits the body size to 1 MiB (maxRequestBodyBytes). 413 if exceeded
1GET /health200 OK without authentication. 405 for other methods
2All other paths403 if there is no Authorization: Bearer <token>. Determines the Fleet API host from the token's aud/ou_code (account.New). If a host was previously updated by a 421, that host is used
3POST /api/1/vehicles/{VIN}/command/{name}404 if the VIN is not 17 characters (expected 17-character VIN in path (do not user Fleet API ID)). Forwarded if the VIN is marked as not supporting the protocol. Otherwise, handleVehicleCommand executes an end-to-end authenticated command. Forwarded on ErrCommandUseRESTAPI
4/api/1/vehicles/fleet_telemetry_configSigns the body's config as a JWS and forwards it to /api/1/vehicles/fleet_telemetry_config_jws
5All remaining paths, including other /api/1/*forwardRequest: copies headers, strips hop-by-hop headers, adds X-Forwarded-For, and forwards to the Fleet API over HTTPS. Both GET and POST
Use the VIN, not the Owner API ID

Legacy Owner API clients put a numeric vehicle ID in the URL. The proxy strictly requires a 17-character VIN on command/ paths. Other paths (for example vehicle_data) are forwarded as-is, so any format the Fleet API accepts works.

Response format and status codes

Command succeeded

{"response":{"result":true,"reason":""}}

Vehicle rejects the command (NominalError)

When the vehicle authenticates the command but cannot execute it (for example, already on, or not in park), the response follows Fleet API convention: HTTP 200 with result set to false and the cause in reason.

{"response":{"result":false,"reason":"car could not execute command: already_on"},"error":"","error_description":""}

Other errors

Signing Fleet Telemetry configuration

If you send an unsigned configuration to POST /api/1/vehicles/fleet_telemetry_config, the proxy creates a JWS with sign.SignMessageForFleet(key, "TelemetryClient", config) and forwards it to /api/1/vehicles/fleet_telemetry_config_jws as {"vins": [...], "token": "<jws>"}. If the configuration contains aud or iss, they are overwritten and a warning is logged. The result is the same as tesla-jws -fleet sign TelemetryClient.

curl --cacert config/tls-cert.pem \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    -X POST --data-binary "@telemetry.json" \
    "https://localhost:4443/api/1/vehicles/fleet_telemetry_config"

Internals

Per-VIN serialization
lockVIN holds a mutex per VIN so that commands to the same vehicle run sequentially. This is required because VCSEC rejects messages whose counters arrive out of order. Different VINs are processed in parallel.
Session cache
cmd/tesla-http-proxy keeps sessions for up to 10000 vehicles in memory (LRU) via proxy.New(ctx, key, 10000). Each command repeats acct.GetVehicle → Connect → StartSession → execute → Disconnect, but thanks to the cache a handshake happens only on the first command or when the session expires. Restarting the process clears the cache.
User-Agent
Passes tesla-http-proxy/1.1.0 (proxyProtocolVersion) to account.New as the app name.
Regional host selection
account.New picks, from the token's aud, an entry that starts with fleet-api. and has a Tesla domain suffix, preferring one that contains the ou_code (region). The default is fleet-api.prd.na.vn.cloud.tesla.com.
421 redirect
If a forwarded response is 421 with an Alt-Svc: h2="https://…" header, the proxy switches host and retries up to 2 times (MaxAttempts), remembering the new host per token sub. On the end-to-end command path, inet.Connection parses use base URL: https://… from the body to update it.
Timeout
-timeout (default 10 seconds) is the overall context for a single command. Within it, the SDK performs handshake retries and command retries.
Test hooks
Proxy.client (httpDoer) and Proxy.fetchVehicle (returns vehicleSession) are replaced in package-internal tests (pkg/proxy/proxy_test.go).

Security considerations

  • Do not bind to anything other than localhost (without authentication). The proxy has no client authentication. If anyone can reach it, excessive traffic may flow from your IP to Tesla's servers, which can get you rate-limited or blocked. At startup, nonLocalhostWarning warns about this.
  • There is no option to disable TLS. Because of past DIY deployments that exposed vehicles to the internet, no --insecure-style flag is provided, by design. To terminate TLS elsewhere, use pkg/proxy directly.
  • Private key file permissions. -key-file is the command authentication key. If it leaks, anyone can send commands to every vehicle it is enrolled on. Use 0600 permissions and the principle of least access.
  • OAuth tokens are not stored. The proxy uses the token in each request's header as-is. Token management is the caller's responsibility.

curl examples

export TESLA_AUTH_TOKEN=<access-token>
export VIN=<17-character VIN>
export CACERT=config/tls-cert.pem

# Health check (no authentication required)
curl --cacert $CACERT https://localhost:4443/health

# Forwarded endpoint: vehicle data
curl --cacert $CACERT \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    "https://localhost:4443/api/1/vehicles/$VIN/vehicle_data" | jq .

# Wake up (end-to-end command path; polls until online)
curl --cacert $CACERT -X POST --data '{}' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    "https://localhost:4443/api/1/vehicles/$VIN/command/wake_up"

# Command without arguments
curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/flash_lights"

# Commands with arguments
curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"percent": 80}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/set_charge_limit"

curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"driver_temp": 21.5, "passenger_temp": 21.5}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/set_temps"

curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"days_of_week":"weekdays","start_time":1320,"start_enabled":true,"end_time":360,"end_enabled":true,"lat":37.4,"lon":-122.1,"enabled":true}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/add_charge_schedule"

JSON parameter types are strict. Numbers must be JSON numbers, booleans must be true/false, and strings must be strings; any other type yields invalid X param (400). For each endpoint's parameters, see 7. Command Reference.

Embedding pkg/proxy and authentication middleware

cmd/tesla-http-proxy/main.go is a thin wrapper around pkg/proxy. To add client authentication, separate TLS termination, request logging, and so on, wrap proxy.Proxy (an http.Handler) in your own handler.

package main

import (
    "context"
    "crypto/subtle"
    "net/http"
    "time"

    "github.com/teslamotors/vehicle-command/pkg/protocol"
    "github.com/teslamotors/vehicle-command/pkg/proxy"
)

type authenticated struct {
    next   http.Handler
    apiKey string
}

func (a *authenticated) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    if r.URL.Path == "/health" {
        a.next.ServeHTTP(w, r)
        return
    }
    if subtle.ConstantTimeCompare([]byte(r.Header.Get("X-Api-Key")), []byte(a.apiKey)) != 1 {
        http.Error(w, "unauthorized", http.StatusUnauthorized)
        return
    }
    a.next.ServeHTTP(w, r) // The Authorization: Bearer header is passed through to the proxy unchanged
}

func main() {
    skey, err := protocol.LoadPrivateKey("config/fleet-key.pem")
    if err != nil { panic(err) }

    p, err := proxy.New(context.Background(), skey, 10000)
    if err != nil { panic(err) }
    p.Timeout = 10 * time.Second

    handler := &authenticated{next: p, apiKey: "..."}
    // TLS can be terminated here or delegated to a reverse proxy in front (pkg/proxy is TLS-agnostic).
    panic(http.ListenAndServeTLS("localhost:4443", "config/tls-cert.pem", "config/tls-key.pem", handler))
}

Calling proxy.ExtractCommandAction(ctx, command, params) directly converts a Fleet API command name + JSON parameters into a func(*vehicle.Vehicle) error without HTTP, so you can reuse the same command mapping in another RPC framework.
