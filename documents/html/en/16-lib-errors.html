16. Error Handling

Every call returns one of three outcomes, and every error says whether the car may have acted and whether trying again could help. The library already retries what is safe to retry, so most apps only need to branch on the outcome.

On this page
  1. Three outcomes
  2. Error types
  3. Bluetooth and key store errors
  4. Broadcast events
  5. Retries and timeouts
  6. What to read after Uncertain

Three outcomes

OutcomeMeaningWhat your app does
SuccessThe car confirmedUse the value
UncertainThe car may have done it, but no confirmation arrivedDo not send it again. Read the state instead (vehicleStatus(); getState() once M5 lands)
FailureIt did not happenLook at error

In Swift, switch onEnum(of: result) covers .success, .uncertain and .failure; see 12. Getting Started. Cancelling your own coroutine or Task is not turned into an outcome; the cancellation propagates as usual.

Error types

Every VehicleError carries a message (English), mayHaveSucceeded and temporary. shouldRetry() is true when the error is temporary and the car cannot have acted. The library already retries those, so you do not need a retry loop.

The meaning of every protocol fault code is in 9. Errors and Troubleshooting.

Codes from the extended protocol definitions

Since 2026-10-18 the library's protocol definitions come from a pinned snapshot of Teslemetry/tesla-protocol, which adds codes to the official ones (see 19. Architecture). A code in that snapshot is now reported with its named error type instead of an Unknown… type with a number. Whether the library retries does not change. The code names come from the snapshot and are not confirmed on a real car.

Check the error type, not message: the message now shows the code name instead of the number.

Bluetooth and key store errors

Connecting is already retried every second until the connect timeout. The last column is what the app should do.

ErrorMeaningWhat to do
ScanTimeoutThe car was not found in timeCheck the car is in range, try again
MaxConnectionsExceededThe car already has three Bluetooth connectionsDisconnect another phone or app, try again
ConnectFailedConnecting, discovering services or subscribing failedTry again in a moment
DisconnectedThe link droppedCall disconnect(), then connect again
BluetoothOffBluetooth is offAsk the user to turn it on
PermissionDeniedNo Bluetooth permissionAsk for permission or open Settings
WriteFailedSending failedRetried automatically; reconnect if it keeps happening
HardwareUnavailableHardware was required but is not availableUse PREFER_HARDWARE
KeyNotFoundNo key under that aliasCreate one with getOrCreate
PlatformFailureThe platform key store failed; stored key is corrupted means the saved key is damagedDamaged keys are not replaced automatically: delete, create, and enroll the new key again
LockediOS: the phone is locked and the key only works while the phone is unlocked, or the phone has not been unlocked since it restarted. A key that cannot be created for this reason is not replaced by a software keyDo not delete or re-create the key: try again after the phone is unlocked. To use the key while the phone is locked, create an AFTER_FIRST_UNLOCK key under a new alias and enroll it (13. Keys and Pairing). The library does not retry key store calls

Broadcast events

vehicle.events has no error values and never throws. It ends normally when the link drops or disconnect() is called (14. Reading Vehicle State, B2); why the link dropped is in connection.

SituationWhat happensWhat to do
A collector falls more than 64 frames behindNew frames are dropped for every collector of the connection and counted. A WARN line (tag Dispatcher) on the first drop and every 100th: Dropping plain broadcast because the broadcast buffer is full (dropped N since connect). Not an error: no VehicleError, and the flow keeps runningKeep the collector light and hand slow work to another coroutine. The car repeats its status every few seconds, so the latest state comes again; or read vehicleStatus()
A broadcast the library cannot decodeAn Unrecognized event with an empty unknownFields; the bytes are in rawKeep raw (with the VIN masked) for analysis

Retries and timeouts

The library retries with the same rules as the Go original.

SituationWhat the library does
A temporary error the car cannot have acted on (busy, wait, expired, bad counter…)Waits one second, signs the command again with a fresh counter and expiry, and resends it. Session information that came with the error is applied first
An error after which the car may have acted (no answer, unreadable answer)Never resends, so a toggle cannot run twice. Returns Uncertain
Time runs out before sendingFailure(Timeout)
Time runs out while waiting for the answerUncertain(Timeout)
The handshake runs out of timeFailure(Timeout); no session was made and nothing changed

What to read after Uncertain

After Uncertain, never resend. Read the state the command changes:

CommandRead withLook at
lock, unlock, wakeUp, remoteDrive, autoSecureVehicle, openTrunk, actuateTrunk, closeTrunk, openFrunk, openTonneau, closeTonneau, stopTonneauvehicleStatus()Lock state, closures, sleep status. openTrunk and actuateTrunk toggle, so compare the closure state before deciding to send again
addKey, removeKeylistKeys()Whether the public key is in the car's key list
addKeyRequest (TimedOut, or the flow ended without a final answer)sessionInfo(publicKey, VehicleDomain.INFOTAINMENT)Success = enrolled; Failure(KeyNotPaired) = not (yet)
