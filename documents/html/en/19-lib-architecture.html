19. Architecture

A summary for contributors: how the modules depend on each other, the path a command takes, the concurrency rules, and how sessions are cached. The full design is docs/sdd/SDD.md. This page covers M0 to M3 and is extended when the control commands land.

Modules

  • Every dependency points towards :domain, and the Gradle convention plugins enforce it.
  • The adapters implement the ports of :domain for each platform; :sdk wires them together.
  • :testing holds fakes such as FakeVehicle and FakeTransport and is used only by tests.

The path of a command

Using a security-controller command such as lock() as the example:

  1. Serialize. VcsecCommands takes the per-connection lock, so only one VCSEC command is in flight.
  2. Retry loop. Each attempt that fails with a retryable error starts again after the transport's retry interval.
  3. Sign and encrypt. Dispatcher.send asks SessionState to authorize the message: the counter goes up, the metadata is bound, a nonce is drawn.
  4. Send. The bytes go to the Transport port, implemented by :adapter-ble.
  5. Wait. The request waits until an answer is judged final.

Infotainment commands take the same steps from the retry loop on, without the lock. On the way back, one receive coroutine per connection reads Transport.incoming, parses each message, matches it to the waiting request, applies attached session information, decrypts it and checks it against replays, then hands it over.

Concurrency

  • Exactly one receive coroutine per connection. It never waits on another coroutine; it hands data over with non-blocking trySend. The only wait: a new receive coroutine waits for the previous one to finish.
  • One VCSEC command at a time per connection. Waiting for the previous one counts against the timeout. Infotainment commands may run in parallel.
  • Each domain has one session state. Its lock covers only encrypting, decrypting and session updates, so waits are short.
  • The handshakes for both domains run in parallel; if one fails, the other is cancelled.
  • Commands, handshakes and connections each have their own timeout; see 16. Error Handling.

Bluetooth adapter

Only two classes know Kable: KableGattConnector (scan, open) and KableGattLink (write, subscribe, notice drops). BleTransportFactory and BleTransport do framing, reassembly, retries and error mapping without Kable, so they are tested on the JVM. When the link drops, the incoming flow closes and the state becomes Disconnected. The scan matches the advertised local name exactly.

Facade

TeslaBle.create assembles the platform adapters: Bluetooth transport, key store, session cache and crypto primitives. connect opens the transport, creates a coroutine scope for that connection, attaches a Dispatcher and a VehicleSession, and restores saved sessions. If anything fails or is cancelled on the way, the transport and the scope are always released. One Vehicle stands for one connection; after disconnect() its calls fail with NotConnected.

Session cache

Sessions are saved in a small binary format (version 1) so the next connection can send commands without a new handshake. They are tied to the client key (SHA-1 of its public key); sessions of other keys are ignored and deleted. They are saved when a handshake finishes, when session information changes, and on disconnect. Private keys, session encryption keys and raw VINs are never saved. Damaged or unrecognized entries are skipped and the rest restored.

Protocol definitions

The :domain module generates Kotlin from 9 .proto files with Wire 7.0.4. Since 2026-10-18 these files are an unmodified copy of Teslemetry/tesla-protocol at a pinned commit (e6f7afb1, Apache-2.0). That snapshot holds the official vehicle-command definitions plus additions marked TESLEMETRY-EXT; some are also marked UNCONFIRMED or name unverified. The sources are recorded in NOTICE and PROTO_SOURCE.md.

What counts as correctThe official Go code (vehicle-command a4b43c1) for meaning, cryptography, routing and errors. If the two disagree, the Go code wins.
