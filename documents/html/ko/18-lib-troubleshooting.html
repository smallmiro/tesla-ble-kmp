스캔과 연결

증상가능한 원인대처
PermissionDenied블루투스 권한이 없거나 거부됨Android: 런타임에 BLUETOOTH_SCAN과 BLUETOOTH_CONNECT를 요청. iOS: NSBluetoothAlwaysUsageDescription을 추가하고, 거부되었으면 사용자를 설정으로 안내
BluetoothOff블루투스가 꺼져 있음사용자에게 켜 달라고 요청
스캔에서 아무것도 찾지 못하고, 연결이 ScanTimeout으로 끝남범위 밖, 잘못된 VIN, 또는 iOS 시뮬레이터가까이 가고, VIN을 확인하고(차량은 VIN에서 만든 이름으로 찾음), 실기기를 사용
연결이 ConnectFailed로 끝났고, 이유에 제한 시간 안에 연결을 끝내지 못했다고 적혀 있음이유에 vehicle found가 있으면 라이브러리의 스캔이 차량을 찾았지만(그 [connect:scan-hit] 줄이 발견을 보여 줍니다) 링크가 제시간에 열리지 않은 것입니다. 이유에 remembered target이 있으면 스캔을 돌리지 않았으므로 차량이 아직 있는지 알 수 없습니다. 범위 밖에 있는 기억한 target은 ConnectFailed를 돌려주고 ScanTimeout이 되지 않습니다. ScanTimeout은 언제나 광고를 찾지 못했다는 뜻입니다다시 시도. 기억한 target으로 실패했으면 스캔이 돌도록 그 값 없이 연결. 차량이 범위 안에 있는데 반복되면 로그 줄을 보고
MaxConnectionsExceeded차량에 이미 블루투스 연결이 세 개 있음다른 휴대폰이나 앱의 연결을 끊고, 내 앱에서는 항상 disconnect()를 호출
ConnectFailed가 계속 발생약한 신호 또는 바쁜 차량라이브러리가 이미 30초 동안 재시도함. 나중에 다시 시도
connect가 connectTimeout보다 몇 초 늦게 돌아옴(예: 30초가 아니라 32.6초)타이머가 늦게 울렸을 가능성이 높음. 그때 앱이 돌고 있지 않았던 것으로 보임(iOS는 백그라운드 앱을 일시 중단함). connect는 실패한 시도의 정리를 기다리지 않음고칠 것 없음. connect 시간 예산 참고
connection이 Disconnected로 바뀜링크가 끊김disconnect()를 호출한 뒤 다시 연결

키와 세션

증상가능한 원인대처
startSession()이 RequiresKey를 반환키 없이 연결함VehicleKey로 연결
startSession()이 KeyNotPaired를 반환차량이 이 키를 모릅니다addKeyRequest로 등록하세요(13. 키와 페어링). listKeys()나 sessionInfo로 확인합니다
stored key is corruptedAndroid 백업이 래핑 키 없이 키 파일만 복원했거나, 저장소가 손상됨삭제하고 새 키를 생성, 등록. 키 파일을 백업에서 제외(플랫폼 노트)
HardwareUnavailableStrongBox, TEE, Secure Enclave가 없는 기기에서 하드웨어를 요구함PREFER_HARDWARE 사용
KeyStoreError.LockediOS: 휴대폰이 잠겨 있고 키가 잠금 해제 중에만 동작하는 키(WHEN_UNLOCKED)이거나, 재시동 뒤 아직 한 번도 잠금을 풀지 않음키를 삭제하지 마세요. 잠금을 푼 뒤 다시 시도합니다. 휴대폰이 잠겨 있을 때도 키를 쓰려면 새 별칭으로 AFTER_FIRST_UNLOCK 키를 만들고 등록합니다(13. 키와 페어링)
iPhone이 잠겨 있을 때 startSession()이 KeyStoreError.Locked를 반환하고, WARN 줄 Session info not applied for <domain>: the private key is locked (device locked)가 남음휴대폰이 잠기기 전에 읽어 둔 Secure Enclave 키 객체가 잠금 해제 중에만 동작하는 키라서 핸드셰이크에 쓸 수 없음키를 삭제하지 마세요. 휴대폰의 잠금을 푼 뒤 같은 키로 startSession()을 다시 부릅니다. 휴대폰이 잠겨 있을 때도 키를 쓰려면 새 별칭으로 AFTER_FIRST_UNLOCK 키를 만들고 등록합니다(13. 키와 페어링)
iPhone이 잠겨 있을 때 연결하면 저장된 세션이 복원되지 않고, WARN 줄 Cached session for <domain> not restored: the private key is locked (device locked)와 나중에 INFO 줄 Keeping the session cache: …가 남음같은 원인이 저장된 세션을 복원할 때 나타남고칠 것은 없습니다. 저장된 세션은 지켜지고, 잠금을 푼 뒤 첫 연결에서 복원됩니다
iPhone이 잠겨 있을 때만 startSession()이 시간 초과되고, WARN 줄 Session info error: MESSAGEFAULT_ERROR_BAD_PARAMETER: invalid public key나 invalid cache: …: invalid public key가 남음iOS가 잠긴 Secure Enclave 키를 라이브러리가 기대하는 오류(-25308)가 아닌 다른 오류로 알림(실기기에서는 아직 확인하지 않음)iOS 버전과 로그 줄을 함께 알려 주세요. 그동안은 연결 직전에 키 보관소에서 키를 다시 읽거나(그러면 Locked가 반환됩니다) AFTER_FIRST_UNLOCK 키를 씁니다
WARN Keychain did not report the protection class of key <alias>; reporting WHEN_UNLOCKEDKeychain이 저장된 키의 보호 방식을 알려 주지 않음(예상하지 않은 경우)키는 WHEN_UNLOCKED로 보고됩니다. iOS 버전과 함께 알려 주세요
오래 잠든 뒤 첫 명령이 실패하고 재시도는 성공휴대폰이 잠든 동안 시계가 멈춤할 일 없음. 라이브러리가 알아서 다시 동기화함
재실행 뒤 첫 서명된 요청이 INVALID_TOKEN_OR_COUNTER와 새 세션 정보로 거부되고, 약 1.2초 뒤에 성공함저장된 카운터가 차량보다 뒤처져 있었음. ADR-0016 이후 라이브러리는 카운터를 사용하기 전에 저장하므로, disconnect() 없이 끝난 앱(강제 종료, iOS가 정지된 앱을 종료, 크래시)은 더 이상 이를 일으키지 않음. 아직 원인이 될 수 있는 경우: 이전 빌드가 저장한 캐시(업그레이드 뒤 한 번), 실패한 캐시 쓰기(아래 두 행), 같은 키를 쓰는 다른 연결이나 앱고칠 것은 없습니다. 거부된 사본은 실행되지 않았고 결과는 Success입니다. 차량과 키마다 살아 있는 연결을 하나만 두고, 끊어진 연결의 disconnect()가 반환된 뒤에 다시 연결하세요. 반복되면 아래 두 행의 경고를 찾아보세요
WARN 줄(태그 Dispatcher) Sending on <domain> with a counter the session cache does not cover …, 흔히 그 앞에 Failed to store the counter reservation for <domain>: …(태그 VehicleSession)나 Keeping the session cache: …가 남음요청 전에 카운터 예약을 저장하지 못함(직접 구현한 TeslaBleConfig.sessionCache가 예외를 던졌거나, 폰 잠금이 복원을 막아 캐시를 그대로 두는 중). 요청은 그래도 보냄이 요청에는 할 일이 없습니다. 앱이 disconnect() 없이 끝난 뒤에는 다음 실행의 첫 요청이 한 번 거부될 수 있습니다(위 행). 저장이 계속 실패하면 TeslaBleConfig.sessionCache나 저장소를 확인하세요
WARN 줄(태그 cache) Failed to store session cache: …내장 캐시가 쓰지 못함(파일 시스템, 키체인 상태). 로그만 남기고 반환하므로 라이브러리는 예약을 저장된 것으로 세고, 이어지는 서명된 요청 16개는 캐시에 없을 수 있는 카운터를 씀이 요청들에는 할 일이 없습니다. 앱이 disconnect() 없이 끝난 뒤에는 다음 실행의 첫 요청이 한 번 거부될 수 있습니다(위 두 행). 반복되면 남은 저장 공간이나 그 줄의 키체인 상태를 확인하세요
연결할 때 차량의 한 부분에 저장된 세션이 복원되지 않고, WARN 줄 invalid cache: <domain>: anti-replay counter exhausted가 남음저장된 카운터에서 0xFFFFFFFF까지 남은 값이 16개 미만(실제로는 예상되지 않음)할 일 없음. startSession()이 핸드셰이크를 하고 차량의 카운터에서 시작합니다
WARN 줄 The anti-replay counter for <domain> is exhausted; startSession() starts a new session 뒤에 서명된 호출이 NoSession을 반환함세션이 마지막 카운터 0xFFFFFFFF까지 씀(실제로는 예상되지 않음)차량의 그 부분에 startSession()을 호출한 뒤 다시 보내세요. 아무것도 보내지 않았습니다

페어링과 명령

증상가능한 원인대처
addKeyRequest 가 TimedOut으로 끝남카드를 태그하지 않았거나, 시간 안에(기본 60초) 화면에서 승인하지 않았거나, 응답을 인식하지 못했습니다사용자에게 센터 콘솔에 키카드를 태그하고 화면에서 승인하도록 안내한 다음 sessionInfo(publicKey, INFOTAINMENT)로 확인하세요. 키가 등록되었을 수도 있습니다
addKeyRequest 가 Rejected(KeychainRejected(WHITELIST_FULL)) 또는 다른 KeychainRejected 코드를 냄차량이 거부했습니다. 키 목록이 가득 찼거나 추가 권한이 없는 등의 이유입니다차량 터치스크린이나 removeKey로 쓰지 않는 키를 제거하세요. 16. 에러 처리를 참고하세요
addKeyRequest 가 Unknown(raw)를 냄처음 보는 응답 형식입니다. 실차 동작은 아직 확인하지 않았습니다(ADR-0009)raw를 16진수로(VIN 제외) 차량이 한 동작과 함께 알려 주세요
addKeyRequest 가 Failed(NotConnected)를 냄Vehicle 객체의 연결이 해제되었거나 링크가 끊겼습니다disconnect()를 호출하고 다시 연결해서 반복하세요
lock() (또는 다른 보안 컨트롤러 명령)이 NoSession을 반환함VCSEC 세션이 아직 없거나 캐시된 세션이 오래되었습니다먼저 startSession(setOf(VehicleDomain.VCSEC))를 호출하세요. sessions가 Ready(fromCache = true)였다면 이 실패 뒤 None으로 바뀝니다(다른 키나 차량의 캐시였던 경우). startSession으로 해결됩니다
addKey / removeKey 가 InsufficientPrivileges를 반환함연결의 키에 키 관리 권한이 없습니다(예: Driver 키)Owner 키를 사용하세요

getState로 상태 읽기

증상가능한 원인할 일
getState()가 NoSession을 반환함인포테인먼트 세션이 아직 없거나 저장된 세션이 오래되었습니다startSession(setOf(VehicleDomain.INFOTAINMENT))를 호출한 뒤 다시 조회하세요. sessions가 Ready(fromCache = true)였다면 이 실패 뒤 None으로 바뀝니다
startSession은 성공했는데 getState()가 Uncertain(Timeout(afterSend = true))을 반환함인포테인먼트가 잠들어 있습니다(저장된 세션은 수면 상태와 무관하며, getState는 차량을 깨우지 않습니다). 또는 응답이 유실되었습니다vehicleStatus()를 읽으세요. ASLEEP이면 14, A8.2의 깨우기 순서를 따르세요. 그 외에는 마지막 값을 유지하고 나중에 다시 조회하세요
getState()가 Failure(Timeout(afterSend = false))를 반환함요청의 쓰기가 시작되기 전이나 재시도 사이에 시간이 다 되었습니다. 예: 깨우는 중에 차량이 busy로 응답하는 경우나중에 다시 조회하세요. 깨운 직후에는 더 긴 timeout을 넘기세요
getState(DRIVE)가 Uncertain(ProtocolFault(RESPONSE_MTU_EXCEEDED))을 반환함응답이 차량의 크기 상한을 넘었습니다. 목적지 이름이 길수록 더 잘 일어납니다. 차량이 사라지거나 잠든 것은 아닙니다마지막 값을 경과 시간과 함께 유지하고, 짧은 간격으로 반복하지 말고 나중에 다시 조회하세요. 더 작은 조회는 없습니다(16. 에러 처리)
getState()가 Success를 반환했지만 필드가 null임차량이 그 필드를 보내지 않았거나, 응답에 vehicleData가 없었습니다0이 아니라 "값 없음"으로 표시하세요(14, A8.3). 실차가 어떤 필드를 보내는지는 아직 확인되지 않았습니다(#118)
getState()가 Success와 함께 같은 값을 또 반환함Success가 새 측정값의 증거는 아닙니다timestamp를 이전 응답과 비교하세요(14, A8.3)

인포테인먼트 명령

증상가능한 원인할 일
인포테인먼트 명령(climateOn(), chargeStart(), honkHorn()…)이 NoSession을 반환함아직 인포테인먼트 세션이 없거나, 저장된 세션이 오래됨startSession(setOf(VehicleDomain.INFOTAINMENT))를 호출한 뒤 명령을 다시 보내세요: 아무것도 전송되지 않았습니다
보안 컨트롤러 명령은 되는데, 모든 인포테인먼트 명령이 Uncertain(Timeout(afterSend = true))를 반환함인포테인먼트가 잠들어 있음: 명령은 인포테인먼트를 깨우지 못하며, 저장된 세션은 수면에 대해 아무것도 알려 주지 않습니다vehicleStatus()를 읽고, ASLEEP이면 차량을 깨운 뒤 AWAKE를 기다리세요(14, A8.2). 명령을 다시 보내기 전에 상태를 읽으세요: 이미 실행되었을 수 있습니다
명령이 Uncertain을 반환했고 앱이 재시도하려 함차량이 실행했을 수 있음절대 다시 보내지 마세요. 명령이 바꾸는 상태를 읽으세요(15. 명령). toggleMediaPlayback과 트렁크 토글은 두 번째 전송이 첫 번째를 되돌립니다. honkHorn, flashLights, setLowPowerMode, setKeepAccessoryPowerMode는 다시 읽을 수 없습니다: 결과를 알 수 없음으로 표시하세요
enableValetMode(pin)이 InvalidArgument("PIN codes must be four digits")를 반환함PIN이 ASCII 숫자 정확히 네 자리가 아님. 예: 키보드로 입력한 전각 숫자나 다른 문자 체계의 숫자, 공백숫자 전용 키보드를 제공하거나 호출 전에 입력을 변환하세요. PIN을 로그에 남기지 마세요

connect 시간 예산

connectTimeout(기본 30초) 또는 ConnectOptions.timeout은 스캔, 링크 열기, 시도 사이의 재시도를 모두 포함합니다. 이 시간이 다 되어 connect가 실패하면 다음과 같습니다.

  • 바로 돌아옵니다. 마지막으로 실패한 시도의 오류를 돌려줍니다. 실패한 시도가 없었으면 스캔이 차량을 찾았거나 기억한 target을 열던 중인 경우 ConnectFailed, 광고를 찾지 못한 경우 ScanTimeout을 돌려줍니다. Go 원본도 마지막 오류를 돌려주고, 그렇지 않으면 이 모든 경우에 일반적인 deadline 오류 하나를 돌려줍니다.
  • 아직 진행 중인 시도를 기다리지 않습니다. 그 시도는 취소되고 connect가 돌아간 뒤에 정리되며, 플랫폼 연결 해제는 최대 5초까지만 기다립니다. 그 시도가 그래도 링크를 열면 라이브러리가 그 링크를 끊습니다.
  • 시간을 넘겨 기다리는 경우는 하나뿐입니다. 시간이 다 된 바로 그 순간 만들어진 연결은 connect가 돌아가기 전에 닫으며, 이것도 최대 5초입니다. 따라서 실패한 connect에 라이브러리가 더하는 시간은 최대 5초입니다.
  • 예산은 타이머이고, 타이머는 앱이 돌지 않는 동안에는 울리지 못합니다. 그래서 일시 중단된 앱은 얼마든지 늦어질 수 있습니다. 실제 iPhone에서 30초 예산이 36분 늦게 끝난 적이 있습니다(docs/analysis/2026-11-01-build18-link-health.md F3, 가능성이 높지만 확정은 아님). 어떤 시간 제한으로도 막을 수 없습니다.

실제 iPhone에서 한 번 관찰했습니다: 32.63초 뒤의 ConnectFailed. 원인은 늦은 타이머일 가능성이 높지만, 로그에 프로세스 상태가 없어 확정할 수 없습니다. 실패한 시도가 없었던 ScanTimeout도 같은 식으로 시간을 넘겼고(31.35, 32.40, 33.19초에 끝남. #140 이전의 그 빌드는 차량을 찾은 뒤에도 ScanTimeout을 돌려줬습니다), 앱의 다음 4초 대기는 9.03초가 걸렸습니다. 위에 적은 라이브러리의 대기 하나는 로그로 배제할 수 없지만, 그러려면 시간이 다 된 바로 그 순간 링크가 열려야 합니다. 피해는 관찰되지 않았습니다(#130).

출발지가 없는 프레임

결정(#130): 출발지가 없는 프레임은 vehicle.events에 넣지 않고, 관찰 로그의 [drop:missing-source] 줄로만 남깁니다.

  • 평문 브로드캐스트가 아니고(14, B2), Go 원본도 버립니다. 출발지가 없으면 그 프레임이 보안 도메인에서 왔다고 말할 근거가 없습니다. reinterpreted=…는 같은 바이트를 FromVCSECMessage로 읽으면 어떻게 보이는지를 보여 줄 뿐입니다.
  • 이런 프레임을 전달하면 공개 계약이 넓어집니다. raw는 언제나 RoutableMessage 프레임 전체이고, 정체를 알 수 없는 프레임까지 모두 이벤트가 됩니다.
  • 얻는 것이 적습니다. 실차가 연결 12번에서 이런 프레임을 2개 보냈습니다. authenticationRequest(DRIVE, IDENTIFICATION)는 앱이 connected를 보기 1 ms 전에 도착해 아직 수집하는 쪽이 없었으므로, 다시 보내 주지 않는 이상 규칙을 넓혔어도 전달되지 않았을 것입니다. 다른 하나는 이벤트 타입이 없는 commandStatus뿐이었습니다. 또한 앱은 AuthenticationRequest를 받아도 할 수 있는 일이 없습니다. 라이브러리는 AuthenticationResponse를 보내지 않습니다.

차량이 이런 프레임을 자주 보낸다면 다시 검토합니다. 다른 곳에서는 약 1.1초마다 온다는 보고가 있습니다(14, B3.2).

디버그 로깅

로그에 절대 나오지 않는 것

라이브러리는 VIN을 마스킹하며 개인키, 세션 키, nonce, 복호화된 내용을 기록하지 않습니다. 앱 자체의 로그도 그렇게 유지하세요. vin.value를 출력하지 말고, 로그를 공유하기 전에 VIN을 마스킹하세요. getState 결과도 toString()을 포함해 로그에 남기지 마세요. VehicleData에는 위치와 목적지가 들어 있을 수 있고, InfotainmentRejected.message에는 차량이 보낸 문구가 들어 있습니다.

문제를 보고할 때는 iOS 샘플의 "결과 전체 복사" 버튼으로 얻은 로그와 DebugLogger를 사용하세요. 프로브나 진단 진입점은 없습니다.

관찰 로그 (개발용)

개발하는 동안 라이브러리는 버리는 메시지마다, 그리고 양쪽 도메인에서 자기 요청에 온 응답마다 요약 한 줄을 남길 수 있습니다. 차량이 요청 없이 보내는 것이 무엇인지, 응답이 요청과 어떻게 이어지는지 보여 줍니다. 동작은 바뀌지 않습니다. 브로드캐스트는 여전히 응답 짝짓기에서 빠지며, 그중 평문 브로드캐스트는 vehicle.events로도 앱에 전달됩니다(앞 절). 푸시된 각 메시지의 의미는 14. 차량 상태 조회의 B부에 있습니다. 블루투스 전송 계층은 connect의 스캔 발견마다 한 줄을 더합니다.

  • 태그 observe, 레벨 DEBUG. DEBUG를 버리는 로거는 이 줄을 만들지도 않습니다. DebugLogger()나 직접 만든 TeslaLogger로 볼 수 있습니다. iOS 샘플의 관찰 모드는 이 줄만 모읍니다.
  • 형식: [지점] NB from=… to=… request_uuid=… payload=…. NB는 받은 프레임의 크기입니다. 응답 줄은 attempt=N auth=…로 끝납니다.
  • 스캔 발견 줄(FR-038): [connect:scan-hit] after=<ms>ms rssi=<dBm|unavailable> connectable=<true|false|unknown> attempt=<n>. connect가 직접 돌린 스캔이 찾은 광고마다 한 줄이며, 연결 가능 여부를 확인하고 링크를 열기 전에 씁니다. 그래서 실패하는 connect에도, 재시도마다에도 나타납니다. after는 connect를 시작한 뒤 지난 시간(hitAfterMillis와 같은 값, 12. 라이브러리 시작하기), attempt는 그 발견이 쓰일 열기 시도 번호입니다. 로거가 이 줄을 받은 시각이 발견의 벽시계 시각입니다. ble.scan(vin)과 스캔 없이 다시 쓴 target은 줄을 남기지 않습니다. 광고 이름과 기기 식별자는 없습니다.
항목값
[drop:unparseable]프레임이 라우팅 메시지로 해석되지 않았습니다. 줄 끝에 reinterpreted=…(또는 undecodable)이 붙습니다
[drop:missing-source]출발지가 없습니다. 줄 끝의 reinterpreted=…는 같은 바이트를 감싸지 않은 FromVCSECMessage로 읽은 결과입니다. 이벤트가 되지 않습니다(출발지가 없는 프레임)
[drop:missing-destination]목적지가 없습니다(실차에서는 보이지 않았습니다)

응답 줄

라이브러리는 받은 프레임마다 복호화 단계 뒤에 [reply:vcsec] 또는 [reply:infotainment] 한 줄을 남깁니다. 그래서 그 단계에서 버린 응답에도 줄이 있습니다. 줄은 attempt=N auth=…로 끝납니다. 그 프레임이 호출자에게 닿지 못하면 [drop:handler-closed] 또는 [drop:queue-full] 줄이 뒤따릅니다. 앱이 연결을 끊어 처리가 중단된 프레임에는 줄이 남지 않고 전달되지도 않으므로, 줄이 없다고 해서 응답이 오지 않았다고 단정할 수는 없습니다.

항목뜻
attempt=N이 연결에서 요청에 매긴 불투명한 번호로, 1부터 시작합니다. 핸드셰이크 요청과 재시도를 포함해 요청마다 새 번호를 쓰므로 명령 하나가 여러 번호를 쓸 수 있습니다. 번호는 한 연결 안에서만 비교하세요. 새 연결은 다시 1부터 시작합니다
auth=gcm-okAES_GCM_Response_data가 있고, 태그가 검증되었고, 카운터가 그 요청의 재전송 검사를 통과했습니다. 전달됩니다
auth=gcm-failedAES_GCM_Response_data가 있지만 검증에 실패했습니다. 버려집니다
auth=gcm-replay태그는 검증되었지만 재전송 창이 카운터를 거부했습니다. 이미 봤거나 창보다 오래된 값입니다. 버려집니다
auth=gcm-no-sessionAES_GCM_Response_data가 있지만 검사할 세션이 없습니다(개인키가 없거나 세션이 맺어지지 않았습니다). 버려집니다
auth=noneAES_GCM_Response_data가 없어 아무것도 검사하지 않았습니다. 전달됩니다. 세션 정보 응답도 이렇게 표시됩니다. 그 HMAC 태그는 따로 검증하며 이 줄에 나오지 않습니다
  • auth=는 페이로드 검사 결과이지 응답 전체에 대한 판정이 아닙니다. AES-GCM은 페이로드와 signed_message_fault를 덮습니다. 바깥 operation_status(status=의 앞부분)는 범위 밖이므로 auth=gcm-ok도 이를 보장하지 않습니다(ADR-0015).
  • 줄은 받은 그대로의 프레임으로 만들며 복호화한 메시지로 만들지 않습니다(FR-112). 암호화된 응답은 auth= 값과 상관없이 payload=encrypted(NB)로 표시되고, encrypted(NB)만으로는 서명 필드가 있다는 것밖에 알 수 없습니다.
  • to=address(16B, closed)는 대응 관계일 뿐입니다. 응답의 키(라우팅 주소, 인포테인먼트는 요청 UUID까지)가 이 연결에서 닫힌 요청과 맞고, attempt=N이 그 요청을 가리킨다는 뜻입니다. 응답이 진짜라거나 요청이 성공했다는 뜻이 아닙니다. 라이브러리는 이런 응답을 복호화하지 않아 요청의 재전송 검사를 건드리지 않고, 전달하지도 않습니다. 그래서 이 줄에는 auth=가 없습니다.
  • 이력은 연결에서 닫힌 요청 32개를 기억하며, 먼저 들어간 항목부터 밀려납니다. 닫힌 요청은 라이브러리의 다음 정리 때 들어가고 한 번의 정리 안에서는 오래된 시도부터 들어가므로, 순서는 닫힌 순서에 가깝지만 정확히 같지는 않습니다. 이력에 없는 요청의 늦은 응답은 보안 도메인에서 other, 모든 요청이 주소 하나를 공유하는 인포테인먼트 도메인에서 self로 표시됩니다.
  • 이력은 링크가 끊기거나 앱이 연결을 끊으면 비워집니다. 링크가 끊길 때 열려 있다가 나중에 닫힌 요청까지 포함해, 새 연결로 넘어가는 것은 없습니다.

상세 형식 (탐색용)

예: unknownFields=[48:len(8){1:varint=3(0x3), 2:len(4)"ABCD"}, 9]. 항목은 도착 순서를 지키고 반복 필드는 반복해서 적습니다. 필드 번호와 wire type은 그대로 두며 필드 이름은 지어내지 않습니다.

Wire type표시
varintvarint=<부호 없는 10진수>(0x<16진수>)
fixed32 / fixed64fixed32=0x + 16진수 8자리, fixed64=0x + 16진수 16자리
LEN전체 범위가 protobuf로 읽히면 len(N){…}(깊이 3, 메시지당 필드 64개, 256바이트까지). 아니면 출력 가능한 ASCII는 len(N)"text"(제어 문자는 이스케이프), 그 밖은 len(N)0x… 헥사
한계 초과 또는 손상len(N, truncated) 또는 len(N, invalid)
키처럼 보이는 LEN정확히 16, 32, 33, 64, 65바이트: redacted(NB). 0x04로 시작하는 65바이트 값: sha1:xxxxxxxx

VIN(17자)은 헥사를 만들기 전에 텍스트와 원시 바이트 모두에서 가립니다. 앞 3자와 뒤 4자만 남습니다. 가리기는 바이트를 해석하기 전에 원시 바이트에서 일어나므로, 가려진 바이트 때문에 보이는 값이나 구조가 달라질 수 있습니다(유출은 없습니다). 이 출력은 탐색용일 뿐입니다. 필드의 뜻을 알려 주지 않습니다. 실차에서는 closureStatuses가 없으면 운전석 문 둘, 뒷트렁크, 충전구는 모두 닫힌 상태였지만, 실내 버튼으로 조작한 트렁크는 브로드캐스트가 전혀 없었으므로 브로드캐스트만으로는 트렁크가 닫혀 있다고 증명할 수 없습니다(14의 B부 참고).

한계와 규칙

  • 상세 디코드는 좁은 예외이며, 차량이 원래 평문으로 보낸 프레임에만 적용됩니다(라이브러리가 복호화한 것에는 절대 쓰지 않으므로 FR-112와 충돌하지 않습니다). vehicle.events는 그런 프레임을 디코딩 여부와 상관없이 raw로 앱에 넘깁니다. 다음이 모두 맞아야 합니다: 보안 도메인에서 출발, 브로드캐스트 도메인으로 도착, 요청 UUID 없음, 서명 없음, 세션 정보 없음, 페이로드가 FromVCSECMessage로 읽힘. 그때 FromVCSECMessage의 미공개 필드 48·53과 VehicleStatus의 미공개 필드 7·8만 풀어 씁니다(필드 7은 이제 이름이 있는 gear이므로 값이 정의 밖일 때만 미공개 필드가 됩니다. 정의 밖의 값이므로 그 원시 값을 unknownFields=[7:varint=9(0x9)]처럼 계속 보여 줍니다). 그 밖의 필드와 프레임은 번호만 적습니다.
  • enum 값이 빠진 것과 0번 값은 구분할 수 없습니다. 잠금 상태가 없으면 VEHICLELOCKSTATE_UNLOCKED로 읽힙니다(sleep, presence는 UNKNOWN). absent로 알 수 있는 것은 메시지 부분뿐입니다.
  • 암호화된 내용과 세션 정보는 길이만, 공개키는 SHA-1 앞부분만 적습니다. VIN과 복호화된 내용은 나오지 않습니다. 줄을 추가할 때도 이 규칙을 지키세요.
  • BLE 전송은 연결마다 수신 버퍼 넘침을 셉니다. 버려진 메시지마다 ERROR로 Dropping received message because inbox is full (dropped N since connect)를 남기고, 링크가 끝나면 WARN으로 BLE inbox overflowed N time(s) during this connection 한 줄을 남깁니다(N이 0보다 클 때만).
  • DebugLogger는 DEBUG에서 BLE 원문 바이트(TX:, RX:)도 출력합니다. 이런 플랫폼 로그는 공유하지 마세요. 거기서는 차량이 암호화한 내용만 암호화되어 있습니다. 나머지는 차량이 보낸 그대로 나타나며, VCSEC 조회 응답, 브로드캐스트, 위치가 들어 있을 수 있는 평문 인포테인먼트 응답(2024.38 이전 펌웨어, 16. 에러 처리 참고)도 여기에 포함됩니다.
