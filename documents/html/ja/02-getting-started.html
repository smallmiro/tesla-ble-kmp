2. はじめに

インストールから鍵の生成、NFC カードによる鍵のペアリング、最初の BLE コマンド送信までを順番に進めます。

必要なもの

  • Go 1.23 以上 (go.mod の go 1.23、CI は 1.23.0 でテスト)。Docker イメージも golang:1.23.0 でビルドされます。
  • macOS または Linux。BLE はこの 2 つのプラットフォームのみサポートします。Windows では BLE 以外の機能だけがビルドされます。
  • Bluetooth アダプターを備えたコンピューター、そして車両の VIN(車両画面の Controls > Software で確認。17 文字、英字 + 数字)。
  • 鍵のペアリングのための車両の NFC カード(またはキーフォブ)と、車内で画面を操作できる状況。
  • インターネット経路を使う場合は Tesla 開発者アカウントと OAuth アクセストークン。BLE だけを使う場合は不要です。

インストール

ソースからビルド

cd vehicle-command
go get ./...        # 依存関係のダウンロード
go build ./...      # 全体のコンパイル (ツール + サンプル)
go install ./...    # $GOBIN (デフォルト ~/go/bin) にツールをインストール

go install の後、次の実行ファイルが PATH に配置されます。

実行ファイル役割
tesla-keygenコマンド認証用の秘密鍵を生成し、システムのキーリングに保存、公開鍵を出力
tesla-controlBLE またはインターネットで車両にコマンドを送信。引数なしで実行すると対話型シェル
tesla-auth-tokenOAuth トークンをキーリングに保存 (トークンの発行は行わない)
tesla-http-proxyREST API プロキシサーバー
tesla-jwsFleet Telemetry 設定 JWS の署名/検証
ble、unlockexamples/ のサンプルプログラム (go install ./... に含まれる)

リポジトリの Makefile も使用できます: make install(go install ./cmd/...)、make test、make build、make linters(golangci-lint)、make proto-gen(protoc が必要)。./check-all.sh は build/test/vet/fmt を一度に検査します。

Docker

BLE はコンテナ内で使うのが難しいため、Docker イメージは主に HTTP プロキシ用です。デフォルトのエントリーポイントは tesla-http-proxy で、--entrypoint で変更できます。

docker pull tesla/vehicle-command:latest
docker run tesla/vehicle-command:latest --help
docker run --entrypoint tesla-keygen tesla/vehicle-command:latest --help

環境変数の設定

すべての CLI ツールは pkg/cli を共有し、コマンドラインフラグの代わりに環境変数を読み取ります。フラグが優先され、空の値だけが環境変数で補われます。

export TESLA_KEY_NAME=$(whoami)            # キーリングで秘密鍵を探す名前
export TESLA_VIN=5YJ30123456789ABC          # 対象車両の VIN
export TESLA_CACHE_FILE=~/.tesla-cache.json # セッションキャッシュ (省略時 ~/.tesla-cache.json)
# インターネット経路を使う場合のみ:
export TESLA_TOKEN_NAME=$(whoami)           # キーリングで OAuth トークンを探す名前
変数対応するフラグ意味
TESLA_KEY_NAME-key-nameシステムキーリング内の秘密鍵の項目名 (実際の項目キーは vehicleCommandKey.<名前>)
TESLA_KEY_FILE-key-filePEM ファイルから秘密鍵を読み込む。キーリングの代わりに使用
TESLA_TOKEN_NAME-token-nameキーリング内の OAuth トークンの項目名 (oauthtoken.<名前>)
TESLA_TOKEN_FILE-token-fileファイルから OAuth トークンを読み込む
TESLA_VIN-vinVIN
TESLA_CACHE_FILE-session-cacheセッションキャッシュ JSON のパス。-disable-session-cache で無効化できる
TESLA_KEYRING_TYPE-keyring-typeキーリングのバックエンドを強制指定。tesla-keygen -h に OS ごとのサポート値を表示
TESLA_KEYRING_PATH-keyring-file-dirファイルベースのキーリングのディレクトリ (デフォルト ~/.tesla_keys)
TESLA_KEYRING_PASSWORD-ファイルキーリング/キーチェーンのパスワード。空の場合はターミナルでプロンプト
TESLA_KEYRING_DEBUG-keyring-debugキーリングのデバッグログ
TESLA_VERBOSE-debug / -verbosetesla-control、tesla-http-proxy の詳細ログ。false/0 以外の値なら有効

秘密鍵の生成

方法 A: tesla-keygen (推奨)

export TESLA_KEY_NAME=$(whoami)
tesla-keygen create > public_key.pem
cat public_key.pem
# -----BEGIN PUBLIC KEY-----
# MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
# -----END PUBLIC KEY-----
  • NIST P-256 秘密鍵を生成して OS のキーリング(macOS ではログインキーチェーン)に保存し、PKIX PEM 形式の公開鍵を stdout に出力します。-output ファイルでファイルに書き出すこともできます。
  • 同じ名前の鍵がすでにある場合は上書きせず、既存の公開鍵を再出力するだけです。強制的に新しく作るには -f。
  • -key-file private.pem を指定すると、キーリングの代わりにファイルに保存します(EC PRIVATE KEY PEM、0600)。
サブコマンド動作
create鍵を生成して保存し、公開鍵を出力。既存の鍵があれば再利用(-f で上書き)
exportキーリングの秘密鍵を EC PRIVATE KEY PEM として stdout に出力
migrate-key-file の PEM 秘密鍵を -key-name のキーリング項目に移す
deleteキーリングから鍵を削除

方法 B: OpenSSL

キーリングを使わずファイルだけで管理するには、examples/ble/doc.go にある方法で作成します。

openssl ecparam -genkey -name prime256v1 -noout > private.pem
openssl ec -in private.pem -pubout > public.pem
export TESLA_KEY_FILE=$PWD/private.pem   # または毎回 -key-file private.pem
秘密鍵の保護

秘密鍵が漏洩すると、車両のロックを解除して運転できてしまいます。ファイルで保管する場合は権限を 0600 に保ち、リポジトリにコミットしないでください。protocol.LoadPrivateKey は暗号化されていない PKCS#8/SEC1 PEM のみを読み込みます。TLS サーバー鍵とコマンド認証鍵に同じ鍵を使うと、tesla-http-proxy は起動を拒否します。

車両への鍵のペアリング

公開鍵を車両のキーチェーン(whitelist)に登録しなければ、車両はコマンドを受け付けません。BLE では NFC カードで承認する add-key-request を使用します。このリクエスト自体は認証が不要なため、まだペアリングされていない鍵でも送信できます。

  1. 車内に座る。 ノートパソコンの Bluetooth をオンにし、NFC カード(またはキーフォブ)を用意します。車両は同時に最大 3 つの BLE 接続しか維持しないため、他のスマートフォンキーが多数接続されているとスキャン結果が Connectable=false になることがあります。
  2. リクエストを送る。 
    export TESLA_VIN=<VIN>
tesla-control -ble add-key-request public_key.pem owner cloud_key
# Sent add-key request to <VIN>. Confirm by tapping NFC card on center console.
    プログラムはリクエストを送信するとすぐに終了します。終了したからといって承認が完了したわけではありません。
  3. NFC カードをセンターコンソール(カードリーダーの位置)にかざす。 車両画面に新しい鍵の承認確認ウィンドウが表示されます。
  4. 画面で Confirm を押す。 Locks 画面に新しい鍵が表示されます。
  5. 確認する。 tesla-control -ble list-keys で登録された公開鍵、ロール、フォームファクターを確認するか、tesla-control -ble session-info public_key.pem infotainment が成功するかを確認します(Infotainment まで同期されれば成功)。

add-key-request PUBLIC_KEY ROLE FORM_FACTOR の引数:

引数許容値説明
PUBLIC_KEYファイルパス公開鍵 PEM。対応する秘密鍵 PEM、65 バイトのバイナリ、130 文字の hex ポイントも可(protocol.LoadPublicKey)
ROLEowner、driver、fm、vehicle_monitor、charging_managerkeys.Role から ROLE_ 接頭辞を除いた小文字。自分のコンピューター用なら通常は owner
FORM_FACTORnfc_card、ios_device、android_device、cloud_key車両 UI に表示される種類。サードパーティのアプリ/サーバーの鍵は cloud_key
すでに Owner 鍵がある場合

ペアリング済みの Owner 鍵があれば、NFC なしで他の鍵を追加できます: tesla-control -ble -key-file owner.pem add-key new_public.pem driver cloud_key。削除は remove-key new_public.pem。インターネット経路では rename-key で車両画面に表示される名前を変更できます(OAuth が必要)。

ペアリングが失敗するよくある理由
  • カードタップのタイムアウト: WHITELISTOPERATION_INFORMATION_LOCAL_ENTITY_AUTH_FAILED_TIMED_OUT_WAITING_FOR_TAP。リクエスト後すぐにカードをかざしてください。
  • 画面で拒否/キャンセル: …UI_DENIED、…CANCELLED。
  • バレーモード中: …LOCAL_ENTITY_AUTH_FAILED_VALET_MODE。
  • キーチェーンが満杯: MESSAGEFAULT_ERROR_KEYCHAIN_IS_FULL または WHITELISTOPERATION_INFORMATION_WHITELIST_FULL。既存の鍵を削除する必要があります。
  • 登録済みの鍵: …ATTEMPTING_TO_ADD_KEY_THAT_IS_ALREADY_ON_THE_WHITELIST。正常です。

最初の BLE コマンド

tesla-control -ble lock
tesla-control -ble unlock
tesla-control -ble body-controller-state   # ロック/ドア/トランク/スリープ状態の JSON。Infotainment がスリープ中でも動作
tesla-control -ble list-keys               # 登録された鍵の一覧
tesla-control -ble climate-on              # Infotainment コマンド。車両がスリープ中なら先に wake
tesla-control -ble wake                    # VCSEC にウェイクアップを要求
tesla-control -ble state charge            # 充電状態の JSON (Infotainment が必要)
  • -ble は OAuth の環境変数が設定されていても BLE 接続を強制します。OAuth の変数がなければ VIN だけで自動的に BLE を選択するため、省略しても構いません。
  • 接続のタイムアウトは -connect-timeout(デフォルト 20s)、コマンドのタイムアウトは -command-timeout(デフォルト 5s)です。スキャンが遅い環境では -connect-timeout 60s のように延ばしてください。
  • 引数なしで tesla-control -ble を実行すると、> プロンプトの対話型シェルが起動します。接続とハンドシェイクを 1 回だけ行い、複数のコマンドを送れます。exit で終了。
  • tesla-control help <コマンド> で引数の説明を確認できます。全一覧は 7. コマンドリファレンス。
ドメインを限定して遅延を減らす

デフォルトでは、StartSession は VCSEC と Infotainment の 2 つのドメインと並列にハンドシェイクします。VCSEC コマンドだけを使う場合は -domain vcsec を指定すると Infotainment を起こさないため高速で、車両がスリープしていても失敗しません。wake と body-controller-state は CLI が自動的に VCSEC のみを使用します。

デバッグ出力とセッションキャッシュ

-debug で送受信バイトを見る

tesla-control -ble -debug list-keys
# 2023-12-13T14:41:13-08:00 [debug] Creating new BLE adapter
# 2023-12-13T14:41:13-08:00 [debug] Dialing to xx:xx:xx:xx:xx:xx (S1a87a5a75f3df858C)...
# 2023-12-13T14:41:13-08:00 [debug] MTU size: 517
# 2023-12-13T14:41:13-08:00 [info ] Connected to vehicle BLE
# 2023-12-13T14:41:13-08:00 [debug] TX: 320208023a1212100a7962c1...
# 2023-12-13T14:41:13-08:00 [debug] RX: ...

TX:/RX: の後の hex は、長さプレフィックスを除いた RoutableMessage です。protoc でデコードできます。ログは stderr に出力され、TESLA_VERBOSE=1 でも有効にできます。

セッションキャッシュ

tesla-control は実行のたびに新しいプロセスになるため、キャッシュがなければ毎回ハンドシェイクを行います。TESLA_CACHE_FILE(デフォルト ~/.tesla-cache.json)にドメインごとのセッション情報が保存され、次回の実行では Session for DOMAIN_VEHICLE_SECURITY loaded from cache というログとともにすぐにコマンドを送ります。キャッシュが古い場合(車両の再起動など)は最初のコマンドが失敗し、車両が新しいセッション情報を送ってくれるので自動的にリトライします。キャッシュファイルは秘密鍵に紐づいており、別の鍵で使うと単に失敗した後に更新されます。ファイルに共有シークレットが直接含まれるわけではありませんが、アクセス権限は制限してください。

Linux の追加設定

Linux 実装は HCI ソケットを直接開き、初期化の過程で HCIDEVDOWN を呼び出すため、CAP_NET_ADMIN 権限が必要です。権限がないと operation not permitted が発生し、CLI が次の案内を出力します。

Failed to initialize BLE adapter:
        ...operation not permitted
Try again after granting this application CAP_NET_ADMIN or running with root:

        sudo setcap 'cap_net_admin=eip' "$(which tesla-control)"
  • setcap は実行ファイル単位で適用されるため、go install でバイナリを再ビルドしたら再設定が必要です。
  • アダプターが複数ある場合は -bt-adapter hci1 のように指定します(hci0〜hci15)。デフォルトは hci0。形式が誤っていると ErrAdapterInvalidID。
  • bluetoothd が同じアダプターを掴んでいてスキャンできない場合は、sudo hciconfig hci0 down の後に再試行するか、専用のアダプターを使ってください。この SDK は BlueZ D-Bus ではなく raw HCI を使用します。

インターネット経路で送る

同じ秘密鍵でインターネット経路も使用できます。違いは、OAuth トークンが必要であること、公開鍵が Tesla 開発者ポータルに登録されたドメインと紐づいている必要があること、そして認証方式が HMAC-SHA256 であることです。

  1. OAuth トークンを取得する。 Fleet API ドキュメントのサードパーティトークンの手順に従います。このリポジトリにはトークンを発行するツールはありません。
  2. トークンをキーリングに保存する。 
    export TESLA_TOKEN_NAME=$(whoami)
tesla-auth-token < token.txt          # または tesla-auth-token token.txt
  3. 公開鍵をドメインに登録し、車両の所有者が承認する。 所有者は Tesla アプリ(4.27.3+)で https://tesla.com/_ak/<your_domain> リンクを開いて承認します。個人の車両であれば、上記の BLE ペアリングで登録した鍵をそのまま使っても構いません。
  4. コマンドを送る。 -ble を外すと、OAuth の設定があれば自動的にインターネット経路を選択します。 
    tesla-control lock
tesla-control product-info          # アカウントコマンド (VIN 不要)
tesla-control get api/1/vehicles/$TESLA_VIN/vehicle_data

車両がスリープしていると Fleet API は 408/503 を返し、SDK は ErrVehicleNotAwake を返します。tesla-control wake は api/1/vehicles/<vin>/wake_up を呼び出し、state == "online" になるまで 10 秒間隔でポーリングします。
