14. 차량 상태 조회

라이브러리가 BLE로 차량에서 읽을 수 있는 모든 정보를 두 부분으로 정리합니다. A부는 요청해서 받는 데이터(보안 컨트롤러 조회 4가지와 인포테인먼트 조회 getState()), B부는 차량이 스스로 보내는 데이터(브로드캐스트)입니다. 보안 컨트롤러 조회 4가지는 인포테인먼트 컴퓨터가 잠들어 있어도 VCSEC가 응답하므로 키도 세션도 깨우기도 필요 없습니다. getState()는 등록된 키, 세션, 깨어 있는 차량이 필요합니다.

현재 구현 범위

A부의 조회는 getState()(A8)를 포함해 구현되어 있으며, 이는 M5의 나머지보다 먼저 들어왔습니다. FakeVehicle 테스트로 확인했고 아직 실차에서는 확인하지 않았습니다. 차량 브로드캐스트(B부)는 vehicle.events로 앱에 전달되며(B2), 관찰 로그에서도 계속 볼 수 있습니다.

VCSEC 요청의 라우팅 규칙:

  • to_destination.domain은 DOMAIN_VEHICLE_SECURITY이고 from_destination.routing_address는 요청마다 새로 만든 무작위 16바이트 주소입니다. 응답은 그 주소로 돌아오며 라이브러리는 주소(와 차량 도메인)로 짝을 찾습니다. VCSEC 응답을 짝지을 때 request_uuid는 쓰지 않습니다. uuid(51)에는 무작위 16바이트를 계속 채웁니다.
  • 다른 라우팅 주소 앞으로 온 응답은 우리 것이 아니며 no-handler로 버립니다(B3 참고).
  • 조회는 인증하지 않습니다. signature_data가 없고 protobuf_message_as_bytes는 평문 UnsignedMessage입니다. 명령은 같은 봉투에 signature_data와 AES-GCM으로 보호한 페이로드를 담습니다.
  • sessionInfo의 페이로드는 session_info_request(14)이고 to_destination.domain은 요청한 도메인입니다. 응답은 session_info(15)에 담겨 옵니다.

A8.2 호출 순서

getState는 세션을 시작하지 않으며 차량도 깨우지 않습니다. 둘 다 앱이 이 순서로 합니다.

상황getState가 하는 일앱이 할 일
인포테인먼트 세션 없음아무것도 보내지 않고 Failure(NoSession)을 반환합니다먼저 startSession(setOf(VehicleDomain.INFOTAINMENT))
캐시에서 복원한 세션을 차량이 더 이상 받아들이지 않음Failure(NoSession)을 반환하고, 이후 sessions에서 INFOTAINMENT가 None으로 표시됩니다startSession(setOf(VehicleDomain.INFOTAINMENT))를 호출한 뒤 다시 조회
인포테인먼트가 잠들어 있음요청을 한 번 보내고 응답을 받지 못해 Uncertain(Timeout(afterSend = true))을 반환합니다아래와 같이 먼저 깨웁니다
 
Awake:    connect → startSession(setOf(INFOTAINMENT)) → getState(category)
Asleep:   connect → vehicleStatus() shows ASLEEP → startSession(setOf(VCSEC)) → wakeUp()
            → vehicleStatus() shows AWAKE → startSession(setOf(INFOTAINMENT)) → getState(category)
  • vehicleStatus()로 판단하세요. 세션이 필요 없고 차량을 깨우지도 않습니다.
  • 잠든 차량에서는 VCSEC만으로 핸드셰이크하세요. Go 도구 tesla-control은 인포테인먼트가 잠들어 있을 것으로 보고 BLE 깨우기에서 이렇게 하며, Go 레시피는 이때 두 도메인으로 핸드셰이크하면 오래 걸릴 수 있다고 경고합니다.
  • wakeUp()이 Success를 반환했다는 것은 VCSEC가 명령을 받아들였다는 뜻이지 인포테인먼트가 켜졌다는 뜻이 아닙니다. AWAKE가 될 때까지 기다린 뒤 인포테인먼트 세션을 시작하세요. 깨운 직후에도 차량이 busy로 응답할 수 있으며, 라이브러리는 이를 시간 제한 안에서 재시도하므로 깨운 뒤 첫 조회에는 더 긴 timeout이 필요할 수 있습니다.
  • 저장된 세션은 수면 상태와 무관합니다. 인포테인먼트가 잠들어 있어도 startSession은 차량에 묻지 않고 성공하며 sessions에는 Ready(fromCache = true)가 표시됩니다. 그러면 첫 조회가 시간 초과될 수 있습니다. 대신 sleepStatus를 읽으세요.
  • 깨울지는 앱이 결정합니다. 라이브러리는 대신 깨우지 않습니다.
import dev.mirolab.teslable.Vehicle
import dev.mirolab.teslable.model.*
import kotlinx.coroutines.delay
import kotlin.time.Duration.Companion.seconds

// vehicle was connected with an enrolled key (12-lib-getting-started.md). True when getState can be called.
suspend fun prepareInfotainment(vehicle: Vehicle): Boolean {
    val status = vehicle.vehicleStatus()                                  // no session needed, never wakes the car
    if (status is VehicleResult.Success && status.value.sleepStatus == SleepStatus.ASLEEP) {
        if (vehicle.startSession(setOf(VehicleDomain.VCSEC)) !is VehicleResult.Success) return false
        if (vehicle.wakeUp() is VehicleResult.Failure) return false       // Uncertain: do not resend, the loop reads the state
        for (attempt in 1..30) {                                          // about 30 s; the real wake time is not confirmed (#118)
            delay(1.seconds)
            val now = vehicle.vehicleStatus()
            if (now is VehicleResult.Success && now.value.sleepStatus == SleepStatus.AWAKE) break
        }
    }
    return vehicle.startSession(setOf(VehicleDomain.INFOTAINMENT)) is VehicleResult.Success
}

func prepareInfotainment(vehicle: Vehicle) async throws -> Bool {
    let status = try await vehicle.vehicleStatus(timeout: nil)                 // no session needed, never wakes the car
    if case .success(let s) = onEnum(of: status), (s.value as? VehicleStatus_)?.sleepStatus == .asleep {
        let vcsec = try await vehicle.startSession(domains: [.vcsec], timeout: nil)
        guard case .success = onEnum(of: vcsec) else { return false }
        let woke = try await vehicle.wakeUp(timeout: nil)
        if case .failure = onEnum(of: woke) { return false }                   // uncertain: do not resend, the loop reads the state
        for _ in 1...30 {                                                      // about 30 s; the real wake time is not confirmed (#118)
            try await Task.sleep(nanoseconds: 1_000_000_000)
            let now = try await vehicle.vehicleStatus(timeout: nil)
            if case .success(let n) = onEnum(of: now), (n.value as? VehicleStatus_)?.sleepStatus == .awake { break }
        }
    }
    let session = try await vehicle.startSession(domains: [.infotainment], timeout: nil)
    if case .success = onEnum(of: session) { return true }
    return false
}

30초는 Go의 BLE 예제에서 가져온 값이며 측정값이 아닙니다. 폴링하는 대신 앱이 vehicle.events의 sleepStatus를 지켜볼 수도 있습니다(B2).

A8.3 응답 읽기

  • 없음은 0이 아닙니다. 12개 응답 메시지에 직접 달린 모든 스칼라 필드와 메시지 필드는 null을 허용합니다. 차량이 보내지 않은 필드는 null이고, speed = 0은 0 그대로입니다. null을 0으로 바꾸지 마세요. 반복 필드(charge_schedules, precondition_schedules)는 없으면 빈 리스트입니다. ChargeSchedule 같은 중첩 메시지 안의 필드는 일반 proto3 값이므로, 없으면 0, 빈 값 또는 false로 읽힙니다.
  • 사용하는 모든 필드를 확인하세요. vehicleData가 없는 응답은 빈 vehicleData와 같은 Success(VehicleData())이며, 둘은 구분할 수 없습니다. Go는 이 경우 (nil, nil)을 반환하지만, 라이브러리는 앱이 어차피 필드마다 확인하므로 null이 아닌 결과를 유지합니다. Ping 같은 다른 종류의 응답도 같은 빈 결과를 줍니다.
  • 응답은 category와 대조해 검사하지 않습니다(Go와 같음). 요청한 카테고리의 필드를 읽으세요. 다른 필드가 오면 그대로 전달됩니다.
  • Success가 새 측정값의 증거는 아닙니다. timestamp를 이전 응답과 비교하세요. 움직이지 않았다면 값을 최신인 것처럼 보여 주지 마세요. null이면 알 수 없습니다. timestamp는 Wire Instant이며, getEpochSecond()는 공통 Kotlin과 Swift에서 모두 동작합니다.
  • 속도, 출력, 주행거리계는 DRIVE에만 있으며, 이 응답은 차량의 크기 상한을 넘을 수 있습니다(16. 에러 처리). 실시간 속도는 보장되지 않으며, 다른 출처도 없습니다.
  • Wire는 proto 이름을 그대로 유지하므로 필드는 drive_state, speed_float, charge_state처럼 직접 작성한 모델의 camelCase와 다릅니다. 생성된 타입은 com.tesla.generated.*에 있습니다.
  • 결과를 로그에 남기지 마세요, toString()도 마찬가지입니다. VehicleData에는 위치와 목적지가 들어 있을 수 있습니다. 라이브러리는 이를 로그에 남기지 않으며, 앱도 남기지 말아야 합니다.

suspend fun readSpeed(vehicle: Vehicle): Int? {
    when (val result = vehicle.getState(StateCategory.DRIVE)) {
        is VehicleResult.Success ->
            return result.value.drive_state?.speed               // null = the vehicle did not send it; 0 = it sent 0
        is VehicleResult.Uncertain -> {

                return null                                      // reply too large
            }
            if (e is VehicleError.Timeout) return null           // no reply
            return null
        }
        is VehicleResult.Failure -> {
            if (result.error == VehicleError.NoSession) return null
            return null
        }
    }
}

A8.5 실차에서 확인되지 않은 것(#118)

  • getState 전체: 지금까지 FakeVehicle에서만 실행되었습니다.
  • 각 카테고리가 실제로 어떤 필드를 담고 있는지, 그리고 얼마나 자주 갱신되는지.
  • speed와 speed_float의 단위. km/h나 mph라고 가정하지 마세요.
  • timestamp가 무엇을 나타내는지: 측정 시각인지 응답 시각인지. 이것이 밝혀질 때까지는 A8.3의 확인이 최선입니다.
  • 깨우는 데 얼마나 걸리는지, 그리고 잠든 인포테인먼트 컴퓨터가 요청을 받으면 어떻게 하는지. 테스트는 응답이 없는 경우로 모델링했습니다. 실차가 대신 busy로 응답하면 라이브러리는 시간 제한까지 재시도하며, 결과는 Failure(Timeout(afterSend = false))가 될 수 있습니다(16. 에러 처리).
  • 크기 상한이 펌웨어별로 어떻게 동작하는지, 그리고 우리 getState에서 오류가 어떻게 오는지. 다른 클라이언트 앞 응답에서는 평문 signedMessageStatus로 왔습니다(유력, 16, 응답 크기 상한).

B2. 브로드캐스트 이벤트: vehicle.events

응답 짝짓기는 이전과 같고 Go 원본과도 같습니다. 브로드캐스트에는 라우팅 주소가 없으므로 디스패처는 이를 라우팅에서 버립니다(드롭 사유 TO_DOMAIN). 브로드캐스트는 대기 중인 요청에 닿지 않으며 응답으로 오인되지 않습니다. 관찰 로그도 여전히 [drop:to-domain] 줄을 남깁니다(18. 문제 해결).

여기에 더해 라이브러리는 평문 브로드캐스트를 모두 vehicle.events로 앱에 넘깁니다(FR-035). Go 원본에는 이런 기능이 없고 프레임을 버리기만 합니다. Kotlin과 Swift 예제는 12. 라이브러리 시작하기에, 각 메시지의 의미는 B3에 있습니다.

val events: Flow<VehicleEvent>                    // Vehicle의 멤버

sealed interface VehicleEvent {                   // dev.mirolab.teslable.model
    val raw: ByteArray                            // 받은 프레임 전체. 읽을 때마다 새 복사본. VIN을 가리지 않음
    val unknownFields: List<String>               // 스키마가 모르는 필드의 경로. 예: "53", "1.8"
    class Status(val status: VehicleStatus, …) : VehicleEvent
    class AuthenticationRequest(val requestedLevel: AuthenticationLevel, val reasons: List<AuthenticationReason>, …) : VehicleEvent
    class Unrecognized(…) : VehicleEvent
}

앱이 지킬 규칙

  • 반복은 변화가 아닙니다. 바뀐 것이 없으면 차량은 직전 Status의 60.0초 뒤에 상태를 다시 보냅니다(유력. 깨어 있고 사람이 있는 차량에서만 측정, B3.1). 변화가 있을 때는 1초 안에 프레임이 여러 개 오기도 하고 그중 일부는 똑같습니다. 모델에 나타나지 않는 필드 8만 다른 프레임도 있어서, 이때 VehicleStatus는 바뀌지 않은 것으로 읽힙니다. 라이브러리는 반복을 거르지 않으므로 이전 값과 직접 비교하세요.
  • 1분 동안 조용한 것은 정상입니다. Status 프레임 사이는 60초까지 벌어질 수 있으므로, 60초까지 오지 않아도 링크 상태를 알 수 없습니다. 링크는 마지막 이벤트 이후 경과 시간이 아니라 connection으로 판단하세요.
  • 트렁크: 밖에서 손으로 트렁크를 열고 닫았을 때는 브로드캐스트가 왔습니다(rearTrunk = OPEN, 이후 closureStatuses 없음). 실내 버튼으로는 전혀 오지 않았으므로, events로 트렁크를 추적하는 앱에는 계속 CLOSED로 보입니다. 트렁크 상태가 중요하면 vehicleStatus()로 확인하세요.
  • 깨어나는 차량: 잠든 차량의 첫 프레임은 닫힘 상태가 UNKNOWN, gear = UNKNOWN으로 보일 수 있으며, 약 0.5초 안에 실제 값이 따라옵니다(B3.1). 그 UNKNOWN 값을 변경으로 취급하지 마세요. 이 프레임에서는 잠금 상태도 UNLOCKED로 읽히는데, UNLOCKED는 인코딩되지 않는 값이라 차가 아직 잠겨 있었는지 알 수 없습니다. 중요하면 vehicleStatus()로 확인하세요.
  • 깨어 있는 차량의 gear = UNKNOWN (유력): 주차 중이고 깨어 있으며 사람이 있는 차량이 기어 필드가 없는 24바이트 프레임을 두 번 보냈고, 0.1초 안에 정상적인 PARK 프레임이 이어졌습니다. 그 UNKNOWN을 변경으로 취급하지 마세요.
  • 구독: 수집은 시작한 순간부터 받습니다. 그 전의 브로드캐스트는 다시 오지 않습니다. 여러 곳에서 수집하면 각자 모든 이벤트를 받습니다.
  • 끝: connection이 이유와 상관없이 Disconnected가 되거나 disconnect()를 호출하면, 먼저 온 쪽에서 흐름이 예외 없이 정상적으로 끝납니다. 그 뒤에 시작한 수집은 바로 끝납니다. 그 순간 전달 중이던 프레임은 잃을 수 있습니다. 재연결 판단은 connection으로 하고, 링크가 끊긴 뒤에도 disconnect()는 호출하세요. 새 연결은 자기 events를 가진 새 Vehicle입니다.
  • 느린 수집자: 라이브러리는 뒤처진 수집자를 위해 프레임을 64개까지 보관합니다. 그 이상이면 그 연결의 모든 수집자에게서 새 프레임이 빠지고, 버린 수를 세며, 첫 번째와 100번째마다 WARN 줄을 남깁니다. 오류가 아닙니다(16. 에러 처리). 수집 코드는 가볍게 유지하세요.
  • 키도 세션도 필요 없으며 connect(vin, key = null)로 충분합니다. 실차 관찰은 등록되지 않은 키로 했습니다.

방향지시등(좌, 우), 비상등, 전조등, 상향등조작해도 메시지가 전혀 없고 BLE 스키마에도 해당 필드가 없습니다(vcsec.proto, vehicle.proto, car_server.proto). 알려진 경로는 Tesla Fleet Telemetry(LightsTurnSignal 240, LightsHazardsActive 239, LightsHighBeams 241)뿐이며, 이는 인터넷 서버 경로라 이 라이브러리의 서버 없음 범위 밖입니다
실내 버튼으로 연 트렁크브로드캐스트 없음. 밖에서 손으로 열고 닫으면 브로드캐스트 있음(B3.1). 키카드, 폰 키, 앱은 미시험
잠든 차량깨어나는 동안의 첫 프레임만(3차, 약 0.1초간 ASLEEP). 계속 잠든 채로 있는 차량은 관찰하지 못함
충전 케이블2차(충전구 열기, 충전기 연결, 충전 시작): chargePort = OPEN, 필드 8의 하위 2가 2에서 1로 변경, ENTERED_HIGHER_AUTH_ZONE이 든 authenticationRequest, 항목 1개짜리 필드 53. 3차(걸쇠 풀기, 뽑기, 충전구 문 닫힘): 꽂혀 있는 동안 chargePort는 CLOSED, 걸쇠를 풀면 OPEN, 충전구 문이 닫힌 뒤 없음. 필드 8의 하위 2가 1에서 2로 변경. 케이블 자체에 대한 별도 브로드캐스트는 찾지 못했으며 필드 8도 그것이 아닙니다(B3.1)
다른 폰 키가 다가올 때기록하지 않음
