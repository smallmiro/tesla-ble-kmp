14. Reading Vehicle State

Everything the library can read from the car over BLE, in two parts: Part A is data you ask for (four security-controller queries), Part B is data the car sends by itself (broadcasts). Queries need no key, no session and no wake-up, because VCSEC answers even while the infotainment computer sleeps.

What exists today

The four queries in Part A are implemented. Broadcasts (Part B) are dropped by the library; you can only see them in the observation log. A public vehicle.events API and getState() (infotainment) are planned for M5 and do not exist yet.

The four queries

CallReturnsGo originalFR
vehicleStatus(timeout = null)VehicleResult<VehicleStatus>BodyControllerState (InformationRequest{GET_STATUS})FR-031
keySummary(timeout = null)VehicleResult<WhitelistSummary>KeySummary (GET_WHITELIST_INFO)FR-032
listKeys(timeout = null)VehicleResult<List<WhitelistEntry>>KeySummary + KeyInfoBySlot per occupied slotFR-025
sessionInfo(publicKey, domain, timeout = null)VehicleResult<SessionInfoSummary>SessionInfo (session_info_request)FR-024
  • Each takes an optional timeout; without it the default command timeout (5 seconds) applies. For listKeys() the timeout covers all of its requests together.
  • The car handles one VCSEC request at a time per connection. A query that has to wait for another one spends part of its timeout waiting.
  • These are queries, so an Uncertain result can simply be asked again.
  • Control payloads (lock, trunk, wake-up) are in 15. Commands.

A1. How a request travels

ItemValue
GATT service00000211-b2d1-43f0-9b88-960cebf8b91e

Every frame, in both directions, is a RoutableMessage (universal_message.proto):

FieldNumberTypeMeaning
to_destination6DestinationEither domain (1, enum Domain) or routing_address (2, bytes)
from_destination7DestinationSame shape. Requests carry our routing address; the car's replies carry the car's domain
protobuf_message_as_bytes10bytesPayload (one of): serialized domain message (UnsignedMessage or ToVCSECMessage to the car, FromVCSECMessage back)
session_info_request14SessionInfoRequestPayload (one of): public_key (1), challenge (2)
session_info15bytesPayload (one of): serialized Signatures.SessionInfo
signature_data13Signatures.SignatureDataPresent on authenticated (AES-GCM) commands and replies
signedMessageStatus12MessageStatusoperation_status (1), signed_message_fault (2, MessageFault_E)
request_uuid50bytesEcho of the request uuid (16 bytes). Used to match infotainment replies
uuid51bytesRequest id, 16 random bytes
flags52uint32Bit mask of Flags (FLAG_USER_COMMAND 0, FLAG_ENCRYPT_RESPONSE 1; 2 to 4 exist only in the Teslemetry schema)

Domain values: DOMAIN_BROADCAST 0, DOMAIN_VEHICLE_SECURITY 2 (VCSEC), DOMAIN_INFOTAINMENT 3. The Teslemetry schema also lists 4, 5, 7 and 8; the library does not use them. Its field 53 message_frame is unconfirmed and unused.

Routing rules for VCSEC requests:

  • to_destination.domain is DOMAIN_VEHICLE_SECURITY and from_destination.routing_address is a fresh random 16-byte address for every request. The reply comes back to that address and the library matches it by address (and the car's domain). request_uuid is not used to match VCSEC replies. The uuid (51) is still filled with 16 random bytes.
  • A reply addressed to any other routing address is not ours and is dropped as no-handler (see B3).
  • Queries are unauthenticated: no signature_data, and protobuf_message_as_bytes is the plain UnsignedMessage. Commands use the same envelope with signature_data and an AES-GCM protected payload.
  • For sessionInfo the payload is session_info_request (14) and to_destination.domain is the requested domain; the reply carries session_info (15).

ClosureStatuses has eight ClosureState_E fields, numbered 1 to 8: frontDriverDoor, frontPassengerDoor, rearDriverDoor, rearPassengerDoor, rearTrunk, frontTrunk, chargePort, tonneau.

Mapping rules

A value outside the schema maps to UNKNOWN instead of the zero value. proto3 cannot tell a missing enum from its zero value, so a missing lock state reads as UNLOCKED; the library keeps that Go behaviour for the query. gear has no Go counterpart (the official Go schema ends at field 5); its zero value is GEAR_UNKNOWN, so a missing gear reads as UNKNOWN. Gear was confirmed in broadcasts; whether the car fills it in a query reply has not been checked on a real car. The real-car results show the car omits closureStatuses when everything is closed and sends it while something is open (driver door and charge port seen), so "absent means all closed" matches what we saw. A trunk opened with the interior button was not visible in broadcasts, so read the trunk with this query.

A7. Other request types in the schema

InformationRequestType also defines GET_TOKEN 1, GET_COUNTER 2, GET_EPHEMERAL_PUBLIC_KEY 3, GET_SESSION_DATA 4, GET_PERSONALIZATION_INFO 7, GET_KEYSTATUS_INFO 8, GET_ACTIVE_KEY 9 and GET_CAPABILITIES 16 (Teslemetry only). The library sends none of them and has no API for them. getState(category) (infotainment) is planned for M5 and has no API either.

Sleep and wake-up

  • None of the queries wakes the car. Use sleepStatus to show whether it is asleep.
  • Coming in M5: getState(category) reads the twelve infotainment categories (charge, climate, drive, location, closures, charge schedule, preconditioning schedule, tire pressure, media, media detail, software update, parental controls). It needs an enrolled key and an awake car.
  • wakeUp() (M4) needs only the VCSEC session.
  • When a lock or trunk command (M4) comes back Uncertain, read vehicleStatus() again instead of sending the command a second time.

B2. What the library does with broadcasts

  • The dispatcher drops every broadcast, the same as the Go original: it has no routing address, so routing returns the drop reason TO_DOMAIN. Broadcasts never reach a pending request and cannot be mixed up with replies, which are matched by our routing address.
  • The only way to see them is the observation log: DEBUG, tag observe, line head [drop:to-domain]. Line format and field names are in 18. Troubleshooting; the meaning of each message is in B3.
  • A public vehicle.events API is planned for M5 and is not implemented. There is no public callback, flow or model type for broadcasts today. Until then, read lock, openings, sleep and presence with vehicleStatus().

Wrapped, not bare

This car sent it inside a RoutableMessage (the broadcast form above), unlike reports elsewhere (Teslemetry PR #179) of a bare FromVCSECMessage{authenticationRequest} about every 1.1 s. No bare frame was seen on this car (drop:missing-source and drop:unparseable: 0 lines).

B3.3 Field 53 (unknown)

Status: Unknown. FromVCSECMessage field 53: repeated {1: small int, 2: 35 bytes}.

  • 54 bytes in total (1 entry, id 4) right after connecting and at the charge port event; 205 to 220 bytes (5 entries, ids 1, 3, 4, 6, 7) at door and lock events. The 35-byte blobs of one message differ only in their last 2 bytes.
  • It arrives with authentication events. The ids 1, 3, 4, 6, 7 overlap with enrolled key slot numbers (7 keys seen in M3), so it is probably a per-key authentication challenge. Unconfirmed.

B3.4 Field 48 (unknown)

Status: Unknown. FromVCSECMessage field 48, 20 bytes, about every 5.0 s while the car is awake and a person is present (with gaps). Seen only in the first round, not in the second. Probably a heartbeat; the condition is unknown.

B3.5 Replies addressed to other clients

These are not broadcasts. A signed 83-byte reply (to_destination.routing_address is another client's 16-byte address, 16-byte request_uuid, empty body) answers another phone's VCSEC request. It reaches our link too, about every 1 to 2 minutes and right after a door event. The library drops it as no-handler (owner other).

B5. Observation method and environment

  • iPhone 16 Pro, iOS 27, Model Y (firmware not recorded). Sample dev.mirolab.TeslableSampleDevice builds 7 and 8, key SECURE_ENCLAVE. The key does not need to be enrolled to observe.
  • First round 2026-10-18 (build 7, one continuous recording, 71 lines). Second round 2026-10-24 (build 8, detailed unknown-field decoding, one recording per scenario).
  • To reproduce: turn on the sample's observation mode, perform the scenario, then press the show button (and "copy whole result"). Details and log syntax: 18. Troubleshooting.
