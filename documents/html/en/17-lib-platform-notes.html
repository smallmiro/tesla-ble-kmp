17. Platform Notes

What an Android or iOS app has to set up, where the library keeps keys and sessions, a few platform behaviours worth knowing, and how Swift calls the library. Items not yet confirmed on a real device say so.

Support

  • Android 12 (API 31) or later, iOS 16 or later, with the app in the foreground. Background Bluetooth is out of scope.
  • The JVM target is for tests and experiments. Its keys live in memory and are gone when the process ends.

Android

Declare the two Bluetooth permissions and request them at runtime. Without them, scanning and connecting return PermissionDenied. No internet permission is needed: the library never calls a server.

<uses-permission android:name="android.permission.BLUETOOTH_SCAN" android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<uses-feature android:name="android.hardware.bluetooth_le" android:required="true" />
  • Create the library with PlatformContext(context); it keeps the application context.
  • On connect the library asks for an MTU of 517 and falls back to 20-byte blocks if that fails.
  • Keystore entries are named teslable.key:<alias> and teslable.wrap:<alias>, so they do not collide with your app's own entries.
Exclude the key files from Auto Backup

A software key is saved as files/teslable/keys/<alias>.enc, wrapped by a Keystore key that is never backed up. If Auto Backup restores the file without its wrapping key, the key reads as corrupted. Exclude files/teslable/keys/ in dataExtractionRules or fullBackupContent. The sample app simply sets android:allowBackup="false". Saved sessions in files/teslable/sessions are harmless to lose, but excluding them is cleaner.

Android background use by the sample

The library is supported in the foreground (see Support). The Android sample's monitor app keeps its connection in the background with a foreground service and has not been checked on a real device yet, so treat the library's behaviour in the background as unconfirmed.

  • Manifest: FOREGROUND_SERVICE, FOREGROUND_SERVICE_CONNECTED_DEVICE, POST_NOTIFICATIONS (asked at runtime) and <service android:foregroundServiceType="connectedDevice" />. Still no INTERNET.
  • Android 14 and later: a connectedDevice foreground service can only start after BLUETOOTH_CONNECT is granted, and only while the app is visible (or another start exemption applies). Do not rely on the system to restart it.
  • The service owns the single library instance and calls vehicle.disconnect() after every link loss, then connects again with a new Vehicle (2 second wait, doubling to 30 seconds). Retrying is the app's job, not the library's.
  • Key store: the sample creates its key with KeyAccessibility.AFTER_FIRST_UNLOCK; Android ignores the argument and reports AFTER_FIRST_UNLOCK (per API, not yet confirmed on a device, see Key storage).

iOS

  • Add NSBluetoothAlwaysUsageDescription to Info.plist. The first scan shows the permission prompt; if the user declines, calls return PermissionDenied.
  • Create the library with PlatformContext().
  • The simulator has no Bluetooth. Scanning and connecting can only be tried on a real iPhone.
  • iOS has no MTU negotiation API; the library uses the write length the system picks. The observed block length on a real iPhone is 512. The response characteristic supports both notifications and indications; the Kable default subscription (notify) was confirmed on a real car (ADR-0003).
  • Swift calls Kotlin through SKIE: suspend functions become async throws, Flow becomes AsyncSequence, sealed types work with switch onEnum(of:), and companion members are reached through .companion.
  • In Swift the public VehicleStatus is named VehicleStatus_, because a generated VCSEC message type already takes the plain name. Results of vehicleStatus() and VehicleEvent.Status.status have this type.

iOS background use by the sample

The library is supported in the foreground (see Support). The iOS sample's monitor app declares UIBackgroundModes: [bluetooth-central] and runs the same reconnect loop as the Android sample. It has not been checked on a real iPhone yet, so treat the library's behaviour in the background as unconfirmed.

  • Info.plist (through project.yml): UIBackgroundModes: [bluetooth-central]; UIFileSharingEnabled and LSSupportsOpeningDocumentsInPlace only for the sample's log folder.
  • The app owns the single library instance for its lifetime and calls vehicle.disconnect() after every link loss, then connects again with a new Vehicle (2 second wait, doubling to 30 seconds). Retrying is the app's job, not the library's.
  • Unconfirmed: whether iOS lets the app scan and reconnect while it is in the background or the phone is locked (the library currently scans by device name, and iOS usually needs a service UUID filter for background scans; plan Tasks 2 and 8). Until the real-car spike runs, the only supported background case is a link that stays up: events keep arriving while iOS keeps the app running.
  • Key store: the sample creates its key with KeyAccessibility.AFTER_FIRST_UNLOCK. While the phone is locked and the key store answers KeyStoreError.Locked, the sample waits, retries, and never deletes the key.

Key storage

protectionMeaning
SECURE_ENCLAVEiOS Secure Enclave. The private key never leaves the chip
STRONGBOXAndroid StrongBox security chip
TEEAndroid Trusted Execution Environment
SOFTWAREEmulators, simulators, or a device where every hardware attempt failed
  • Software keys are wrapped by an Android Keystore AES key, or stored as an iOS Keychain item that never leaves the device and is protected according to the key's accessibility setting.
  • On iOS, a failed Secure Enclave lookup is reported as an error, not as "no key", so a working key is never overwritten by mistake.
  • There is no API to export a private key.
  • Key handles are released automatically. On iOS each key object holds one Security framework reference (SecKeyRef). It is released once neither the app nor a connected Vehicle uses the key any more and the Kotlin/Native garbage collector has run. There is nothing to close, and reading the key again does not pile up handles.

Using the key while the phone is locked

Each key has an accessibility setting, VehicleKey.accessibility. How to choose it and switch keys is in 13. Keys and Pairing.

PlatformWhen a key is createdWhat an existing key reports
iOSWHEN_UNLOCKED (default) uses kSecAttrAccessibleWhenUnlockedThisDeviceOnly and AFTER_FIRST_UNLOCK uses kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, for the Secure Enclave key and the software key alikeThe setting read back from the stored key. It never changes afterwards
AndroidThe setting is ignoredAlways AFTER_FIRST_UNLOCK: the Keystore keys have no unlock or user-authentication requirement, and the key file can be read after the first unlock. By the API; not yet confirmed on a device
JVMThe setting is ignoredAlways AFTER_FIRST_UNLOCK: keys in memory have no lock
  • On a locked iPhone, the Keychain error errSecInteractionNotAllowed (-25308) becomes KeyStoreError.Locked. A WHEN_UNLOCKED key cannot be read or used for a handshake while the phone is locked; an AFTER_FIRST_UNLOCK key can, once the phone was unlocked after the last restart. Before that first unlock every key is locked. A key that cannot be created because the phone is locked is not replaced by a software key.
  • A key object read before the phone locked: when the Secure Enclave refuses the key agreement with the same error (-25308), the handshake ends with KeyStoreError.Locked as soon as the car answers and is not retried, and a saved session that needed the key is not restored but stays saved (13). Other key agreement errors behave as before (the handshake keeps trying until its timeout). A software key object keeps its private key in memory and keeps working after the lock (per the API).
  • Not yet confirmed on a device: the Keychain round trip of both settings, reading the setting back, and a handshake on a locked iPhone with an AFTER_FIRST_UNLOCK Secure Enclave key; also which error a locked iPhone reports for the key agreement of a WHEN_UNLOCKED Secure Enclave key (the library expects -25308; with another error startSession() still ends with a timeout). They are checked with the sample app (build 12 is ready; the checks are plan Task 11). Using the key while the phone is locked also needs the app to keep running in the background, which these pages do not cover yet.
A corrupted key is never replaced automatically

If getOrCreate or get returns PlatformFailure with stored key is corrupted, tell the user, then call delete and getOrCreate. The new key has a different public key and must be enrolled on the car again. Replacing it silently would leave the user unable to control the car without knowing why.

Session cache

  • Saved sessions let the next connection skip the handshake. They are stored in files/teslable/sessions/ on Android, in the Keychain on iOS, and in memory on the JVM. You can supply your own with TeslaBleConfig.sessionCache.
  • Names are hashes of the VIN, so the VIN itself is not stored.
  • Sessions belong to one key. After the key changes, or when the car has moved on, old sessions are discarded on the next connection.
  • A missing or outdated cache is not an error; the library simply starts a new session.
  • A saved session that could not be restored because the phone lock blocked the key (iOS) is not outdated. The library writes nothing to the cache until that part of the car has a session again, so disconnecting while the phone is locked keeps the saved sessions. Exception: if another saved session turned out to be outdated in the same connection, the library rewrites the cache without it, and the blocked session is dropped too (that part of the car makes a new handshake next time).
  • The app may end without disconnect(): the user force-quits it, the system ends it while suspended, or it crashes. On iOS this is how an app usually ends. The library saves the anti-replay counter before it uses it (a reservation 16 counters ahead, ADR-0016), so the first signed request of the next launch is accepted at once, without a handshake and without a refusal. Before this change (builds up to 2026-11-14) the car refused that request once with an invalid-counter fault and fresh session information; the library applied it and resent the request, which added about 1.2 s. The result was still Success and the refused copy did not run. A cache saved by such an older build can still cause this once after the upgrade.
  • The reservation costs one cache write (a file write on Android, a Keychain write on iOS) before the first signed request of each connection and then one every 16 requests. It counts against that call's time limit; a timeout there is Failure(Timeout) because nothing was sent.
  • This assumes that the cache write succeeds and that your app keeps one live connection per car and key. If a write fails, the library logs it, sends the request anyway, and the old behaviour can come back once. Two connections to the same car with the same key, or another app using the same key, are not protected.

Clocks

Session timing uses the monotonic clock, which stops on some platforms while the phone sleeps. After a long sleep, the first command from a saved session may fail with an expiry fault. The library then takes the fresh session information the car sends back and retries; the app sees nothing.

Connection slots and dropped links

  • A car accepts at most three Bluetooth connections. Call disconnect() when you are done so the slot is free. When all three are taken, connecting returns MaxConnectionsExceeded.
  • When the link drops and connection turns Disconnected, still call disconnect() so the session keys are erased. Calling it again is harmless.
  • A disconnected Vehicle cannot be reused; connect again with TeslaBle.connect.

Swift: timeouts

Kotlin's Duration is an inline value class. Swift sees it only as a boxed Any?, so Swift code cannot build one directly. Two helpers solve this.

  • Timeouts.shared.seconds(seconds:) returns the boxed value to pass as any timeout: argument. Zero, negative, NaN or infinite input throws IllegalArgumentException. Timeouts.shared.millisecondsOf(timeout:) returns the milliseconds of a boxed value (-1 for nil); it exists to check the round trip. The iOS sample's XCTest target runs in tools/ci/verify.sh step (d).
  • TeslaBleConfig.companion.withSeconds(logger:commandTimeoutSeconds:handshakeTimeoutSeconds:connectTimeoutSeconds:pairingTimeoutSeconds:) builds a config from seconds. Every argument is required; commandLifetime keeps its default. TeslaBleConfig.companion.default(logger:) is unchanged.
  • timeout: nil still means "use the config default".

Swift: generated types (getState)

getState returns the Wire generated VehicleData, which behaves differently in Swift from the hand-written models. The full example is in 14. Reading Vehicle State. These forms pass a Swift typecheck against the framework; they have not run in a Swift program.

  • vehicle is the Vehicle protocol. Pass every argument: vehicle.getState(category: .drive, timeout: nil), or timeout: Timeouts.shared.seconds(seconds: 8). Without timeout: the compiler reports missing argument for parameter 'timeout' in call.
  • The generic of VehicleResult is erased, so s.value is AnyObject?. Cast it: s.value as? VehicleData.
  • Nullable numbers bridge as KotlinInt? and KotlinFloat?, not Int32? and Float?. Read .int32Value and .floatValue. let speed: Int32? = data.drive_state?.speed is rejected, and the compiler says only failed to produce diagnostic for expression, so that message will not help.
  • Generated fields keep their proto names in Swift (drive_state, speed_float, charge_state), unlike the camelCase hand-written models.
  • timestamp is a Wire Instant: charge.timestamp?.getEpochSecond() gives Int64?.
  • shift_state is not an enum. ShiftState is a Wire oneof message: its members P, R, N, D, SNA and CarServer_Invalid are nullable, and the one that is not nil is the gear (data.drive_state?.shift_state?.P != nil). If none is set, the vehicle sent no gear. Do not compare it with a string or an enum value.
  • Every other state oneof with Void members works the same way: charge_state?.charging_state, charge_port_latch, closures_state?.sun_roof_state, sentry_mode_state, software_update_state?.status, location_state?.native_type (GCJ or WGS) and climate_state?.climate_keeper_mode. The member that is not nil is the value (charging_state?.Charging != nil). A message that arrives with no member set reads the same as an absent one, so treat both as "no value". Fields of nested messages such as ParentalControlsSettings are KotlinBoolean? / KotlinFloat? / KotlinInt? like the top-level ones, while ChargeSchedule and PreconditionSchedule entries in the repeated lists have plain values (enabled, one_time), so an absent flag there reads as false.
  • The type names are plain: VehicleData, DriveState, StateCategory. Only VehicleStatus_ has the name clash.
  • StateCategory is a real Swift enum, so a switch over all 12 needs no default: .charge, .climate, .drive, .location, .closures, .chargeSchedule, .preconditioningSchedule, .tirePressure, .media, .mediaDetail, .softwareUpdate, .parentalControls.
  • The enum in .protocolFault is MessageFault_E. The size limit case is .messagefaultErrorResponseMtuExceeded: case .protocolFault(let p) where p.fault == .messagefaultErrorResponseMtuExceeded:.

Swift: command arguments (infotainment commands)

How Swift calls the infotainment commands (15. Commands). These forms pass a Swift typecheck against the framework (the debug simulator framework, 2026-11-08); they have not run in a Swift program.

  • Pass every argument, including timeout: (nil uses the config default): try await vehicle.climateOn(timeout: nil). Without it the compiler reports missing argument for parameter 'timeout' in call.
  • The argument enums are real Swift enums, so a switch over them needs no default: SeatPosition (.unknown, .frontLeft, .frontRight, .secondRowLeft, .secondRowLeftBack, .secondRowCenter, .secondRowRight, .secondRowRightBack, .thirdRowLeft, .thirdRowRight), SeatClimateLevel (.off, .low, .med, .high), ClimateKeeperMode (.off, .on, .dog, .camp), CabinOverheatProtectionTemperature (.unspecified, .low, .medium, .high), ChargingPolicy (.off, .allDays, .weekdays).
  • setSeatHeater(levels:timeout:) takes a Swift dictionary [SeatPosition: SeatClimateLevel], and a literal works: try await vehicle.setSeatHeater(levels: [.frontLeft: .high, .secondRowCenter: .off], timeout: nil). An empty [:] is sent too. Swift dictionaries have no order; the library sends the seats in the order of SeatPosition anyway.
  • autoSeatAndClimate(seats:enabled:timeout:) takes a Swift array: seats: [.frontLeft, .frontRight].
  • Numbers: percent, amps, the minutes, the sunroof level and delaySeconds are Int32, schedule ids Int64, temperatures and volume Float; plain number literals work, as in scheduleDeparture(departAtMinutes: 480, offPeakEndMinutes: 360, preconditioning: .allDays, offPeak: .weekdays, timeout: nil), setVolume(volume: 5.5, timeout: nil), setSunroof(level: 0, timeout: nil) and scheduleSoftwareUpdate(delaySeconds: 7200, timeout: nil).
  • The valet PIN is a Swift String: enableValetMode(pin: pin, timeout: nil). Do not log it.
  • After an uncertain toggleMediaPlayback(timeout:), read the playback state instead of sending it again: data.media_state?.media_playback_status == .playing (MediaPlaybackStatus is a Swift enum: .playing, .paused, .stopped).
  • ChargeSchedule and PreconditionSchedule are generated protocol classes. Swift gets no default arguments, so build them with every field plus unknownFields: OkioByteString.companion.EMPTY. ChargeSchedule() is rejected with 'init()' is unavailable. The fields keep their protocol names:
let schedule = ChargeSchedule(
    id: 1_700_000_000, name: "Home", days_of_week: 127, start_enabled: true, start_time: 120,
    end_enabled: false, end_time: 0, one_time: false, enabled: true,
    latitude: 0, longitude: 0, unknownFields: OkioByteString.companion.EMPTY)
_ = try await vehicle.addChargeSchedule(schedule: schedule, timeout: nil)
_ = try await vehicle.removeChargeSchedule(id: schedule.id, timeout: nil)   // id is Int64

let precondition = PreconditionSchedule(
    id: 2, name: "Work", days_of_week: 62, precondition_time: 450, one_time: false, enabled: true,
    latitude: 0, longitude: 0, unknownFields: OkioByteString.companion.EMPTY)
_ = try await vehicle.addPreconditionSchedule(schedule: precondition, timeout: nil)
  • An argument the library refuses comes back as .failure with .invalidArgument: if case .failure(let f) = onEnum(of: result), case .invalidArgument(let bad) = onEnum(of: f.error) { … bad.detail … } (16. Error Handling).
