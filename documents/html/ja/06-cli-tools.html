6. CLI ツール

cmd/ 配下の 5 つのツール(tesla-keygen、tesla-control、tesla-auth-token、tesla-jws、tesla-http-proxy)の使い方、オプション、環境変数、キーリングの動作をまとめます。

インストール

cd vehicle-command
go get ./...
go build ./...
go install ./...          # $GOBIN (デフォルト ~/go/bin) に 5 つのツールをインストール。make install と同等(./cmd/... のみインストール)

Docker イメージ tesla/vehicle-command にも 5 つのツールがすべて含まれており、デフォルトのエントリーポイントは tesla-http-proxy です。他のツールは --entrypoint で指定します。ただし、コンテナ内からはホストの BLE アダプターにアクセスできないため、BLE コマンドはローカルビルドで実行してください。

docker run --entrypoint tesla-keygen tesla/vehicle-command:latest -h
プラットフォーム

macOS と Linux に対応しています。Windows では BLE 以外の機能はビルドされますが、pkg/connector/ble の newAdapter が not supported on Windows を返すため、tesla-control -ble は動作しません。Linux では BLE アダプターの初期化に CAP_NET_ADMIN が必要です(トラブルシューティング)。

共通の環境変数

pkg/cli.Config.ReadFromEnvironment() は、コマンドラインフラグで設定されなかった値だけを環境変数で埋めます。つまり、常にフラグが優先されます。

環境変数対応するフラグ意味使用するツール

TESLA_KEY_FILE-key-file秘密鍵 PEM ファイルのパス。名前とファイルの両方があればファイルが優先して読み込まれるkeygen, control, jws, http-proxy
TESLA_TOKEN_NAME-token-nameキーリングに保存された OAuth トークンの名前control, auth-token, keygen(登録のみ)
TESLA_TOKEN_FILE-token-fileOAuth トークンファイルのパス。ファイルがなければキーリングにフォールバックcontrol
TESLA_VIN-vin17 文字の VINcontrol, jws
TESLA_CACHE_FILE-session-cacheセッションキャッシュの JSON ファイル。未指定時は $HOME/.tesla-cache.json。-disable-session-cache で無効化control, keygen, jws, http-proxy(読み込みのみ)
TESLA_KEYRING_TYPE-keyring-typeキーリングのバックエンドの種類。対応一覧は tesla-keygen -h の -keyring-type の説明に OS ごとに表示keygen, control, jws, http-proxy, auth-token(環境変数のみ)

TESLA_VERBOSE-debug / -verbosefalse、0 以外の値ならデバッグログ(TX/RX の 16 進を含む)control, http-proxy

TESLA_HTTP_PROXY_HOST-hostバインドするホスト。デフォルト localhosthttp-proxy
TESLA_HTTP_PROXY_PORT-portバインドするポート。デフォルト 443http-proxy
TESLA_HTTP_PROXY_TIMEOUT-timeoutコマンドのタイムアウト(例: 10s)。デフォルト 10 秒http-proxy

一般的な初期設定:

export TESLA_KEY_NAME=$(whoami)
export TESLA_TOKEN_NAME=$(whoami)
export TESLA_VIN=5YJ30123456789ABC
export TESLA_CACHE_FILE=~/.tesla-cache.json

キーリングの動作

秘密鍵と OAuth トークンは 99designs/keyring を介して OS の資格情報ストアに保管されます。

サービス名
com.tesla.auth (macOS のキーチェーンではこの名前で項目が表示されます)
秘密鍵の項目
vehicleCommandKey.<TESLA_KEY_NAME>。データは 32 バイトの P-256 スカラー(ビッグエンディアン)
OAuth トークンの項目
oauthtoken.<TESLA_TOKEN_NAME>。データはトークン文字列そのまま
デフォルトのバックエンド
OS のデフォルト。macOS はログインキーチェーン(KeychainTrustApplication: true)、Linux は secret-service/kwallet/keyctl など利用可能なもの、ファイルバックエンドは ~/.tesla_keys
パスワード
ファイルバックエンドやキーチェーンのロック解除にパスワードが必要な場合は、ターミナルにプロンプトを表示します。stdout/stderr がどちらもターミナルでなければ no terminal output available for password prompt エラー。無人実行では TESLA_KEYRING_PASSWORD を設定してください。
KeyCtl のスコープ
Linux の keyctl バックエンドは user スコープを使います。

tesla-control は接続タイムアウトが始まる前に config.LoadCredentials() を呼び出し、パスワードプロンプトがタイムアウトを消費しないようにしています。独自のツールを作るときも同じ順序を守ってください。

tesla-keygen

コマンド認証用の P-256 秘密鍵を生成・削除・エクスポート・移行し、公開鍵を PEM で出力します。

usage: tesla-keygen [OPTION...] create|delete|export|migrate
サブコマンド動作
create鍵がすでにある場合(キーリング名またはファイル)は生成せず、既存の鍵の公開鍵だけを出力します。-f を指定すると新しい鍵で上書きします。保存先は、-key-name があればキーリング、なければ -key-file(SEC1 PEM、0600)。どちらもなければ private key location not provided。
deleteキーリングから vehicleCommandKey.<name> を削除します。ファイルの鍵は削除しません。
export秘密鍵を EC PRIVATE KEY PEM として stdout に出力します。エクスポートできない鍵の実装であればエラー。
migrate-key-file の PEM 秘密鍵を読み込み、-key-name の名前でキーリングに保存します。両方とも必須。元のファイルはそのまま残します。
オプション説明
-f既存の鍵があっても上書きする (create)
-output file公開鍵を stdout の代わりにファイルに保存
-key-name name, -key-file file鍵の場所。デフォルト $TESLA_KEY_NAME、$TESLA_KEY_FILE
-keyring-type type, -keyring-file-dir directory, -keyring-debugキーリングの設定
-token-name, -token-file, -session-cache, -disable-session-cache, -domaincli.FlagOAuth | cli.FlagPrivateKey で登録されているためフラグは存在しますが、keygen の動作には影響しません
 
# キーリングに生成して公開鍵を保存
export TESLA_KEY_NAME=$(whoami)
tesla-keygen create > public_key.pem

# ファイルベースの鍵を生成 (キーリングなし)
tesla-keygen -key-file ~/.tesla/private.pem create > public_key.pem

# OpenSSL で作った鍵をキーリングへ移行
tesla-keygen -key-file private.pem -key-name $(whoami) migrate

# バックアップ用のエクスポート (出力は秘密情報。安全に保管)
tesla-keygen export > private_backup.pem

# ファイルバックエンドを強制 + 無人実行
TESLA_KEYRING_TYPE=file TESLA_KEYRING_PASSWORD=... tesla-keygen create

出力される公開鍵は PKIX PEM(-----BEGIN PUBLIC KEY-----)です。Fleet API のパートナー登録(/.well-known/appspecific/com.tesla.3p.public-key.pem)と tesla-control add-key-request の両方にそのまま使えます。

tesla-control

BLE またはインターネットで車両にコマンドを送る汎用 CLI です。Windows では動作しません。

Usage: tesla-control [OPTION...] COMMAND [ARG...]
       tesla-control help            # 全コマンドの一覧
       tesla-control help COMMAND    # コマンドごとの引数の説明
       tesla-control                 # COMMAND なしで実行すると対話型シェル

オプション

オプションデフォルト値説明
-blefalseOAuth の環境変数があっても BLE 接続を強制。Fleet API 専用コマンドと併用すると command requires a FleetAPI OAuth token
-debugfalseデバッグログ。TX/RX の 16 進ダンプを含む。TESLA_VERBOSE でも有効化できる
-command-timeout duration5sコマンド 1 つのタイムアウト。この時間内で SDK がリトライを繰り返す
-connect-timeout duration20sスキャン + 接続 + ハンドシェイクのタイムアウト
-vin VIN$TESLA_VIN対象の車両
-key-name name / -key-file file$TESLA_KEY_NAME / $TESLA_KEY_FILEコマンド認証用の秘密鍵
-token-name name / -token-file file$TESLA_TOKEN_NAME / $TESLA_TOKEN_FILEOAuth トークン(インターネット経路)
-session-cache file$TESLA_CACHE_FILE → ~/.tesla-cache.jsonセッションキャッシュファイル。終了時に自動で更新
-disable-session-cachefalseキャッシュを使わない
-domain vcsec|infotainment(すべて)ハンドシェイクするドメイン。繰り返し指定可。例: -domain vcsec でインフォテインメントを起こさない
-keyring-type, -keyring-file-dir, -keyring-debugOS のデフォルト / ~/.tesla_keys / falseキーリングの設定
-bt-adapter id (Linux のみ)hci0使用する Bluetooth アダプター(hci0~hci15)

資格情報の選択ルール

各コマンドは cmd/tesla-control/commands.go で requiresAuth(秘密鍵が必要)と requiresFleetAPI(OAuth トークンが必要)に分類されます。実行前に configureFlags と checkReadiness が次のルールを適用します。

コマンドの種類必要なものトランスポート例
車両コマンド、認証が必要 (requiresAuth)VIN + 秘密鍵OAuth があればインターネット、-ble 指定時または OAuth がなければ BLElock, climate-on, state charge
車両コマンド、認証不要VIN同上list-keys, session-info, body-controller-state, add-key-request, wake(インターネット)
アカウントコマンド (requiresFleetAPI)OAuth トークンインターネットのみ。-ble と併用するとエラーproduct-info, rename-key, get, post
-ble wakeVIN + 秘密鍵BLE。VCSEC とだけハンドシェイク(インフォテインメントがスリープ中のため)tesla-control -ble wake

body-controller-state は domain: protocol.DomainVCSEC が指定されているため、VCSEC とだけハンドシェイクします。他のコマンドは -domain フラグで制限できます。

対話型シェル

COMMAND なしで実行すると、接続を 1 回確立し、> プロンプトから複数のコマンドを続けて送れます。ハンドシェイクを毎回繰り返さないので、複数のコマンドを試すときに便利です。引数は shlex でパースされるため引用符を使え、exit で終了します。各コマンドには -command-timeout が適用されます。

$ tesla-control -ble
> body-controller-state
{ "vehicleLockState": "VEHICLELOCKSTATE_LOCKED", ... }
> unlock
> climate-set-temp 21C
> exit

出力と終了コード

  • 成功: 終了コード 0。ほとんどのコマンドは何も出力しません。state、body-controller-state、session-info、list-keys、product-info、get/post、charging-schedule-add(生成された ID)などは stdout に結果を出力します。
  • Couldn't verify success: …: コマンドは届いた可能性があるが確認が取れていない(protocol.MayHaveSucceeded)。終了コード 1。
  • You must provide a private key with -key-name or -key-file to execute this command: protocol.ErrNoSession。終了コード 1。
  • Failed to execute command: …: その他のエラー。終了コード 1。
  • Linux でアダプターの権限エラーの場合は setcap の案内文を出力します。

例

# 鍵のペアリング (車内で、NFC カードを用意)
tesla-control -ble add-key-request public_key.pem owner cloud_key

# 登録の確認
tesla-control -ble list-keys
tesla-control -ble session-info public_key.pem infotainment

# 基本コマンド
tesla-control -ble lock
tesla-control -ble -domain vcsec unlock           # インフォテインメントを起こさない
tesla-control -ble climate-set-temp 72F
tesla-control -ble seat-heater front-left high
tesla-control -ble charging-set-limit 80
tesla-control -ble state climate
tesla-control -ble -debug ping                    # TX/RX ダンプを確認

# インターネット経路 (OAuth トークンがキーリングにある場合)
tesla-control wake
tesla-control lock
tesla-control product-info
tesla-control get "api/1/vehicles/$TESLA_VIN/vehicle_data"

# 充電スケジュール
tesla-control -ble charging-schedule-add weekdays 22:00-06:00 37.4 -122.1
tesla-control -ble charging-schedule-remove home

全コマンドと引数は 7. コマンドリファレンス を参照してください。

tesla-auth-token

OAuth トークンを stdin またはファイルから読み込み、キーリングの oauthtoken.<name> 項目として保存します。トークンの発行は行いません。発行手順は Fleet API のドキュメントに従ってください。

usage: tesla-auth-token [-token-name token_name] [file]
オプション説明
-token-name nameキーリングの項目名。デフォルト $TESLA_TOKEN_NAME。これが唯一のフラグです。キーリングの種類/パス/パスワードは TESLA_KEYRING_TYPE、TESLA_KEYRING_PATH、TESLA_KEYRING_PASSWORD 環境変数でのみ指定します。
file (位置引数)トークンを含むファイル。省略すると stdin から EOF まで読み込みます。2 つ以上指定するとエラー。
 
export TESLA_TOKEN_NAME=$(whoami)
echo -n "$ACCESS_TOKEN" | tesla-auth-token
tesla-auth-token token.txt
# 保存後、tesla-control は OAuth があるためデフォルトでインターネット経路を使う。BLE を使うには -ble。
トークン文字列はそのまま保存されます

読み込んだバイト列を加工せずに保存するため、末尾の改行が含まれることがあります。account.New が strings.TrimSpace で整えるので、動作には問題ありません。期限切れのトークンは更新後に再度保存する必要があります。

tesla-jws

Fleet Telemetry の設定などに使う JWS(JSON Web Signature)を、コマンド認証用の秘密鍵で署名または検証します。署名アルゴリズムは JWS 標準にはない Tesla.SS256(Schnorr/P-256 + SHA-256)で、既存の ECDH/P-256 鍵を署名鍵として安全に再利用するためのものです。

usage: tesla-jws [OPTION...] sign APP [JSON_FILE]
       tesla-jws verify [JWS_FILE]
サブコマンド / オプション説明
sign APP [JSON_FILE]JSON_FILE(なければ stdin)の JSON オブジェクトをクレームとして署名します。iss は base64 の公開鍵、aud はコンテキスト文字列で上書きされます。結果の JWS を stdout に出力。
-fleetフリート全体用の署名。aud = com.tesla.fleet.<APP>。指定しない場合は -vin が必須となり、aud = com.tesla.vehicle.<VIN>.<APP> となって該当車両だけが受け入れる。
verify [JWS_FILE]署名が iss の公開鍵で有効かどうかだけを検査し、クレームを JSON で出力します。発行者が信頼できるか、aud が正しいかは検査しません。
-vin, -key-name, -key-file, -keyring-*, -session-cache, -domaincli.FlagPrivateKey | cli.FlagVIN の共通フラグ
 
# Fleet Telemetry 設定に署名 → Fleet API /api/1/vehicles/fleet_telemetry_config_jws に POST
tesla-jws -fleet sign TelemetryClient telemetry_config.json > signed-config.jws
tesla-jws verify signed-config.jws

# 特定車両専用の署名
tesla-jws -vin $TESLA_VIN sign TelemetryClient telemetry_config.json

生成された .jws ファイルは秘密情報ではありません(JWT と同じ構文ですが、bearer トークンではありません)。プロキシの /api/1/vehicles/fleet_telemetry_config エンドポイントは、同じ署名をサーバー側で自動的に行います(8. HTTP プロキシ)。

tesla-http-proxy

REST リクエストをエンドツーエンド認証コマンドに変換する HTTPS サーバーです。オプション、ルーティング、レスポンス形式、デプロイについては 8. HTTP プロキシ で詳しく扱います。概要:

tesla-http-proxy -tls-key config/tls-key.pem -cert config/tls-cert.pem -key-file config/fleet-key.pem -port 4443
オプションデフォルト値説明
-cert file(必須)サーバー + 中間 CA + ルート CA を連結した TLS 証明書チェーン
-tls-key file(必須)サーバーの TLS 秘密鍵。コマンド認証鍵と同じ場合は起動を拒否
-host hostnamelocalhostバインドするアドレス。localhost 以外なら警告を出力
-port Port443ポート
-timeout duration10sTesla サーバー/車両のレスポンスのタイムアウト
-verbosefalseデバッグログ
-key-name, -key-file, -keyring-*, -session-cache, -domaincli.FlagPrivateKey の共通フラグ。コマンド認証用秘密鍵の場所
