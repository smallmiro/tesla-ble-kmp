메시지 인코딩: RoutableMessage

모든 메시지는 Protocol Buffers로 인코딩되며 최상위 타입은 UniversalMessage.RoutableMessage(protobuf/universal_message.proto)입니다. 전형적인 요청은 다음과 같습니다(바이너리 필드는 hex로 표기).

to_destination {
  domain: DOMAIN_VEHICLE_SECURITY
}
from_destination {
  routing_address: 0a7962c10d38b61dd2a7722780a4f096
}
protobuf_message_as_bytes: 0a020805
uuid: 05514f57616bcc81a8ce0f9d7b483229
필드 (번호)타입요청에서응답에서
to_destination (6)Destination oneof {domain, routing_address}명령을 처리할 도메인요청의 from_destination(routing_address)이 복사됨
from_destination (7)Destination연결을 식별하는 랜덤 16바이트 routing_address. 차량이 응답을 전송 계층 주소로 되돌릴 때 사용응답한 도메인
payload oneof: protobuf_message_as_bytes (10)bytes애플리케이션 페이로드. VCSEC → VCSEC.UnsignedMessage, Infotainment → CarServer.Action. AES-GCM이면 암호문VCSEC → VCSEC.FromVCSECMessage, Infotainment → CarServer.Response. 응답 암호화 시 암호문
payload: session_info_request (14)SessionInfoRequest{public_key, challenge}핸드셰이크 요청. 클라이언트 공개 키-
payload: session_info (15)bytes (인코딩된 Signatures.SessionInfo)-핸드셰이크 응답, 또는 동기화 오류 시 오류와 함께 동봉
signature_data (13)Signatures.SignatureDatasigner_identity.public_key + HMAC_Personalized_data 또는 AES_GCM_Personalized_datasession_info_tag(핸드셰이크 HMAC) 또는 AES_GCM_Response_data(암호화 응답)
signedMessageStatus (12)MessageStatus{operation_status, signed_message_fault}-프로토콜 계층 오류. MessageFault_E 값은 9장
uuid (51)bytes ≤ 16명령을 유일하게 식별하는 예측 불가능한 값. 핸드셰이크 응답 재생 방지에 쓰이므로 랜덤이어야 함-
request_uuid (50)bytes-요청 uuid 복사본. VCSEC는 메모리 제약으로 보통 채우지 않음
flags (52)uint32 비트마스크Flags enum 비트. 항상 1 << FLAG_ENCRYPT_RESPONSE(= 2)를 설정 권장. 차량이 인증하며 모르는 비트는 무시응답의 flags. 응답 메타데이터에 포함

Flags enum: FLAG_USER_COMMAND = 0, FLAG_ENCRYPT_RESPONSE = 1. SDK의 vehicle.DefaultFlags = 1 << FLAG_ENCRYPT_RESPONSE이며 Vehicle.Flags 필드로 바꿀 수 있습니다.

protoc로 메시지 디코딩

tesla-control -ble -debug list-keys의 TX: 로그에 찍힌 hex를 pkg/protocol 디렉터리에서 다음처럼 디코딩할 수 있습니다.

echo 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805 \
    | xxd -r -p \
    | protoc --decode=UniversalMessage.RoutableMessage -I protobuf protobuf/*.proto
to_destination {
  domain: DOMAIN_VEHICLE_SECURITY
}
from_destination {
  routing_address: "\nyb\301\r8\266\035\322\247r\'\200\244\360\226"
}
protobuf_message_as_bytes: "\n\002\010\005"
uuid: "\005QOWak\314\201\250\316\017\235{H2)"

VCSEC로 가는 메시지이므로 protobuf_message_as_bytes는 VCSEC.UnsignedMessage입니다.

printf "\n\002\010\005" | protoc --decode=VCSEC.UnsignedMessage -I protobuf protobuf/*.proto
# InformationRequest {
#   informationRequestType: INFORMATION_REQUEST_TYPE_GET_WHITELIST_INFO
# }

반대로 protoc --encode로 페이로드를 만들 수도 있습니다(아래 AES-GCM 예시). *.proto로 다른 언어 바인딩도 생성할 수 있습니다.

프로토콜 개념: 도메인, 시간, 역할

도메인

차량 하위 시스템은 서로 다른 공개 키를 가지므로 도메인별로 핸드셰이크와 세션 상태를 따로 관리합니다. VCSEC(DOMAIN_VEHICLE_SECURITY = 2)는 잠금, 원격 시동, 트렁크, 키체인을 담당하고 Infotainment(DOMAIN_INFOTAINMENT = 3)가 나머지를 처리합니다. VCSEC는 Infotainment가 잠들어 있어도 BLE로 접근할 수 있습니다.

시간

각 도메인은 자기 시계를 갖고 시간을 (epoch_id, timestamp) 쌍으로 표현합니다. epoch_id는 부팅 시 생성되는 랜덤 16바이트, timestamp는 epoch 시작 이후 초 단위 정수입니다. 클라이언트는 도메인 시계와 로컬 시계의 차이를 추적해 명령 만료 시각(expires_at)을 계산합니다. SDK는 SessionInfo.clock_time과 수신 시각으로 timeZero를 잡고, 요청 후 AllowedLatency(BLE 4초, 인터넷 10초)를 넘겨 도착한 세션 정보는 시계 보정에 쓰지 않습니다.

역할

공개 키마다 역할(Owner, Driver, Fleet Manager, Vehicle Monitor, Charging Manager, Guest, Service)이 있으며 1장 역할 표를 참고하세요. 역할별 권한은 펌웨어 갱신에 따라 달라질 수 있습니다.

메타데이터 직렬화 (TLV)

인증은 메시지를 VIN 같은 메타데이터에 결합해야 하므로, 메타데이터를 해시 입력으로 쓸 수 있는 정규 직렬화가 필요합니다. 각 항목은 tag(1B) || length(1B) || value로 인코딩되며 tag 값은 Signatures.Tag에 정의되어 있습니다.

Tag값내용
TAG_SIGNATURE_TYPE0SignatureType 1바이트
TAG_DOMAIN1Domain 1바이트
TAG_PERSONALIZATION2VIN (17자 ASCII)
TAG_EPOCH316바이트 epoch_id
TAG_EXPIRES_AT4uint32 big-endian
TAG_COUNTER5uint32 big-endian
TAG_CHALLENGE616바이트 (핸드셰이크 요청 uuid)
TAG_FLAGS7uint32 big-endian
TAG_REQUEST_HASH8응답 복호화용 요청 해시
TAG_FAULT9uint32 big-endian MessageFault_E
TAG_END255종료 마커 0xFF
 
TLV(VIN: "abc")   = TAG_PERSONALIZATION || LEN("abc") || "abc"
                  = 0x02 || 0x03 || 0x61 0x62 0x63
                  = 0x0203616263

TLV(COUNTER: 100) = TAG_COUNTER || LEN(uint32) || 0x00000064    (정수는 4바이트 big-endian)
                  = 0x05 || 0x04 || 0x00000064
                  = 0x050400000064

SERIALIZE({COUNTER: 100, VIN: "abc"})
                  = TLV(VIN) || TLV(COUNTER) || 0xFF               (tag 오름차순 정렬 후 연결, 끝에 0xFF)
                  = 0x0203616263050400000064FF

Go 구현(internal/authentication/metadata.go)은 항목을 반드시 tag 오름차순으로 추가해야 하고(errOutOfOrderMetadata), 값 길이는 255바이트 이하여야 하며(ErrMetadataFieldTooLong), nil 값은 건너뜁니다. Checksum(message)가 0xFF를 붙인 뒤 메시지 바이트를 이어서 해시합니다.

직접 구현하지 말 것

ECDH와 AES-GCM은 OpenSSL, Go crypto 같은 검증된 라이브러리를 쓰세요. 프로토콜은 항상 K의 바이너리 값을 사용하며 위 hex는 표시용입니다.

응답 인증 (session_info_tag 검증)

MITM 공격자가 만료 시각이 더 긴 명령을 얻지 못하도록 클라이언트는 세션 정보 응답을 인증해야 합니다. 공격자가 공개 키를 바꾸면 차량이 명령을 거부하고, 공개 키를 그대로 두고 나머지를 바꾸면 클라이언트가 태그 검증에서 거부합니다.

  1. 세션 정보 인증 키 유도. SESSION_INFO_KEY = HMAC-SHA256(K, "session info"). 문자열은 ASCII 리터럴. 
    export SESSION_INFO_KEY=$(echo -n "session info" | openssl dgst -sha256 -mac hmac -macopt hexkey:"$K")
# fceb679ee7bca756fcd441bf238bf2f338629b41d9eb9c67be1b32c9672ce300
  2. 메타데이터 직렬화. TAG_SIGNATURE_TYPE = SIGNATURE_TYPE_HMAC(6), TAG_PERSONALIZATION = VIN, TAG_CHALLENGE = 요청 uuid. 
    VIN = 5YJ30123456789ABC
METADATA = 00 01 06
        || 02 11 35594a3330313233343536373839414243
        || 06 10 1588d5a30eabc6f8fc9a951b11f6fd11
        || ff
       = 000106021135594a333031323334353637383941424306101588d5a30eabc6f8fc9a951b11f6fd11ff
  3. 태그 계산. HMAC-SHA256(SESSION_INFO_KEY, METADATA || session_info) 
    echo "$METADATA$SESSION_INFO" | xxd -r -p | openssl dgst -sha256 -mac hmac -macopt hexkey:"$SESSION_INFO_KEY"
# 996c1fe38331be138f8039c194b14db2198846ed7d8251e6749284d7b32ea002
  4. 비교. 응답의 signature_data.session_info_tag.tag와 상수 시간 비교(Go: hmac.Equal). 불일치하면 응답을 폐기.

Go에서는 internal/authentication.NewAuthenticatedSigner가 이 검증을 수행하고, NativeSession.SessionInfoHMAC이 태그를 계산합니다. SDK는 uuid가 최근 요청의 것이 아니거나 AllowedLatency를 넘겨 도착한 세션 정보는 태그 검증 전에 버립니다.

명령 인가

핸드셰이크 후 클라이언트는 도메인 시계(epoch, timestamp), 안티리플레이 카운터, 공유 키 K를 갖습니다. 명령 protobuf P(VCSEC.UnsignedMessage 또는 CarServer.Action)를 만든 뒤 아래 메타데이터 M을 직렬화합니다.

값Tag설명
서명 종류TAG_SIGNATURE_TYPESIGNATURE_TYPE_HMAC_PERSONALIZED(8) 또는 SIGNATURE_TYPE_AES_GCM_PERSONALIZED(5)
도메인TAG_DOMAINDOMAIN_VEHICLE_SECURITY(2) 또는 DOMAIN_INFOTAINMENT(3)
VINTAG_PERSONALIZATION17자 VIN
EpochTAG_EPOCHsession_info.epoch 복사
만료 시각TAG_EXPIRES_AT도메인 시계 기준 초. SDK는 ctx 데드라인까지(없으면 5초)로 설정
카운터TAG_COUNTER단조 증가. 초기값 session_info.counter, 명령마다 +1
플래그TAG_FLAGS요청 flags. 0이 아닐 때만 포함
  • 카운터는 같은 epoch 안에서 명령마다 증가해야 합니다. Infotainment는 순서가 뒤바뀐 도착을 허용하는 슬라이딩 윈도우를 유지하지만 VCSEC는 카운터 순서대로 도착해야 합니다.
  • 너무 먼 만료 시각은 MESSAGEFAULT_ERROR_TIME_TO_LIVE_TOO_LONG으로 거부됩니다.

HMAC-SHA256 인증

  1. 키 유도: K' = HMAC-SHA256(K, "authenticated command").
  2. RoutableMessage를 만들고 payload.protobuf_message_as_bytes = P.
  3. signature_data.signer_identity.public_key = ENCODE_PUBLIC(C).
  4. tag = HMAC-SHA256(K', M || P).
  5. signature_data.HMAC_Personalized_data에 epoch, counter, expires_at, tag를 채운다.
message HMAC_Personalized_Signature_Data {
    bytes   epoch       = 1;
    uint32  counter     = 2;
    fixed32 expires_at  = 3;
    bytes   tag         = 4;
}

AES-GCM 암호화

  1. 128비트 키 K를 그대로 AES-GCM 키로 사용.
  2. 랜덤 12바이트 nonce(IV). 다른 길이는 MESSAGEFAULT_ERROR_IV_INCORRECT_LENGTH.
  3. AAD(Associated Authenticated Data) = SHA256(M).
  4. P를 암호화해 암호문 x와 16바이트 tag를 얻는다.
  5. payload.protobuf_message_as_bytes = x, signer_identity.public_key = ENCODE_PUBLIC(C).
  6. signature_data.AES_GCM_Personalized_data에 epoch, nonce, counter, expires_at, tag를 채운다. epoch은 생략 가능하지만 넣으면 불일치 시 더 구체적인 오류를 받는다.

세션 캐시와 동기화 오류 복구

세션 캐시

계속 실행되지 않는 클라이언트는 세션 상태와 로컬/차량 시계 차이를 디스크에 저장해야 합니다. 캐시를 쓰면 첫 명령의 지연이 줄고 Fleet API 호출 수도 줄어듭니다. 캐시가 낡았더라도 아래 복구 절차가 핸드셰이크 한 번과 같은 비용이므로 낙관적으로 캐시를 신뢰해도 손해가 없습니다. SDK: pkg/cache.SessionCache, Vehicle.UpdateCachedSessions/LoadCachedSessions, CLI의 TESLA_CACHE_FILE.

동기화 오류 복구

차량은 인증 오류가 동기화 문제(예: Infotainment 재부팅으로 epoch 변경)일 수 있을 때 오류 메시지에 최신 세션 정보를 동봉합니다. 클라이언트는 다음 중 하나라도 참이면 세션 정보를 폐기해야(MUST) 합니다.

  • 최근 몇 초 안에 그 request_uuid로 요청을 보낸 적이 없다.
  • 세션 정보 HMAC 태그가 틀리다.
  • 같은 epoch에서 이전에 인증된 세션 정보보다 clock_time이 이르다.

모두 거짓이면 세션 상태를 갱신해야(MUST) 합니다. 갱신할 때 epoch이 바뀌지 않는 한 안티리플레이 카운터를 되돌리면 안 됩니다(MUST NOT). 이는 보안 요구라기보다(재생 거부는 차량 책임) 불안정한 연결과 순서 뒤바뀜을 견디기 위한 규칙입니다. Go: Dispatcher.checkForSessionUpdate → session.processHello → Signer.UpdateSignedSessionInfo. dispatcher는 세션을 갱신한 뒤 오류 응답도 그대로 receiver에 전달하고, Vehicle.Send가 ShouldRetry인 오류(INVALID_SIGNATURE, INVALID_TOKEN_OR_COUNTER, INCORRECT_EPOCH, TIME_EXPIRED 등)면 갱신된 세션으로 재전송합니다.

응답 처리

응답이 없어도 실행되었을 수 있다

명령을 보냈는데 응답을 받지 못했다면 차량은 이미 명령을 수신·실행했을 수 있습니다. 불안정한 네트워크에서 특히 흔합니다. SDK는 이런 경우 protocol.MayHaveSucceeded(err) == true인 오류를 반환하며, 자동 재시도하지 않습니다.

프로토콜 계층 오류

응답도 RoutableMessage입니다. 프로토콜 계층 오류가 있으면 signedMessageStatus.signed_message_fault가 설정됩니다. 코드와 대처법은 universal_message.proto의 MessageFault_E 주석과 9장에 있습니다. Go의 protocol.GetError가 이를 *RoutableMessageError(또는 UNKNOWN_KEY_ID는 ErrKeyNotPaired)로 변환하고, session_info.status == KEY_NOT_ON_WHITELIST도 ErrKeyNotPaired, operation_status == WAIT는 ErrBusy로 만듭니다.

응답 복호화

응답에 signature_data.AES_GCM_Response_data가 있으면 protobuf_message_as_bytes가 암호문이고, 없으면 평문입니다.

message AES_GCM_Response_Signature_Data {
    bytes  nonce   = 1;
    uint32 counter = 2;
    bytes  tag     = 3;
}

요청 해시 (request hash)

클라이언트는 보낸 요청마다 "요청 해시"를 계산해 두어야 합니다. 인증 방식 1바이트 || 요청의 인증 태그입니다.

  • AES-GCM 요청: 0x05 || AES_GCM_Personalized_data.tag (16바이트 태그 → 총 17바이트)
  • HMAC 요청: 0x08 || HMAC_Personalized_data.tag (32바이트 태그 → 총 33바이트)
  • VCSEC로 보낸 요청은 17바이트로 절단: 방식 1바이트 + MAC 앞 16바이트. AES-GCM 태그는 원래 16바이트이므로 HMAC 요청에만 영향

Go: internal/authentication.RequestID(message). dispatcher가 Send 시 receiver에 requestID로 저장합니다.

카운터 검증

응답의 counter가 같은 요청에 대한 이전 응답에서 이미 사용된 값이 아닌지 검증해야 합니다. 한 요청이 여러 응답을 유발할 수 있고 순서가 뒤바뀔 수 있습니다. 이 검사를 빠뜨리면 재생 공격에 취약합니다. Go: receiver마다 authentication.SlidingWindow를 두고 session.decrypt에서 antireplay.Update(counter)가 false면 ErrReplayedResponse로 폐기(internal/authentication/window.go).

응답 메타데이터

AES-GCM으로 키 K, 응답의 nonce와 tag, 그리고 아래 메타데이터의 직렬화를 AAD로 써서 복호화합니다. 요청과 달리 flags는 0이어도 항상 포함하고, fault는 32비트 big-endian으로 인코딩합니다.
