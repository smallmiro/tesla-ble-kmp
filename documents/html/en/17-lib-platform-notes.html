17. Platform Notes

What an Android or iOS app has to set up, where the library keeps keys and sessions, and a few platform behaviours worth knowing. Items not yet confirmed on a real device say so.

On this page
  1. Support
  2. Android
  3. iOS

  7. Connection slots and dropped links
  8. Swift: timeouts

Support

  • Android 12 (API 31) or later, iOS 16 or later, with the app in the foreground. Background Bluetooth is out of scope.
  • The JVM target is for tests and experiments. Its keys live in memory and are gone when the process ends.

Android

Declare the two Bluetooth permissions and request them at runtime. Without them, scanning and connecting return PermissionDenied. No internet permission is needed: the library never calls a server.

<uses-permission android:name="android.permission.BLUETOOTH_SCAN" android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<uses-feature android:name="android.hardware.bluetooth_le" android:required="true" />
  • Create the library with PlatformContext(context); it keeps the application context.
  • On connect the library asks for an MTU of 517 and falls back to 20-byte blocks if that fails.
  • Keystore entries are named teslable.key:<alias> and teslable.wrap:<alias>, so they do not collide with your app's own entries.
Exclude the key files from Auto Backup

A software key is saved as files/teslable/keys/<alias>.enc, wrapped by a Keystore key that is never backed up. If Auto Backup restores the file without its wrapping key, the key reads as corrupted. Exclude files/teslable/keys/ in dataExtractionRules or fullBackupContent. The sample app simply sets android:allowBackup="false". Saved sessions in files/teslable/sessions are harmless to lose, but excluding them is cleaner.

iOS

  • Add NSBluetoothAlwaysUsageDescription to Info.plist. The first scan shows the permission prompt; if the user declines, calls return PermissionDenied.
  • Create the library with PlatformContext().
  • The simulator has no Bluetooth. Scanning and connecting can only be tried on a real iPhone.
  • iOS has no MTU negotiation API; the library uses the write length the system picks. The observed block length on a real iPhone is 512. The response characteristic supports both notifications and indications; the Kable default subscription (notify) was confirmed on a real car (ADR-0003).
  • Swift calls Kotlin through SKIE: suspend functions become async throws, Flow becomes AsyncSequence, sealed types work with switch onEnum(of:), and companion members are reached through .companion.
  • In Swift the public VehicleStatus is named VehicleStatus_, because a generated VCSEC message type already takes the plain name. Results of vehicleStatus() and VehicleEvent.Status.status have this type.

Key storage

protectionMeaning
SECURE_ENCLAVEiOS Secure Enclave. The private key never leaves the chip
STRONGBOXAndroid StrongBox security chip
TEEAndroid Trusted Execution Environment
SOFTWAREEmulators, simulators, or a device where every hardware attempt failed
  • Software keys are wrapped by an Android Keystore AES key, or stored as an iOS Keychain item that never leaves the device and is protected according to the key's accessibility setting.
  • On iOS, a failed Secure Enclave lookup is reported as an error, not as "no key", so a working key is never overwritten by mistake.
  • There is no API to export a private key.

Using the key while the phone is locked

Each key has an accessibility setting, VehicleKey.accessibility. How to choose it and switch keys is in 13. Keys and Pairing.

PlatformWhen a key is createdWhat an existing key reports
iOSWHEN_UNLOCKED (default) uses kSecAttrAccessibleWhenUnlockedThisDeviceOnly and AFTER_FIRST_UNLOCK uses kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, for the Secure Enclave key and the software key alikeThe setting read back from the stored key. It never changes afterwards
AndroidThe setting is ignoredAlways AFTER_FIRST_UNLOCK: the Keystore keys have no unlock or user-authentication requirement, and the key file can be read after the first unlock. By the API; not yet confirmed on a device
JVMThe setting is ignoredAlways AFTER_FIRST_UNLOCK: keys in memory have no lock
  • On a locked iPhone, the Keychain error errSecInteractionNotAllowed (-25308) becomes KeyStoreError.Locked. A WHEN_UNLOCKED key cannot be read or used for a handshake while the phone is locked; an AFTER_FIRST_UNLOCK key can, once the phone was unlocked after the last restart. Before that first unlock every key is locked. A key that cannot be created because the phone is locked is not replaced by a software key.
  • Not yet confirmed on a device: the Keychain round trip of both settings, reading the setting back, and a handshake on a locked iPhone with an AFTER_FIRST_UNLOCK Secure Enclave key. They are checked with the sample app. Using the key while the phone is locked also needs the app to keep running in the background, which these pages do not cover yet.
A corrupted key is never replaced automatically

If getOrCreate or get returns PlatformFailure with stored key is corrupted, tell the user, then call delete and getOrCreate. The new key has a different public key and must be enrolled on the car again. Replacing it silently would leave the user unable to control the car without knowing why.

Session cache

  • Saved sessions let the next connection skip the handshake. They are stored in files/teslable/sessions/ on Android, in the Keychain on iOS, and in memory on the JVM. You can supply your own with TeslaBleConfig.sessionCache.
  • Names are hashes of the VIN, so the VIN itself is not stored.
  • Sessions belong to one key. After the key changes, or when the car has moved on, old sessions are discarded on the next connection.
  • A missing or outdated cache is not an error; the library simply starts a new session.

Clocks

Session timing uses the monotonic clock, which stops on some platforms while the phone sleeps. After a long sleep, the first command from a saved session may fail with an expiry fault. The library then takes the fresh session information the car sends back and retries; the app sees nothing.

Connection slots and dropped links

  • A car accepts at most three Bluetooth connections. Call disconnect() when you are done so the slot is free. When all three are taken, connecting returns MaxConnectionsExceeded.
  • When the link drops and connection turns Disconnected, still call disconnect() so the session keys are erased. Calling it again is harmless.
  • A disconnected Vehicle cannot be reused; connect again with TeslaBle.connect.

Swift: timeouts

Kotlin's Duration is an inline value class. Swift sees it only as a boxed Any?, so Swift code cannot build one directly. Two helpers solve this.

  • Timeouts.shared.seconds(seconds:) returns the boxed value to pass as any timeout: argument. Zero, negative, NaN or infinite input throws IllegalArgumentException. Timeouts.shared.millisecondsOf(timeout:) returns the milliseconds of a boxed value (-1 for nil); it exists to check the round trip. The iOS sample's XCTest target runs in tools/ci/verify.sh step (d).
  • TeslaBleConfig.companion.withSeconds(logger:commandTimeoutSeconds:handshakeTimeoutSeconds:connectTimeoutSeconds:pairingTimeoutSeconds:) builds a config from seconds. Every argument is required; commandLifetime keeps its default. TeslaBleConfig.companion.default(logger:) is unchanged.
  • timeout: nil still means "use the config default".
