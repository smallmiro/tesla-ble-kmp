14. 차량 상태 조회

라이브러리가 BLE로 차량에서 읽을 수 있는 모든 정보를 두 부분으로 정리합니다. A부는 요청해서 받는 데이터(보안 컨트롤러 조회 4가지), B부는 차량이 스스로 보내는 데이터(브로드캐스트)입니다. 조회는 인포테인먼트 컴퓨터가 잠들어 있어도 VCSEC가 응답하므로 키도 세션도 깨우기도 필요 없습니다.

현재 구현 범위

A부의 조회 4가지는 구현되어 있습니다. 차량 브로드캐스트(B부)는 vehicle.events로 앱에 전달되며(B2), 관찰 로그에서도 계속 볼 수 있습니다. getState()(인포테인먼트)는 M5 예정이며 아직 없습니다.

VCSEC 요청의 라우팅 규칙:

  • to_destination.domain은 DOMAIN_VEHICLE_SECURITY이고 from_destination.routing_address는 요청마다 새로 만든 무작위 16바이트 주소입니다. 응답은 그 주소로 돌아오며 라이브러리는 주소(와 차량 도메인)로 짝을 찾습니다. VCSEC 응답을 짝지을 때 request_uuid는 쓰지 않습니다. uuid(51)에는 무작위 16바이트를 계속 채웁니다.
  • 다른 라우팅 주소 앞으로 온 응답은 우리 것이 아니며 no-handler로 버립니다(B3 참고).
  • 조회는 인증하지 않습니다. signature_data가 없고 protobuf_message_as_bytes는 평문 UnsignedMessage입니다. 명령은 같은 봉투에 signature_data와 AES-GCM으로 보호한 페이로드를 담습니다.
  • sessionInfo의 페이로드는 session_info_request(14)이고 to_destination.domain은 요청한 도메인입니다. 응답은 session_info(15)에 담겨 옵니다.

변환 규칙

스키마 밖의 값은 0번 값이 아니라 UNKNOWN으로 바꿉니다. proto3에서는 빠진 enum과 0번 값을 구분할 수 없으므로 잠금 상태가 빠지면 UNLOCKED로 읽히며, 조회에서는 Go 동작을 그대로 따릅니다. gear는 Go에 대응하는 것이 없습니다(공식 Go 스키마는 필드 5까지). 0번 값이 GEAR_UNKNOWN이므로 기어가 빠지면 UNKNOWN으로 읽힙니다. 기어는 브로드캐스트로 확인했으며, 차량이 조회 응답에 기어를 채우는지는 실차로 확인하지 않았습니다. 실차 결과상 차량은 모두 닫히면 closureStatuses를 생략하고 무언가 열려 있으면 보내므로(운전석 문과 충전구에서 확인) "없으면 모두 닫힘"은 관찰과 맞습니다. 실내 버튼으로 연 트렁크는 브로드캐스트로 보이지 않았으므로, 트렁크는 이 조회로 읽으세요.

A7. 스키마의 다른 요청 종류

InformationRequestType에는 GET_TOKEN 1, GET_COUNTER 2, GET_EPHEMERAL_PUBLIC_KEY 3, GET_SESSION_DATA 4, GET_PERSONALIZATION_INFO 7, GET_KEYSTATUS_INFO 8, GET_ACTIVE_KEY 9, GET_CAPABILITIES 16(Teslemetry 전용)도 정의되어 있습니다. 라이브러리는 어느 것도 보내지 않으며 API도 없습니다. getState(category)(인포테인먼트)는 M5 예정이고 API가 아직 없습니다.

B2. 브로드캐스트 이벤트: vehicle.events

응답 짝짓기는 이전과 같고 Go 원본과도 같습니다. 브로드캐스트에는 라우팅 주소가 없으므로 디스패처는 이를 라우팅에서 버립니다(드롭 사유 TO_DOMAIN). 브로드캐스트는 대기 중인 요청에 닿지 않으며 응답으로 오인되지 않습니다. 관찰 로그도 여전히 [drop:to-domain] 줄을 남깁니다(18. 문제 해결).

여기에 더해 라이브러리는 평문 브로드캐스트를 모두 vehicle.events로 앱에 넘깁니다(FR-035). Go 원본에는 이런 기능이 없고 프레임을 버리기만 합니다. Kotlin과 Swift 예제는 12. 라이브러리 시작하기에, 각 메시지의 의미는 B3에 있습니다.

val events: Flow<VehicleEvent>                    // Vehicle의 멤버

sealed interface VehicleEvent {                   // dev.mirolab.teslable.model
    val raw: ByteArray                            // 받은 프레임 전체. 읽을 때마다 새 복사본. VIN을 가리지 않음
    val unknownFields: List<String>               // 스키마가 모르는 필드의 경로. 예: "53", "1.8"
    class Status(val status: VehicleStatus, …) : VehicleEvent
    class AuthenticationRequest(val requestedLevel: AuthenticationLevel, val reasons: List<AuthenticationReason>, …) : VehicleEvent
    class Unrecognized(…) : VehicleEvent
}

이벤트가 되는 프레임

다음을 모두 만족해야 합니다. 관찰 로그의 상세 디코드 조건과 같지만, 페이로드가 디코딩되지 않아도 됩니다(디코딩되지 않는 페이로드는 Unrecognized가 됩니다).

필드필요한 값
from_destinationdomain = DOMAIN_VEHICLE_SECURITY
to_destinationdomain = DOMAIN_BROADCAST (라우팅 주소 없음)
request_uuid비어 있음
signature_data없음
session_info없음

그 밖의 프레임은 관찰 로그의 한 줄로만 남습니다. 다른 폰 앞 응답, 서명되거나 암호화된 프레임, 해석되지 않는 프레임, 출발지가 없는 프레임이 그렇습니다. 라이브러리는 브로드캐스트를 복호화하지 않으며, 복호화한 데이터가 이벤트에 들어가는 일도 없습니다(FR-112).

이벤트 종류

이벤트언제담는 내용
VehicleEvent.Status프레임에 vehicleStatus(필드 1)가 있음status: vehicleStatus()(A2)와 같은 규칙으로 만든 VehicleStatus. 열린 곳이 보고되지 않으면 모두 닫힘, 모르는 값은 UNKNOWN, gear 포함
VehicleEvent.AuthenticationRequest프레임에 authenticationRequest(필드 3)가 있음requestedLevel과 reasons(B3.2). 20바이트 토큰은 필드로 주지 않으며 raw에 있음
VehicleEvent.Unrecognized둘 다 없음: 모르는 필드만 있음(실차에서는 48과 53), 다른 필드, 페이로드 없음, 디코딩되지 않는 페이로드(이때 unknownFields는 비어 있음)raw와 unknownFields뿐
  • 프레임 하나가 이벤트 두 개가 될 수 있습니다. 두 필드가 다 있으면 Status가 먼저, AuthenticationRequest가 다음에 오고, 둘의 raw와 unknownFields는 같습니다. 스키마가 두 필드를 하나의 oneof에 넣었기 때문에 보통의 디코딩은 하나만 남기지만, 라이브러리는 둘 다 읽습니다.
  • raw는 받은 프레임 전체(BLE 길이 접두 2바이트 제외)로, 차량이 평문으로 보낸 그대로입니다. 읽을 때마다 새 복사본을 만들므로 한 번만 읽으세요. VIN을 가리지 않았으므로 저장하거나 공유하기 전에 VIN을 가리세요. 관찰 로그의 상세 디코드처럼 "평문 페이로드 금지"의 좁은 예외이며 FR-112와 충돌하지 않습니다. 차량이 평문으로 보낸 프레임만 해당하고, 라이브러리가 복호화한 것은 절대 들어가지 않습니다.
  • 두 이벤트는 필드와 raw 바이트가 같으면 같습니다. 이벤트를 출력하면 raw는 길이만 보입니다.

unknownFields

각 항목은 FromVCSECMessage에서 스키마가 모르는 필드까지 내려가는 필드 번호 경로입니다.

경로뜻

"1.8"vehicleStatus 안의 필드 8

스키마 밖의 enum 값도 그 필드 번호로 나옵니다(모델에서는 UNKNOWN). 새 기어 값이면 "1.7"입니다. 하위 메시지 안에서는 그 메시지 자신의 필드가 그 안 메시지의 필드보다 먼저 옵니다. 두 번 나온 번호는 두 번 적힙니다. 목록이 비어 있지 않으면 프레임의 일부를 해석하지 못했다는 뜻이며, 바이트는 raw에 있습니다.

앱이 지킬 규칙

  • 반복은 변화가 아닙니다. 차량은 바뀐 것이 없어도 1~25초마다, 때로는 1초 안에 여러 번 상태를 다시 보냅니다. 라이브러리는 반복을 거르지 않으므로 이전 값과 직접 비교하세요.
  • 트렁크: 실내 버튼으로 트렁크를 열고 닫았을 때 브로드캐스트가 오지 않았습니다(다른 방법은 시험하지 않음). 트렁크는 vehicleStatus()로 읽으세요.
  • 구독: 수집은 시작한 순간부터 받습니다. 그 전의 브로드캐스트는 다시 오지 않습니다. 여러 곳에서 수집하면 각자 모든 이벤트를 받습니다.
  • 끝: connection이 이유와 상관없이 Disconnected가 되거나 disconnect()를 호출하면, 먼저 온 쪽에서 흐름이 예외 없이 정상적으로 끝납니다. 그 뒤에 시작한 수집은 바로 끝납니다. 그 순간 전달 중이던 프레임은 잃을 수 있습니다. 재연결 판단은 connection으로 하고, 링크가 끊긴 뒤에도 disconnect()는 호출하세요. 새 연결은 자기 events를 가진 새 Vehicle입니다.
  • 느린 수집자: 라이브러리는 뒤처진 수집자를 위해 프레임을 64개까지 보관합니다. 그 이상이면 그 연결의 모든 수집자에게서 새 프레임이 빠지고, 버린 수를 세며, 첫 번째와 100번째마다 WARN 줄을 남깁니다. 오류가 아닙니다(16. 에러 처리). 수집 코드는 가볍게 유지하세요.
  • 키도 세션도 필요 없으며 connect(vin, key = null)로 충분합니다. 실차 관찰은 등록되지 않은 키로 했습니다.

B3.2 authenticationRequest (필드 3)

상태: 발생은 확인됨, 하위 필드 이름은 미검증(Teslemetry 스키마).

#필드(AuthenticationRequest)타입의미
2sessionInfo(이름 미검증)AuthenticationRequestToken{token = 1}token: 20바이트
3requestedLevel(이름 미검증)AuthenticationLevel_E0 NONE, 1 UNLOCK, 2 DRIVE (접두어 AUTHENTICATION_LEVEL_)
4reasonsForAuth(이름 미검증)repeated AuthenticationReason_E차량이 인증을 요구하는 이유

AuthenticationReason_E(접두어 AUTHENTICATIONREASON_): 0 NOT_DOCUMENTED, 1 IDENTIFICATION, 2 POWER_ON_VEHICLE_REQUEST, 3 GTW_REQUEST, 4 UI_UNLOCK_PASSIVE_AUTH, 5 PASSIVE_UNLOCK_EXTERIOR_HANDLE_PULL, 6 PASSIVE_UNLOCK_INTERIOR_HANDLE_PULL, 7 PASSIVE_UNLOCK_AUTOPRESENT_DOOR, 8 ENTERED_HIGHER_AUTH_ZONE, 9 WALK_UP_UNLOCK, 10 IMMOBILIZER. 관련된 AuthenticationResponse(UnsignedMessage 필드 3, 폰 키가 보냄)와 AuthenticationRejection_E는 스키마에 있으며 라이브러리는 보내지 않습니다.

공개 모델(VehicleEvent.AuthenticationRequest, B2)에서 requestedLevel은 NONE, UNLOCK, DRIVE이고, 스키마 밖 값은 UNKNOWN입니다. 수준이 없는 것과 NONE은 구별할 수 없습니다. reasons는 차량이 보낸 값마다 하나씩이며 이름은 위에서 접두어를 뺀 것입니다. 스키마 밖 값은 UNKNOWN이 되어 아는 값들 뒤에 옵니다(정확한 순서는 raw에 있습니다).

관찰: 실내 손잡이를 당기면 requestedLevel = DRIVE, reasons = [PASSIVE_UNLOCK_INTERIOR_HANDLE_PULL]. 충전구를 열고 충전이 시작될 때는 ENTERED_HIGHER_AUTH_ZONE이 추가되었습니다. 같은 순간 vehicleStatus(와 필드 53)가 함께 왔습니다. 다른 이유는 관찰하지 못했습니다.

감싼 형태이며 맨몸이 아님

이 차량은 이것을 RoutableMessage 안에 담아(위의 브로드캐스트 형태) 보냈습니다. 약 1.1초마다 감싸지 않은 FromVCSECMessage{authenticationRequest}가 온다는 다른 보고(Teslemetry PR #179)와 다릅니다. 이 차량에서는 감싸지 않은 프레임이 보이지 않았습니다(drop:missing-source, drop:unparseable: 0줄).

B3.3 필드 53 (미확인)

상태: 미확인. FromVCSECMessage 필드 53: {1: small int, 2: 35 bytes}의 반복.

  • 연결 직후와 충전구 사건에서는 총 54바이트(항목 1개, id 4), 문과 잠금 사건에서는 205~220바이트(항목 5개, id 1, 3, 4, 6, 7). 한 메시지 안의 35바이트 블롭은 마지막 2바이트만 다릅니다.
  • 인증 사건과 함께 옵니다. id 1, 3, 4, 6, 7은 등록된 키 슬롯 번호(M3에서 키 7개 확인)와 겹치므로 키마다의 인증 챌린지로 추정합니다. 미확정.

B3.4 필드 48 (미확인)

상태: 미확인. FromVCSECMessage 필드 48, 20바이트. 차량이 깨어 있고 사람이 있을 때 약 5.0초마다(끊긴 구간 있음). 1차에서만 보였고 2차에서는 나타나지 않았습니다. 하트비트로 추정하며 조건은 모릅니다.

B3.5 다른 클라이언트 앞으로 온 응답

브로드캐스트가 아닙니다. 서명된 83바이트 응답(to_destination.routing_address가 다른 클라이언트의 16바이트 주소, 16바이트 request_uuid, 빈 본문)은 다른 폰의 VCSEC 요청에 대한 응답입니다. 우리 링크로도 약 1~2분마다, 그리고 문 사건 직후에 옵니다. 라이브러리는 이를 no-handler(주인 other)로 버립니다.

B4. 브로드캐스트로 받을 수 없는 것

항목결과
방향지시등(좌, 우), 비상등, 전조등, 상향등조작해도 메시지가 전혀 없고 BLE 스키마에도 해당 필드가 없습니다(vcsec.proto, vehicle.proto, car_server.proto). 알려진 경로는 Tesla Fleet Telemetry(LightsTurnSignal 240, LightsHazardsActive 239, LightsHighBeams 241)뿐이며, 이는 인터넷 서버 경로라 이 라이브러리의 서버 없음 범위 밖입니다
실내 버튼으로 연 트렁크브로드캐스트 없음(다른 조작 방법은 미시험)
잠든 차량관찰하지 못함
충전 케이블2차에 기록함(충전구 열기, 충전기 연결, 충전 시작): chargePort = OPEN, 필드 8의 하위 2가 2에서 1로 변경, ENTERED_HIGHER_AUTH_ZONE이 든 authenticationRequest, 항목 1개짜리 필드 53. 케이블 자체에 대한 별도 브로드캐스트는 찾지 못했습니다
다른 폰 키가 다가올 때기록하지 않음
