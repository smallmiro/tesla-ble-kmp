4. Monitor App

A phone left running in or near the car connects by itself, stays connected, shows the car's state live, polls everything the library can read, and records every broadcast with its raw bytes so unknown protocol fields can be analysed later.

Android and iOS built, real-device checks pending

The Android app (build 0.4.0 (4)) and the iOS app (build 0.5.0 (26)) are implemented and their unit tests pass; both wait for the real-car check. Whether iOS reconnects in the background is unconfirmed until the plan Task 2 spike. The library APIs it needs are available: Vehicle.events (library manual, chapter 12 "Broadcast events" and chapter 14, B2) and the key accessibility choice on iOS (chapter 13 "Using the key while the phone is locked", FR-037).

The key on a locked phone

The monitor uses its own key, teslable-monitor, created so that it can be used while the phone is locked (KeyAccessibility.AFTER_FIRST_UNLOCK on iOS; Android keys already report that they work when locked, not yet confirmed on a device). This setting is fixed when the key is made. If the phone already has that key with the stricter setting, the app asks you to delete it, make a new one and enroll it on the car again. The Control tab shows which setting the key has. The app reads the key when it starts and keeps using that handle. If the key store answers KeyStoreError.Locked (the phone has not been unlocked since it restarted, or the key only works unlocked), the app waits, reads the key again after the phone is unlocked, and never deletes the key for this reason.

Key nickname (local only)

The vehicle has no key-name field: the VCSEC KeyMetadata message carries only keyFormFactor, so the car shows default names and listKeys() returns no name (library manual, chapter 14, A4). To tell keys apart, the Control tab lets you give each key a nickname that exists only on this phone. It is never sent to the vehicle, never shown on the car's screen, and never written to the log files or the result list (the result list gets only a line with the slot).

RuleDetail

State diagnostics (SFR-023)

The Query tab has a manual area where a person calls getState() and reads what the car returns. It exists to collect real-car facts that the library manual lists as unconfirmed (chapter 14, A8.5): which fields a category carries, the unit of speed, whether a reply is too large, and what a sleeping car does. It is not a product feature: there is no periodic getState and no automatic retry. Since build 26 there is one button for each of the 12 StateCategory values (A8.1); a tap asks for one category, never several.

RuleDetail
WhereThe Query tab, under the periodic-query section: twelve buttons (Drive, Media, MediaDetail, Charge, Climate, Location, Closures, TirePressure, SoftwareUpdate, ChargeSchedule, PreconditioningSchedule, ParentalControls), the last result, and a separate send to a sleeping car (experiment) section with the same twelve in a menu.

ASLEEP, UNKNOWN and "not read yet" keep the buttons off, and the reason is shown under them. The buttons are also off while a query runs.

(2) startSession(setOf(INFOTAINMENT), timeout: null): the library sends nothing when the session is already Ready (chapter 14, A8.2: getState never starts a session). (3) one getState(category, timeout: null). The default timeout is used (chapter 16, "Retries and timeouts").
ResultsSuccess, Uncertain and Failure as the library returns them, plus NotSent when the app stops before sending (asleep, sleep unknown, vehicleStatus() failed, session failed). Each has its own sentence: a size fault says the car answered, a timeout says nothing came back, NoSession says nothing was sent. A Timeout sentence follows 16-lib-errors.md (Timeout(afterSend) row): afterSend = true says it may have been sent (Uncertain, the first BLE write had started), that the value was not confirmed and that a query changes nothing so it can be asked again, and notes that BLE writes can be slow in the background; afterSend = false says it was not executed (no write had started, or the car had asked for a retry and the wait ran out, or the handshake timed out; Failure). There is no automatic retry. After Failure(NoSession) (a cached session the car no longer accepts, A8.2) the next tap starts a new session; the sample does not do it by itself.
WakingThe screen never calls wakeUp() and says "does not call wakeUp()", not "does not wake the car": what the Infotainment handshake does to a sleeping car is unconfirmed.

After the confirmation it skips only the sleep check: it still needs a connection and an enrolled key, runs the same session step and sends one getState. It never calls wakeUp(). Meant for one recorded try.
OverlapThe tab refuses to start while the key is being replaced or while another tab (Control, Key & Control) runs a call, and while a query runs the key cannot be replaced (KeyOperationGate). A second tap while a query runs does nothing.
Connection changeThe result and the sleep state belong to the connection that read them. When the connection changes the result is cleared, the sleep state goes back to UNKNOWN, and a result that arrives late from the old connection is dropped (not shown, not logged).

Fields shown. Only these named fields are read; DriveState also has route and destination fields and the app never reads them. Absent is — and 0 stays 0 (chapter 14, A8.3). A unit is printed only where the proto states it or the name says it plainly (*_celsius, bar, mph, meters, *_ms, *_sec, minutes_*, and % for battery_level, usable_battery_level, charge_limit_soc, *_perc, sun_roof_percent_open, which are percentages by name); every other number is the raw value followed by "(unit unconfirmed)", for example the range fields, charger_power, charger_voltage, the charger currents, the set temperatures, heading and gps_as_of (A8.5). Timestamps are shown as local time followed by the epoch seconds.

Under the fields the screen lists "received fields": the proto field names the car actually sent. The list is the same one the log gets.

Log. One query line per finished tap, nothing else: call is getState(<CATEGORY>) with the Kotlin constant name (DRIVE, CHARGE, TIRE_PRESSURE, ...), result is Success, Uncertain, Failure or NotSent, summary is durationMs=<n> plus error=<type> or reason=<why>, and on Success present=[<field names>], and startedAt is the time the first library call of the tap started. No value, no coordinate, no location name and no track title reaches the log (FR-112; chapter 14, A8.3, "Do not log a result"): the log line is built from a small value (StateLogEntry) whose only free text is the list of field names, and the sample's record helper, whose summary goes to the log, is not used for getState. The present names are fixed constants of the sample, one for each proto field it reads and the car sent (native_latitude, heading, location_name, ...); a name says only that a field was there. An empty present=[] is a Success whose reply had none of them. The reply size, the attempt number and auth= are in the library's observe line ([reply:infotainment] <N>B ... attempt=<n> auth=<value>, chapter 18, "Observation log"), not in this line. The sample does not log the unknownFields of a getState reply: Wire keeps them as raw bytes and the manual gives no path form for them (only for broadcast events, B2.3). Error types are the library's type names (ResponseTooLarge, Timeout(afterSend=true), NoSession, or the class name), never message or the vehicle's own text.

Library calls and manual chapters: vehicleStatus(timeout: nil) (14, A2), startSession(domains:timeout:) (14, A8.2, and 15), getState(category:timeout:) with s.value as? VehicleData, KotlinInt? numbers and getEpochSecond() (14, A8.3, and 17, "Swift: generated types"), the coordinate choice (14, A8.4), result handling and the size fault (16, "getState results" and "Response size limit on getState"). The pure rules (StateDiagnostics, StateCategoryFields, the coordinate rule LocationRule) and the screen state (StateDiagnosticsModel, with a fake link) are unit tested without a vehicle (Tests/StateDiagnosticsTests.swift, Tests/StateCategoriesTests.swift); the real-device checklist is in samples/ios/README.md (SFR-023, "additional categories" for the nine added in build 26).

Status: iOS built (0.5.0 (26)), unit tests pass, real-device check pending. Android: planned, same spec.

Wide and foldable screens (SFR-024)

The app follows the large-screen layout of the official Tesla app on the foldable iPhone Duo (app 4.62): on the inner display it shows two panes, a navigation menu on the left and a large, always visible vehicle on the right with quick actions along the bottom; the outer display keeps the normal phone layout. The sample does the same with its own screens. It uses only the size class and the usable width, so it also applies to an iPad or a split window. It never looks at the device model, UIScreen, the orientation or the hinge angle, and uses no iOS 27.1 fold API.

Log files

One JSON object per line. Every line has ts (time with offset) and kind. Each file starts with a session line describing the phone and the app build.

{"ts":"2026-10-24T10:00:00.123+09:00","kind":"session","platform":"ios","app":"0.4.0(11)","os":"27.0.1","phone":"iPhone"}
{"ts":"…","kind":"event","type":"Status","summary":"lock=LOCKED gear=PARK presence=NOT_PRESENT","unknownFields":["1.8"],"unrecognized":true,"raw":"<hex>"}
{"ts":"…","kind":"observe","line":"[drop:no-handler] 83B from=domain(DOMAIN_VEHICLE_SECURITY) …"}
{"ts":"…","kind":"query","call":"vehicleStatus","result":"Success","summary":"…","startedAt":"…"}

{"ts":"…","kind":"link","state":"backoff","reason":"…","attempt":3,"delayMs":8000}

Field notes (both apps write the same names and order, except the iOS-only additions below):

  • event.summary starts with lock=… gear=… presence=…, then sleep=…, doors=FD/FP/RD/RP, frunk=…, trunk=…, chargePort=… for Status; level=… reasons=[…] for AuthenticationRequest; unknownFields=[…] for Unrecognized.
  • link: reason, attempt and delayMs are left out when they do not apply. connecting.attempt counts the tries since the start or since the link dropped. backoff.attempt is the number of consecutive failures (a dropped link counts as the first) and delayMs is the wait before the next try, so the delays read 2000, 4000, 8000, 16000, 30000, 30000. A disconnected line is written when the link drops (with the library's reason when it gave one), followed by a backoff line. A connection that stayed up for 10 seconds or more restarts the wait at 2 seconds.
  • query.summary of vehicleStatus has the same form as the summary of a Status event. It holds no public keys and no VINs.
  • query lines whose call is getState(<CATEGORY>) (iOS only, SFR-023, State diagnostics) come from a manual tap, not from the poll. result is Success, Uncertain, Failure or NotSent; summary is durationMs=<n> and, unless Success, error=<type> or reason=<why>, and on Success present=[<field names>]. They never carry values, coordinates or names.

Additions since build 18 (iOS only)

From issue #128 and the build 18 link-health analysis. New fields are added at the end of a line and new lines use a new kind, so a parser that ignores unknown keys and kinds keeps working. Android does not write them yet; the Android app has a gap here until it is brought level.

  • query.startedAt: the time the request was sent (same format as ts). ts stays the time the result arrived, so ts - startedAt is how long the call took. Written for vehicleStatus, keySummary and listKeys.
  • app / event: "scenePhase": phase is active, inactive or background (SwiftUI scene phase). The first scenePhase line of a run gives the phase at start; the session line and a start line (auto connect) can come before it.
  • app / event: "protectedData": state is available (the phone was unlocked) or unavailable (the phone is about to lock).
  • app / event: "start": written each time the connection loop's start() is called, before the connecting line it may cause. reason: launch (auto connect at app start), connect-button, protected-data (an unlock woke a waiting retry), key-replaced (reconnect after "delete and recreate the key"). effect: started (a new loop began), woke (it was waiting in backoff and was told to try at once) or ignored (already connecting or connected, nothing happened). A connecting line with no start line of effect started or woke right before it came from the backoff timer (an ignored line causes no attempt).
  • link / state: "connected": scanHitMs, rssi and openAttempt (#134), taken from Vehicle.scanObservation (manual chapter 12, Connect scan observation). scanHitMs is the time from the start of connect until the library received the advertisement the link opened through (it includes earlier attempts and the waits between them); rssi is the signal strength in dBm and is left out when the platform gave no value; openAttempt is which open attempt made the link (above 1 means earlier opens failed, not that the car was scanned again). All three are left out when connect used a remembered target (no scan ran). scanHitMs is a monotonic-clock reading, so for a wall-clock time use the ts of the [connect:scan-hit] observe line. A failed connect returns no Vehicle, so its scan hits are only in the observe lines (manual chapter 18). The monitor does not scan before connect, so the measured connection path is unchanged.
  • VIN masking: before writing, any run of 17 or more VIN characters in the raw bytes or text keeps its first 3 and last 4 characters of the run; the rest become *, so the length stays the same. A VIN with such characters right before or after it is masked as part of one longer run.
  • Mark memos are at most 80 characters; an empty memo is ignored.
  • Files are named monitor-<yyyyMMdd-HHmmss>.jsonl. A new file starts at 20 MB, and the oldest files are deleted when the folder passes 200 MB.
  • Writing never holds up event collection. The writer is behind a small interface so a cloud destination can be added later.
  • Where the files are: Android Android/data/dev.mirolab.teslable.sample/files/logs/ (readable with adb pull); iOS Documents/logs/, also visible in Finder and the Files app.

How it behaves, where the design left room:

  • One connection. The Control tab uses the monitor's connection and key (the car allows 3 BLE connections). Its Connect and Disconnect buttons start and stop the monitor's loop. A new connection waits until the previous vehicle has been disconnected.
  • One engine per process. It is created on first use and kept for the process (one library instance per process, chapter 12); the service keeps the process in the foreground. The notification's Stop disconnects, stops automatic reconnection and takes the service down. Opening the app again in the same process does not connect by itself: press Connect. A new process connects by itself when a VIN is saved.
  • Key errors. KeyStoreError.Locked fails the attempt, so the loop waits and reads the key again (the key is never deleted). Any other key error connects without a key: broadcasts and the three queries need none (chapter 14, B2.4). The Control tab shows the key's protection and accessibility and a warning if the key is WHEN_UNLOCKED.
  • Live tab. The recent-events list holds changes, authentication requests and unrecognized broadcasts (at most 100); repeated equal statuses (broadcast or query) only move "last received". Every event, repeat or not, goes into the log file. The first status shows "first seen" times because nothing earlier is known. The saved VIN is shown masked.
  • Query tab. Changing the interval queries once at once and then counts again. The queries do not wake the car.
  • Log files. Sizes are decimal MB (20 000 000 and 200 000 000 bytes). Pruning keeps the folder at or below the limit and never deletes the file being written. If two files would start in the same second, the second is named one second later. Each line is flushed as it is written. The writer has a queue of 4096 lines; when it is full the new line is dropped and counted (Log tab) instead of blocking. A write error (disk full, folder gone) drops that line (counted) and the next line opens a file again; it never crashes the app.
  • Pulling. adb pull puts the files in samples/logs/android/<date>/logs/.
  • Style gate. lintKotlin and detekt also run on :samples:android (main and test sources), so tools/ci/verify.sh step (a) covers it. The library-only rules (explicitApi, forbiddenTokens) do not apply to the sample; detekt layers config/detekt/detekt-samples.yml on detekt.yml (Compose function naming and length, android.* imports, optional injection parameters). The Swift sources in samples/ios/ are not covered by these Kotlin tasks.

How it behaves, where the design left room:

  • Same behaviour as Android. The log schema, the field notes above, the back-off numbers, the 10 second stable reset, the VIN runs, the write-error rule and "a new connection waits for the previous vehicle to be released" are the same logic in Swift, and the same test names exist (VinMaskTests, LogWriterTests, ConnectionLoopTests, LiveStateTests).
  • One connection. The Control tab uses the monitor's connection and key. Its Connect and Disconnect buttons start and stop the monitor's loop. The VIN is entered and cleared on the Live tab; Control shows it masked.
  • Key errors. Locked fails the attempt, so the loop waits and reads the key again; the app also retries at once when UIApplication.protectedDataDidBecomeAvailableNotification arrives. The key is never deleted. Any other key error connects without a key (broadcasts and the three queries need none). The Control tab shows protection and accessibility and a warning for a WHEN_UNLOCKED key (delete it, make a new one, enroll it again).
  • Library gaps found. None; no library request was raised.
  • Log tab. The old observation mode is gone: the observe lines are always written to the log file, and the memo and Mark buttons write mark lines. "Copy last lines" and the Control tab's "Copy all results" (which now ends with the last log lines) replace the old copy button.
  • Log files. Same rules as Android (decimal MB, pruning never deletes the open file, names one second apart, a queue of 4096 lines, a write error drops and counts the line and the next line opens a file again). Lines go to the file as they arrive (no buffering). The files are in Documents/logs/ with the default file protection (readable after the first unlock).
  • Screen on. isIdleTimerDisabled is true only while the scene is active; it returns to the system default in the background and when inactive.
  • Background. The same loop runs in the background as long as iOS keeps the app running. Whether iOS wakes the app to scan and reconnect after a link loss is unconfirmed (plan Task 2 spike). While iOS keeps the app suspended the loop does not run, and the gap between two link lines shows how long that was.
  • Pulling. tools/samples/pull-monitor-logs.sh ios [--device <id>] copies Documents/logs of the device build (dev.mirolab.TeslableSampleDevice) with xcrun devicectl device copy from into samples/logs/ios/<date>/.
  • Version. project.yml has MARKETING_VERSION 0.5.0 and CURRENT_PROJECT_VERSION 12; raise the build number for every real-device round.

Real-car checklist

  1. Fresh install: enter the VIN, create the monitor key, enroll it. Restart the app: it connects by itself.
  2. Live tab: open and close the driver door, shift through P, R, N, D, lock from outside. Each change appears with its time.
  3. Walk away until the link drops, then come back: it reconnects without touching the phone, with the screen on and then locked.
  4. Leave the locked phone near the car for 30 minutes: still connected or reconnected, and the log keeps growing.
  5. Press Disconnect: no reconnect attempts for 2 minutes.
  6. Pull the logs on the Mac with the script: the first line is a session line, and searching for a 17-character VIN finds nothing.

iOS only (the full runbook with expected results is in samples/ios/README.md, "Monitor app: real-device checklist"):

  1. The monitor key reports afterFirstUnlock after the app is started again (Secure Enclave key, plan Task 11).
  2. Handshake on a locked iPhone with the monitor key (plan Task 11). If creating a Secure Enclave key fails while the phone is locked, copy the exact error text.
  3. Background: lock the phone, leave and come back, then read the link lines to see whether iOS reconnected on its own (the result of the plan Task 2 spike).
