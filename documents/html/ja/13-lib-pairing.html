13. キーとペアリング

スマートフォンには専用のキーペアが必要で、車両はその公開キーを登録していないとコマンドを受け付けません。ライブラリはキーの作成と保存、車両のキー一覧の読み取り、車両へのキー登録を行います。ユーザーが NFC キーカードをタッチし、画面で承認します。

キーストア

TeslaBle.keys は VehicleKeyStore です。キーはエイリアスで検索します。ほとんどのアプリではデフォルトのエイリアスだけで足ります。

呼び出し戻り値動作
getOrCreate(alias, policy)VehicleResult<VehicleKey>保存済みのキーを返すか、そのエイリアスでスマートフォンのロック解除中にだけ使える (WHEN_UNLOCKED) NIST P-256 キーペアを作成します
getOrCreate(alias, policy, accessibility)VehicleResult<VehicleKey>同じですが、新しいキーには選んだアクセシビリティが付きます (下記参照)。既存のキーはそのまま返ります
get(alias)VehicleResult<VehicleKey?>キーがない場合は Success(null)
delete(alias)VehicleResult<Unit>キーがない場合も成功します
  • デフォルトのエイリアスは "teslable-default" です (VehicleKeyStore.DEFAULT_ALIAS、Swift では VehicleKeyStoreCompanion.shared.DEFAULT_ALIAS)。
  • エイリアスには英字、数字、.、_、- を 64 文字まで使えます。ただし . や .. にはできません。
  • VehicleKey はハンドルです。alias、protection、accessibility、publicKey (65 バイト、0x04 ‖ X ‖ Y) を公開します。秘密鍵はプラットフォームのキーストアから出ることはなく、エクスポート API もありません。
  • VehicleKey には閉じるものがありません。使っている間は保持し、使い終わったらそのまま手放してください。iOS と Android では get や getOrCreate は呼ぶたびに同じ保存済みキーの新しいハンドルを返し（メモリ上のストアは同じものを返します）、どこからも参照されなくなったハンドルは自動的に片付けられるため、接続のたびにキーを読み直してもハンドルはたまりません。接続した Vehicle は、自分のキーへの参照を自分で保持します。
  • セッションを開始するとき、ライブラリはハンドルの鍵合意関数 sharedX を呼びます。アプリは呼びません。電話のロックがキーを妨げると、この関数は KeyLockedException を投げ、ライブラリはそれを KeyStoreError.Locked に変えます (下記参照)。

キーの保存場所

policy 引数はソフトウェアキーを許容するかどうかを決めます。VehicleKey.protection でキーが実際にどこに置かれたかがわかります。

KeyPolicy動作
PREFER_HARDWARE (デフォルト)ハードウェアを優先し、失敗した場合はソフトウェア
REQUIRE_HARDWAREハードウェアのみ。使えない場合は KeyStoreError.HardwareUnavailable
SOFTWARE_ONLYソフトウェアのみ。テストやエミュレーター用
KeyProtectionハードウェア場所
SECURE_ENCLAVEはいiOS Secure Enclave
STRONGBOXはいAndroid StrongBox
TEEはいAndroid Trusted Execution Environment
SOFTWAREいいえAndroid Keystore でラップされるか iOS キーチェーンに保存されます。JVM ではメモリ上

実機が SOFTWARE を報告した場合は、ユーザーに知らせることを検討してください。そのキーはハードウェアキーより弱いためです。

スマートフォンのロック中にキーを使う

キーを作成するときに、スマートフォンがロックされている間もそのキーを使えるようにするかを選びます。この選択が意味を持つのは iOS だけです。デフォルトはこれまでと同じ動作で、モニターサンプルのようにバックグラウンドで車両を見守るアプリだけが明示的に選びます。

KeyAccessibilityiOS キーチェーンのクラスロック中の使用用途
WHEN_UNLOCKED (デフォルト)kSecAttrAccessibleWhenUnlockedThisDeviceOnlyいいえほとんどのアプリ。スマートフォンがロックされている間、このキーは読み込めず、Secure Enclave のキーではセッションを開始できません (Locked)
AFTER_FIRST_UNLOCKkSecAttrAccessibleAfterFirstUnlockThisDeviceOnlyはい 最後の再起動後に一度ロックを解除してからスマートフォンがロックされていてもバックグラウンドで動き続ける必要があるアプリ
  • 3 番目の引数で渡します: getOrCreate(alias, policy, accessibility)、Swift では getOrCreate(alias:policy:accessibility:)。引数が 2 つの呼び出しは WHEN_UNLOCKED のキーを作成します。
  • どちらの設定でもキーはこのスマートフォンにだけ置かれます。バックアップやデバイスの移行で別のデバイスに移ることはありません。
  • 設定はキーの作成時に決まります。既存のエイリアスに別の値を求めても、既存のキーがそのまま返ります。実際の値は key.accessibility でわかり、iOS では保存されたキーから読み直した値です。キーチェーンが値を返さない場合 (想定外) は、キーは WHEN_UNLOCKED と報告され、WARN 行が記録されます。
  • Android と JVM ではこの引数は無視され、すべてのキーが AFTER_FIRST_UNLOCK を報告します。Android Keystore のキーはロック解除やユーザー認証の要件なしで作成されるためです (API 上の話で、実機ではまだ確認していません)。
  • ロックされた iPhone では、ロック解除中にだけ使えるキー、または再起動後の最初のロック解除前のすべてのキーについて、getOrCreate、get、delete が KeyStoreError.Locked を返します。Locked を理由にキーを削除したり作り直したりしないでください。ロックを解除してから再試行します。スマートフォンがロックされていて新しいキーを作成できない場合、ライブラリはより弱いソフトウェアキーで代用しません。
  • ロック解除中にだけ使える Secure Enclave のキーを、スマートフォンのロックが解除されているときに読み込んでおき、ロックされた後に使うと、セッションを開始できません。startSession() は車両が応答するとすぐに KeyStoreError.Locked を返し (車両の両方の部分で同じ)、ライブラリは再試行しません。車両がその応答に自らエラーを含めた場合 (例: キーが登録されていない) は、そのエラーが優先されます。スマートフォンのロックを解除してから、同じキーで startSession() をもう一度呼んでください。
  • 同じ理由で、スマートフォンがロックされている間に接続すると、保存されたセッションは復元されません。保存されたセッションは残ります。車両のその部分に再びセッションができるまで、ライブラリはセッションキャッシュに何も書き込まないため、ロック解除後の最初の接続でそのセッションが復元されます。例外: 同じ接続で復元した別のセッションが古いと判明した場合、ライブラリはそのセッションを除いてキャッシュを書き直し、妨げられたセッションも一緒に外れます (車両のその部分は次回新しくハンドシェイクします)。
  • ソフトウェアキー (SOFTWARE) は秘密鍵をメモリに持つため、スマートフォンがロックされる前に読み込んだキーオブジェクトはロック後も動き続けます (API に基づく。実機では未確認)。キーストアから読み込むときだけ Locked になります。
  • 実機ではまだ確認していません: ロックされた Secure Enclave のキーを、iOS がライブラリの想定するエラーコード (-25308) で知らせるかどうか。別のコードで知らせる場合、startSession() はこれまでどおりタイムアウトで終わります。1 つのキーオブジェクトを使い続けてください。電話がロックされている間にキーストアから読み直すと Locked になります。
  • すでに進行中のセッションは、設定にかかわらず画面がロックされても動き続けます。進行中のセッションのコマンドは秘密鍵を使いません。秘密鍵が必要なのは、新しいセッションを開始するときと保存されたセッションを復元するときだけです。
AFTER_FIRST_UNLOCK のリスク

再起動後に一度ロックが解除されたスマートフォンであれば、ロックされたスマートフォンを手にした人やアプリの権限で動くコードが、Bluetooth でこのキーを使えます。キーのロールが許すこと、たとえば車両のロック解除までできます。Secure Enclave はキーのコピーは防ぎますが使用は防がず、コマンドごとの確認も求めません。ユーザーに知らせ、画面に key.accessibility を表示し、モニタリング用にはロールを制限したキーを検討してください。ソフトウェアキー (protection が SOFTWARE) はより多くさらされます。ハードウェアキーが必要なら REQUIRE_HARDWARE を使ってください。

キーを別の設定に切り替える

設定は変えられないため、切り替えるには新しいエイリアスで新しいキーを作成して登録し直します。

  1. 新しいエイリアスを決めます。例: teslable-monitor。新しいキーが動くまで、古いキーはそのまま残します。
  2. keys.getOrCreate(newAlias, KeyPolicy.PREFER_HARDWARE, KeyAccessibility.AFTER_FIRST_UNLOCK) を呼び出し、key.accessibility と key.protection を確認します。
  3. 新しい公開キーを登録します (キーの登録)。NFC キーカードで登録するか、登録済みのキーがキーを追加できる接続から addKey で登録します。
  4. sessionInfo(key.publicKey, VehicleDomain.INFOTAINMENT) または listKeys() で確認します。
  5. 必要なら、古い公開キーを車両 (removeKey) とスマートフォン (keys.delete(oldAlias)) から削除します。

Kotlin

val key = when (val r = ble.keys.getOrCreate("teslable-monitor", KeyPolicy.PREFER_HARDWARE, KeyAccessibility.AFTER_FIRST_UNLOCK)) {
    is VehicleResult.Success -> r.value
    is VehicleResult.Failure ->
        if (r.error == VehicleError.KeyStoreError.Locked) return waitForUnlock()   // never delete or re-create here
        else return show("Key store: ${r.error.message}")
    is VehicleResult.Uncertain -> return                                          // the key store does not return it
}
if (key.accessibility != KeyAccessibility.AFTER_FIRST_UNLOCK) {
    show("This key works only while the phone is unlocked. Create a key under a new alias and enroll it again.")
}

Swift

let r = try await ble.keys.getOrCreate(alias: "teslable-monitor", policy: .preferHardware, accessibility: .afterFirstUnlock)
switch onEnum(of: r) {
case .success(let s):
    guard let key = s.value as? VehicleKey else { return }
    if key.accessibility != .afterFirstUnlock { print("unlocked-only key: create a new alias and enroll it again") }
case .failure(let f):
    if f.error is VehicleErrorKeyStoreErrorLocked { print("phone locked: try again after unlock") }   // never delete
    else { print("key store: \(f.error.message)") }
case .uncertain: break                                                                               // not returned by the key store
}

自分のキーは登録されているか

vehicle.listKeys() はキーなしで、車両をウェイクアップせずに動作します。車両のリストと自分の公開鍵を比較します:

val mine = key.publicKey.toByteArray()
val enrolled = when (val r = vehicle.listKeys()) {
    is VehicleResult.Success -> r.value.firstOrNull { it.publicKey?.toByteArray()?.contentEquals(mine) == true }
    else -> null                                   // Uncertain または Failure: 不明なので後でもう一度問い合わせる
}
// enrolled?.role は KeyRole、enrolled?.slot はホワイトリストのスロット

登録されていないキーでも接続と読み取りはできます。そのキーでセッションを開始すると KeyNotPaired で失敗します。

キーの削除と置き換え

  • keys.delete(alias) はスマートフォンからだけキーを削除します。車両側で削除されるまで、車両はその公開鍵をリストに残します。
  • 保存されたセッションは 1 つのキーに属します。キーが変わると、次の接続で古いセッションを破棄して新しいハンドシェイクを始めます。
  • 破損した 保存キー (KeyStoreError.PlatformFailure、stored key is corrupted) が自動で置き換えられることはありません。ユーザーに知らせ、delete を呼んでから getOrCreate を呼び、新しいキーを車両に登録し直してください。プラットフォームノート を参照してください。
  • KeyStoreError.Locked は破損ではありません。キーは正常で、スマートフォンがロックされているだけです。削除せず、ロックを解除してから再試行してください。startSession() が返した Locked も同じです。

キーの登録

Go の原本は鍵登録リクエストを送るだけで、返信を読みません。返信を PairingEvent の値として読むのはこのライブラリで新しく加えた動作で、実車ではまだ確認していません。

呼び出し戻り値動作
addKeyRequest(publicKey, role, formFactor, timeout)Flow<PairingEvent>車両にキーの追加を依頼します (FR-022, FR-023)。コールドフローで、収集するたびにリクエストを 1 回送ります。署名しないのでセッションは不要です。timeout = null のときは pairingTimeout (60 秒) を使います。リクエストは 1 つずつ実行されます
sessionInfo(publicKey, domain, timeout)VehicleResult<SessionInfoSummary>ドメインごとに登録を確認します (FR-024)。接続にキーは不要です。Failure(KeyNotPaired) は車両の一覧にキーがないという意味です。接続自身のキーで問い合わせるとそのドメインのセッションも作られ、sessions に Ready(fromCache = false) と表示されます
addKey(publicKey, role, formFactor, timeout)VehicleResult<Unit>十分な権限を持つ登録済みキーが、NFC カードなしで別のキーを追加します (FR-027)。認証付きの VCSEC コマンドで、VCSEC セッションが必要です
removeKey(publicKey, timeout)VehicleResult<Unit>車両からキーを削除します (FR-026)。認証付きの VCSEC コマンドで、VCSEC セッションが必要です
  • role のデフォルトは KeyRole.OWNER、formFactor のデフォルトは platformKeyFormFactor() です。Android は ANDROID_DEVICE、iOS は IOS_DEVICE、JVM (テスト) は CLOUD_KEY です。
  • Swift では Kotlin のデフォルト引数を使えません。すべての引数 (role:、formFactor:、timeout:) を渡してください。例: formFactor: .iosDevice。
  • addKey と removeKey は InsufficientPrivileges (接続のキーにキー管理の権限がない場合。例: Driver キー)、KeychainRejected(code) (例: WHITELIST_FULL)、NoSession、InvalidArgument (role = UNKNOWN) で失敗することがあります。Uncertain は車両のキー一覧が変わった可能性を示します。listKeys() で確認し、再送しないでください。

ペアリングイベント

PairingEvent意味最後のイベント
Sentリクエストを送信しました。ユーザーはセンターコンソールで NFC キーカードをタッチし、画面で承認する必要がありますいいえ
WaitingForTap車両が待機中 (WAIT) であることを通知していますいいえ
Accepted車両がキーを受け入れました。インフォテインメントが認識するまでさらに数十秒かかることがありますはい
Rejected(error)車両が拒否しました: KeychainRejected、UnknownKeychainCode、VcsecRejected、UnknownVcsecErrorはい
Unknown(raw)解読できなかったフレームです。raw はバイト列のコピーですいいえ
Failed(error)送信できなかった (NotConnected、書き込み失敗、InvalidArgument)、または待機中にリンクが切れましたはい
TimedOuttimeout 内に最終応答がありませんでした。キーは登録されている可能性があるので sessionInfo で確認してくださいはい

最後のイベントの後でフローは終了します (isTerminal が true)。ステータスもエラーも持たないフレーム、途中の OK ステータス、リクエスト送信前に受信したフレームは無視されます。

実車では未確認です

鍵登録リクエストの返信形式は、まだ実車で観察できていません (ADR-0009)。Unknown(raw) を受け取った場合は、raw を 16 進数で (VIN は含めずに)、車両がとった動作と一緒に報告してください。

ペアリングの流れ

  1. キーを作成し (keys.getOrCreate())、そのキーで接続します。
  2. vehicle.addKeyRequest(key.publicKey) を収集します。ユーザーにセンターコンソールでキーカードをタッチし、画面で承認するよう案内します。
  3. Accepted (または TimedOut) の後、sessionInfo(key.publicKey, VehicleDomain.INFOTAINMENT) を 3 秒ごとに最大 2 分間呼び出します。KeyNotPaired は「まだ」という意味なので続けてください。Success ならキーは登録され同期済みです。
  4. startSession(setOf(VehicleDomain.VCSEC)) を実行してからコマンドを送ります (15. コマンド)。

Kotlin

val key = (ble.keys.getOrCreate() as VehicleResult.Success).value
val vehicle = (ble.connect(vin, key) as VehicleResult.Success).value

vehicle.addKeyRequest(key.publicKey).collect { event ->
    when (event) {
        PairingEvent.Sent -> show("Tap the key card on the center console, then confirm on the screen")
        PairingEvent.WaitingForTap -> show("Waiting for the card")
        PairingEvent.Accepted -> show("Accepted, waiting for the car to sync")
        is PairingEvent.Rejected -> show("Rejected: ${event.error.message}")
        is PairingEvent.Unknown -> report(event.raw.joinToString("") { it.toUByte().toString(16).padStart(2, '0') })      // see the warning below
        is PairingEvent.Failed -> show("Failed: ${event.error.message}")
        PairingEvent.TimedOut -> show("No answer, checking enrollment")
    }
}

suspend fun waitUntilEnrolled(vehicle: Vehicle, key: VehicleKey): Boolean {
    val deadline = TimeSource.Monotonic.markNow() + 2.minutes
    while (deadline.hasNotPassedNow()) {
        when (val r = vehicle.sessionInfo(key.publicKey, VehicleDomain.INFOTAINMENT)) {
            is VehicleResult.Success -> return true
            is VehicleResult.Failure -> if (r.error != VehicleError.KeyNotPaired) return false
            is VehicleResult.Uncertain -> Unit                  // reply lost: ask again
        }
        delay(3.seconds)
    }
    return false
}

Swift

for await event in vehicle.addKeyRequest(publicKey: key.publicKey, role: .owner, formFactor: .iosDevice, timeout: nil) {
    switch onEnum(of: event) {
    case .sent: print("Tap the key card on the center console, then confirm on the screen")
    case .waitingForTap: print("Waiting for the card")
    case .accepted: print("Accepted, waiting for the car to sync")
    case .rejected(let r): print("Rejected: \(r.error.message)")
    case .unknown(let u): print("Unknown frame, \(u.raw.size) bytes")
    case .failed(let f): print("Failed: \(f.error.message)")
    case .timedOut: print("No answer, checking enrollment")
    }
}

// then, every 3 s for up to 2 minutes:
let r = try await vehicle.sessionInfo(publicKey: key.publicKey, domain: .infotainment, timeout: nil)
switch onEnum(of: r) {
case .success: print("enrolled")
case .failure(let f): print("not yet or failed: \(f.error.message)")   // KeyNotPaired: keep polling
case .uncertain: print("reply lost, ask again")
}

ロール (KeyRole) は OWNER、DRIVER、FLEET_MANAGER、VEHICLE_MONITOR、CHARGING_MANAGER、GUEST、SERVICE です。各ロールが送信できるコマンドは 7. コマンドリファレンス に記載しています。 拡張されたプロトコル定義にだけあるロールとキー形態（例: ROLE_RIDER、KEY_FORM_FACTOR_APPLE_WATCH）は UNKNOWN として読まれます。
