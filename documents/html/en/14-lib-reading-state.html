14. Reading Vehicle State

Everything the library can read from the car over BLE, in two parts: Part A is data you ask for (four security-controller queries and the infotainment query getState()), Part B is data the car sends by itself (broadcasts). The four security-controller queries need no key, no session and no wake-up, because VCSEC answers even while the infotainment computer sleeps. getState() does need an enrolled key, a session and an awake car.

What exists today

The queries in Part A are implemented, including getState() (A8). It is checked with FakeVehicle tests, not yet on a real car. The car's broadcasts (Part B) reach your app through vehicle.events (B2); the observation log still shows them too.

  • Each takes an optional timeout; without it the default command timeout (5 seconds) applies. For listKeys() the timeout covers all of its requests together.
  • The car handles one VCSEC request at a time per connection. A query that has to wait for another one spends part of its timeout waiting. getState() goes to infotainment and does not wait in that queue.
  • These are queries. An Uncertain result means no data was confirmed, not that a command may have run, so it is safe to ask again, just not in a tight loop (see 16. Error Handling).
  • While another Bluetooth client is active, a query can get no reply at all, listKeys() most often (16. Error Handling).
  • Control payloads (lock, trunk, wake-up, climate, charging, media and the other infotainment commands) are in 15. Commands.

Domain values: DOMAIN_BROADCAST 0, DOMAIN_VEHICLE_SECURITY 2 (VCSEC), DOMAIN_INFOTAINMENT 3. The Teslemetry schema also lists 4, 5, 7 and 8; the library does not use them. Its field 53 message_frame is unconfirmed and unused.

Routing rules for VCSEC requests:

  • to_destination.domain is DOMAIN_VEHICLE_SECURITY and from_destination.routing_address is a fresh random 16-byte address for every request. The reply comes back to that address and the library matches it by address (and the car's domain). request_uuid is not used to match VCSEC replies. The uuid (51) is still filled with 16 random bytes.
  • A reply addressed to any other routing address is not ours and is dropped as no-handler (see B3).
  • Queries are unauthenticated: no signature_data, and protobuf_message_as_bytes is the plain UnsignedMessage. Commands use the same envelope with signature_data and an AES-GCM protected payload.
  • For sessionInfo the payload is session_info_request (14) and to_destination.domain is the requested domain; the reply carries session_info (15).

Mapping rules

A value outside the schema maps to UNKNOWN instead of the zero value. proto3 cannot tell a missing enum from its zero value, so a missing lock state reads as UNLOCKED; the library keeps that Go behaviour for the query. gear has no Go counterpart (the official Go schema ends at field 5); its zero value is GEAR_UNKNOWN, so a missing gear reads as UNKNOWN. Gear was confirmed in broadcasts. Query replies also fill it (Likely, B5): 144 of 144 carried gear; NEUTRAL not seen. The real-car results show the car omits closureStatuses when every field is CLOSED (the zero value) and sends it while any field is not (front and rear driver doors, rear trunk and charge port seen), so "absent means all closed" matches what we saw. The one exception is a trunk operated with the interior button, which sent no broadcast at all; this query should still report it (not yet checked on a real car).

A7. Other request types in the schema

InformationRequestType also defines GET_TOKEN 1, GET_COUNTER 2, GET_EPHEMERAL_PUBLIC_KEY 3, GET_SESSION_DATA 4, GET_PERSONALIZATION_INFO 7, GET_KEYSTATUS_INFO 8, GET_ACTIVE_KEY 9 and GET_CAPABILITIES 16 (Teslemetry only). The library sends none of them and has no API for them. getState(category) is not one of these: it goes to infotainment (A8).

A8.2 Call order

getState never starts a session and never wakes the car. Your app does both, in this order.

SituationWhat getState doesWhat your app does
No infotainment sessionSends nothing and returns Failure(NoSession)startSession(setOf(VehicleDomain.INFOTAINMENT)) first
A session restored from the cache that the car no longer acceptsReturns Failure(NoSession); sessions then shows None for INFOTAINMENTstartSession(setOf(VehicleDomain.INFOTAINMENT)), then ask again
Infotainment asleepSends one request, gets no reply and returns Uncertain(Timeout(afterSend = true))Wake it first, as below
 
Awake:    connect → startSession(setOf(INFOTAINMENT)) → getState(category)
Asleep:   connect → vehicleStatus() shows ASLEEP → startSession(setOf(VCSEC)) → wakeUp()
            → vehicleStatus() shows AWAKE → startSession(setOf(INFOTAINMENT)) → getState(category)
  • Decide with vehicleStatus(): it needs no session and never wakes the car.
  • On a sleeping car, handshake with VCSEC alone. The Go tool tesla-control does this for a BLE wake because infotainment is presumably asleep, and the Go recipes warn that a handshake with both domains can then take a long time.
  • wakeUp() returning Success means VCSEC accepted the command, not that infotainment is up. Wait for AWAKE, then start the infotainment session. The car can still answer busy right after waking; the library retries that inside the timeout, so the first query after a wake may need a longer timeout.
  • A saved session says nothing about sleep. startSession succeeds without asking the car and sessions shows Ready(fromCache = true) even while infotainment sleeps; the first query can then time out. Read sleepStatus instead.
  • Waking is your app's decision. The library never does it for you.
  • ping() (15. Commands) is a command that changes nothing and returns no data. Success shows that the key and the infotainment session work. It needs the same session and awake car as getState.
import dev.mirolab.teslable.Vehicle
import dev.mirolab.teslable.model.*
import kotlinx.coroutines.delay
import kotlin.time.Duration.Companion.seconds

// vehicle was connected with an enrolled key (12-lib-getting-started.md). True when getState can be called.
suspend fun prepareInfotainment(vehicle: Vehicle): Boolean {
    val status = vehicle.vehicleStatus()                                  // no session needed, never wakes the car
    if (status is VehicleResult.Success && status.value.sleepStatus == SleepStatus.ASLEEP) {
        if (vehicle.startSession(setOf(VehicleDomain.VCSEC)) !is VehicleResult.Success) return false
        if (vehicle.wakeUp() is VehicleResult.Failure) return false       // Uncertain: do not resend, the loop reads the state
        for (attempt in 1..30) {                                          // about 30 s; the real wake time is not confirmed (#118)
            delay(1.seconds)
            val now = vehicle.vehicleStatus()
            if (now is VehicleResult.Success && now.value.sleepStatus == SleepStatus.AWAKE) break
        }
    }
    return vehicle.startSession(setOf(VehicleDomain.INFOTAINMENT)) is VehicleResult.Success
}

func prepareInfotainment(vehicle: Vehicle) async throws -> Bool {
    let status = try await vehicle.vehicleStatus(timeout: nil)                 // no session needed, never wakes the car
    if case .success(let s) = onEnum(of: status), (s.value as? VehicleStatus_)?.sleepStatus == .asleep {
        let vcsec = try await vehicle.startSession(domains: [.vcsec], timeout: nil)
        guard case .success = onEnum(of: vcsec) else { return false }
        let woke = try await vehicle.wakeUp(timeout: nil)
        if case .failure = onEnum(of: woke) { return false }                   // uncertain: do not resend, the loop reads the state
        for _ in 1...30 {                                                      // about 30 s; the real wake time is not confirmed (#118)
            try await Task.sleep(nanoseconds: 1_000_000_000)
            let now = try await vehicle.vehicleStatus(timeout: nil)
            if case .success(let n) = onEnum(of: now), (n.value as? VehicleStatus_)?.sleepStatus == .awake { break }
        }
    }
    let session = try await vehicle.startSession(domains: [.infotainment], timeout: nil)
    if case .success = onEnum(of: session) { return true }
    return false
}

The 30 seconds comes from the Go BLE example and is not a measurement. Instead of polling, your app can watch sleepStatus in vehicle.events (B2).

A8.3 Reading the reply

  • Absent is not 0. Every scalar and message field directly on the 12 reply messages is nullable: a field the car did not send is null, and speed = 0 stays 0. Never replace null with 0. Repeated fields (charge_schedules, precondition_schedules) are empty lists when absent. Inside nested messages such as ChargeSchedule, fields are plain proto3 values: absent reads as 0, empty or false.
  • Check every field you use. A reply with no vehicleData is Success(VehicleData()), the same as an empty vehicleData, and the two cannot be told apart. Go returns (nil, nil) here; the library keeps a non-null result because your app checks each field anyway. Another kind of reply, such as Ping, gives the same empty result.
  • The reply is not checked against category (same as Go). Read the field for the category you asked for; a different field that arrives is passed through.
  • Success is not proof of a new measurement. Compare timestamp with the previous reply: if it did not move, do not present the values as fresh. If it is null, you cannot tell. timestamp is a Wire Instant: getEpochSecond() works in common Kotlin and in Swift.
  • Speed, power and odometer exist only in DRIVE, and that reply can go over the car's size limit (16. Error Handling). Live speed is not guaranteed, and there is no other source for it.
  • Wire keeps proto names, so fields are drive_state, speed_float, charge_state, unlike the camelCase hand-written models. Generated types are in com.tesla.generated.*.
  • Some states are wrapper messages, not enums: charging_state, climate_keeper_mode, sentry_mode_state and others carry one empty member that names the value (A8.6).
  • Do not log a result, toString() included. A VehicleData can hold the location and the destination. The library does not log it, and neither should your app.
import com.tesla.generated.universalmessage.MessageFault_E
import dev.mirolab.teslable.Vehicle
import dev.mirolab.teslable.model.*
import kotlin.time.Duration.Companion.seconds

suspend fun readSpeed(vehicle: Vehicle): Int? {
    when (val result = vehicle.getState(StateCategory.DRIVE)) {
        is VehicleResult.Success ->
            return result.value.drive_state?.speed               // null = the vehicle did not send it; 0 = it sent 0
        is VehicleResult.Uncertain -> {
            val e = result.error
            if (e is VehicleError.ProtocolFault && e.fault == MessageFault_E.MESSAGEFAULT_ERROR_RESPONSE_MTU_EXCEEDED) {
                return null                                      // reply too large
            }
            if (e is VehicleError.Timeout) return null           // no reply
            return null
        }
        is VehicleResult.Failure -> {
            if (result.error == VehicleError.NoSession) return null
            return null
        }
    }
}

// With an explicit timeout, and reading the reply's timestamp:
suspend fun readBattery(vehicle: Vehicle, lastSeconds: Long?) {
    val result = vehicle.getState(StateCategory.CHARGE, timeout = 8.seconds)
    if (result !is VehicleResult.Success) return
    val charge = result.value.charge_state ?: return             // no charge data in this reply
    val level: Int? = charge.battery_level
    val seconds: Long? = charge.timestamp?.getEpochSecond()
    val fresh = seconds != null && seconds != lastSeconds
    render(level, fresh)
}

Swift passes every argument. s.value needs a cast and numbers bridge as KotlinInt?; see 17. Platform Notes. This form passes a Swift typecheck against the framework; it has not run in a Swift program.

func readSpeed(vehicle: Vehicle) async throws -> Int32? {
    let result = try await vehicle.getState(category: .drive, timeout: nil)
    switch onEnum(of: result) {
    case .success(let s):
        // VehicleResult's generic is erased in Swift: s.value is AnyObject?, so cast it.
        guard let data = s.value as? VehicleData else { return nil }
        // Nullable numerics bridge as KotlinInt? / KotlinFloat?, not Int32? / Float?.
        let speed: KotlinInt? = data.drive_state?.speed
        let speedFloat: KotlinFloat? = data.drive_state?.speed_float
        _ = speedFloat?.floatValue
        return speed?.int32Value // nil = the vehicle did not send it; 0 = it sent 0
    case .uncertain(let u):
        switch onEnum(of: u.error) {
        case .protocolFault(let p) where p.fault == .messagefaultErrorResponseMtuExceeded:
            return nil // reply too large
        case .timeout(let t):
            _ = t.afterSend
            return nil // no reply
        default:
            return nil
        }
    case .failure(let f):
        if case .noSession = onEnum(of: f.error) { return nil }
        return nil
    }
}

// With an explicit timeout, and reading the reply's timestamp:
func readBattery(vehicle: Vehicle, lastSeconds: Int64?) async throws {
    let result = try await vehicle.getState(category: .charge, timeout: Timeouts.shared.seconds(seconds: 8))
    guard case .success(let s) = onEnum(of: result), let data = s.value as? VehicleData else { return }
    guard let charge = data.charge_state else { return }   // no charge data in this reply
    let level: KotlinInt? = charge.battery_level
    let seconds: Int64? = charge.timestamp?.getEpochSecond()
    let fresh = seconds != nil && seconds != lastSeconds
    render(level?.int32Value, fresh)
}

B2. Broadcast events: vehicle.events

Reply matching works as before and as in the Go original: a broadcast has no routing address, so the dispatcher drops it from routing (drop reason TO_DOMAIN). A broadcast never reaches a pending request and cannot be mistaken for a reply. The observation log still writes its [drop:to-domain] line (18. Troubleshooting).

In addition, the library hands every plain broadcast to your app through vehicle.events (FR-035). The Go original has nothing like it; it just drops the frame. Kotlin and Swift examples are in 12. Getting Started with the Library; what each message means is in B3.

val events: Flow<VehicleEvent>                    // member of Vehicle

sealed interface VehicleEvent {                   // dev.mirolab.teslable.model
    val raw: ByteArray                            // the whole received frame; a new copy on every access; not VIN-masked
    val unknownFields: List<String>               // paths of fields the schema does not know, for example "53", "1.8"
    class Status(val status: VehicleStatus, …) : VehicleEvent
    class AuthenticationRequest(val requestedLevel: AuthenticationLevel, val reasons: List<AuthenticationReason>, …) : VehicleEvent
    class Unrecognized(…) : VehicleEvent
}

Which frames become events

All of the following must hold. It is the observation log's gate for its detailed decode, except that the payload does not have to decode (a payload that does not decode gives Unrecognized).

Everything else stays an observation log line only: replies to other phones, signed or encrypted frames, frames that do not parse, frames without a source (including bare frames, B3.2). The library never decrypts a broadcast, and nothing it decrypted ever reaches an event (FR-112).

Event types

EventWhenWhat it carries
VehicleEvent.StatusThe frame has vehicleStatus (field 1)status: a VehicleStatus built with the same rules as vehicleStatus() (A2): no opening reported means all closed, unknown values become UNKNOWN, gear included
VehicleEvent.AuthenticationRequestThe frame has authenticationRequest (field 3)requestedLevel and reasons (B3.2). The 20-byte token is not a field; it is in raw
VehicleEvent.UnrecognizedNeither: only unknown fields (44, 48 and 53 on the real car), another field, no payload, or a payload that does not decode (then unknownFields is empty)Only raw and unknownFields
  • One frame can give two events. With both fields, Status comes first and AuthenticationRequest second, with the same raw and the same unknownFields. The schema puts the two fields in one oneof, so an ordinary decode would keep only one of them; the library reads both.
  • raw is the whole frame as received (without the 2-byte BLE length prefix), exactly as the car sent it in plaintext. Each access makes a new copy, so read it once. It is not VIN-masked: mask the VIN before you store or share it. Like the observation log's detailed decode, this is a narrow exception to "no plaintext payloads" that does not touch FR-112: only frames the car sent as plaintext, never anything the library decrypted.
  • Two events are equal when their fields and their raw bytes are equal. Printing an event shows only the length of raw.

unknownFields

Each entry is a path of field numbers from FromVCSECMessage down to a field the schema does not know:

PathMeaning

An enum value outside the schema is listed under its field number too (the model shows UNKNOWN); a new gear value gives "1.7". Inside a sub-message its own fields come before those of its nested messages. A number that occurs twice is listed twice. A non-empty list means part of the frame was not understood; the bytes are in raw.

Rules for your app

  • A repeat is not a change. With nothing changing, the car resends its status 60.0 seconds after the previous Status (Likely; measured only on an awake car with a person present, B3.1), and several frames can come within one second around a change, some of them identical. A frame can also differ only in field 8, which the model does not show, so it reads as an unchanged VehicleStatus. The library does not filter repeats; compare with the previous value yourself.
  • A quiet minute is normal. Status frames can be 60 seconds apart, so up to 60 seconds without one says nothing about the link. Judge the link from connection, not from the time since the last event.
  • Trunk: opening and closing the trunk by hand from outside sent broadcasts (rearTrunk = OPEN, then no closureStatuses). With the interior button it sent none, so an app that tracks the trunk from events keeps seeing it CLOSED. When the trunk state matters, confirm it with vehicleStatus().
  • Waking car: the first frames of a sleeping car can show UNKNOWN closures and gear = UNKNOWN; real values follow within about 0.5 s (B3.1). Do not treat those UNKNOWN values as a change. The lock state reads UNLOCKED in them too, and since UNLOCKED is never encoded you cannot tell whether the car was still locked; confirm with vehicleStatus() if it matters.
  • gear = UNKNOWN on an awake car (Likely): twice a parked, awake car with a person present sent a 24-byte frame with no gear field, and a normal PARK frame followed within 0.1 s. Do not treat that UNKNOWN as a change.
  • Subscribing: a collection receives from the moment it starts; earlier broadcasts are not replayed. Several collectors each receive every event.
  • The end: the flow ends normally, without an exception, when connection becomes Disconnected for any reason or when you call disconnect(), whichever comes first. A collection started later ends at once. A frame that was still on its way at that moment can be lost. Decide about reconnecting from connection, and still call disconnect() after a link loss. A new connection is a new Vehicle with its own events.
  • Slow collector: the library keeps up to 64 frames for collectors that fall behind. Beyond that, new frames are dropped for every collector of the connection, counted, and logged as a WARN line on the first drop and every 100th. This is not an error (16. Error Handling). Keep the collector light.
  • No key and no session are needed; connect(vin, key = null) is enough. The real-car observation used a key that was not enrolled.

  • The earlier guess of a per-key authentication challenge is weaker now: at most 16 bits differ between entries. Its meaning is unknown.

B3.4 Field 48 (unknown)

Status: Unknown. FromVCSECMessage field 48: {1: 5 bytes}, in a 20-byte frame. All 3 frames of the later recordings (B5) carry 01 03 06 07 04, the id order of the 5-entry field 53 frames (B3.3).

Rate: round 1 saw it about every 5.0 s while the car was awake and a person was present (with gaps), and round 2 did not see it. The later recordings have 3 frames in about 68 minutes connected, with no visible trigger. That does not fit a steady heartbeat, the earlier guess. The condition is unknown.

B3.5 Replies addressed to other clients

These are not broadcasts. Replies to another Bluetooth client reach our link too: to_destination.routing_address is that client's 16-byte address, and the library drops them as no-handler (owner other). They do not meet the conditions for an event (B2), so they are never events. Counts are from the later recordings (B5).

B3.6 Field 44 (unknown)

Status: Unknown for the meaning, Likely for the link with slow connects. FromVCSECMessage field 44: a varint, value 2 in all 4 frames seen, in a 13-byte frame. Alone it is an Unrecognized event with "44" in unknownFields.

B5. Observation method and environment

  • iPhone 16 Pro, iOS 27, Model Y (firmware not recorded). Sample dev.mirolab.TeslableSampleDevice builds 7 and 8, key SECURE_ENCLAVE. The key does not need to be enrolled to observe.
  • First round 2026-10-18 (build 7, one continuous recording, 71 lines). Second round 2026-10-24 (build 8, detailed unknown-field decoding, one recording per scenario). Third round 2026-10-24 (build 8, one 40-second recording of 25 lines: sleeping, locked car; rear driver door opened from outside; charge port latch released while holding the handle; charger unplugged; rear door closed; charge port door closed; trunk opened and closed by hand from outside; driver door opened and closed from outside).
  • Later recordings: six recordings of the Monitor app on 2026-10-31 and 2026-11-01 (builds 13, 14 and 18), 12 connections, about 68 minutes connected, on the phone and car above. No scenario was given, so what a person did is inferred from the frames and these findings stay Likely or Unknown.
