왜 새 프로토콜인가

Tesla 차량은 종단 간 명령 인증(end-to-end command authentication)을 제공하는 프로토콜을 지원합니다. 명령은 클라이언트의 개인 키로 인증(또는 암호화)되어 차량까지 전달되고, 차량은 자신의 키체인에 등록된 공개 키로만 명령을 검증합니다. Tesla 서버조차 명령을 위조할 수 없습니다.

  • 기존 Owner API는 차량이 종단 간 인증을 요구하기 시작하면서 동작을 멈춥니다. Owner API 기반 애플리케이션은 이 SDK로 직접 포팅하거나, 이 저장소의 HTTP 프록시를 앞에 두어 REST 호출을 그대로 유지할 수 있습니다.
  • 2021년 이전 Model S/X는 이 프로토콜을 지원하지 않습니다. 이 차량들에는 Fleet API가 계속 동작하며, 프록시는 ErrProtocolNotSupported(HTTP 422)를 받으면 해당 VIN을 기억해 두었다가 이후 요청을 REST API로 그대로 전달합니다.
  • 이 SDK는 Go로 작성된 공식 구현입니다. 프로토콜 사양(pkg/protocol/protocol.md)과 protobuf 정의가 공개되어 있으므로 다른 언어로 구현할 수도 있습니다(../md/10-porting-guide.md 참고).

두 단계 인증 모델

인터넷 경로로 명령을 보내려면 두 가지 서로 독립적인 인증을 통과해야 합니다. BLE 경로는 두 번째 단계만 필요합니다.

  1. Tesla 서버 인증 (OAuth). Tesla 서버는 클라이언트가 유효한 OAuth 액세스 토큰을 제시할 때만 메시지를 차량으로 전달합니다. 토큰의 aud/ou_code 클레임에서 지역별 Fleet API 호스트를 결정합니다(pkg/account). BLE에서는 이 단계가 없습니다.
  2. 차량 인증 (개인 키). 차량은 명령이 키체인에 등록된 공개 키로 인증될 때만 실행합니다. 키는 NIST P-256 ECDH 키이며, 사용자가 NFC 카드로 승인하거나(BLE), Tesla 앱의 https://tesla.com/_ak/<domain> 링크를 통해 등록합니다.
BLE에서는 OAuth가 필요 없다

BLE로 직접 연결하면 Tesla 서버를 거치지 않으므로 OAuth 토큰 없이 VIN과 개인 키만으로 명령을 보낼 수 있습니다. 단, 차량은 MESSAGEFAULT_ERROR_COMMAND_REQUIRES_ACCOUNT_CREDENTIALS로 일부 명령을 거부할 수 있고, Fleet Manager 역할 키는 2023.38 이후 BLE로 명령을 보낼 수 없습니다.

도메인: VCSEC와 Infotainment

차량에는 도메인(domain)이라 부르는 독립된 하위 시스템이 있습니다. 각 도메인은 자기만의 공개 키, 시계(epoch + timestamp), 안티리플레이 카운터를 가지므로 도메인마다 별도의 핸드셰이크와 세션이 필요합니다.

VCSEC는 잠들지 않는다

VCSEC는 Infotainment가 절전 상태여도 BLE로 응답합니다. 따라서 body-controller-state, wake, lock 같은 VCSEC 명령은 차량을 깨우지 않고 실행할 수 있습니다. StartSession(ctx, []Domain{DomainVCSEC})처럼 도메인을 제한하면 불필요하게 Infotainment를 깨우지 않습니다. 반대로 VCSEC는 메모리 제약으로 응답에 request_uuid를 넣지 않고, 카운터가 순서대로 도착해야 하며, 동시 요청을 피해야 합니다.

키 역할(Role)

차량은 등록된 공개 키마다 역할을 부여하고, 역할에 따라 인가할 수 있는 명령이 달라집니다. 값은 pkg/protocol/protobuf/keys.proto에 정의되어 있습니다.

  • Connector는 바이트 배열만 주고받는 데이터그램 전송입니다. 인증이나 protobuf를 전혀 모릅니다. 직접 구현하면 다른 전송(예: 시리얼, 테스트용 메모리 파이프)을 붙일 수 있습니다.
  • Dispatcher는 Connector를 감싸 RoutableMessage를 인코딩/디코딩하고, 도메인별 세션(session)을 유지하며, 들어오는 메시지를 routing_address(+ Infotainment는 request_uuid)로 대기 중인 receiver에 배달합니다. 차량이 오류와 함께 새 session_info를 보내면 자동으로 세션을 갱신합니다.
  • Vehicle은 사용자에게 보이는 메서드 집합입니다. 각 메서드는 도메인에 맞는 protobuf를 만들고 Send(재시도 포함)로 보낸 뒤 응답을 protocol.Error로 변환합니다.

명령 한 개의 생애주기

tesla-control -ble lock이 실행될 때 일어나는 일입니다. 인터넷 경로는 1~2단계가 account.GetVehicle로 대체됩니다.

  1. 스캔: VIN의 SHA1 앞 8바이트로 광고 이름을 계산해 일치하는 광고를 찾습니다.
  2. GATT 연결: 서비스 00000211-…를 찾고 쓰기 특성(0212)과 알림 특성(0213)을 구독한 뒤 MTU를 협상합니다.
  3. Connect: Dispatcher.Start가 수신 고루틴을 띄웁니다. 세션 캐시가 있으면 이 시점에 도메인별 세션을 복원합니다.
  4. StartSession: 캐시가 없는 도메인마다 SessionInfoRequest를 보내고 응답의 HMAC 태그를 검증한 뒤 ECDH로 공유 키 K를 만듭니다. 캐시가 있으면 이 왕복이 생략됩니다.
  5. Send: 명령 protobuf를 메타데이터와 함께 AES-GCM(BLE) 또는 HMAC(인터넷)으로 인가하고 전송합니다. protocol.ShouldRetry가 참인 오류(Busy, 카운터/epoch 불일치 등)는 RetryInterval 후 자동 재시도합니다.
  6. 응답: 차량이 오류와 함께 새 세션 정보를 보내면 dispatcher가 세션을 갱신하고, 응답이 암호화되어 있으면 복호화와 카운터 검증을 거쳐 Vehicle 메서드가 최종 결과를 오류 타입으로 반환합니다.
