8. HTTP プロキシ

tesla-http-proxy は、Fleet API 形式の REST リクエストを受け取り、秘密鍵で署名したエンドツーエンド認証コマンドに変換して、Tesla のサーバー経由で車両に届ける HTTPS サーバーです。既存の Owner API クライアントを最小限の修正で移行するときに使います。

動作の流れ

プロキシは 2 種類の認証情報を扱います。クライアントが送る OAuth トークン（Tesla サーバーの認証）と、プロキシが起動時に読み込む秘密鍵（車両の認証）です。秘密鍵に対応する公開鍵は、ユーザーの車両にあらかじめ登録されている必要があります。

OAuth トークンを取得する手順（パートナートークン → ユーザー認可 → コード交換）は doc/authorization.puml と Fleet API ドキュメント に従ってください。プロキシはトークンの発行や更新を行いません。

実行

tesla-http-proxy -tls-key config/tls-key.pem -cert config/tls-cert.pem -key-file config/fleet-key.pem -port 4443
オプション環境変数デフォルト説明
-cert fileTESLA_HTTP_PROXY_TLS_CERT（必須）サーバー証明書 + 中間 CA + ルート CA を連結した PEM チェーン
-tls-key fileTESLA_HTTP_PROXY_TLS_KEY（必須）サーバーの TLS 秘密鍵
-host hostnameTESLA_HTTP_PROXY_HOSTlocalhostバインドアドレス。localhost 以外なら起動時に警告を stderr に出力
-port PortTESLA_HTTP_PROXY_PORT443ポート。本番環境では 443 を推奨
-timeout durationTESLA_HTTP_PROXY_TIMEOUT10sTesla サーバー/車両との通信タイムアウト（proxy.DefaultTimeout）
-verboseTESLA_VERBOSEfalseデバッグログ
-key-file file / -key-name nameTESLA_KEY_FILE / TESLA_KEY_NAMEコマンド認証用の秘密鍵。ファイルが優先
-keyring-type, -keyring-file-dir, -keyring-debugTESLA_KEYRING_*キーリングの設定
-session-cache, -disable-session-cache, -domaincli.FlagPrivateKey で登録されますが、プロキシは独自のメモリキャッシュを使うため影響はありません

フラグは環境変数より優先されます。環境変数はフラグがデフォルト値のときだけ読み込まれます。ポート/タイムアウトの形式が不正な場合は invalid port/invalid timeout エラーで終了します。

TLS 証明書

プロキシでは TLS を無効にできません。開発用の自己署名証明書は OpenSSL で作成します。

mkdir config
openssl req -x509 -nodes -newkey ec \
    -pkeyopt ec_paramgen_curve:secp384r1 \
    -pkeyopt ec_param_enc:named_curve  \
    -subj '/CN=localhost' \
    -keyout config/tls-key.pem -out config/tls-cert.pem -sha256 -days 3650 \
    -addext "extendedKeyUsage = serverAuth" \
    -addext "keyUsage = digitalSignature, keyCertSign, keyAgreement"

クライアント側では --cacert config/tls-cert.pem でこの証明書を信頼させます。本番環境では公的 CA の証明書を使い、-cert にチェーン全体を指定してください。

TLS 鍵とコマンド認証鍵に同じ鍵を使うと起動が拒否されます

main.go は -tls-key のファイルを protocol.LoadPublicKey で読み込み、コマンド鍵の公開鍵と比較します。同じであれば It is unsafe to use the same private key for TLS and command authentication. を出力して終了します。上の例で secp384r1（P-384）を使っている理由の一つです（コマンド鍵は P-256）。

Docker でのデプロイ

イメージ tesla/vehicle-command は distroless ランタイムの上に 5 つのツールを収めており、デフォルトのエントリーポイントは tesla-http-proxy です。秘密鍵はファイルとしてマウントします（コンテナにはシステムのキーリングがありません）。

# docker run
docker pull tesla/vehicle-command:latest
docker run --security-opt=no-new-privileges:true -v ./config:/config -p 127.0.0.1:4443:4443 \
    tesla/vehicle-command:latest \
    -tls-key /config/tls-key.pem -cert /config/tls-cert.pem -key-file /config/fleet-key.pem -host 0.0.0.0 -port 4443

# docker compose (リポジトリの docker-compose.yml)
docker compose up

リポジトリの docker-compose.yml は、環境変数で同じ設定を行います。

services:
  tesla_http_proxy:
    image: tesla/vehicle-command:latest
    ports:
      - "4443:4443"
    environment:
      - TESLA_HTTP_PROXY_TLS_CERT=/config/tls-cert.pem
      - TESLA_HTTP_PROXY_TLS_KEY=/config/tls-key.pem
      - TESLA_HTTP_PROXY_HOST=0.0.0.0
      - TESLA_HTTP_PROXY_PORT=4443
      - TESLA_HTTP_PROXY_TIMEOUT=10s
      - TESLA_KEY_FILE=/config/fleet-key.pem
      - TESLA_VERBOSE=true
    security_opt:
      - no-new-privileges:true
    volumes:
      - ./config:/config

コンテナ内では -host 0.0.0.0 が避けられませんが、ホストのポートマッピングを 127.0.0.1:4443:4443 のようにループバックに限定するか、前段に認証プロキシを置いて外部への公開を防いでください。

ルーティング規則

(*proxy.Proxy).ServeHTTP は、リクエストのパスに応じて次の順序で処理します。

順序パス処理
0すべてのリクエストボディサイズを 1 MiB（maxRequestBodyBytes）に制限。超過すると 413
1GET /health認証なしで 200 OK。他のメソッドは 405
2それ以外のすべてのパスAuthorization: Bearer <token> がなければ 403。トークンの aud/ou_code から Fleet API のホストを決定（account.New）。以前に 421 で更新されたホストがあればそれを使用
3POST /api/1/vehicles/{VIN}/command/{name}VIN が 17 文字でなければ 404（expected 17-character VIN in path (do not user Fleet API ID)）。プロトコル非対応として記録された VIN ならフォワーディング。そうでなければ handleVehicleCommand でエンドツーエンド認証コマンドを実行。ErrCommandUseRESTAPI ならフォワーディング
4/api/1/vehicles/fleet_telemetry_configボディの config を JWS で署名し、/api/1/vehicles/fleet_telemetry_config_jws にフォワーディング
5残りの /api/1/* などすべてのパスforwardRequest：ヘッダーをコピーして hop-by-hop ヘッダーを除去し、X-Forwarded-For を追加して HTTPS で Fleet API に転送。GET/POST のいずれも対象
Owner API の ID ではなく VIN を使ってください

レガシーな Owner API クライアントは URL に数値の車両 ID を入れます。プロキシは command/ パスでは必ず 17 文字の VIN を要求します。その他のパス（例：vehicle_data）はそのままフォワーディングされるため、Fleet API が受け付ける形式であれば構いません。

レスポンス形式とステータスコード

コマンド成功

{"response":{"result":true,"reason":""}}

車両がコマンドを拒否 (NominalError)

車両がコマンドを認証したものの実行できない場合（例：すでにオン、パーキング状態ではない）は、Fleet API の慣例どおり HTTP 200 となり、result が false、reason に理由が入ります。

{"response":{"result":false,"reason":"car could not execute command: already_on"},"error":"","error_description":""}

その他のエラー

{"response":null,"error":"vehicle unavailable: vehicle is offline or asleep","error_description":""}
HTTP状況発生元
200成功、または車両のアプリケーション層での拒否（reason を確認）handleVehicleCommand
400JSON のパース失敗、パラメーターの欠落/形式エラー（missing X param、invalid X param）、不明なコマンド（{"response":null,"error":"invalid_command","error_description":""}）、remote_boombox 未実装、不正な window_control の値extractCommandAction
403Authorization ヘッダーに Bearer トークンがない（client did not provide an OAuth token）ServeHTTP
404command/ パスの VIN が 17 文字ではないServeHTTP
405command/ に POST 以外のメソッド、/health に GET 以外のメソッド
408車両がオフライン/スリープ中（inet.ErrVehicleNotAwake）。Fleet API が 503 または "vehicle is offline" の 408 を返した場合。先に wake_up を呼び出してくださいhttpStatusCode
412公開鍵が車両に登録されていない（protocol.ErrKeyNotPaired）。OAuth は有効なので 401 ではないhttpStatusCode
413リクエストボディが 1 MiB を超過
422 (Fleet API)車両がこのプロトコルをサポートしていない（protocol.ErrProtocolNotSupported）。プロキシはその VIN を非対応として記憶し、元のリクエストを REST でフォワーディング。以後、その VIN のコマンドは常にフォワーディングhandleVehicleCommand
500分類されないエラー、車両オブジェクトの生成失敗、JWS 署名の失敗
502Fleet API への接続失敗、レスポンスが 10 MB を超過、421 のリトライ上限到達（max retry exhausted）forwardRequest
503同じ VIN の別のコマンドが進行中で、タイムアウト内にロックを取得できないlockVIN
504Fleet API のレスポンスタイムアウトforwardRequest
（そのまま）フォワーディングされたリクエストは、Fleet API のステータスコード、ヘッダー、ボディをそのまま返します。inet.HTTPError に分類されたエラーも元のコードとボディを維持します

Fleet Telemetry 設定の署名

POST /api/1/vehicles/fleet_telemetry_config に署名されていない設定を送ると、プロキシが sign.SignMessageForFleet(key, "TelemetryClient", config) で JWS を作成し、/api/1/vehicles/fleet_telemetry_config_jws に {"vins": [...], "token": "<jws>"} としてフォワーディングします。設定に aud や iss があれば上書きし、警告をログに残します。tesla-jws -fleet sign TelemetryClient と同じ結果になります。

curl --cacert config/tls-cert.pem \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    -X POST --data-binary "@telemetry.json" \
    "https://localhost:4443/api/1/vehicles/fleet_telemetry_config"

内部動作

VIN ごとの直列化
lockVIN が VIN ごとにミューテックスを取得し、同じ車両へのコマンドを順番に実行します。VCSEC はカウンターの順序が乱れると拒否するため、これは必須です。異なる VIN は並列に処理されます。
セッションキャッシュ
cmd/tesla-http-proxy は proxy.New(ctx, key, 10000) により、最大 10000 台分のセッションをメモリに保持します（LRU）。コマンドごとに acct.GetVehicle → Connect → StartSession → 実行 → Disconnect を繰り返しますが、キャッシュのおかげでハンドシェイクは最初のコマンドかセッションの期限切れ時にしか発生しません。プロセスを再起動するとキャッシュは消えます。
User-Agent
tesla-http-proxy/1.1.0（proxyProtocolVersion）をアプリ名として account.New に渡します。
リージョンホストの決定
account.New は、トークンの aud のうち fleet-api. で始まり Tesla のドメインサフィックスを持つものを選び、ou_code（リージョン）を含むものを優先します。デフォルトは fleet-api.prd.na.vn.cloud.tesla.com。
421 リダイレクト
フォワーディングのレスポンスが 421 で Alt-Svc: h2="https://…" ヘッダーがあれば、ホストを切り替えて最大 2 回（MaxAttempts）リトライし、トークンの sub ごとに新しいホストを記憶します。エンドツーエンドのコマンド経路では、inet.Connection がボディ内の use base URL: https://… をパースして更新します。
タイムアウト
-timeout（デフォルト 10 秒）がコマンド 1 つ分のコンテキスト全体です。この中で SDK がハンドシェイクのリトライとコマンドのリトライを行います。
テストフック
Proxy.client（httpDoer）と Proxy.fetchVehicle（vehicleSession を返す）は、パッケージ内部のテストで差し替えられます（pkg/proxy/proxy_test.go）。

セキュリティ上の注意

  • localhost 以外へのバインドは禁止（認証なしの場合）。 プロキシにはクライアント認証がありません。誰でもアクセスできる状態だと、あなたの IP から Tesla サーバーへ過剰なトラフィックが発生し、rate limit やブロックを受ける可能性があります。起動時に nonLocalhostWarning がこれを警告します。
  • TLS を無効にするオプションはありません。 過去の DIY デプロイで車両がインターネットに露出した事例があったため、意図的に --insecure のようなフラグを提供していません。TLS の終端を別の場所に置きたい場合は、pkg/proxy を直接使ってください。
  • 秘密鍵ファイルの権限。 -key-file はコマンド認証用の鍵です。漏洩すると、登録済みのすべての車両にコマンドを送れてしまいます。0600 の権限と最小アクセスの原則を守ってください。
  • OAuth トークンは保存しません。 プロキシはリクエストごとにヘッダーのトークンをそのまま使用します。トークンの管理は呼び出し側の責任です。

curl の例

export TESLA_AUTH_TOKEN=<access-token>
export VIN=<17 文字の VIN>
export CACERT=config/tls-cert.pem

# ヘルスチェック (認証不要)
curl --cacert $CACERT https://localhost:4443/health

# フォワーディングされるエンドポイント: 車両データ
curl --cacert $CACERT \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    "https://localhost:4443/api/1/vehicles/$VIN/vehicle_data" | jq .

# 起動 (エンドツーエンドのコマンド経路。online になるまでポーリング)
curl --cacert $CACERT -X POST --data '{}' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    "https://localhost:4443/api/1/vehicles/$VIN/command/wake_up"

# 引数なしのコマンド
curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/flash_lights"

# 引数ありのコマンド
curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"percent": 80}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/set_charge_limit"

curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"driver_temp": 21.5, "passenger_temp": 21.5}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/set_temps"

curl --cacert $CACERT \
    --header 'Content-Type: application/json' \
    --header "Authorization: Bearer $TESLA_AUTH_TOKEN" \
    --data '{"days_of_week":"weekdays","start_time":1320,"start_enabled":true,"end_time":360,"end_enabled":true,"lat":37.4,"lon":-122.1,"enabled":true}' \
    "https://localhost:4443/api/1/vehicles/$VIN/command/add_charge_schedule"

JSON パラメーターの型は厳格です。数値は JSON の数値、ブール値は true/false、文字列は文字列でなければならず、それ以外の型だと invalid X param（400）になります。各エンドポイントのパラメーターは 7. コマンドリファレンス を参照してください。

pkg/proxy の組み込みと認証ミドルウェア

cmd/tesla-http-proxy/main.go は pkg/proxy を包む薄いラッパーです。クライアント認証、独自の TLS 終端、リクエストのロギングなどを追加したい場合は、proxy.Proxy（http.Handler）を独自のハンドラーで包みます。

package main

import (
    "context"
    "crypto/subtle"
    "net/http"
    "time"

    "github.com/teslamotors/vehicle-command/pkg/protocol"
    "github.com/teslamotors/vehicle-command/pkg/proxy"
)

type authenticated struct {
    next   http.Handler
    apiKey string
}

func (a *authenticated) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    if r.URL.Path == "/health" {
        a.next.ServeHTTP(w, r)
        return
    }
    if subtle.ConstantTimeCompare([]byte(r.Header.Get("X-Api-Key")), []byte(a.apiKey)) != 1 {
        http.Error(w, "unauthorized", http.StatusUnauthorized)
        return
    }
    a.next.ServeHTTP(w, r) // Authorization: Bearer ヘッダーはそのままプロキシへ渡す
}

func main() {
    skey, err := protocol.LoadPrivateKey("config/fleet-key.pem")
    if err != nil { panic(err) }

    p, err := proxy.New(context.Background(), skey, 10000)
    if err != nil { panic(err) }
    p.Timeout = 10 * time.Second

    handler := &authenticated{next: p, apiKey: "..."}
    // TLS はここで終端してもよいし、前段のリバースプロキシに任せてもよい (pkg/proxy は TLS に依存しない)。
    panic(http.ListenAndServeTLS("localhost:4443", "config/tls-cert.pem", "config/tls-key.pem", handler))
}

proxy.ExtractCommandAction(ctx, command, params) を直接呼び出すと、HTTP を介さずに Fleet API のコマンド名 + JSON パラメーターを func(*vehicle.Vehicle) error に変換できるため、他の RPC フレームワークで同じコマンドのマッピングを再利用できます。
