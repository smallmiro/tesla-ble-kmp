18. Troubleshooting

Common problems with scanning, connecting, keys, pairing and commands, what usually causes them, and what to do. A development-only observation log is described at the end.

Scanning and connecting

Debug logging

  • Pass a logger in TeslaBleConfig. The default logs nothing.
  • DebugLogger() writes to Logcat on Android, the unified log on iOS and java.util.logging on the JVM. Use it in development builds only.
  • To send logs elsewhere, implement TeslaLogger: one function receiving a level, a tag and a lazily built message. A logger that throws does not stop the library.
  • Levels: DEBUG (raw bytes sent and received), INFO (connections and sessions), WARN (dropped or discarded messages), ERROR (situations the library cannot recover from).
What never appears in logs

The library masks VINs and never logs private keys, session keys, nonces or decrypted content. Keep it that way in your own logs: do not print vin.value, and mask VINs before sharing logs.

To report a problem, use the iOS sample's "copy whole result" button log together with DebugLogger. There is no probe or diagnostics entry point.

Observation log (development)

While you develop, the library can write one summary line for every message it drops and for every reply from the vehicle security domain. It shows what the car sends without being asked. It changes no behaviour: the library still drops those messages (vehicle.events is planned for M5).

  • Tag observe, level DEBUG. A logger that discards DEBUG never builds the line. Visible through DebugLogger() or your own TeslaLogger. The iOS sample's observation mode collects only these lines.
  • Shape: [point] NB from=… to=… request_uuid=… payload=…, where NB is the size of the received frame.
PartValues
[drop:unparseable]The frame did not decode as a routable message. The line ends with reinterpreted=… (or undecodable)
[drop:missing-source]No source. The line ends with reinterpreted=…: the same bytes read as an unwrapped FromVCSECMessage
[drop:missing-destination]No destination (the typical push from the car)
[drop:to-domain]Addressed to a domain, not to a client address
[drop:malformed]Wrong request UUID length or wrong address length
[drop:no-handler]A valid address, but no open request owns it
[drop:handler-closed], [drop:queue-full]The matching request closed meanwhile, or its answer queue was full
[reply:vcsec]A security-domain reply delivered to an open request
from=, to=domain(DOMAIN_X), address(16B, self|open-request|other) (to= only), none, empty
payload=FromVCSECMessage{…}, Response{fields=[…]}, encrypted(NB), NB, none
unknownFields=[n]Field numbers on the wire that the generated protocol does not know
absent=[…]Parts of the vehicle status the car did not send (closureStatuses, detailedClosureStatus)
key=sha1:xxxxxxxxA public key: only the first 4 bytes of its SHA-1

Detail form (exploration only)

Example: unknownFields=[48:len(8){1:varint=3(0x3), 2:len(4)"ABCD"}, 9]. Entries keep their arrival order and repeated fields repeat. The field number and wire type are kept; no field name is invented.

Wire typeShown as
varintvarint=<unsigned decimal>(0x<hex>)
fixed32 / fixed64fixed32=0x + 8 hex digits, fixed64=0x + 16 hex digits
LENlen(N){…} when the whole range parses as protobuf (depth 3, 64 fields per message, 256 bytes at most). Otherwise len(N)"text" for printable ASCII (control characters escaped), otherwise len(N)0x… hex
Over a limit or corruptlen(N, truncated) or len(N, invalid)
Key-like LENExactly 16, 32, 33, 64 or 65 bytes: redacted(NB). A 65-byte value that starts with 0x04: sha1:xxxxxxxx

VINs (17 characters) are masked in text and in raw bytes before any hex is produced; only the first 3 and last 4 characters stay. This output is for exploration only. It does not tell what a field means, and a missing closureStatuses in a broadcast does not mean that everything is closed.

Limits and rules

  • Detailed decoding is a narrow exception, and only for frames the car originally sent as plaintext (never for anything the library decrypted, so FR-112 is unaffected). All of these must hold: from the security domain, to the broadcast domain, empty request UUID, no signature, no session info, and a payload that reads as FromVCSECMessage. Then only FromVCSECMessage unknown fields 48 and 53 and VehicleStatus unknown fields 7 and 8 are decoded. Every other field and frame keeps the number-only form.
  • A missing enum value cannot be told from its zero value: an absent lock state reads VEHICLELOCKSTATE_UNLOCKED (sleep and presence read UNKNOWN). Only message parts can be reported as absent.
  • Encrypted content and session info appear by length only, public keys by SHA-1 prefix only. The VIN and decrypted content never appear. Keep this rule when you add lines.
  • The BLE transport counts inbox overflows per connection. Each dropped message logs Dropping received message because inbox is full (dropped N since connect) at ERROR; when the link ends, one line BLE inbox overflowed N time(s) during this connection is logged at WARN (only if N is above 0).
  • DebugLogger also prints the raw BLE bytes (TX: and RX:) at DEBUG. Do not share such platform logs.
