スキャンと接続

症状考えられる原因対処
PermissionDeniedBluetooth 権限がない、または拒否されたAndroid: 実行時に BLUETOOTH_SCAN と BLUETOOTH_CONNECT を要求します。iOS: NSBluetoothAlwaysUsageDescription を追加します。拒否された場合はユーザーを設定に誘導します
BluetoothOffBluetooth がオフオンにするようユーザーに依頼します
スキャンで何も見つからず、接続が ScanTimeout で終わる範囲外、VIN の誤り、または iOS シミュレーター車両に近づく、VIN を確認する (車両は VIN から導出した名前で照合されます)、実機を使う
MaxConnectionsExceeded車両にすでに 3 つの Bluetooth 接続がある別のスマートフォンやアプリを切断し、自分のアプリでは必ず disconnect() を呼びます
ConnectFailed が繰り返し返る電波が弱い、または車両がビジーライブラリはすでに 30 秒間リトライしています。時間をおいてもう一度試します

症状考えられる原因対処
startSession() が RequiresKey を返すキーなしで接続したVehicleKey を指定して接続します
startSession() が KeyNotPaired を返す車両がこのキーを知りませんaddKeyRequest で登録してください (13. キーとペアリング)。listKeys() や sessionInfo で確認します
stored key is corruptedAndroid のバックアップがラップ用のキーなしでキーファイルを復元した、またはストレージの破損削除して新しいキーを作成し、登録します。キーファイルをバックアップから除外します (プラットフォームノート)
HardwareUnavailableStrongBox、TEE、Secure Enclave のいずれもないデバイスでハードウェアを必須にしたPREFER_HARDWARE を使います
KeyStoreError.LockediOS: スマートフォンがロックされていて、キーがロック解除中にだけ使えるキー（WHEN_UNLOCKED）である、または再起動後にまだ一度もロックを解除していないキーを削除しないでください。ロックを解除してから再試行します。ロック中もキーを使うには、新しいエイリアスで AFTER_FIRST_UNLOCK のキーを作成して登録します (13. キーとペアリング)

長いスリープ後の最初のコマンドが失敗し、リトライで成功するスリープ中にスマートフォンのクロックが止まっていた対処不要です。ライブラリが自動で再同期します

ペアリングとコマンド

症状考えられる原因対処
addKeyRequest が TimedOut で終わるカードをタッチしていない、時間内 (デフォルト 60 秒) に画面で承認していない、または返信を認識できませんでしたユーザーにセンターコンソールでキーカードをタッチし画面で承認するよう案内し、sessionInfo(publicKey, INFOTAINMENT) で確認してください。キーは登録されている可能性があります
addKeyRequest が Rejected(KeychainRejected(WHITELIST_FULL)) など別の KeychainRejected コードを出す車両が拒否しました。キー一覧が満杯、追加の権限がないなど車両のタッチスクリーンか removeKey で使っていないキーを削除してください。16. エラー処理 を参照
addKeyRequest が Unknown(raw) を出す見たことのない返信形式です。実車での動作はまだ確認していません (ADR-0009)raw を 16 進数で (VIN は含めずに)、車両の動作と一緒に報告してください
addKeyRequest が Failed(NotConnected) を出すVehicle オブジェクトが切断された、またはリンクが切れましたdisconnect() を呼び、再接続してやり直してください
lock() (または他のセキュリティコントローラーのコマンド) が NoSession を返すVCSEC セッションがまだない、またはキャッシュ済みセッションが古くなっています先に startSession(setOf(VehicleDomain.VCSEC)) を呼んでください。sessions が Ready(fromCache = true) だった場合、この失敗の後に None に変わります (別のキーや車両のキャッシュだった場合)。startSession で解決します
addKey / removeKey が InsufficientPrivileges を返す接続のキーにキー管理の権限がありません (例: Driver キー)Owner キーを使ってください

その他のメッセージ

症状考えられる原因対処

デバッグログ

  • TeslaBleConfig にロガーを渡します。デフォルトでは何もログに出しません。
  • DebugLogger() は Android では Logcat、iOS では統合ログ、JVM では java.util.logging に出力します。開発ビルドでのみ使ってください。
  • ログを別の場所に送るには TeslaLogger を実装します。レベル、タグ、遅延生成されるメッセージを受け取る関数が 1 つあるだけです。ロガーが例外を投げてもライブラリは止まりません。
  • レベル: DEBUG (送受信した生のバイト)、INFO (接続とセッション)、WARN (破棄または無視されたメッセージ)、ERROR (ライブラリが回復できない状況)。
ログに決して出ないもの

ライブラリは VIN をマスクし、秘密鍵、セッションキー、ノンス、復号した内容を決してログに出しません。自分のログでもこれを守ってください。vin.value を出力せず、ログを共有する前に VIN をマスクしてください。

問題を報告するときは、iOS サンプルの「結果全体をコピー」ボタンで得たログと DebugLogger を使ってください。プローブや診断用のエントリポイントはありません。

観察ログと vehicle.events

どちらも車両のブロードキャストを見せますが、読み手が違います。

観察ログvehicle.events

どのフレーム破棄したすべてのフレーム (他のスマートフォン宛ての応答、読めないフレーム、ブロードキャスト) とすべてのセキュリティドメインの応答平文のブロードキャストだけ (14、B2)

VINライブラリがマスクするraw ではマスクしない。保存や共有の前にアプリがマスクする
必要なものDEBUG を残すロガー (開発ビルド)なし。リリースビルドでも動く
用途プロトコルの探索、問題の報告ライブの状態などのアプリ機能、分析用の生フレームの収集
  • 1 つのフレームに vehicleStatus と authenticationRequest の両方があると、観察ログの行には最後に来た片方しか出ません。スキーマが両方を 1 つの oneof に入れており、通常のデコードは最後の 1 つだけを残すためです。vehicle.events は両方のフィールドを読み、2 つのイベント (Status、次に AuthenticationRequest) を出します。
  • アプリのコードで観察ログの行を解析しないでください。形式は開発用で、変わることがあります。vehicle.events を使ってください。

観察ログ（開発用）

開発中、ライブラリは破棄するメッセージごと、および車両セキュリティドメインの応答ごとに、要約を1行ログに出せます。車が要求なしに送ってくるものを確認できます。動作は変わりません。ブロードキャストは引き続き応答の対応付けから外れ、そのうち平文のものは vehicle.events でもアプリに届きます（前の節）。プッシュされた各メッセージの意味は 14. 車両状態の取得 の B 部にあります。

  • タグ observe、レベル DEBUG。DEBUG を捨てるロガーはこの行を組み立てもしません。DebugLogger() または自作の TeslaLogger で見られます。iOS サンプルの観察モードはこの行だけを集めます。
  • 形式: [地点] NB from=… to=… request_uuid=… payload=…。NB は受信したフレームのサイズです。
項目値
[drop:unparseable]フレームがルーティングメッセージとして解釈できませんでした。行末に reinterpreted=…（または undecodable）が付きます
[drop:missing-source]送信元がありません。行末の reinterpreted=… は同じバイト列をラップされていない FromVCSECMessage として読んだ結果です
[drop:missing-destination]宛先がありません（実車では見られませんでした）
[drop:to-domain]クライアントのアドレスではなくドメイン宛てです（車両のブロードキャストは DOMAIN_BROADCAST を使います）
[drop:malformed]リクエスト UUID の長さまたはアドレスの長さが不正です
[drop:no-handler]正しいアドレスですが、そのアドレスの開いたリクエストがありません
[drop:handler-closed], [drop:queue-full]対応するリクエストがその間に閉じた、または応答キューが満杯でした
[reply:vcsec]開いたリクエストに渡されたセキュリティドメインの応答です
from=, to=domain(DOMAIN_X), address(16B, self|open-request|other)（to= のみ）, none, empty
payload=FromVCSECMessage{…}, Response{fields=[…]}, encrypted(NB), NB, none
unknownFields=[n]通信上にはあったが、生成されたプロトコルが知らないフィールド番号です
uiDesire=, gear=車両状態のフィールド 6・7 で、拡張されたプロトコル定義が付けた名前です（GEAR_UNKNOWN、GEAR_PARK、GEAR_DRIVE、GEAR_REVERSE、GEAR_NEUTRAL）。gear は実車で確認済みで（14. 車両状態の取得 参照）、uiDesire の意味は確認されていません。enum は欠けると 0 の値として読まれるので、常に記します
authenticationRequest{requestedLevel=…, reasons=[…], token=NB}FromVCSECMessage のフィールド 3 で、拡張されたプロトコル定義が付けた名前です（フィールド名は未確認）。トークンは長さだけを記します
absent=[…]車が送ってこなかった車両状態の部分です（closureStatuses, detailedClosureStatus）
key=sha1:xxxxxxxx公開鍵: SHA-1 の先頭4バイトだけを記します

詳細形式（探索用）

例: unknownFields=[48:len(8){1:varint=3(0x3), 2:len(4)"ABCD"}, 9]。項目は到着順を保ち、繰り返しフィールドは繰り返して記します。フィールド番号と wire type はそのまま残し、フィールド名は作りません。

Wire type表示
varintvarint=<符号なし10進数>(0x<16進数>)
fixed32 / fixed64fixed32=0x + 16進数8桁、fixed64=0x + 16進数16桁
LEN範囲全体が protobuf として読めれば len(N){…}（深さ3、メッセージごとにフィールド64個、256バイトまで）。読めなければ、表示可能な ASCII は len(N)"text"（制御文字はエスケープ）、それ以外は len(N)0x… の16進
上限超過または破損len(N, truncated) または len(N, invalid)
鍵らしい LENちょうど16、32、33、64、65バイト: redacted(NB)。0x04 で始まる65バイトの値: sha1:xxxxxxxx

VIN（17文字）は16進を作る前に、テキストと生バイトの両方で伏せます。先頭3文字と末尾4文字だけが残ります。伏せ字化は解析の前に生バイトに対して行うため、伏せたバイトによって表示される値や構造が変わることがあります（漏れはありません）。この出力は探索用にすぎません。フィールドの意味は分かりません。実車では closureStatuses がなければドアと充電ポートはすべて閉じていましたが、室内ボタンで操作したトランクはブロードキャストがなかったため、トランクの状態はまだブロードキャストから推測できません（14 の B 部参照）。

制限とルール

  • 詳細デコードは狭い例外で、車両が元々平文で送ったフレームにだけ適用します（ライブラリが復号したものには使わないので FR-112 とは衝突しません）。vehicle.events はそのようなフレームを、デコードできるかどうかに関係なく raw としてアプリに渡します。次がすべて成り立つ必要があります: セキュリティドメインから発信、ブロードキャストドメイン宛て、リクエスト UUID なし、署名なし、セッション情報なし、ペイロードが FromVCSECMessage として読める。その場合 FromVCSECMessage の未公開フィールド 48・53 と VehicleStatus の未公開フィールド 7・8 だけを展開します（フィールド 7 は名前のある gear になったので、値が定義外のときだけ未公開フィールドになります。定義外の値なので、その生の値を unknownFields=[7:varint=9(0x9)] のように引き続き表示します）。それ以外のフィールドとフレームは番号だけを記します。
  • enum の値が欠けている場合と 0 番の値は区別できません。ロック状態がなければ VEHICLELOCKSTATE_UNLOCKED と読めます（sleep と presence は UNKNOWN）。absent として分かるのはメッセージの部分だけです。
  • 暗号化された内容とセッション情報は長さだけ、公開鍵は SHA-1 の先頭だけを記します。VIN と復号した内容は出力されません。行を追加するときもこのルールを守ってください。
  • BLE トランスポートは接続ごとに受信バッファの溢れを数えます。破棄したメッセージごとに ERROR で Dropping received message because inbox is full (dropped N since connect) を出し、リンクが終わると WARN で BLE inbox overflowed N time(s) during this connection を1行出します（N が 0 より大きいときだけ）。
  • DebugLogger は DEBUG で BLE の生バイト（TX:、RX:）も出力します。このようなプラットフォームのログは共有しないでください。
