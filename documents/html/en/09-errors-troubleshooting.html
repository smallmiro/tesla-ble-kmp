Error model

Errors returned by the SDK implement the protocol.Error interface wherever possible. Two methods determine what the caller should do.

type Error interface {
    error
    MayHaveSucceeded() bool // The vehicle may have received and executed the command (cannot be confirmed)
    Temporary() bool        // May be resolved by retrying without user intervention
}
TypeLayerMayHaveSucceededTemporaryDescription
*protocol.CommandErrorGeneralField PossibleSuccessField PossibleTemporaryCreated with protocol.NewError(msg, mayHaveSucceeded, temporary). On context expiry, wrapped as {ctx.Err(), true, true}. Supports Unwrap()
*protocol.RoutableMessageErrorProtocoltrue only for ERROR_NONE, RESPONSE_MTU_EXCEEDEDtrue only for the retryable codes in the tableThe vehicle's signedMessageStatus.signed_message_fault. .Code is a universal.MessageFault_E. Error() is the enum name
*protocol.NominalErrorApplicationDelegated to DetailsDelegated to DetailsThe vehicle authenticated the command but cannot execute it. Infotainment produces car could not execute command: <reason>; for VCSEC it wraps a NominalVCSECError. The proxy converts it to HTTP 200 + reason
*protocol.NominalVCSECErrorApplicationfalsefalseFromVCSECMessage.nominalError. .Details.GetGenericError() is a GenericError_E
*protocol.KeychainErrorApplicationfalsefalseKey add/remove failure. .Code is a WhitelistOperation_information_E. Message keychain operation failed: <code>
*inet.HTTPErrorTransport (HTTP)false for 4xx and 503, true otherwise503, 504, 408, 421The Fleet API returned something other than 200. .Code, .Message (body)

The helper functions protocol.MayHaveSucceeded(err), protocol.Temporary(err), protocol.ShouldRetry(err), and protocol.IsNominalError(err) use errors.As to see through wrapping. Commit a4b43c1 fixed the classification of wrapped protocol errors, so errors wrapped with fmt.Errorf("%w") are also classified correctly.

Retry policy

func ShouldRetry(err error) bool {
    // true only if err implements the Error interface, MayHaveSucceeded() is false, and Temporary() is true
}

At the following points, the SDK retries while ShouldRetry is true, at the connector's RetryInterval() (1 second for both BLE and inet), until the context expires.

PointWhat is retriedNotes
Vehicle.StartSessionThe entire handshakeThe dispatcher resends the request if no response arrives within RetryInterval
Vehicle.Send (Infotainment commands)Send + wait for responseEach retry builds a new message with a newly incremented counter
getVCSECResult (VCSEC commands)Send + wait for final responseOPERATIONSTATUS_WAIT is converted to ErrBusy and retried
Dispatcher.SendThe connector's Send itselfResends the same bytes (counter unchanged). Only when the connector returns a protocol.Error
inet.Connection.Wakeupwake_up pollingEvery 10 seconds, until state == "online". Continues only on Temporary errors
ble.NewConnectionFromScanResultScan/dial/service discoveryAdapter errors (IsAdapterError), a wrong Local Name, and non-connectable beacons fail immediately. Everything else repeats until the context expires
Errors where MayHaveSucceeded is true are not retried automatically

For context timeouts, response parsing failures, and similar errors, the vehicle may already have executed the command, so the SDK does not resend it. For commands that are problematic if executed twice, such as unlocking or opening the trunk, check the state with BodyControllerState or GetState before deciding. In this case tesla-control prints Couldn't verify success: ….

Infotainment application-layer errors

If the Infotainment response carserver.Response.actionStatus.result is OPERATIONSTATUS_ERROR, result_reason.plain_text becomes the NominalError message: car could not execute command: <plain_text>. If the text is empty, it is unspecified error. Examples mentioned in the code: already off (treated as success when disabling valet mode), low_power_mode_enforced, parental_controls_active. The proxy returns this string as reason.

Debugging tools

Decoding TX/RX dumps

tesla-control -debug (or TESLA_VERBOSE=1) prints sent and received RoutableMessages in hexadecimal.

2023-12-13T14:41:13-08:00 [debug] TX: 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805

Decode it with protoc (run from the repository root).

cd vehicle-command/pkg/protocol
echo 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805 \
    | xxd -r -p \
    | protoc --decode=UniversalMessage.RoutableMessage -I protobuf protobuf/*.proto

# Decode protobuf_message_as_bytes from the output again, using the type that matches the domain
printf "\n\002\010\005" | protoc --decode=VCSEC.UnsignedMessage -I protobuf protobuf/*.proto      # VCSEC request
printf "..." | protoc --decode=VCSEC.FromVCSECMessage -I protobuf protobuf/*.proto              # VCSEC response
printf "..." | protoc --decode=CarServer.Action -I protobuf protobuf/*.proto                    # Infotainment request
printf "..." | protoc --decode=CarServer.Response -I protobuf protobuf/*.proto                  # Infotainment response

Over BLE, messages are encrypted with AES-GCM, so protobuf_message_as_bytes is ciphertext. To see the plaintext, you need the -debug log entries from when the request was built, or the session key. Handshake messages and the error fields of responses (signedMessageStatus) are plaintext.

Security notes

  • Do not enroll test keys on a real vehicle. The keys in pkg/protocol/protocol.md, internal/authentication/test_data/, and pkg/protocol/test/ are public.
  • Session cache file permissions. ~/.tesla-cache.json does not contain private keys, but it does contain session state. Do not let third parties read or tamper with it. A tampered cache recovers automatically after the first command fails, but it causes unnecessary failures.
  • Exporting private keys. The output of tesla-keygen export and the -key-file file grant command authority over every enrolled vehicle. Use 0600 permissions, exclude them from version control, and encrypt backups.
  • Debug logs. -debug output includes public keys, epochs, counters, and ciphertext. Private keys and session keys are not printed, but mask the VIN when posting logs to public issues.
  • Reporting vulnerabilities. Report directly to Tesla as described in SECURITY.md: https://www.tesla.com/legal/security.
