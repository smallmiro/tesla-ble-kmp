エラーモデル

SDK が返すエラーは、可能な限り protocol.Error インターフェースを実装しています。2 つのメソッドが、呼び出し側が取るべき対応を決めます。

type Error interface {
    error
    MayHaveSucceeded() bool // 車両がコマンドを受け取って実行した可能性がある (確認不可)
    Temporary() bool        // ユーザーの介入なしにリトライで解決できる可能性がある
}
型層MayHaveSucceededTemporary説明
*protocol.CommandError汎用フィールド PossibleSuccessフィールド PossibleTemporaryprotocol.NewError(msg, mayHaveSucceeded, temporary) で生成。コンテキストの期限切れ時は {ctx.Err(), true, true} でラップされます。Unwrap() をサポート
*protocol.RoutableMessageErrorプロトコルERROR_NONE、RESPONSE_MTU_EXCEEDED のみ true表のリトライ可能なコードのみ true車両の signedMessageStatus.signed_message_fault。.Code は universal.MessageFault_E。Error() は enum 名
*protocol.NominalErrorアプリケーションDetails に委譲Details に委譲車両がコマンドを認証したものの実行できない。Infotainment は car could not execute command: <理由>、VCSEC は NominalVCSECError をラップ。プロキシは HTTP 200 + reason に変換
*protocol.NominalVCSECErrorアプリケーションfalsefalseFromVCSECMessage.nominalError。.Details.GetGenericError() が GenericError_E
*protocol.KeychainErrorアプリケーションfalsefalseキーの追加/削除の失敗。.Code は WhitelistOperation_information_E。メッセージは keychain operation failed: <コード>
*inet.HTTPErrorトランスポート（HTTP）4xx と 503 は false、それ以外は true503, 504, 408, 421Fleet API が 200 以外を返した。.Code、.Message（ボディ）

ヘルパー関数 protocol.MayHaveSucceeded(err)、protocol.Temporary(err)、protocol.ShouldRetry(err)、protocol.IsNominalError(err) は、errors.As でラップを辿って検査します。コミット a4b43c1 でラップされたプロトコルエラーの分類が修正されたため、fmt.Errorf("%w") でラップしたエラーも正しく分類されます。

リトライポリシー

func ShouldRetry(err error) bool {
    // Error インターフェースを実装し、MayHaveSucceeded() が false で、Temporary() が true のときのみ true
}

SDK は次の箇所で、ShouldRetry が真である間、コネクターの RetryInterval()（BLE、inet ともに 1 秒）間隔で、コンテキストが期限切れになるまでリトライします。

箇所リトライ対象備考
Vehicle.StartSessionハンドシェイク全体ディスパッチャーは、レスポンスが RetryInterval 内に届かなければリクエストを再送
Vehicle.Send（Infotainment コマンド）送信 + レスポンス待ちリトライ時はカウンターを新たにインクリメントした新しいメッセージを作成
getVCSECResult（VCSEC コマンド）送信 + 最終レスポンス待ちOPERATIONSTATUS_WAIT は ErrBusy に変換されてリトライ
Dispatcher.Sendコネクターの Send そのもの同一バイト列を再送（カウンターは不変）。コネクターが protocol.Error を返した場合のみ
inet.Connection.Wakeupwake_up のポーリング10 秒間隔、state == "online" になるまで。Temporary なエラーの場合のみ継続
ble.NewConnectionFromScanResultスキャン/ダイヤル/サービス探索アダプターエラー（IsAdapterError）、不正な Local Name、接続不可のビーコンは即座に失敗。それ以外はコンテキストの期限切れまで繰り返し
MayHaveSucceeded が真のエラーは自動リトライされません

コンテキストのタイムアウトやレスポンスのパース失敗などでは、車両がすでにコマンドを実行している可能性があるため、SDK は再送しません。ロック解除やトランクを開くなど、2 回実行されると困るコマンドは、BodyControllerState や GetState で状態を確認してから判断してください。この場合、tesla-control は Couldn't verify success: … を出力します。

プロトコル層：MessageFault_E

車両が RoutableMessage.signedMessageStatus.signed_message_fault に設定します。protocol.GetError が RoutableMessageError に変換し、UNKNOWN_KEY_ID だけは ErrKeyNotPaired に置き換えます。説明は universal_message.proto のコメントを訳したものです。

6ERROR_INVALID_TOKEN_OR_COUNTER自動アンチリプレイカウンターがすでに使用済み。セッション更新後にリトライ（自動）

VCSEC アプリケーション層：GenericError_E

FromVCSECMessage.nominalError.genericError。NominalVCSECError として公開され、メッセージは vcsec could not execute command: <名前> です。

値名前意味
0GENERICERROR_NONEエラーなし
1GENERICERROR_UNKNOWN不明
2GENERICERROR_CLOSURES_OPENドア/トランクが開いているため実行できない（例：ロック）
3GENERICERROR_ALREADY_ONすでにその状態
4GENERICERROR_DISABLED_FOR_USER_COMMANDユーザーコマンドでは無効化されている
5GENERICERROR_VEHICLE_NOT_IN_PARKパーキング（P）状態ではない

7GENERICERROR_NOT_ALLOWED_OVER_TRANSPORTこのトランスポート経路（BLE/インターネット）では許可されていないコマンド

Infotainment アプリケーション層のエラー

Infotainment のレスポンス carserver.Response.actionStatus.result が OPERATIONSTATUS_ERROR の場合、result_reason.plain_text が NominalError のメッセージになります：car could not execute command: <plain_text>。テキストが空なら unspecified error。コード中に登場する例：already off（バレー解除時は成功として扱う）、low_power_mode_enforced、parental_controls_active。プロキシはこの文字列を reason として返します。

トラブルシューティングのシナリオ

症状考えられる原因確認と対処
BLE スキャンが終わらない / ble: failed to scan for <VIN>: context deadline exceededVIN のタイプミス、車両が遠い、アドバタイズ名の不一致、アダプターの問題VIN が 17 文字か確認（大文字）。アドバタイズの Local Name は S + SHA1(VIN) の先頭 8 バイトの hex + C（ble.VehicleLocalName）。一般的な BLE スキャナーアプリでその名前が見えるか確認。examples/ble -scan-only -vin … でスキャンだけをテスト。車のそばで試す
the vehicle is already connected to the maximum number of BLE devicesビーコンが Connectable=false。VCSEC の BLE 接続は最大 3 つ（キーフォブ、フォンキーを含む）スマートフォンアプリのフォンキーを一時的にオフにするか、他のクライアントを切断。自動リトライはされない
Linux：operation not permitted、Failed to initialize BLE adapterHCI ソケットへのアクセス権限がない（go-ble が HCIDEVDOWN を呼び出す）sudo setcap 'cap_net_admin=eip' "$(which tesla-control)" または root で実行。-bt-adapter hci1 で別のアダプターを選択。bluetoothd がアダプターを占有していると競合することがある
macOS：スキャン結果がまったくないターミナルアプリに Bluetooth の権限がない、Bluetooth がオフシステム設定 → プライバシーとセキュリティ → Bluetooth でターミナル/IDE を許可。macOS は -bt-adapter をサポートしない（ErrAdapterInvalidID）
Windows で not supported on WindowsBLE パッケージが Windows 非対応macOS/Linux を使用するか、インターネット経路（OAuth）に切り替える
接続はできるが ble: failed to find required characteristics / failed to discover service別のデバイスに接続している（Local Name は検査するがアドレスは再利用されうる）、GATT キャッシュの問題リトライ（自動）。OS の Bluetooth をオフ/オンする。近くに別の Tesla があれば VIN を再確認
ハンドシェイク失敗：your public key has not been paired with the vehicle公開鍵が未登録、別のキーで実行している、登録がまだ Infotainment に同期されていないtesla-control -ble list-keys で登録一覧を確認。tesla-keygen create で現在のキーの公開鍵を出力して比較。session-info public_key.pem infotainment が成功するまでしばらく待つ。TESLA_KEY_NAME/-key-file が意図したキーを指しているか確認
ペアリング要求後に何も起きない車両がスリープ中、バレーモード、NFC カードのタップのタイムアウト、画面で拒否車内で画面がオンの状態で実行。add-key-request の直後に NFC カードをセンターコンソールにかざし、画面の確認を押す。バレーモードを解除。-debug で WhitelistOperation_information_E のコードを確認
MESSAGEFAULT_ERROR_INVALID_SIGNATURE、INCORRECT_EPOCH、INVALID_TOKEN_OR_COUNTER がログに繰り返し出るセッションキャッシュが古い（車両の再起動、ファームウェア更新）、同じキーを複数のプロセスが同時に使ってカウンターが衝突通常はレスポンスに含まれるセッション情報で自動復旧し、リトライ後に成功します。失敗が続く場合はキャッシュファイル（~/.tesla-cache.json）を削除するか -disable-session-cache。同じキーを使うプロセスを 1 つに減らすか、プロキシのように VIN ごとに直列化
MESSAGEFAULT_ERROR_TIME_EXPIRED / TIME_TO_LIVE_TOO_LONGローカル時計とドメイン時計の推定値のずれ、レスポンスの遅延が AllowedLatency（BLE は 4 秒）を超えて時計の同期が破棄された、コンテキストのデッドラインが長すぎる自動復旧の対象。続く場合は Vehicle.SetMaxLatency を増やすか -command-timeout を減らす。キャッシュを削除
vehicle busy or finishing wake-up が長く続くVCSEC が別のリクエストを処理中（OPERATIONSTATUS_WAIT）、車両が起動中自動でリトライされます。-command-timeout 15s のように延ばす。VCSEC に同時リクエストを送らないようアプリの構造を確認（メモリの制約により同時リクエストは非推奨）
Infotainment コマンドだけがタイムアウトし、VCSEC コマンドは正常インフォテインメントがスリープ中BLE：tesla-control -ble wake の後しばらく待つ。インターネット：wake（Fleet API）。body-controller-state の vehicleSleepStatus で確認
Couldn't verify success: …レスポンスを受信できなかった（タイムアウト）。コマンドは実行された可能性があるbody-controller-state/state closures で結果を確認し、必要なら再実行。タイムアウトを延ばす
You must provide a private key with -key-name or -key-file to execute this commandErrNoSession：キーなしで認証付きコマンドを実行TESLA_KEY_NAME または -key-file を設定。-domain で該当ドメインを除外していないか確認
no terminal output available for password prompt / 実行が止まるキーリングのバックエンドがパスワードを要求しているが、ターミナルではない（cron、systemd、CI）TESLA_KEYRING_PASSWORD を設定するか、ファイルベースのキー（-key-file）を使用。TESLA_KEYRING_DEBUG=1 でバックエンドを確認

デバッグツール

TX/RX ダンプのデコード

tesla-control -debug（または TESLA_VERBOSE=1）は、送受信した RoutableMessage を 16 進数で出力します。

2023-12-13T14:41:13-08:00 [debug] TX: 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805

protoc でデコードします（リポジトリのルートで実行）。

cd vehicle-command/pkg/protocol
echo 320208023a1212100a7962c10d38b61dd2a7722780a4f0969a031005514f57616bcc81a8ce0f9d7b48322952040a020805 \
    | xxd -r -p \
    | protoc --decode=UniversalMessage.RoutableMessage -I protobuf protobuf/*.proto

# 出力の protobuf_message_as_bytes を、ドメインに合った型で再度デコード
printf "\n\002\010\005" | protoc --decode=VCSEC.UnsignedMessage -I protobuf protobuf/*.proto      # VCSEC リクエスト
printf "..." | protoc --decode=VCSEC.FromVCSECMessage -I protobuf protobuf/*.proto              # VCSEC レスポンス
printf "..." | protoc --decode=CarServer.Action -I protobuf protobuf/*.proto                    # Infotainment リクエスト
printf "..." | protoc --decode=CarServer.Response -I protobuf protobuf/*.proto                  # Infotainment レスポンス

BLE では AES-GCM で暗号化されるため、protobuf_message_as_bytes は暗号文です。平文を見るには、-debug ログのうちリクエスト組み立て時点のログか、セッション鍵が必要です。ハンドシェイクメッセージとレスポンスのエラーフィールド（signedMessageStatus）は平文です。

セキュリティ上の注意

  • テスト用のキーを実際の車両に登録しないでください。 pkg/protocol/protocol.md、internal/authentication/test_data/、pkg/protocol/test/ にあるキーは公開されています。
  • セッションキャッシュファイルの権限。 ~/.tesla-cache.json は秘密鍵を含みませんが、セッション状態を含みます。第三者に読まれたり改ざんされたりしないようにしてください。改ざんされたキャッシュは最初のコマンドの失敗後に自動復旧しますが、不要な失敗を引き起こします。
  • 秘密鍵のエクスポート。 tesla-keygen export の出力と -key-file のファイルは、登録済みのすべての車両に対するコマンド権限です。0600 の権限、バージョン管理からの除外、バックアップの暗号化を徹底してください。
  • デバッグログ。 -debug の出力には公開鍵、epoch、カウンター、暗号文が含まれます。秘密鍵やセッション鍵は出力されませんが、ログを公開の issue に載せるときは VIN を伏せてください。
  • 脆弱性の報告。 SECURITY.md に従い、Tesla に直接報告します：https://www.tesla.com/legal/security。
