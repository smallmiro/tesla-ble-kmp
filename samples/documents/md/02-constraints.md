# Sample Constraints

Every sample change follows these rules. They add to, and never relax, the repository rules in `AGENTS.md` §3.

## 1. Allowed library surface

- Use **only** the public API of `:sdk` that the library manual (`documents/md/11-lib-*.md` to `19-lib-*.md`) lists as
  available. Find the page with the "Reference files by task" table in `documents/md/11-lib-overview.md`.
- Never use: `:application` or `:adapter-*` types, anything marked `@InternalTeslableApi`, an API the manual calls
  planned or not implemented, or text parsing of library log lines as a data source.
- If a sample needs behaviour the manual does not describe, or the library behaves differently from the manual, **do not
  work around it in the sample.** Fix the manual first (MD + HTML ko/en/ja), or raise a library request with the
  `library-api-request` skill and put it in the plan. The sample requirement waits (`01-requirements.md`).
- Call order, error handling (`Success` / `Uncertain` / `Failure`, re-query after `Uncertain`), timeouts and platform
  setup follow the manual. After an `Uncertain` VCSEC command, re-read with `vehicleStatus()`; never resend.
- Swift: Kotlin default arguments do not become Swift overloads. Pass every argument (`17-lib-platform-notes.md`).
- Sample code and the code examples in the manual must agree. If a manual example is wrong, fix it in the same PR.

## 2. Platform setup

| | Android | iOS |
|---|---|---|
| Bluetooth permission | `BLUETOOTH_SCAN` (`neverForLocation`) and `BLUETOOTH_CONNECT`, requested at runtime | `NSBluetoothAlwaysUsageDescription` in `project.yml` `info:` |
| Background (monitor app) | Foreground service of type `connectedDevice`: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`, `POST_NOTIFICATIONS` (asked at runtime). The service starts only after `BLUETOOTH_CONNECT` is granted | `UIBackgroundModes: [bluetooth-central]` |
| Network | No `INTERNET` permission (PRD NFR-014) | No network calls |
| Backup | `android:allowBackup="false"` (software fallback key must not be restored without its wrapping key) | Keys are `ThisDeviceOnly` Keychain items |
| Generated files | – | `TeslableSample.xcodeproj` and `Sources/Info.plist` are generated by `xcodegen generate`; never commit them |
| Signing | – | `Local.xcconfig` holds `DEVELOPMENT_TEAM`; never commit it |

Background operation is out of the library's documented scope today (`17-lib-platform-notes.md`). A sample that needs
it documents the platform setup it uses here and in `17-lib-platform-notes.md` in the same PR. The Android monitor app
does so (table above, `17-lib-platform-notes.md` §Android background use by the sample); a real-device check is pending.

## 3. Logs, secrets and vehicle data

- Never log, store in a fixture or commit: private keys, session keys, a real VIN. Mask VINs (first 3 and last 4
  characters kept) before anything leaves the device.
- On-screen and copied logs carry only the library's `observe` lines and the sample's own result lines. BLE `TX:`/`RX:`
  hex from `DebugLogger` stays in the platform log (Logcat, unified log) and is never shared.
- Logs pulled from a device go to `samples/logs/` (git-ignored). Analysis reports go to `docs/analysis/`.
- UI text is Korean today (the maintainer's language). Error messages from the library are English (PRD D19) and are shown
  as they are.

## 4. Build and test

| Purpose | Command |
|---|---|
| Android sample build | `./gradlew :samples:android:assembleDebug` |
| iOS framework for the simulator | `./gradlew :sdk:linkDebugFrameworkIosSimulatorArm64` |
| iOS framework for a device | `./gradlew :sdk:linkDebugFrameworkIosArm64` |
| iOS project | `cd samples/ios && xcodegen generate` |
| iOS build and Swift unit tests (simulator) | `xcodebuild -project TeslableSample.xcodeproj -scheme TeslableSample -destination 'platform=iOS Simulator,name=<device>' CODE_SIGNING_ALLOWED=NO test` |
| Whole local gate (includes both samples) | `tools/ci/verify.sh` |

- Logic that can be tested without a vehicle (parsing, masking, timers, state reduction) gets a unit test first (TDD,
  `AGENTS.md` rule 1): Swift tests in `samples/ios/Tests/`, Kotlin tests in `samples/android/src/test/` (`./gradlew :samples:android:testDebugUnitTest`).
- Screens and real-vehicle behaviour are checked with a written checklist on a real phone. The simulator has no
  Bluetooth.

## 5. Documentation duty

- A change in sample behaviour updates `01-requirements.md` / `03-current-apps.md` (or the app's own page) and the HTML
  pages in `ko/`, `en/`, `ja/` in the same PR.
- A sample PR body lists the library manual pages and sections it relied on (`AGENTS.md` rule 14).
