17. プラットフォームノート

Android や iOS のアプリで設定すべきこと、ライブラリがキーとセッションを保存する場所、知っておくべきいくつかのプラットフォーム固有の動作をまとめます。実機でまだ確認していない項目はその旨を記載しています。

サポート範囲

  • Android 12 (API 31) 以降、iOS 16 以降で、アプリが フォアグラウンド にある場合に対応します。バックグラウンドでの Bluetooth は対象外です。
  • JVM ターゲットはテストと実験用です。キーはメモリ上にあり、プロセスの終了とともに消えます。

Android

2 つの Bluetooth 権限を宣言し、実行時に要求してください。権限がないと、スキャンと接続は PermissionDenied を返します。ライブラリはサーバーを呼び出さないため、インターネット権限は不要です。

<uses-permission android:name="android.permission.BLUETOOTH_SCAN" android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<uses-feature android:name="android.hardware.bluetooth_le" android:required="true" />
  • ライブラリは PlatformContext(context) で作成します。アプリケーションコンテキストを保持します。
  • 接続時、ライブラリは 517 の MTU を要求し、失敗した場合は 20 バイトのブロックにフォールバックします。
  • Keystore のエントリ名は teslable.key:<alias> と teslable.wrap:<alias> なので、アプリ自身のエントリと衝突しません。
キーファイルを自動バックアップから除外してください

ソフトウェアキーは files/teslable/keys/<alias>.enc として保存され、バックアップされることのない Keystore キーでラップされています。自動バックアップがラップ用のキーなしでこのファイルを復元すると、キーは破損していると判定されます。dataExtractionRules または fullBackupContent で files/teslable/keys/ を除外してください。サンプルアプリは単に android:allowBackup="false" を設定しています。files/teslable/sessions の保存済みセッションは失われても害はありませんが、除外しておく方がすっきりします。

サンプルアプリの Android バックグラウンド利用

ライブラリはフォアグラウンドでの利用をサポートします（サポート範囲を参照）。Android サンプルのモニターアプリはフォアグラウンドサービスでバックグラウンドでも接続を保ちますが、まだ実機では確認していないため、バックグラウンドでのライブラリの動作は未確認として扱ってください。

  • マニフェスト: FOREGROUND_SERVICE、FOREGROUND_SERVICE_CONNECTED_DEVICE、POST_NOTIFICATIONS（実行時に要求）、<service android:foregroundServiceType="connectedDevice" />。INTERNET は引き続きありません。
  • Android 14 以降: connectedDevice のフォアグラウンドサービスは、BLUETOOTH_CONNECT が許可された後で、かつアプリが表示されている間にだけ（または別の開始の例外が当てはまるとき）開始できます。システムがサービスを再開してくれるとは期待しないでください。
  • サービスがライブラリのインスタンスを 1 つ所有し、リンクが切れるたびに vehicle.disconnect() を呼んでから、新しい Vehicle で再接続します（2 秒待ち、最大 30 秒まで倍々）。再試行はライブラリではなくアプリの仕事です。
  • キーストア: サンプルは KeyAccessibility.AFTER_FIRST_UNLOCK でキーを作ります。Android はこの引数を無視して AFTER_FIRST_UNLOCK を返します（API 仕様に基づく値で、まだ端末では確認していません。キーの保管を参照）。

iOS

  • Info.plist に NSBluetoothAlwaysUsageDescription を追加します。最初のスキャンで権限ダイアログが表示されます。ユーザーが拒否すると、呼び出しは PermissionDenied を返します。
  • ライブラリは PlatformContext() で作成します。
  • シミュレーターには Bluetooth がありません。スキャンと接続は実機の iPhone でのみ試せます。
  • iOS には MTU ネゴシエーションの API がないため、ライブラリはシステムが選んだ書き込み長を使います。実機の iPhone で観測したブロック長は 512 です。応答キャラクタリスティックは通知 (notification) と指示 (indication) の両方に対応し、Kable 既定の購読 (notify) が実車で動作することを確認しました (ADR-0003)。
  • Swift は SKIE を通して Kotlin を呼び出します。suspend 関数は async throws に、Flow は AsyncSequence になり、sealed 型は switch onEnum(of:) で扱えます。companion メンバーには .companion を通してアクセスします。
  • Swift では公開の VehicleStatus は VehicleStatus_ という名前になります。生成された VCSEC メッセージ型がそのままの名前を使っているためです。vehicleStatus() の結果と VehicleEvent.Status.status がこの型です。

サンプルアプリの iOS バックグラウンド利用

ライブラリはフォアグラウンドでの利用をサポートします（サポート範囲を参照）。iOS サンプルのモニターアプリは UIBackgroundModes: [bluetooth-central] を宣言し、Android サンプルと同じ再接続ループを実行します。まだ実機の iPhone では確認していないため、バックグラウンドでのライブラリの動作は未確認として扱ってください。

  • Info.plist（project.yml 経由）: UIBackgroundModes: [bluetooth-central]。UIFileSharingEnabled と LSSupportsOpeningDocumentsInPlace はサンプルのログフォルダー用にのみ設定します。
  • アプリがライブラリのインスタンスを起動中ずっと 1 つ所有し、リンクが切れるたびに vehicle.disconnect() を呼んでから、新しい Vehicle で再接続します（2 秒待ち、最大 30 秒まで倍々）。再試行はライブラリではなくアプリの仕事です。
  • 未確認: アプリがバックグラウンドにある間、またはスマートフォンがロックされている間に、iOS がスキャンと再接続を許可するかどうか（ライブラリは現在デバイス名でスキャンしていますが、iOS のバックグラウンドスキャンには通常サービス UUID のフィルターが必要です。計画の Task 2 と Task 8）。実車でのスパイクを行うまでは、サポートするバックグラウンドのケースはリンクが維持されている場合だけです。iOS がアプリを動かし続けている間は、イベントが届き続けます。
  • キーストア: サンプルは KeyAccessibility.AFTER_FIRST_UNLOCK でキーを作ります。スマートフォンがロックされていてキーストアが KeyStoreError.Locked を返す間、サンプルは待って再試行し、キーを削除することはありません。

キーの保存

protection意味
SECURE_ENCLAVEiOS Secure Enclave。秘密鍵がチップの外に出ることはありません
STRONGBOXAndroid StrongBox セキュリティチップ
TEEAndroid Trusted Execution Environment
SOFTWAREエミュレーター、シミュレーター、またはハードウェアの試行がすべて失敗したデバイス
  • ソフトウェアキーは Android Keystore の AES キーでラップされるか、デバイスの外に出ず、キーのアクセシビリティ設定に従って保護される iOS キーチェーン項目として保存されます。
  • iOS では、Secure Enclave の検索失敗は「キーなし」ではなくエラーとして報告されるため、正常なキーが誤って上書きされることはありません。
  • 秘密鍵をエクスポートする API はありません。
  • キーのハンドルは自動的に解放されます。iOS では、キーのオブジェクトごとに Security フレームワークの参照 (SecKeyRef) を 1 つ持ちます。この参照は、アプリも接続した Vehicle もそのキーを使わなくなり、Kotlin/Native のガベージコレクタが動いた後に解放されます。閉じるものはなく、キーを読み直してもハンドルはたまりません。

スマートフォンのロック中にキーを使う

キーごとにアクセシビリティ設定 VehicleKey.accessibility があります。選び方とキーを切り替える手順は 13. キーとペアリング にあります。

プラットフォームキーを作成するとき既存のキーが報告する値
iOSWHEN_UNLOCKED (デフォルト) は kSecAttrAccessibleWhenUnlockedThisDeviceOnly、AFTER_FIRST_UNLOCK は kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly を使います。Secure Enclave のキーとソフトウェアキーのどちらも同じです保存されたキーから読み直した設定。後から変わることはありません
Android設定は無視されます常に AFTER_FIRST_UNLOCK。Keystore のキーにはロック解除やユーザー認証の要件がなく、キーファイルは最初のロック解除後に読み取れます。API 上の話で、実機ではまだ確認していません
JVM設定は無視されます常に AFTER_FIRST_UNLOCK。メモリ上のキーにはロックがありません
  • ロックされた iPhone では、キーチェーンのエラー errSecInteractionNotAllowed (-25308) が KeyStoreError.Locked になります。WHEN_UNLOCKED のキーはスマートフォンのロック中は読み取ることもハンドシェイクに使うこともできず、AFTER_FIRST_UNLOCK のキーは最後の再起動後に一度ロックを解除してからは使えます。最初のロック解除の前は、すべてのキーがロックされています。スマートフォンがロックされていて作成できなかったキーを、ソフトウェアキーで代用することはありません。
  • スマートフォンがロックされる前に読み込んだキーオブジェクト: Secure Enclave が同じエラー (-25308) で鍵合意を拒むと、ハンドシェイクは車両が応答するとすぐに KeyStoreError.Locked で終わってリトライせず、そのキーが必要な保存済みのセッションは復元しませんが、そのまま残します (13)。ほかの鍵合意のエラーはこれまでと同じです (ハンドシェイクはタイムアウトまで試行を続けます)。ソフトウェアキーのオブジェクトは秘密鍵をメモリに持つため、ロック後も動き続けます (API に基づく)。
  • 実機でまだ確認していないこと: 両方の設定でのキーチェーンの往復、設定の読み直し、ロックされた iPhone での AFTER_FIRST_UNLOCK の Secure Enclave キーによるハンドシェイク、そしてロックされた iPhone が WHEN_UNLOCKED の Secure Enclave キーの鍵合意にどのエラーを返すか (ライブラリは -25308 を想定しています。別のエラーなら startSession() はこれまでどおりタイムアウトで終わります)。サンプルアプリで確認します（ビルド 10 は準備済みで、確認は計画の Task 11 です）。スマートフォンのロック中にキーを使うには、アプリがバックグラウンドで動き続ける必要がありますが、その内容はまだこのドキュメントで扱っていません。
破損したキーが自動で置き換えられることはありません

getOrCreate または get が stored key is corrupted 付きの PlatformFailure を返した場合は、ユーザーに知らせてから delete と getOrCreate を呼んでください。新しいキーは公開鍵が異なるため、車両に登録し直す 必要があります。黙って置き換えると、ユーザーは理由もわからないまま車両を制御できなくなります。

セッションキャッシュ

  • 保存済みセッションを使うと、次の接続でハンドシェイクを省略できます。保存先は Android では files/teslable/sessions/、iOS ではキーチェーン、JVM ではメモリです。TeslaBleConfig.sessionCache で独自の実装を渡すこともできます。
  • 名前は VIN のハッシュなので、VIN そのものは保存されません。
  • セッションは 1 つのキーに属します。キーが変わった後や、車両側の状態が進んでいる場合、古いセッションは次の接続で破棄されます。
  • キャッシュがない、または古くなっていてもエラーではありません。ライブラリは単に新しいセッションを開始します。
  • 電話のロックがキーを妨げたため復元できなかった保存済みのセッション (iOS) は、古くなったわけではありません。車両のその部分に再びセッションができるまで、ライブラリはキャッシュに何も書き込まないため、スマートフォンのロック中に切断しても保存済みのセッションは残ります。

クロック

セッションの時間管理には単調クロックを使いますが、一部のプラットフォームではスマートフォンのスリープ中にこのクロックが止まります。長いスリープの後、保存済みセッションからの最初のコマンドが有効期限のフォールトで失敗することがあります。その場合、ライブラリは車両が返す新しいセッション情報を取り込んでリトライするため、アプリ側には何も見えません。

接続スロットとリンク切断

  • 車両が受け付ける Bluetooth 接続は 最大 3 つ です。スロットを空けるため、使い終わったら disconnect() を呼んでください。3 つすべてが使われていると、接続は MaxConnectionsExceeded を返します。
  • リンクが切れて connection が Disconnected になった場合でも、セッションキーを消去するため 必ず disconnect() を呼んでください。もう一度呼んでも害はありません。
  • 切断された Vehicle は再利用できません。TeslaBle.connect で接続し直してください。

Swift: タイムアウト

Kotlin の Duration はインライン値クラスです。Swift からはボックス化された Any? としてしか見えないため、Swift のコードでは直接作れません。2 つのヘルパーで解決します。

  • Timeouts.shared.seconds(seconds:) は、任意の timeout: 引数に渡すボックス化された値を返します。0、負数、NaN、無限大を渡すと IllegalArgumentException になります。Timeouts.shared.millisecondsOf(timeout:) はボックス化された値のミリ秒を返し（nil なら -1）、往復の確認用です。iOS サンプルの XCTest ターゲットは tools/ci/verify.sh のステップ (d) で実行されます。
  • TeslaBleConfig.companion.withSeconds(logger:commandTimeoutSeconds:handshakeTimeoutSeconds:connectTimeoutSeconds:pairingTimeoutSeconds:) は秒単位で設定を作ります。すべての引数が必須で、commandLifetime は既定値のままです。TeslaBleConfig.companion.default(logger:) は変わりません。
  • timeout: nil は引き続き「設定の既定値を使う」を意味します。
